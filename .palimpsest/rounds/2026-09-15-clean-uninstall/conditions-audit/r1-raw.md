## 발견

### A2 의 기대값을 어디서 뜨는지 안 정해져 있어, 새 병합 코드로 기대값을 만들면 항등식이 된다
「착수 커밋의 병합 규칙과 JSON 값으로 같다」는 기대값의 출처를 적지 않았다. 시험이 기대값을 지금 빌드의 `hooks::plan`·`hooks::apply`(`crates/pal-cli/src/install/settings.rs:110`)로 계산하면, 비교하는 두 쪽이 같은 코드에서 나온다. 그러면 음성 대조 「훅 묶음 하나를 빼먹는 변이」는 기대값까지 함께 바꿔 초록으로 남는다. 착수 커밋에서 떠 둔 고정 fixture(골든)라고 문면에 있어야 음성 대조가 성립한다.
- 모집단: 저장소
- 유효성: 추정
- 해악도: 거짓신호
- 어디가 걸리나: A2

### A3 는 한 경우만 재서, 「사용자가 스스로 고친 것은 남긴다」가 settings 안에서 갈리는 경우를 안 가른다
A3 가 재는 편집은 「키를 더하고 들여쓰기를 바꾼」 한 가지다. 다음 두 경우가 모집단에 없다.
- 설치 뒤 사용자가 pal 이 더한 `agent` 값을 자기 값으로 바꾼 경우. 지금 코드는 그 키를 지우고 「사용자 수정 — 지웠다」라고만 말한다(`crates/pal-cli/src/install/settings.rs:158-166`, `crates/pal-cli/src/install.rs:1425-1434`).
- 설치 뒤 사용자가 pal 훅과 같은 사건 배열에 자기 훅을 더한 경우.

두 경우 모두 조건이 어느 쪽 동작도 요구하지 않는다. 그래서 「남긴다」와 「지운다」가 둘 다 통과한다.
- 모집단: 원의도
- 유효성: 참
- 해악도: 실패
- 어디가 걸리나: A3

### A4 는 음성 대조가 없고, 「`HEAD` 바이트로 되돌린다」가 틀리는 방이 모집단에 없다
A4 는 커밋된 `settings.json` 이 `HEAD` 바이트로 돌아오는지만 잰다. 무조건 `HEAD` 본을 되써도 통과하는 구조다. 그런데 그렇게 하면 두 방에서 틀린다.
- 설치 뒤 사용자가 `settings.json` 을 편집한 방: 사용자 편집이 사라진다.
- 설치 **뒤에** 그 파일을 커밋해서 `HEAD` 에 pal 키가 들어 있는 방: pal 흔적이 남는다.

두 방이 조건에 없고, 음성 대조도 적혀 있지 않다.
- 모집단: 원의도
- 유효성: 참
- 해악도: 실패
- 어디가 걸리나: A4

### B2 는 설치 전부터 있던 파생물을 지우라고 요구한다. 원문 「원래 설치된 것이 없었던 것처럼」과 증인 「설치 전과 바이트로 같은가」에 어긋나는데, 차선책이나 범위 밖에 적혀 있지 않다
설치 전에 이미 `index.redb` · `cache/` 가 있던 방이라면, B2 대로 하면 uninstall 뒤 워킹트리가 설치 전과 달라진다. 소유자가 고른 칸은 정본 보존만 말하고 파생물 삭제는 말하지 않았다. 이 편차가 조건 안에서 당연한 요구처럼 적혀 있으니, 증인이 반증될 방을 조건이 통과로 센다.
- 모집단: 원의도
- 유효성: 참
- 해악도: 거짓신호
- 어디가 걸리나: B2

### B3 는 `intent.redb` 한 줄만 재서, 그것을 가리려고 남긴 흔적(`M .gitignore` 등)을 안 잰다
「`git status --porcelain -uall` 에 `intent.redb` 가 안 나온다」는 무시 규칙 블록을 `.gitignore` 에 남기거나 새 무시 파일을 두는 빌드도 통과시킨다. 이 방에서는 워킹트리의 다른 파일을 재는 스냅샷이 없다(B1 은 결박이 0 인 방이다). 목적 기여 절이 문제로 지목한 「거두면 `git status` 에 … 남는다」가 이 방에서 그대로 돌아올 수 있다.
- 모집단: 원의도
- 유효성: 참
- 해악도: 실패
- 어디가 걸리나: B3

### B4 는 `--purge` 가 설치 전부터 있던 정본을 남기는지 안 잰다
B4 의 방에는 설치 전 정본이 없고, B2 는 기본 uninstall 만 잰다. 그래서 `.palimpsest/` 를 통째로 지우는 `--purge` 도 B4 · B2 를 다 통과한다. 조건 문면은 「설치 뒤에 생긴 안의 정본」만 걷는다고 적었는데, 그 한정을 재는 방이 없다. 설치 전 `bindings.jsonl` 에 설치 뒤 줄이 더해진 경우처럼 섞인 파일을 어떻게 다룰지도 정해져 있지 않다.
- 모집단: 원의도
- 유효성: 참
- 해악도: 실패
- 어디가 걸리나: B4

### C1 의 「ok 가 아닌 검사를 하나 이상」은 무관한 검사로도 채워지고, 대조하는 방도 전부 ok 를 요구하지 않아 항등식이 될 수 있다
`doctor --install` 의 검사 4 는 `PATH` 에 `pal` 이 없으면 어느 방에서나 Failed 를 낸다(`crates/pal-cli/src/install/doctor.rs:284-302`). 기존 설치 시험 몇은 `PATH` 를 따로 세팅한다(`crates/pal-cli/tests/install_hostile.rs:57` 등). 시험 환경이 그렇지 않으면 이렇게 된다.
- 고친 방이 무관한 검사 하나로 조건을 채운다.
- 안 고친 방은 「지금과 같다」만 요구받으므로, 고친 방과 똑같은 결과로 둘 다 통과한다.

RED 「여섯 다 ok」도 환경에 달렸다. 어느 검사가 발화해야 하는지, 대조 방은 전부 ok 여야 하는지를 문면이 정하지 않는다. 블록 파일도 둘(`CLAUDE.md` · `.gitignore`, `crates/pal-cli/src/install.rs:661`)인데 어느 쪽을 고친 방인지 모집단이 서 있지 않다.
- 모집단: 저장소
- 유효성: 참
- 해악도: 거짓신호
- 어디가 걸리나: C1

### C2 의 `--force` 는 소유자가 고른 「거부 유지 + 미리 알림」보다 크다
원문 칸이 요구한 것은 거부를 유지하고 미리 알리는 것이다. 우회 플래그를 새로 만들라는 요구는 칸 문장에 없다. 칸 설명문을 에이전트가 썼기 때문에 `--force` 가 그 설명에 들어 있었는지는 이 입력만으로 확인할 수 없다.
- 모집단: 원의도
- 유효성: 추정
- 해악도: 미관
- 어디가 걸리나: C2

### D2 의 봉인 음성 대조는 봉인에도 표시 파일이 붙으면 발화하지 않는다
종료 봉인도 승인과 같은 `approval::approve` 로 `<digest>.json` 에 쓰인다(`crates/pal-cli/src/round/verify.rs:300-301`). D1 이 표시 파일을 `approve` 가 쓰는 기록 옆에 두라고 하므로, 구현이 봉인에도 `.project` 를 붙이면 봉인은 표시 파일로도 걷힌다. 그 경우 「봉인을 원장에서 안 모으는 빌드」는 여전히 초록이다. 음성 대조가 성립하는지가 조건이 정하지 않은 구현 선택에 달려 있다.
- 모집단: 저장소
- 유효성: 추정
- 해악도: 거짓신호
- 어디가 걸리나: D2

### D2 의 「조상 디렉터리를 미리 만든 HOME」은 조상이 비었는지를 안 정해서 두 변형이 서로를 가르지 못한다. Windows 의 「HOME 스냅샷」은 무엇을 찍는지 서 있지 않다
`store_dir` 은 조상까지 `create_dir_all` 로 만든다(`crates/pal-cli/src/round/approval.rs:119`). 「HOME 까지 빈 조상을 지운다」는 규칙은 미리 만든 조상에 파일이 들어 있는 fixture 에서는 두 변형을 다 통과한다. 그런데 실제 사용자의 원래 비어 있던 `~/.local/share` 같은 디렉터리를 지운다. 미리 만든 조상이 비어 있어야 기록 없는 삭제를 잡는다. Windows 는 실제 `LocalAppData` 를 쓴다고 했는데, 스냅샷 범위가 `palimpsest` 하위인지 전체인지 문면에 없다.
- 모집단: 저장소
- 유효성: 참
- 해악도: 거짓신호
- 어디가 걸리나: D2

### D4 는 「거부」의 rc 와 범위를 안 정하고, 연결된 worktree 쪽에서 실행하는 방이 없고, 소유자가 고른 「클론은 경고」를 재는 방도 없다
- 「밖의 기록을 하나도 안 지우고」가 명령 전체 거부(rc≠0, 워킹트리도 안 건드림)인지, 밖만 건너뛰고 안은 걷는다는 뜻인지 문면에 없다.
- 기본 uninstall 은 worktree 들이 공유하는 식별자로 활성화 파일을 지운다(`crates/pal-cli/src/round/stop.rs:166-183`). 이 동작이 「worktree 있으면 거부」에 드는지 판단이 없다.
- 실행 위치가 주 체크아웃뿐이다. 연결된 worktree 에서 실행하는 경우는 모집단에 없다.
- 클론 방(같은 origin, worktree 아님)에서 경고가 나오는지 재는 조건이 없다.
- 모집단: 원의도
- 유효성: 참
- 해악도: 거짓신호
- 어디가 걸리나: D4

### E1 은 CI 성공만 재서, A–D 시험이 세 OS 에서 실제로 돌았는지는 안 잰다
「시험은 세 OS CI 가 돈다」가 머리말의 주장인데, E1 은 `conclusion=success` 만 본다. 다음 경우에도 초록이다.
- OS 조건 컴파일로 빠진 시험
- `#[ignore]` 가 붙은 시험
- 차선책에 따라 Windows 에서 다른 걸음으로 바뀐 D2

OS 별로 실행된 시험 이름을 대조하는 자리가 없다.
- 모집단: 회차기록
- 유효성: 추정
- 해악도: 거짓신호
- 어디가 걸리나: E1

### F1 은 결정론으로 태그됐지만 「남기기로 한 부류와 그 까닭만」을 가를 기준이 등록돼 있지 않다
diff 한 줄이 「안의 정본 · 조건부 `intent.redb` · 밖의 승인·봉인 · 가를 수 없는 것」 가운데 어디에 드는지 정하는 허용 목록(경로 패턴)이 없다. 체크리스트도 없다. 「까닭」은 diff 에 들어 있지 않은 산문이다. 실제 HOME 을 찍는지 격리 HOME 을 찍는지도 정해지지 않았는데, 실제 HOME 이면 다른 프로세스의 변화 때문에 `--purge` diff 가 「비었다」가 될 수 없다. 저장소 한 곳 · OS 한 곳이라는 모집단도 문면에 없다.
- 모집단: 원의도
- 유효성: 참
- 해악도: 거짓신호
- 어디가 걸리나: F1

### 증인 「설치 → 실제 사용 → uninstall 뒤 워킹트리와 HOME 이 설치 전과 바이트로 같은가 — 세 OS CI」가 CI 조건 어디에서도 한 흐름으로 안 선다
- B1 은 touch · narrative 만 쓰고 워킹트리만 찍는다.
- D2 는 approve · 봉인 · Stop 을 쓰고 HOME 만 찍는다.
- B4 는 어떤 사용 걸음을 거치는지 적지 않았다.

approve · verify · Stop 훅이 워킹트리에 남기는 것과 touch · narrative 가 HOME 에 남기는 것을 함께 재는 흐름은 F1 뿐이다. F1 은 수동이고 OS 하나다. 조각마다 초록이어도 걸음 사이의 상호작용이 남긴 흔적은 CI 에서 안 잡힌다.
- 모집단: 원의도
- 유효성: 참
- 해악도: 거짓신호
- 어디가 걸리나: B1 · B4 · D2 · F1

### 사용자가 설치 뒤 고친 pal 파일을 uninstall 이 지우는데, 「사용자가 스스로 고친 것은 남긴다」에 비춘 조건이 없다
지금 uninstall 은 sha 가 달라진 파일도 지우고 「되돌릴 수 없다」고만 알린다(`crates/pal-cli/src/install.rs:1356-1371`, `crates/pal-cli/src/install.rs:1273-1291`). 대상은 에이전트 정의 · 커맨드 · 스킬처럼 pal 이 놓은 파일이다. 사용자 편집을 남겨야 하는지, 이 파일들은 우리 몫이라 지우는지를 A–F 어느 조건도 정하지 않는다. 그래서 어느 쪽 동작이든 통과한다.
- 모집단: 원의도
- 유효성: 참
- 해악도: 실패
- 어디가 걸리나: A3 · B1 (해당 조건 없음)

## 조건의 합이 의도를 덮나

덮이지 않는 대목이 셋 있다.

첫째, 증인 「설치 → 실제 사용 → uninstall 뒤 **프로젝트 워킹트리와 HOME 스냅샷이 설치 전과 바이트로 같은가**. 세 OS CI 시험으로 건다.」는 CI 에서 한 흐름으로 서지 않는다. 두 스냅샷을 전체 사용 걸음과 함께 재는 것은 수동 · 단일 OS 인 F1 뿐이다. 발견 「증인 … CI 조건 어디에서도 한 흐름으로 안 선다」와 「E1 은 CI 성공만 재서 …」가 이 대목이다.

둘째, 「설치 **뒤에** 사용자가 스스로 고친 것은 남기고 우리 몫만 걷는다.」는 settings 의 키 추가와 들여쓰기 변경(A3) · 블록 편집(C1 · C2)만 덮는다. pal 이 넣은 `agent` 값을 사용자가 바꾼 경우, 설치 뒤 더한 훅, pal 이 놓은 파일의 사용자 편집에 대해서는 어느 조건도 판정을 요구하지 않는다. 발견 A3 항과 마지막 항이 이 대목이다.

셋째, 「같은 원격의 클론·worktree 가 나눠 쓰는 외부 기록 → **worktree 있으면 거부, 클론은 경고**」에서 「클론은 경고」를 재는 방이 없고, 「거부」의 범위도 서 있지 않다(발견 D4).

반대 방향으로 의도보다 큰 것이 둘 있다. C2 의 `--force` 는 추정이다. B2 의 「설치 전부터 있던 파생물 삭제」는 원문과 어긋나는 크기다.

## 내가 기각한 것

### A1 의 모집단 중 일부는 착수 커밋에서 이미 바이트 동일일 수 있어 RED 가 원소마다 서지 않는다
- 기각 사유: RED 와 음성 대조가 모집단 전체를 묶은 시험에 걸려 있다. 탭 · CRLF · 끝 개행 없음 같은 원소는 착수 커밋의 재직렬화(`crates/pal-cli/src/install/settings.rs:176-179`)에서 확실히 빨갛다. 그래서 전체 시험의 RED 와 음성 대조는 성립한다.
- 모집단: 저장소
- 유효성: 참
- 해악도: 미관
- 어디가 걸리나: A1

### 재직렬화가 키 순서를 바꿔 A1 · A3 기대 바이트가 설 수 없다
- 기각 사유: `Cargo.lock` 에서 `serde_json` 이 `indexmap` 에 의존한다. 순서 보존이 켜진 빌드라 키 순서는 원인이 아니다.

- 기각 사유: 문면상 맞는 지적이다. 다만 D1 의 검사(착수 커밋 v1 바이트와 대조, 표시 파일 존재)는 스스로 만든 조건 위의 발화가 아니라 외부 고정값과의 대조다. 적힌 행동도 D2 의 「Y 는 그대로」가 함께 잰다. 해악이 없다.
