# F18 — 선언 팩과 개념 층 (프로젝트 온톨로지)

| 우선순위 | 의존 | 규모 | 크레이트 |
|---|---|---|---|
| **P3** | F07 · F11 · F15 | L | `packs/schema` · `pal-extract::pack` |

---

## 1. 왜

지금까지의 모든 것은 **프로젝트 중립**이다. 그런데 실제 프로젝트에는 그 프로젝트만의 어휘가 있다 — *"이 프로젝트에서 `@RequireAuth`가 붙은 함수는 인가 가드다"*, *"`ServiceTask`는 정산 경계 안쪽 개념이다"*.

**팩은 능력을 늘리지 않고 하한을 올린다.** 값의 측정은 `UnresolvedRef`·`candidate` 밀도의 **감소**다.

그리고 여기가 **온톨로지가 실제로 서는 자리**다.

---

## 2. 3층 구조

| 층 | 무엇 | 누가 실행 | 출처 |
|---|---|---|---|
| **코어 추출** | 언어 문법 수준 | 코어 | `extracted` |
| **선언 팩** | 프레임워크 인식기 · 가드/효과 규칙 · **개념·관계 선언** | 코어가 해석 | `asserted` (`asserted_via = rule(규칙 좌표)`) |
| **실행 팩** | 환경 의존 절차 | **호스트가 실행** | `observed` (F16으로 수용) |

**코어는 팩 스키마만 알고 팩 내용은 모른다.** 그리고 **코어는 실행 팩을 실행하지 않는다** — CI가 이 경계를 검사한다.

### 2.1 규칙 파생 사실

```
asserted_via ∈ { direct, rule(규칙 좌표) }      // 비면 저장 거부
```

1. **규칙 파생 라벨은 규칙 좌표에 결박된다.** 규칙이 바뀌면 파생된 전부가 `stale`이 되고, **규칙 하나의 재승인으로 300개가 함께 갱신된다** — 일괄 승인의 기계적 형태.
2. **거짓 양성의 진단이 좌표를 갖는다.** "왜 붙었나"의 답이 "규칙 R-7이 붙였다"가 되고, R-7이 잘못 쓰였으면 파급 범위가 즉시 계산된다.
3. **팩의 완화가 `ScopeReduction`이 된다**(F15) — 규칙을 지우면 파생 라벨이 사라지고, 잔여 감소의 원인이 "판정됨"이 아니라 "범위 축소"임이 잡힌다.

**팩 지문이 `extractor_version`에 합성된다** — 팩이 자라면 좌표가 움직이고, 그것이 관측된다.

## 3. 온톨로지 — 개념을 1급 노드로

### 3.1 지금까지 빠져 있던 것

이 설계가 만드는 노드는 전부 둘 중 하나다 — **코드 좌표를 갖는 것**(심볼·엣지·미해소참조) 또는 **코드 좌표에 결박되는 것**(라벨·결정·계획·잔여). **프로젝트의 도메인 개념 자체가 노드가 되는 자리는 없다.** "주문", "정산 경계", "멱등 처리 대상"은 라벨의 **대상**으로만 존재하고 그 자신은 존재하지 않는다.

### 3.2 딜레마와 제3의 답

> 코어가 팩 스키마에서 어떤 원시 개념까지 표현 가능하게 할 것인가 — **팩이 자유 형식이면 코어가 그 위에서 아무 판정도 못 하고, 코어가 어휘를 고정하면 프로젝트별 계층의 의미가 사라진다.**

**답: 코어가 *어휘*를 고정하지 않고 *메타 어휘*를 고정한다.** 코어는 "개념·관계·제약을 **어떻게 선언하는가**"의 문법만 알고, **어떤 개념이 있는지는 프로젝트가 정한다.**

```toml
# packs/example/concepts.toml
[[concept]]
id = "settlement-boundary"
label = "정산 경계"
grounds = ["kotlin:com.example.settlement.**"]   # 코드 좌표에 결박 — 못 하면 pending

[[relation]]
kind = "contains"
from = "settlement-boundary"
to   = "order-cancellation"

[[constraint]]
rule = "settlement-boundary 안의 심볼은 outbox 경유로만 외부에 쓴다"
predicate = { kind = "effect-dominance", guard = "outbox-write" }
```

### 3.3 개념도 결박된다

**개념은 코드 좌표를 갖지 않는다.** 처분은 계획 항목과 같은 형태다 — **2단 결박**, 결박 못 하면 `pending`. 이미 있는 장치(F09·F12)를 재사용하며 새 장치를 만들지 않는다.

**추론 산물의 출처**: 규칙이 파생시킨 개념 관계는 `asserted_via = rule(규칙 좌표)`다. 출처 축을 늘리지 않는다. 공리가 틀리면 파생 전부가 `stale`이 되고 파급 범위가 계산된다.

## 4. 이슈와 대응

| 이슈 | 왜 | 대응 | 안 되면 |
|---|---|---|---|
| **팩이 저작되지 않는다** | [R-10](../00-risks.md#r-10)의 둘째 뿌리 | P0-preflight T4가 이미 1차 판정 | 이 기능을 "있으면 좋은 것"으로 강등 |
| **개념 저작은 더 앞선 노동** | 세 번째 뿌리 | P0-preflight T6이 이미 측정 | 개념 층을 만들지 않고 자리만 비워 둔다 |
| **개념이 코드에 안 붙는다** | 도메인 개념이 추상적 | 결박률을 측정해 소수면 개념 층은 결박 없는 덩어리 | 만들지 않는다 |
| **메타 어휘가 자유 형식으로 흘러감** | 코어가 그 위에서 아무 판정도 못 함 | 제약(`constraint`)의 `predicate`를 **코어가 아는 술어 집합**으로 제한. 자유 텍스트는 라벨일 뿐 판정 입력이 아니다 | 양쪽 실패면 재설계 대상 |
| **코어가 도메인 어휘를 고정하게 됨** | 판정 가능하게 만들려다 | 술어는 고정(효과 지배·포함 관계·가드 지배), **개념 이름은 자유** | 위와 같음 |
| **팩 로딩 비용** | 설치 시간 잠식 | 지문 캐시 | — |

## 5. 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| **개념 층을 처음부터 만든다** | 사실층 하한이 서기 전에 개념을 세우면 결박할 좌표가 없다 |
| **RDF/OWL 채택** | 개념 체계·추론에는 강하지만, 이 설계가 매 질의에 요구하는 것들(`Envelope`·등급·출처)을 얹는 비용이 다르다. 그리고 **"온톨로지 → 그래프 DB → 특정 제품"의 사슬은 자동으로 이어지지 않는다** |
| **팩을 코어가 실행** | 실행 팩이 코어에 들어오면 `extracted`의 결정론 계약이 프로젝트 코드로 넘어간다 |
| **언어 추출기를 팩으로** | 같은 이유. 언어 추출기는 코어에 있다 |
| **개념에 별도 출처 축(`derived`) 신설** | 출처 파티션 규칙이 다시 열린다. `asserted_via`로 충분 |

---

## 6. 검증

- **팩 있는/없는 대장 대조** — `UnresolvedRef`·`candidate` 감소량. **이것이 팩의 유일한 값 측정.**
- **규칙 재승인 파급** — 규칙 하나 변경 시 파생 N개가 `stale`이 되는가.
- **개념 결박률**.
- **코어가 실행 팩을 실행하지 않음** — CI 검사.
- **대조 불가 명시** — 팩 자체가 문서이므로 "문서 한 장" 대조군이 성립하지 않는다. **"대조 불가"를 적고 통과로 처리하지 않는다.**
