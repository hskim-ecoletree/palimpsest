# F04 — 추출 캐시 (1층)

| 우선순위 | 의존 | 규모 | 크레이트 |
|---|---|---|---|
| **P0** | F02 | M | `pal-store::cache` |

---

## 1. 왜 — 성능이 아니라 계약이다

이 도구는 **임의의 과거 커밋에 대해 같은 방식으로 답해야** 한다(계보 질의가 과거를 요구하므로). 동시에 **설치·운영 비용이 사용자의 것**이라 전 이력을 미리 추출할 수 없다.

두 요구의 화해가 이 기능이다.

> 이력은 **요구가 아니라 지연 평가**다. 콘텐츠 주소 캐시가 있으면 과거 커밋 추출 비용이 **변경 파일 수에 비례**한다.

| 시점 | 무엇을 추출하나 |
|---|---|
| 설치 | HEAD 하나 |
| 결박 발생 | 그 결박이 가리키는 커밋 |
| 계보 질의 | 계보가 지나는 커밋만 |
| 전 이력 replay | 옵션. 기본값 아님 |

**그리고 2층을 통째로 버려도 재파싱 없이 복구된다** — 이것이 "투영은 교체 가능한 캐시"라는 주장을 실물로 만든다.

## 2. 키와 값

```
키:  (blob_hash, extractor_version)      # extractor_version = (문법 버전, 추출기 코드 버전)
값:  FileGraph  (F02)
```

**커밋이 키에 없다.** 그래서:
- 브랜치 전환 → 바뀐 파일만 재파싱
- 과거 커밋 조회 → 대부분 캐시 적중
- **워킹트리 편집 → 그대로 적중**([R-06](../00-risks.md#r-06)) — 파이프라인이 커밋을 전혀 모르므로

**팩 지문도 키에 없다** ([스택 §5.1](../00-stack.md#51-버전-축-셋--하나로-합치면-캐시가-상시-전량-무효화된다)). 팩을 `extractor_version`에 합성하면 **규칙 한 줄을 고칠 때마다 전량 재파싱**이 걸린다 — 팩은 대개 심볼의 존재를 바꾸지 않고 그것에 붙는 라벨을 바꾸는데도. 팩 지문은 파생 라벨·판정의 버전 축이고, 그쪽은 이미 규칙 좌표 결박으로 `stale`을 관리한다(F18). 추출 자체를 바꾸는 팩(`affects = "extraction"`)만 예외적으로 이 키에 합성된다.

```rust
pub struct BlobKey { blob: BlobHash, extractor: ExtractorVersion }

pub trait ExtractCache: Send + Sync {
    fn get(&self, k: BlobKey) -> Result<Option<FileGraph>>;
    fn put(&self, k: BlobKey, g: &FileGraph) -> Result<()>;
    fn stats(&self) -> CacheStats;      // 적중률·크기·엔트리 수
    fn evict_to(&self, budget_bytes: u64) -> Result<EvictReport>;
}
```

## 3. 구현

### 3.1 파일시스템 콘텐츠 주소 저장

```
.palimpsest/
├── cache/                              # 파생 — 지워도 됨
│   ├── 3a/
│   │   └── 3af21c9e....v7.pg.zst      # blob 해시 앞 2바이트로 샤딩 + 추출기 버전
│   └── ...
├── worktree.state                      # 파생
├── index.redb                          # 2층 (F05) — 파생
├── intent.redb                         # ★ 의도 저장소 — 원본. 이 기능의 축출 대상이 아니다
└── intent/*.jsonl                      # ★ 의도 저장소 내보내기 (커밋 권장)
```

**`pal cache prune`이 닿는 범위는 `cache/`뿐이다** ([R-21](../00-risks.md#r-21)). `intent.*`를 지우는 코드 경로가 이 크레이트에 **존재하지 않는 것**이 대응이고, 문자열 스캔으로 CI가 검사한다.

**왜 redb에 안 넣는가**

| | 파일시스템 | redb |
|---|---|---|
| 병렬 쓰기 | 락 없음(파일마다 독립) | 쓰기 트랜잭션 직렬화 |
| OS 페이지 캐시 | 그대로 활용 | DB 내부 캐시와 이중 |
| 부분 손상 | 그 파일 하나로 격리 | DB 전체 위험 |
| 축출 | 파일 삭제 | 트랜잭션 필요 |
| 트랜잭션이 필요한가 | **필요 없다** — 각 엔트리가 독립이고 손실돼도 재계산됨 | — |

1층은 **순수 캐시**다. 원자성이 필요 없다. 2층은 다르다(F05는 redb).

**쓰기 원자성**: 같은 디렉터리에 임시 파일로 쓰고 `rename` — POSIX에서 원자적. 중간에 죽어도 반쪽 파일이 남지 않는다.

### 3.2 직렬화

`postcard`(serde) + `zstd` 레벨 3.

| 후보 | 판정 |
|---|---|
| **`postcard`** ✅ | 컴팩트, 스키마리스 바이너리. 버전은 이미 키에 있으므로 호환성 부담이 없다 |
| `bincode` ⬜ | 비슷하지만 postcard가 varint로 더 작다 |
| `rkyv` ⬜ | zero-copy라 역직렬화가 사실상 공짜. **다만 타입 제약이 크고 초심자 함정이 많다**([R-01](../00-risks.md#r-01)). **P1에서 실측 후 재론** — 역직렬화가 병목으로 확인되면 그때 바꾼다 |
| JSON ❌ | 부피·속도 |

**압축을 켜는 이유**: 부분 그래프는 반복이 많다(같은 문자열·비슷한 구조). 실측 목표는 **파일당 2KB 이하(압축 후)** — 10⁵ 파일 × 1커밋 = 200MB.

### 3.3 무효화 — 파일 경계를 넘는 문제 ([R-05](../00-risks.md#r-05))

> **이 절은 배경 설명이고 구현 소유는 [F07](F07-reference-resolution.md)이다.** 무효화 전파는 파일 간 연산이므로 2층에 산다. 여기서 준비하는 것은 `FileGraph`가 `export_digest`·`import_set`을 **담고 있다**는 것뿐이다. 같은 작업을 F04·F05·F07 세 곳에서 완료로 세지 않는다.

**1층 자체는 무효화가 필요 없다.** 콘텐츠 주소이므로 내용이 바뀌면 키가 바뀐다. 문제는 2층이다.

파일 A를 고쳤을 때:

```
A 의 export_digest 가 그대로  →  A 의 노드만 갱신. 끝.
A 의 export_digest 가 바뀜   →  역 import 색인으로 A 를 참조하는 파일 집합 S 를 찾고
                                 S 의 "해소"만 다시 돌린다 (재파싱 아님 — 1층은 유효)
```

`export_digest`와 `import_set`을 `FileGraph`에 넣어 둔 것(F02)이 이 계산을 가능하게 한다. 역 import 색인은 2층 테이블 하나(F05).

### 3.4 축출 ([R-12](../00-risks.md#r-12))

- 기본 예산 **2GB**. 초과 시 접근 시각 기준 LRU 축출.
- 접근 시각은 파일 mtime으로 근사(별도 메타데이터 불필요, `noatime` 마운트 대비).
- **축출은 정확성에 영향이 없다** — 재파싱될 뿐. 그래서 정책이 단순해도 된다.
- `pal cache stats` / `pal cache prune`로 노출.

## 4. 이슈와 대응

| 이슈 | 왜 | 대응 | 안 되면 |
|---|---|---|---|
| **디스크 증가** | 커밋마다 바뀐 파일이 쌓임 | 압축 + LRU 2GB + `stats` 노출 | 예산을 낮추고 적중률 저하를 실측 |
| **작은 파일 수백만 개** | 파일시스템 inode·디렉터리 엔트리 압박 | 2바이트 샤딩(256 디렉터리). 그래도 많으면 **팩 파일**(append-only + 오프셋 인덱스)로 전환 | 전환 지점을 실측으로 정함 |
| **추출기 버전 올릴 때 전량 무효** | 버전이 키 성분 | 정상 동작이다. 다만 **점진 재추출**(질의된 것부터)로 사용자가 한 번에 10분을 기다리지 않게 | 백그라운드 워밍업 |
| **동시 실행** (CLI와 MCP 서버가 동시에) | 같은 캐시 디렉터리 | 파일 단위 원자 rename이라 안전. 같은 키를 둘이 계산해도 결과가 같다(결정론) | — |
| **캐시 손상** | 디스크 오류·중단 | 역직렬화 실패 시 그 엔트리만 버리고 재계산 + 경고 로그 | 전체 무효화는 하지 않는다 |
| **적중률이 낮다** | 파일이 매번 바뀌는 프로젝트 | `stats`로 관측. 적중률이 낮으면 캐시가 손해이므로 끌 수 있게 | 플래그로 비활성 |

## 5. 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| **캐시 없음(항상 재파싱)** | 과거 커밋 조회·브랜치 전환이 매번 전량 파싱. 계보 질의가 불가능해진다 |
| **커밋 단위 캐시** | 커밋이 하나 늘 때마다 전량 저장. 콘텐츠 주소의 이점(브랜치 전환 적중)을 전부 잃는다 |
| **캐시를 redb에** | §3.1 표 |
| **메모리 전용 캐시** | 프로세스 재시작마다 콜드. MCP 서버는 오래 살지만 CLI는 매번 죽는다 |
| **git notes / git objects에 저장** | git 저장소를 오염시킨다. 사용자 저장소는 우리 것이 아니다 |
| **rkyv로 시작** | [R-01](../00-risks.md#r-01) — 초심자 함정. postcard로 시작하고 병목이 확인되면 교체(트레잇 뒤라 교체 비용이 낮다) |

## 6. 검증

- **재구축 등가성** — 2층을 통째로 지우고 **1층 + 의도 저장소**로 재구축했을 때 ① `extracted`가 전부 복원되고 ② `asserted`·`observed`가 **전부 복원되며** ③ **`intent.*` 파일의 바이트가 변하지 않는가.** **CI 상시.**
  - 이전 판(“그 외 출처는 복원되지 않는가”)은 **의도 유실을 정상으로 승인하는 검사**였다([R-21](../00-risks.md#r-21)). 캐시와 원본의 경계는 "복원되지 않음"이 아니라 **"어느 저장소에서 오는가"** 로 검사한다.
- **캐시 폐기 격리** — `pal cache prune` 실행 후 결박·승인 건수가 불변인가. **CI 상시.**
- **적중률 시나리오** — 브랜치 전환 / 3커밋 전으로 이동 / 워킹트리 편집 각각의 적중률 측정.
- **팩 변경 무영향** — 팩 규칙을 바꿔도 1층 적중률이 떨어지지 않는가(`affects="extraction"` 팩 제외).
- **크기** — 코퍼스별 파일당 평균 바이트(목표 2KB 이하).
- **원자성** — 쓰기 도중 프로세스 kill 후 캐시 무결성.
- **벤치** — 콜드 10³ 파일 30초 이내 / 증분 10² 파일 2초 이내.
