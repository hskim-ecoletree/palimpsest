# F14 — 진입점(C3)과 경계 통과(C4)

| 우선순위 | 의존 | 규모 | 크레이트 |
|---|---|---|---|
| **P2** | F07 · F16 | L | `pal-extract::framework` · `pal-core::graph` |

---

## 1. 왜

**여정은 진입점에서 시작하므로 진입점 목록이 곧 가능한 서사의 목록이다.** 하나를 놓치면 거기서 시작하는 모든 서사가 시야에서 사라진다.

그리고 실제 사용자 여정은 거의 항상 경계를 넘는다 — 프론트가 부르는 백엔드, 서비스가 부르는 서비스, 큐를 건너는 메시지, **다른 저장소에 있는 대상.** 경계에서 끊기는 추적은 여정을 추적하지 못한다. (실측상 저장소 경계가 전체 흐름의 8%에 관여했다.)

**달성 기여**: 목표 3(온보딩). 그리고 F15(감사)의 경로 시작점.

---

## 2. 진입점 (C3)

**진입점은 프레임워크가 정의한다.** 대상 프레임워크를 고를 수 없으므로 이 능력은 **프레임워크가 늘어날 때마다 자라고, 아직 모르는 프레임워크의 진입점은 공백으로 표시된다.**

```rust
pub struct Entrypoint {
    coord: Coord,
    kind: EntrypointKind,       // HttpRoute | MessageConsumer | Scheduler | CliCommand | EventHandler
    detector: DetectorVersion,  // 어느 인식기가 몇 버전에서 찾았나 — 좌표에 실린다
    evidence: NonEmpty<Site>,   // 데코레이터·설정 파일 등
}
```

**인식기 버전이 좌표에 실리는 이유**: 인식기를 개선하면 진입점이 늘어난다. 그것이 **관측된 변화**여야지 조용한 증가면 안 된다.

**인식기는 데이터로 둔다** — 코어는 "데코레이터/애노테이션/설정 파일에서 이런 형태를 찾는다"는 **구조**만 알고, 어떤 프레임워크인지는 인식기 정의가 안다.

**그 스키마의 소유자는 이 기능이다.** 원래 인식기가 F18(P3)에 있었는데 이 기능은 P2다 — 그러면 구현자는 인식기를 코어에 하드코딩하게 되고, 그 순간 "코어는 프레임워크를 모른다"는 경계가 깨진다. **최소 인식기 스키마(`packs/schema/detector.toml`)는 여기서 만든다.** F18은 그 위에 개념·관계·제약 층을 얹는 것이고, 그때 인식기 스키마를 바꾸지 않는다.

```toml
# packs/<name>/detectors.toml — F14가 정의, F18이 확장
[[detector]]
id      = "nest-controller"
kind    = "HttpRoute"
match   = { node = "decorator", name = "Controller" }   # 코어가 아는 형태 집합
version = 1
```

| 초기 인식기 | 형태 |
|---|---|
| Express/Fastify/Hono | `app.get('/path', handler)` 리터럴 경로 |
| NestJS | `@Controller`/`@Get` 데코레이터 |
| Next.js/Remix | 파일시스템 라우팅(경로 규약) |
| Spring | `@RestController`/`@RequestMapping` |
| 큐 컨슈머 | `@KafkaListener`, `queue.process(...)` |

## 3. 경계 통과 (C4) — 증거 없이 엣지를 세우지 않는다

경계에는 명시적 임포트가 없다. 그런데 **이름 기반 해소는 언어 경계를 넘지 않는다**(F07 §3.4)는 규칙이 있다. 화해:

> 경계 엣지는 `extracted`가 아니라 **`inferred`** 이며 `contract` 등급으로만 존재하고, **이름 일치가 아니라 계약 아티팩트를 증거로 요구한다.**

| 증거 | 예 | 강도 |
|---|---|---|
| 선언된 스키마 | OpenAPI · AsyncAPI · protobuf · GraphQL SDL | 강 |
| 양쪽의 리터럴 경로·토픽 + 메서드 일치 | `POST /v1/tasks` ↔ 라우트 선언 | 중 |
| DTO 형태 일치 | 필드 이름·타입 집합 | 약 — **단독으로는 엣지를 세우지 못한다** |

**증거의 추출과 엣지의 성립을 구별한다.**

| | 출처 | 왜 |
|---|---|---|
| 증거 노드 (OpenAPI가 `POST /v1/tasks`를 선언함) | `extracted` | 저장소 안의 파일이고 재현된다 |
| 경계 엣지 (이 호출이 저 라우트에 닿는다) | `inferred` | 명세는 계약을 선언할 뿐 **호출의 실재를 보증하지 않는다** |
| 관측된 호출 (트레이스가 실제로 봄) | `observed` | 별도 엣지가 **나란히** 선다. 덮어쓰지 않고, 어긋나면 그 불일치가 보고 대상 |

```rust
pub struct ContractEdge {
    from: Coord, to: Coord,
    evidence: NonEmpty<Coord>,        // 비면 생성 불가 — 타입으로 강제
    strength: EvidenceStrength,       // Strong | Medium | Weak
}
```

**증거 없이 이름만 같은 것은 엣지를 만들지 않고 `unresolved-boundary`로 대장에 남는다.**

## 4. 멀티레포 ([R-14](../00-risks.md#r-14))

`Snapshot = {(repo_id, commit_sha)}`. 선례가 비워둔 칸이다.

- **P0/P1에서는 원소 1개만 구현하되 타입은 처음부터 집합이다.** 확장 시 타입이 안 바뀌는 것이 핵심.
- **부분 갱신을 1급으로**: 저장소 A는 최신이고 B는 3일 전이면 그 사실이 `Envelope`에 실린다. 동기화를 강요하지 않는다.
- 저장소 하나가 매니페스트에서 빠지면 그것을 지나는 경로가 조용히 사라지는 대신 **대장이 계속 말한다.**

## 5. 이슈와 대응

| 이슈 | 왜 | 대응 | 안 되면 |
|---|---|---|---|
| **계약 증거가 없는 프로젝트** | OpenAPI를 안 쓰는 곳이 많다 | 중강도(리터럴 경로 일치)로 내려감. 그것도 없으면 `unresolved-boundary` | **C4가 전부 비면 "때때로 있는 능력"이고 그 사실을 대장에 명시** |
| **경로 리터럴이 조립됨** | `` `${base}/v1/tasks` `` | 상수 전파 1단계까지만. 이상은 미해소 | F16 관측이 표적 |
| **인식기 커버리지** | 프레임워크가 무한 | 미인식은 공백으로 표시. 밀도가 다음 인식기의 우선순위 | — |
| **파일시스템 라우팅** | 규약이 프레임워크마다 다름 | 규약을 인식기 데이터로 표현 | — |
| **버전 스큐** | 두 저장소의 계약 버전이 다름 | 증거 노드에 좌표가 있으므로 어느 커밋 기준인지 보인다 | — |
| **관측과 정적 추론의 불일치** | 트레이스가 명세에 없는 호출을 봄 | 나란히 저장 + **불일치를 보고 대상으로** | — |

---

## 6. 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| **경로 문자열 일치만으로 엣지** | 거짓 엣지 대량 생산. 이 제품의 규칙 위반 |
| **경계 엣지를 `extracted`로** | 명세는 호출의 실재를 보증하지 않는다. 출처 배정이 거짓이 된다 |
| **관측된 호출이 정적 추론을 덮어쓰기** | 둘은 다른 것을 말한다. 겹쳐 보여야 불일치가 보인다 |
| **`evidence_strength`를 출처 축에 넣기** | 출처를 5·6값으로 늘리면 파티션 규칙이 다시 열린다. 필수 필드로 뺀다 |
| **멀티레포를 나중에 확장** | 좌표 타입이 바뀌면 전량 마이그레이션. 타입은 처음부터 집합 |

---

## 7. 검증

- **코퍼스 실제 경계 재현** — boxwood 프론트↔백 호출을 재현 검출하는가.
- **거짓 엣지 0** — 증거 없이 선 엣지가 있으면 타입 위반(테스트로 검사).
- **인식기 커버리지** — 진입점 수 대 실제 라우트 수(수동 대조).
- **불일치 보고** — 관측과 어긋나는 경계를 실제로 잡는가.
