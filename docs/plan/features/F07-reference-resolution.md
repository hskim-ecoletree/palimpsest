# F07 — 참조 해소와 등급 엣지 (C2)

| 우선순위 | 의존 | 규모 | 크레이트 |
|---|---|---|---|
| **P1** | F05 | **XL — 이 프로젝트 최대의 기술 미지** | `pal-extract::resolve` · `pal-store::stitch` |

---

## 1. 왜

"무엇이 무엇을 부르는가"가 없으면 에이전트는 **"아마 이걸 부를 것"이라고 가정한다.** 그리고 컨설팅("여기를 바꾸면 무엇이 깨지나")이 성립하지 않는다.

**그런데 요구가 충돌한다.** 넓게 잡으라는 요구와 거짓 엣지가 없는 엣지보다 나쁘다는 요구가 둘 다 옳다. 같은 이름의 대상 열 개에 엣지 열 개를 거는 것은 그래프를 채우지만 신호를 죽이고, 그걸 피하려고 엣지를 안 만들면 완전성을 잃는다.

**화해는 "하나를 고르는 것"이 아니라 엣지에 자격을 박는 것이다.**

## 2. 해소 등급 넷

| 등급 | 성립 조건 | 출처 | 저장 형태 |
|---|---|---|---|
| `exact` | 임포트·정의가 해소되어 대상이 유일 | `extracted` | 엣지 1개 |
| `scoped` | 스코프 해소로 후보가 유일 (L2+) | `extracted` | 엣지 1개 |
| `candidate` | 후보가 여럿 | `extracted` | **엣지 1개 + 후보 배열** ← 엣지 N개가 아니다 |
| `contract` | 경계를 넘는 계약 매칭 (F14) | `inferred` | 증거 필수 |

**`candidate`의 표현이 핵심이다.** 후보 집합을 하나의 엣지로 저장하면 완전성은 집합이 지고 정밀도는 질의가 진다.

**질의가 등급을 고른다** — 감사(완전성 우선)는 `candidate`를 포함해 넓게 돌고, 컨설팅(정밀도 우선)은 `exact|scoped`만 쓰되 "제외된 `candidate` N건"을 `Envelope`에 붙인다.

```rust
pub struct Edge {
    from: SymbolId,
    kind: EdgeKind,                 // Calls | Imports | TypeRef | Extends | ...
    grade: ResolutionGrade,
    target: EdgeTarget,
}
pub enum EdgeTarget {
    Resolved(SymbolId),                          // exact | scoped
    Candidates(BoundedSet<SymbolId, 32>),        // K=32. 타입이 상한을 안다
}
```

## 3. 구현 — 4단계로 쪼갠다 ([R-02](../00-risks.md#r-02))

tree-sitter는 **구문 트리까지만** 준다. "이 이름이 가리키는 정의가 어느 심볼인가"는 전부 우리가 짜야 한다. 이것이 이 프로젝트의 최대 미지이므로 **각 단계가 독립적으로 값을 내도록** 쪼갠다.

| 단계 | 무엇을 해소 | 난이도 | 없으면 |
|---|---|---|---|
| **L2a 파일 내** | 같은 파일 안의 정의 참조 | 중 | 대부분의 호출이 `candidate` |
| **L2b 임포트** | 명시적 import/export를 따라간 파일 간 해소 | **높음** ([R-04](../00-risks.md#r-04)) | 파일 경계에서 그래프가 끊긴다 |
| **L2c 멤버** | `obj.method()` 수신자 타입 추론 | **매우 높음** | 메서드 호출이 전부 `candidate` |
| L3 정의-사용 | 읽기/쓰기 집합 | 매우 높음 | F13에서 다룬다 |

**L2c를 P1에서 시도하지 않는다.** 수신자 타입을 모르면 같은 이름의 메서드 전부가 후보가 되고, 그 집합에 상한 `K`를 걸어 초과분은 `UnresolvedRef{후보 과다}`로 강등한다. **이것이 우리 설계가 정직할 수 있는 이유다** — 못 푼 것을 기록하는 자리가 이미 있다.

### 3.1 L2a — 파일 내 스코프 체인

```rust
struct Scope { kind: ScopeKind, bindings: HashMap<Name, LocalIx>, parent: Option<ScopeIx> }
// 블록 · 함수 · 클래스 · 모듈 스코프를 순회 중에 push/pop
// 이름 참조 시 안쪽 스코프부터 위로 탐색 → 첫 일치가 exact
```

호이스팅(함수 선언), TDZ(`let`/`const`), 섀도잉을 언어별로 다룬다. TypeScript는 **값 네임스페이스와 타입 네임스페이스가 분리**되어 있다 — `interface Foo`와 `const Foo`가 공존 가능하므로 스코프 테이블을 둘로 유지한다.

### 3.2 L2b — 모듈 해소 ([R-04](../00-risks.md#r-04))

TypeScript 모듈 해소는 규격이 아니라 관습의 더미다. **커버리지 순으로 계단식**:

| 단계 | 다루는 것 | 구현 |
|---|---|---|
| 1 | 상대 경로 + 확장자 추론 | `./x` → `x.ts` / `x.tsx` / `x/index.ts` 순 |
| 2 | `tsconfig.json` `baseUrl`·`paths` | `extends` 체인 병합. 글롭 패턴 매칭 |
| 3 | barrel 재수출 1단계 | `export * from` · `export { a } from` 추적 |
| 4 | `package.json` `exports` · workspace | 모노레포 |
| — | `node_modules` 내부 | **하지 않는다.** `OutOfScope`로 대장에 |

해소 결과는 `MODULE_MAP` 테이블에 캐시(같은 지정자가 수천 번 나온다).

**tsconfig는 `asserted`가 아니라 `extracted`다** — 저장소 안의 파일이고 해석이 결정론적이다.

### 3.3 스티칭과 무효화 ([R-05](../00-risks.md#r-05))

```
1층(파일 부분 그래프) = f(blob)                    ← 정확한 콘텐츠 주소
2층(해소된 엣지)      = g(1층 전체, Snapshot)      ← 파일 간 연산

A 를 고쳤을 때:
  A.export_digest 불변  →  A 의 노드만 갱신
  A.export_digest 변경  →  IMPORTED_BY[A] 로 영향 파일 집합을 찾아 g 만 재실행 (재파싱 없음)
```

### 3.4 언어 경계

**이름 기반 해소는 언어 경계를 넘지 않는다.** 한 언어의 이름이 다른 언어의 동명 대상에 붙으면 순수한 거짓 엣지다. 언어를 잇는 것은 이름의 우연한 일치가 아니라 명시적 임포트이며, 그것이 없는 경계(HTTP·큐)는 F14의 `contract` 엣지로만 선다.

## 4. 이슈와 대응

| 이슈 | 왜 | 대응 | 안 되면 |
|---|---|---|---|
| **L2c 부재로 메서드 호출이 전부 후보** | 수신자 타입 미추론 | ① 같은 파일/임포트된 클래스면 좁혀진다 ② 후보 K=32 초과는 `UnresolvedRef` ③ **`exact\|scoped` 비율을 게이트 숫자로 공개** | 컨설팅을 약하게 선언하고 큐레이션에 집중 |
| **후보 폭발** | 흔한 메서드명(`get`, `run`) | K 상한 + 경로 곱 예산 B(F05) | K를 낮추고 `UnresolvedRef` 밀도를 지도로 씀 |
| **barrel 체인이 깊다** | `index.ts`가 `index.ts`를 재수출 | 1단계만 추적하고 그 이상은 `UnresolvedRef{정의 없음}`. **깊이 제한을 명시** | 깊이 2로 늘리고 비용 실측 |
| **순환 임포트** | 흔하다 | 해소는 이름 기준이라 순환이 문제되지 않는다. 다만 무효화 전파에서 무한루프 방지 필요(방문 집합) | — |
| **동적 import / require 변수** | 리터럴이 아닌 인자 | `UnresolvedRef{문자열 기반}` — F16 실행 관측의 표적 | — |
| **무효화가 전 파일에 번짐** | 모든 것이 barrel을 거치는 구조 | **먼저 전체 스티칭 비용을 잰다.** 10⁵ 파일 스티칭이 수 초면 증분이 필요 없다 | 전량 재스티칭으로 단순화 |
| **Kotlin** | [R-03](../00-risks.md#r-03) 문법 성숙도 61.2% | 착수 전 측정, 등급을 낮춰 선언 | Kotlin을 L1로 고정 |

## 5. 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| **stack-graphs 채택** | 좌표계·심볼 정체성이 우리 뼈대인데 남의 노드 모델에 얹으면 그 뼈대가 그쪽 모델의 함수가 된다. **대조군 + 장기 `observed` 조달원으로만 둔다** |
| **이름만 같으면 엣지** | 거짓 엣지가 없는 엣지보다 나쁘다 |
| **해소 안 되면 엣지 없음** | 완전성 손실이 조용해진다 |
| **후보마다 엣지 N개** | 그래프가 채워지고 신호가 죽는다 |
| **타입 추론기를 직접 구현** | 사실상 컴파일러를 다시 만드는 일. 1인 프로젝트 범위 밖. **필요하면 SCIP 수용(F16)으로 조달** |
| **`tsc --noEmit` 호출해서 타입 정보 얻기** | 빌드 의존. 균일성 포기. 다만 **`observed` 조달원으로는 정당**(F16) |

## 6. 검증 — 숫자가 게이트다

| 측정 | 게이트 |
|---|---|
| **호출 엣지 중 `exact\|scoped` 비율** | 코퍼스별로 기록. **이 숫자가 컨설팅 산출의 신뢰도 상한이다** |
| 임포트 해소율 (단계 1→4 각각) | 단계별 증분을 기록해 다음에 뭘 만들지 정한다 |
| `candidate` 집합 크기 분포 | K=32가 적정한지 |
| **stack-graphs 대조** | 같은 코퍼스에서 우리 `scoped` 해소의 정밀도/재현율 비교. 유의미하게 나쁘면 `observed` 조달원으로 승격 검토 |
| 차등 재추출 | 전체 vs 증분 경로가 같은 엣지 집합을 내는가 |
| 무효화 전파 범위 | 파일 1개 변경 시 재해소되는 파일 수의 분포 |

**반증 게이트**: ① `candidate` 집합이 실제 프로젝트에서 폭발해 쓸 수 없다 ② 미해소가 대부분이라 신호가 없다 → 그러면 **컨설팅(목표 2)을 약하게 선언하고 큐레이션(목표 1)에 집중한다.** 큐레이션은 결박·낡음이 핵심이고 호출 그래프 정밀도에 덜 의존한다.
