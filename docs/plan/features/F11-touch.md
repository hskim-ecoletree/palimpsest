# F11 — 적시 제시 `touch`

| 우선순위 | 의존 | 규모 | 크레이트 |
|---|---|---|---|
| **P1 — 제품이 완성되는 지점** | F09 · F10 | M | `pal-query::touch` |

---

## 1. 왜 — 이것이 목적이지 수단이 아니다

앞의 열 기능은 전부 이 하나를 위한 것이다.

**문제의 진짜 형태는 "지식이 없다"가 아니라 "지식이 필요한 순간에 도달하지 않는다"다.** 결정을 기록해도, 결박해도, 낡음을 감지해도 — 사람이나 에이전트가 그 코드를 만지려는 순간에 그것이 눈앞에 오지 않으면 아무 일도 일어나지 않는다. 선행 하네스가 실패한 지점이 정확히 여기다: **포착은 포화했는데 항해가 실패했다.**

그래서 `touch`는 세 입구 중 하나가 아니라 **목적**이다.

**달성 기여**: 목표 1(큐레이션)·2(컨설팅)이 실제로 값을 내는 지점. [목표 §1의 완성 장면](../00-goals.md#1-완성-장면--이-화면이-제품이다)이 곧 이 질의의 출력이다.

---

## 2. 무엇을 반환하는가 — 결박의 역방향 색인

```rust
pub struct TouchResult {
    target: Coord,
    bindings: Vec<BoundItem>,               // 아래 일곱 종류
    facts: SymbolFacts,                     // 호출자/피호출자 요약
    effects: Capable<EffectSet>,            // F13 — 없으면 NotBuilt{F13}
    unresolved: Vec<UnresolvedRef>,         // "내가 모르는 것"
    judgments: Capable<JudgmentSummary>,    // F15 — 없으면 NotBuilt{F15}
}

pub enum BoundItem {
    Decision(DecisionRef),          // 결정
    SupersededHistory(Vec<DecisionRef>),  // superseded 이력 — 대체된 결정도 보인다
    Label(LabelRef),                // 가드·효과 라벨
    PlanItem(PlanItemRef),          // 계획 항목 (F12)
    DefectLineage(DefectRef),       // 결함 계보
    Residual(ResidualRef),          // 미판정 잔여 (F15)
    ScopeReduction(ScopeReductionRef), // 범위 축소 (F20)
}
```

**일곱 종류를 한 번에 반환하는 것이 요점이다.** 사람은 "이 코드에 관련된 게 뭐가 있지"를 종류별로 묻지 않는다.

### 2.1 `Capable<T>` — **이 기능이 P1인데 P2·P3 산출을 자리로 갖기 때문에 필요하다**

`judgments`(F15, P2) · `effects`(F13, P2) · `ScopeReduction`(F20, P3)은 이 기능이 완성될 때 **아직 존재하지 않는다.** 그런데:

| 후보 | 왜 안 되나 |
|---|---|
| `Option<T>` | 선택 필드 금지 위반. `None`이 "없음"인지 "안 만듦"인지 구별 안 됨 |
| 빈 `Vec` / `Finding 0` | **이 제품의 정면 위반.** "판정 결과 위반 없음"과 "감사 능력이 없음"이 같은 화면이 된다 |
| 필드를 나중에 추가 | 표면 스키마가 기능마다 깨져 소비자가 못 따라온다 |

`Capable<T>`([스택 §5.3](../00-stack.md#53-capablet--점진-구축이-정직함을-깨지-않게))가 답이다. 자리는 처음부터 있고 값이 `NotBuilt{capability}`다. 출력은 이렇게 된다:

```
■ 판정
  (이 빌드에는 감사 능력이 없습니다 — F15 미구축)
```

**`Finding 0`이라고 말하지 않는다.** 그리고 `Envelope.capabilities`가 능력 목록을 매 응답에 실으므로 소비자는 질의 없이 안다. `BoundItem`의 `Residual`·`ScopeReduction` 변형은 **타입에는 처음부터 있고 값이 안 들어올 뿐**이며, 그 사실이 `capabilities`로 설명된다.

**`ScopeReduction`이 `touch` 대상인 이유**: 기준이 완화되어 판정 대상에서 빠진 코드가 있으면, 그 사실이 **사람이 있는 곳으로 와야 한다.** 조용히 목록에서 사라지면 그것이 게이트 오염이다.

## 3. 구현

### 3.1 역방향 조회

```rust
fn touch(coord: &Coord, ctx: &QueryCtx) -> Result<Envelope<TouchResult>> {
    let sym = resolve(coord)?;                        // F03
    let binding_ids = ctx.proj.bound_by(sym)?;        // BOUND_BY 테이블 범위 스캔 — O(결박 수)
    let bindings = binding_ids.map(|id| {
        let b = ctx.proj.binding(id)?;
        let state = state_of(&b, ctx.proj)?;          // F09 — 반경만큼의 비용
        BoundItem::from(b, state)
    }).collect();
    // ...
    Ok(Envelope::new(result, snapshot, freshness, coverage, ledger, elision))
}
```

핵심은 `BOUND_BY` 역방향 색인(F05)이다. 정방향만 있으면 O(전체 결박)이 되고, 그러면 대화 흐름을 끊는다.

### 3.2 무엇이 `touch`를 부르는가 — 세 경로

| 경로 | 시점 | 구현 |
|---|---|---|
| **에이전트가 명시적으로** | 코드를 읽기/고치기 전 | MCP 툴 `touch` |
| **사람이 CLI로** | 아무 때나 | `pal touch <coord>` |
| **편집 감지 자동 제시** | 파일을 열거나 저장할 때 | 플러그인 훅 — **P1에서는 하지 않는다**(호스트 결합 위험). 다만 워킹트리 좌표([R-06](../00-risks.md#r-06))가 이미 이것을 가능하게 해 둔다 |

### 3.3 출력 형태 — 점진 회상

에이전트 컨텍스트는 유한하다([R-11](../00-risks.md#r-11)). `touch`가 200건을 한 번에 쏟으면 그 지식은 쓸모를 잃는다.

| 규칙 | |
|---|---|
| 기본 응답은 **요약 + 상위 N건**(기본 10) | 나머지는 `elision`에 건수로 |
| 정렬 우선순위 | `stale` > `pending` > `live`, 그리고 결박 시점이 최근인 것 우선 |
| **`stale`은 항상 보인다** | 상한에 걸려도 `stale` 항목은 우선 포함. 낡은 것이 안 보이면 이 기능의 존재 이유가 사라진다 |
| 상세는 후속 질의 | `binding.status`, `refs.callers` 등 |

### 3.4 재발 사례 재현 장치

이 기능이 실제로 값을 내는지 검사하는 방법: **코퍼스에서 같은 실수가 반복된 지점을 찾고, `touch`가 그 규칙을 띄우는지 본다.**

선행 하네스에서 같은 종류의 실수가 5회 재발한 기록이 있다. 그 5회 각각의 커밋 시점에서 `touch`를 돌려 "이때 이 결정이 떴다면 막혔을까"를 검사한다. **이것이 이 기능의 유일한 직접 효능 측정이다.**

## 4. 이슈와 대응

| 이슈 | 왜 | 대응 | 안 되면 |
|---|---|---|---|
| **결박이 없어 빈 답** | 의도층 콜드스타트 | F10·F12가 채운다. 빈 답일 때 **"결박 0건, 미결박 서술물 N건"**을 반환해 다음 행동을 알린다 | 빈 답이 지속되면 F10의 해소율이 문제 |
| **응답 부피** | 일곱 종류 × N건 | §3.3 점진 회상 + `stale` 우선 | 상한을 낮춘다 |
| **상태 계산 비용** | 결박마다 반경만큼 | 증분 갱신(F09)으로 대부분 캐시됨. `closure(k)`는 예산 제한 | 반경별 지연 실측 후 기본값 조정 |
| **좌표 표기의 사용성** | `repo:path#Container.name` 문자열을 사람이 못 씀 | 부분 매칭 + 근접 후보 제안. `pal touch cancel`이 후보를 보여줌 | — |
| **읽히지 않는다** | 에이전트가 툴을 안 부름 | 툴 설명(description)을 정확히 + 플러그인이 프롬프트로 유도. **다만 이것을 코어에 넣지 않는다** | 효능 측정에서 드러난다 |
| **효능을 측정할 수 없다** | 호스트가 열람 여부를 안 알려줌 | ① 직접 측정: 호스트 로그를 `observed`로 조달 ② 대리 측정: **재발 사례에서 여섯 번째가 나는가** | 대리 측정만으로 판정 |

## 5. 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| **결박 목록을 프롬프트에 통째로 싣기** | 컨텍스트를 잡아먹고 그 지식은 쓸모를 잃는다. 점진 회상이 요구사항 |
| **종류별 질의로 분리** | 사람은 종류별로 묻지 않는다. 한 번에 반환하는 것이 이 기능의 값 |
| **낡은 것을 숨기고 유효한 것만** | `stale`이 이 제품의 핵심 산출이다. 정반대 |
| **자동 훅으로 강제 제시** | 호스트 결합. 그리고 원치 않는 개입은 무시로 이어진다. P1에서는 명시적 호출만 |
| **관련도 점수로 정렬** | 점수는 근거가 없다. `stale`/`pending`/시점이라는 **사실 기반 정렬**을 쓴다 |

## 6. 검증 — 이 기능의 게이트가 프로젝트의 게이트다

| 측정 | 게이트 |
|---|---|
| **재발 사례 재현** — [P0-preflight T8](P0-preflight.md)이 `corpus/tasks/recurrence.toml`에 **미리 고정해 둔** 5건에서 `touch`가 관련 결정을 띄우는가 | 띄우지 못하면 **적시 제시가 목적이라는 판단 자체가 틀린 것.** 사례를 지금 고르면 결과를 보고 고르는 것이 되어 게이트가 무효다 |
| 응답 지연 | 대화 흐름을 끊지 않는가 (목표: p95 < 500ms) |
| 응답 크기 | 실 MCP 세션 토큰 분포 |
| 빈 답 비율 | 높으면 F10으로 되돌아간다 |
| **행동 변화** — 브리핑을 본 뒤의 변경이 계획 이탈률(F12)을 낮추는가 | [목표 G2](../00-goals.md#5-성공실패의-판정-형태) |

**반증되면**: `touch`가 사람/에이전트의 다음 행동을 바꾸지 못하면 목표 1·2가 무의미하고, **이 제품의 전제가 틀린 것이다.** 그때는 무엇이 실제로 행동을 바꾸는지 다시 관측하는 데서 시작한다.
