# F12 — 계획-구현 결박과 이탈률

| 우선순위 | 의존 | 규모 | 크레이트 |
|---|---|---|---|
| **P1** | F11 | M | `pal-core::intent` · `pal-query::deviation` |

---

## 1. 왜 — 이미 지불되고 있는 승인에 올라탄다

의도층의 최대 비용은 **사람의 노동**이다([R-10](../00-risks.md#r-10)). 그런데 계획 검토는 **이미 일어나고 있다** — 에이전트가 계획을 세우고 사람이 승인하는 절차는 이미 존재한다. 거기에 좌표를 붙이면 **새 노동 없이** 의도층이 채워진다.

그리고 이것이 F10(과거 문서 인입)보다 정확하다 — **계획은 쓰는 시점에 좌표를 요구할 수 있다.** 소급 해소가 아니라 사전 선언이다.

**두 번째 이유**: 이탈률이 **F19(브리핑)의 유일한 효능 측정 수단**이 된다. "브리핑을 본 뒤의 변경이 계획에서 덜 벗어나는가"를 재려면 이탈률이 먼저 있어야 한다.

---

## 2. 데이터

```rust
pub struct Plan { items: NonEmpty<PlanItem> }

pub struct PlanItem {
    id: EntityId,
    statement: String,                    // 무엇을 할 것인가
    expected_coords: Vec<CoordPattern>,   // 어디를 건드릴 것인가 — 아직 없을 수 있다
    verification: VerificationStep,       // 무엇으로 됐다고 판정할 것인가
}

pub struct Deviation {
    as_planned: Vec<(PlanItemId, Coord)>,      // 계획대로
    unplanned: Vec<Coord>,                      // 계획에 없던 변경
    unimplemented: Vec<PlanItemId>,             // 계획했으나 없는 변경
    unmeasurable: Vec<PlanItemId>,              // 좌표가 해소되지 않아 판정 불가 ← 분리 필수
}
```

**`unmeasurable`을 분리하는 것이 중요하다.** 좌표로 해소되지 않은 계획 항목을 "계획대로"나 "미구현"에 섞으면 이탈률이 거짓말이 된다. 못 잰 것은 못 쟀다고 적는다 — 이 제품 전체의 규칙([목표 §3.1](../00-goals.md#31-모르는-것을-안다고-하지-않는다))이 여기에도 적용된다.

## 3. 구현

### 3.1 계획 인입

- 마크다운 계획 문서를 F10의 파서로 조각화.
- 항목마다 **예상 좌표**를 찾는다. 세 형태를 허용:

| 형태 | 예 | 해소 |
|---|---|---|
| 기존 심볼 | `` `OrderService.cancel` `` | 즉시 해소 → 결박 |
| 아직 없는 심볼 | `` `OrderService.refund` (신규) `` | **`pending` 결박** — 좌표가 생기면 자동으로 `live` |
| 경로 패턴 | `src/order/**` | 파일 단위 결박. 정밀도는 낮지만 `unmeasurable`보다 낫다 |

**`pending`이 이 기능의 핵심 상태다.** 신생 프로젝트에서는 의도가 코드를 선행하므로 결박할 좌표가 없다. "아직 만들지 않았다"와 "만든 뒤 어긋났다"를 구별하는 것이 F09가 5상태를 가진 이유다.

### 3.2 이탈 대조

```
Deviation = 대조(계획 좌표 집합, 실제 변경 좌표 집합)

실제 변경 좌표 = git diff (base..head) → 변경 파일 → 변경된 심볼 (body_digest 비교)
```

**심볼 단위 diff가 필요하다.** 파일 단위로 하면 한 줄 포매팅에도 "계획에 없던 변경"이 뜬다. F03의 `body_digest`가 여기서 두 번째로 값을 낸다.

### 3.3 기획 → 결정 2단 결박

계획보다 앞선 것(기획·요구사항)은 코드 좌표를 아예 갖지 않는다. 처분:

```
기획 항목 ──(결박)──> 결정 ──(결박)──> 코드 좌표
                        └─ 결박 못 하면 pending
```

**이 2단 결박 자체가 미검증 장치다**([R-10](../00-risks.md#r-10)의 사슬). 개념 노드(F18)도 같은 형태를 쓰므로, 여기서 실측한 해소 비율이 그쪽 판단의 근거가 된다.

### 3.4 이 계획 문서 자신을 첫 `Plan`으로 삼는다

`docs/plan/features/*.md`의 완료 체크리스트 항목들이 첫 `Plan`이다. 실제 커밋과 대조해 이탈률을 잰다.

**자기 적용의 값**: 계획 항목이 좌표로 해소되는 비율을 실제로 재볼 수 있다. **한계**: 편의 표본([R-19](../00-risks.md#r-19)).

## 4. 이슈와 대응

| 이슈 | 왜 | 대응 | 안 되면 |
|---|---|---|---|
| **계획 항목이 좌표로 안 풀린다** | "인증 로직 개선" 같은 서술 | ① 세 형태 허용(신규 심볼·경로 패턴 포함) ② 못 풀면 `unmeasurable`로 **분리** ③ 계획 작성 시 좌표를 요구하는 템플릿 제공 | `unmeasurable`이 지배하면 이 기능의 값이 낮다 — 그 사실이 숫자로 보인다 |
| **`pending`이 영원히 안 풀림** | 계획했는데 안 만듦 | 정상이다. `unimplemented`로 잡히는 것이 이 기능의 산출 | — |
| **경로 패턴의 정밀도** | `src/**`는 무의미 | 패턴이 매칭하는 파일 수에 상한. 초과하면 거부하고 좁히라고 요구 | — |
| **리팩터링이 "계획에 없던 변경"으로** | 계획에 안 적힌 정리 작업 | `unplanned`가 나쁜 것이 아니다. **판정이 아니라 관측**이다. 분류만 하고 평가하지 않는다 | — |
| **base 커밋 선택** | 어디부터가 이 계획의 변경인가 | 계획 승인 시점의 Snapshot을 계획에 기록 | — |
| **2단 결박 해소율이 낮다** | 기획→결정이 안 풀림 | 실측하고 낮으면 그 마디를 이름만 남기지 않게 재설계 | F18(개념)의 근거가 됨 |

## 5. 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| **커밋 메시지에서 계획을 추출** | 커밋 메시지는 결정의 기록이 아니라 흔적이다. 그리고 사후다 |
| **이슈 트래커 연동** | 외부 시스템 의존. 그리고 티켓은 좌표를 갖지 않는다. (나중에 조달원으로는 가능) |
| **`unmeasurable`을 미구현에 합산** | 이탈률이 거짓말이 된다 |
| **파일 단위 diff** | 포매팅에 반응한다. 심볼 단위여야 한다 |
| **계획 준수를 강제(게이트)** | 거버넌스는 이 층 위에 선다. 이 기능은 관측이지 집행이 아니다 |

---

## 6. 검증

| 측정 | 게이트 |
|---|---|
| **계획 항목의 좌표 해소율** | 낮으면 `unmeasurable`이 지배 → 기능의 값이 낮다 |
| 소급 대조 | 코퍼스의 과거 계획 문서와 실제 커밋을 대조해 3분류가 말이 되는가 |
| 자기 적용 | 이 계획 문서로 이탈률 측정 |
| 기획→결정 해소 비율 | F18(개념) 판단의 입력 |
