# P0-preflight — 코드를 쓰기 전에 손으로 재는 것

| 우선순위 | 의존 | 규모 | 산출 |
|---|---|---|---|
| **P0 — 맨 앞. 이것 전에 코드를 쓰지 않는다** | 없음 | M | `corpus/` · `docs/gates/preflight.md` |

---

## 1. 왜 — 이 프로젝트에서 가장 비싼 것을 가장 먼저 검사한다

이 설계에는 **사람의 노동을 요구하는 뿌리가 셋**이고, 뿌리가 무너지면 그 위의 기능 전부가 빈 껍데기가 된다.

```
        ① 라벨 승인 노동        ② 규칙 팩 저작        ③ 개념 저작
              │                       │                     │
              └───────────┬───────────┴──────────┬──────────┘
                          ▼                      ▼
              감사(F15) · 효과 판정(F13) · 구조 평가(F20) · 팩(F18)
              — 뿌리가 각각 절반씩만 일어나면 잎에 남는 것은 8분의 1
```

이 셋을 마지막에 검사하면 **F13·F15·F18·F20의 비용이 이미 지불된 뒤다.** 그래서 맨 앞에 둔다. 코드가 한 줄도 필요 없다.

**그리고 성공 기준을 사후에 고르지 않기 위해서다.** 평가 과제와 합격선을 코드 이전에 커밋해야 그 커밋 해시가 등록 증거가 된다. 나중에 등록하면 그건 등록이 아니다([R-18](../00-risks.md#r-18)).

## 2. 작업

| **T4** | **규칙 팩을 손으로 써 보기** — boxwood에 규칙 5~10개를 종이 위에서 쓰고, 그것이 파생시킬 라벨 수와 줄어들 미해소 참조 수를 손으로 센다 | 파생 비율 | 팩이 값을 못 내면 F18을 강등 |
| **T5** | **평가 코퍼스·과제·합격선 사전 등록** | `corpus/` 커밋 | §4 |
| **T6** | **온톨로지 저작 가능성** — 실 프로젝트 하나의 도메인 개념 20개와 그 관계를 손으로 적고, **몇 개가 코드 좌표로 결박되는지**와 저작에 든 시간을 센다 | 결박률 | 개념이 코드에 안 붙으면 온톨로지 층은 결박 없는 덩어리가 된다 |
| **T7** | **Kotlin 파싱 사전 측정** — `tree-sitter-kotlin`으로 boxwood 전 파일을 파싱해 성공/부분/에러 비율과 최상위 선언 추출 정확도를 센다 | 숫자 | [R-03](../00-risks.md#r-03). 30분이면 되고, 안 하면 F07 한복판에서 안다 |

## 3. 반증 게이트 — 무엇이 나오면 계획이 바뀌는가

| 관측 | 처분 |
|---|---|
| 라벨 30건 승인이 감당 불가한 시간을 먹는다 | **감사(F15)·구조 평가(F20)를 산출 목록에서 내린다.** 큐레이션·컨설팅만 남긴다 |
| 손으로 쓴 팩이 라벨을 유의미하게 파생시키지 못한다 | F18(선언 팩)을 "있으면 좋은 것"으로 강등 |
| 과제·합격선을 사전 등록할 수 없다 | **이후 모든 게이트가 자기 판정이 된다.** 이 사실을 명시하고 진행하거나, 등록 가능한 형태로 과제를 다시 짠다 |
| 개념 20개 중 코드 좌표로 결박되는 것이 소수 | 온톨로지 층은 결박 없는 덩어리다. 자리만 비워 두고 층은 만들지 않는다 |
| Kotlin 파싱 성공률이 낮다 | 판정 코퍼스를 TypeScript 프로젝트로 교체 |
| boxwood 복원 실패 | 대체 코퍼스 선정 후 T2~T4 재실행 |

> **취소는 실패가 아니라 이 계획이 작동한 것이다.** preflight이 반증되면 기능 20개 중 여섯이 착수 전에 취소된다 — 그것이 이 단계를 맨 앞에 둔 이유다.

## 4. `corpus/` 레이아웃 — 사전 등록의 실물

```
corpus/
├── manifest.toml     # 저장소·커밋·언어 구성·규모
├── tasks/            # 과제 5건 이상. 각각: 질문 / 기대 산출의 형태 / 채점 절차
├── arms.toml         # 대조군 — ① 문서 한 장 ② 기성 코드그래프 MCP 도구 ③ 기존 정적 분석 도구
└── criteria.toml     # 기능별 합격선. 이 파일의 커밋 시각이 등록 증거
```

**규칙 셋**

1. **사후에 과제를 고르지 않는다.** 과제를 기능 구현 도중에 바꾸면 그것이 곧 게이트 오염이다.
2. **n ≥ 5.** 사례 하나로 "되더라"를 결론 삼지 않는다.
3. **기권을 명시한다.** 대조가 성립하지 않는 기능(예: 팩 — 팩 자체가 문서다)은 "대조 불가"를 적는다. 생략하고 통과로 처리하는 것이 가장 조용한 실패 경로다.

**코퍼스 후보**

| 저장소 | 스택 | 무엇의 판정 대상인가 |
|---|---|---|
| boxwood | Kotlin/Spring/Exposed + Svelte | 효과 집합(F13)·감사(F15)·다언어 |
| ditto | TypeScript | 적시 제시(F11)·계획 결박(F12) |
| palimpsest 자신 | 문서 위주 | 서술물 인입(F10) — **편의 표본임을 명시**([R-19](../00-risks.md#r-19)) |
| 대형 OSS 1건 (preflight에서 선정) | TypeScript | 규모 목표(10⁵ 파일) 검사 |
