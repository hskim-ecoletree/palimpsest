## R-01 {#r-01}
### 소유자가 Rust에 미숙하다 · **치명**

**증상** — 타입으로 제약을 강제한다는 스택 결정의 근거가, 정작 그 타입 시스템과 싸우느라 진척이 0인 상태로 뒤집힌다. 소유권·수명·트레잇 객체에서 막히면 며칠이 사라진다.

**원인** — 언어 선택의 근거(§[stack §1](00-stack.md#1-언어--rust-edition-2024))는 언어를 다룰 줄 알 때만 값을 낸다.

**대응 — 셋 다 F01~F03 안에 있다**
1. **첫 세 기능의 범위가 언어 입문의 범위와 겹치도록 짰다.** 좌표·해시·파일 상태 열거·테이블 출력. `Coord`·`BodyDigest`가 전부 값 타입(`Copy`/`Clone`)이라 참조 그래프가 거의 생기지 않는다. 수명 파라미터가 등장하는 곳은 커서(`EdgeCursor`) 하나뿐이고 그것도 P0 후반이다.
2. **의존 크레이트를 넷으로 고정**(파서·해시·직렬화·CLI). 크레이트 선택이 학습을 대체하는 것을 막는다.
3. **`#![forbid(unsafe_code)]` + `clippy::pedantic` 상시.** 초심자의 실수가 조용히 통과하지 않게.

**대응이 실패하면** — F01~F03이 언어 때문에 막히면 언어를 재론한다. 그때 바뀌는 것은 언어이지 [구조](00-stack.md#4-코드-구조--워크스페이스와-의존-방향)가 아니다. 대체안은 Go이며, 그 경우 §5의 다섯 제약 중 셋이 컴파일 타임에서 CI 검사로 내려온다(그 사실을 명시적 손실로 기록한다).

**판정** — F01·F02·F03이 완료되는가. 완료 여부가 곧 판정이다.

## R-02 {#r-02}
### tree-sitter 위에서 스코프 해소(L2)를 직접 만들어야 한다 · **치명**

**증상** — tree-sitter는 **구문 트리까지만** 준다. "이 이름이 가리키는 정의가 어느 심볼인가"는 주지 않는다. 즉 C2(참조)의 `exact`/`scoped` 등급은 전부 우리가 짜야 한다. 이것이 이 프로젝트에서 가장 큰 단일 기술 미지다.

**원인** — 빌드하지 않기로 했으므로 컴파일러의 심볼 테이블을 못 쓴다. tree-sitter는 파서이지 의미 분석기가 아니다.

**대응 — 4단계로 쪼개고 각 단계가 독립적으로 값을 낸다**

| 단계 | 무엇을 해소하나 | 난이도 | 없으면 |
|---|---|---|---|
| L1 구조 | 심볼 존재·포함 관계 | 낮음 | 아무것도 안 됨 |
| L2a 파일 내 | 같은 파일 안의 정의 참조 (지역 스코프 체인) | 중간 | 대부분의 호출이 `candidate` |
| L2b 임포트 | 명시적 import/export를 따라간 파일 간 해소 | **높음** ([R-04](#r-04)) | 파일 경계에서 그래프가 끊김 |
| L2c 멤버 | `obj.method()` 의 수신자 타입 추론 | **매우 높음** | 메서드 호출이 전부 `candidate` |

- **L2c를 P0/P1에서 시도하지 않는다.** 수신자 타입을 모르면 같은 이름의 메서드 전부가 후보 집합이 되고, 그 집합에 상한 `K`를 걸어 초과분은 `UnresolvedRef{후보 과다}`로 강등한다. **이것이 우리 설계가 정직할 수 있는 이유다** — 못 푼 것을 못 풀었다고 기록하는 자리가 이미 있다.
- **부분 조달원으로 stack-graphs를 둔다.** 채택하지 않는다(좌표계·심볼 정체성이 우리 뼈대인데 남의 노드 모델에 얹으면 그 뼈대가 그쪽 모델의 함수가 된다). 대신 ① 우리 `scoped` 해소의 정확도 대조군 ② 장기적으로 `observed` 조달원.
- **정확도 상한을 미리 선언한다.** L2c 없이 TypeScript에서 호출 엣지의 몇 %가 `exact|scoped`로 서는지를 F07의 게이트 숫자로 삼는다.

**대응이 실패하면** — `exact|scoped` 비율이 낮아 그래프가 `candidate`와 `UnresolvedRef`로 덮이면, **컨설팅(목표 2)이 성립하지 않는다.** 그러면 큐레이션(목표 1)만 남기고 범위를 줄인다 — 큐레이션은 결박·낡음이 핵심이고 호출 그래프 정밀도에 덜 의존한다.

**판정** — F07의 코퍼스 실측.

## R-03 {#r-03}
### tree-sitter-kotlin 문법이 L2를 못 받칠 수 있다 · **높음**

**증상** — Kotlin 파일이 `partial`로 대량 떨어지거나, 파싱은 되는데 노드 구조가 불안정해 심볼 추출 규칙을 못 짠다.

**원인 — 이것은 추측이 아니라 관측이다.** `fwcd/tree-sitter-kotlin`은 JetBrains Kotlin 컴파일러의 PSI 참조 파서 대비 **구조 일치율 61.2%(74/121 테스트)** 를 공개하고 있다. 활발히 유지되고 최근에도 수정이 들어가지만, TypeScript 문법과 같은 급의 성숙도를 전제할 수 없다.

**대응**
1. **Kotlin을 첫 언어로 삼지 않는다.** TypeScript로 파이프라인 전체를 세운 뒤 두 번째로 붙인다.
2. **붙이기 전에 30분짜리 측정을 먼저 한다** — 코퍼스의 Kotlin 파일 전부를 파싱해 `parsed`/`partial`/에러 노드 비율과, 최상위 선언 추출의 정확도를 센다. 코드를 짜기 전에 숫자를 본다.
3. **언어 등급을 언어별로 낮춰 선언한다.** Kotlin이 L1까지만 되면 대장에 `Kotlin: L1 · identity_grade=ordinal`로 적히고, 그 결과 Kotlin 파일에서는 오버로드 구별이 순서에 의존한다는 것이 **사용자에게 보인다**. 숨기지 않는 것이 대응이다.

**대응이 실패하면** — Kotlin이 L1 이하면 그 언어로 된 코퍼스(boxwood)에서 효과 집합(F13)·감사(F15)의 판정 대상이 성립하지 않는다. 그러면 판정 코퍼스를 TypeScript 프로젝트로 바꾸거나, 문법에 직접 기여한다(비용이 크므로 최후 수단).

**판정** — F07에서 Kotlin 착수 직전의 측정.

## R-04 {#r-04}
### TypeScript 모듈 해소가 규격이 아니라 관습의 더미다 · **높음**

**증상** — `import { x } from '@/utils'` 가 실제로 어느 파일의 어느 심볼인지 알아내려면 tsconfig `paths`, `baseUrl`, `moduleResolution`(node/node16/bundler), package.json `exports`/`imports`, barrel 파일(`index.ts` 재수출), 확장자 생략, `.d.ts` 매핑, 모노레포 workspace 링크를 전부 알아야 한다.

**원인** — TypeScript 모듈 해소는 컴파일러 구현이 사실상의 명세다.

**대응 — 커버리지 순으로 계단식 구현. 각 단계가 끝날 때마다 해소율을 측정한다**

| 단계 | 다루는 것 | 예상 커버리지 |
|---|---|---|
| 1 | 상대 경로 + 확장자 추론(`./x` → `x.ts`/`x.tsx`/`x/index.ts`) | 대부분의 프로젝트 내부 참조 |
| 2 | `tsconfig.json`의 `baseUrl`·`paths`(extends 체인 포함) | 별칭 임포트 |
| 3 | barrel 재수출 1단계 추적(`export * from`, `export { a } from`) | 대형 프로젝트의 공용 모듈 |
| 4 | `package.json` `exports` 맵 · workspace 링크 | 모노레포 |
| — | `node_modules` 내부 | **하지 않는다.** 범위 밖(`OutOfScope`)으로 대장에 적는다 |

- **못 푼 임포트는 전부 `UnresolvedRef{사유=정의 없음}`** 이고, 사유별 밀도가 다음에 무엇을 구현할지의 지도가 된다. 즉 이 리스크는 **로드맵을 자동 생성하는 장치**를 이미 갖고 있다.
- tsconfig 자체는 `asserted`가 아니라 `extracted`다(저장소 안의 파일이고 해석이 결정론적).

**대응이 실패하면** — 단계 3까지 해도 해소율이 낮으면 그 프로젝트는 대장에 낮은 등급으로 표시되고, 그 상태로도 큐레이션(결박·낡음)은 작동한다. 컨설팅만 약해진다.

**판정** — F07, 코퍼스별 임포트 해소율.

## R-05 {#r-05}
### 증분 재추출의 무효화가 파일 경계를 넘는다 · **높음**

**증상** — 파일 A를 고쳤다. A만 다시 파싱하면 되는가? **아니다.** A가 export하는 심볼의 시그니처가 바뀌면, A를 import하는 B·C·D의 참조 해소 결과가 바뀐다. 순진하게 A만 갱신하면 2층 인덱스가 조용히 틀린다.

**원인** — 1층은 파일 단위 콘텐츠 주소라 정확하지만, **해소는 파일 간 연산**이다.

**대응 — 스티칭을 두 단계로 나누고 무효화 범위를 명시적으로 계산한다**

```
1층(파일 부분 그래프)  = f(blob 내용)                 ← 파일 A만 바뀌면 A만 재계산. 정확.
2층(해소된 엣지)       = g(1층 전체, Snapshot)        ← A의 export 집합이 바뀌면
                                                        A를 import 하는 파일들의 g 를 재계산
```

- 1층 부분 그래프에 **`export_digest`(그 파일이 밖에 노출하는 이름·시그니처의 해시)** 와 **`import_set`(그 파일이 참조하는 외부 모듈 목록)** 을 함께 저장한다.
- 재추출 시: A의 `export_digest`가 그대로면 → A의 노드만 갱신하고 끝. 바뀌면 → 역 import 색인으로 A를 참조하는 파일 집합을 찾아 그들의 해소만 다시 돌린다(**재파싱은 하지 않는다** — 1층은 유효하다).
- 역 import 색인은 2층의 테이블 하나.

**대응이 실패하면** — 무효화 전파가 대부분의 파일에 번지는 프로젝트(모든 것이 barrel을 거치는 구조)에서는 증분의 이득이 사라진다. 그때는 전체 스티칭 비용을 재는 쪽으로 목표를 바꾼다(10⁵ 파일 스티칭이 수 초면 증분이 필요 없을 수도 있다 — **먼저 재본다**).

**판정** — F04·F07. 벤치로 상시 감시.

## R-06 {#r-06}
### 워킹트리에 좌표가 없다 — **설계 공백** · **치명**

**증상** — 에이전트가 코드를 **편집하는 중**에 `touch`를 부른다. 그런데 그 편집은 아직 커밋되지 않았다. `Coord = (repo, commit_sha, extractor_version, symbol_id)`인데 **워킹트리에는 `commit_sha`가 없다.** 좌표가 없으면 결박도 낡음 판정도 성립하지 않는다.

**원인** — 설계는 커밋을 시간축으로 삼았다. 그런데 이 제품의 1순위 사용 장면(적시 제시)은 정확히 **커밋 전 순간**에 일어난다. `DESIGN §2.3`은 "워킹트리와 일치하는지 표시한다"까지만 말하고, 워킹트리 자체를 좌표화하는 규정이 없다.

**대응 — 커밋 축을 확장한다. 지금 결정한다(F01).**

```rust
pub enum TreeRef {
    Committed(CommitSha),
    // 워킹트리: 추적 파일들의 blob 해시 집합에 대한 머클 루트.
    // 내용이 같으면 같은 값 → 편집이 멈춘 동안은 안정적인 식별자다.
    Worktree { base: CommitSha, tree_digest: Blake3 },
}
```

**이것이 성립하는 이유가 1층 캐시의 성질에 이미 있다.** 캐시 키는 `(blob_hash, extractor_version)`이지 커밋이 아니다. 워킹트리 파일의 blob 해시를 직접 계산하면(`gix`가 인덱스에서 주거나 파일을 해시하면 된다) **캐시는 아무 변경 없이 그대로 적중한다.** 파싱 파이프라인은 커밋을 전혀 모른다.

귀결:
- `stale-projection` 표시가 "낡음"이 아니라 "워킹트리 좌표로 계산됨"이라는 **1급 상태**가 된다.
- 결박은 커밋 좌표에 걸리고, 워킹트리 질의는 "이 결박이 지금 편집 중인 코드 기준으로도 live인가"를 답한다 — 이것이 적시 제시의 실제 값이다.
- 브랜치 전환·stash에도 캐시가 그대로 적중한다.

**대응이 실패하면** — 워킹트리 머클 계산이 매 질의마다 비싸면(10⁵ 파일 stat), git 인덱스의 mtime/size 캐시를 신뢰하는 경로로 낮춘다(git 자신이 쓰는 방법).

**판정** — F01에서 타입으로 확정. 성능은 F05.

**→ 이 항목은 `DESIGN.md` §2.1 갱신을 요구한다.** [갱신 대장](README.md#설계-문서-갱신-필요-항목) 참조.

## R-07 {#r-07}
### 낡음 표시의 거짓 양성 · **치명**

**증상** — 포매팅 커밋 하나에 결박 300개가 `stale`로 켜진다. 사람이 표시를 무시하기 시작하면 그 순간 제품이 죽는다([목표 §5 G1](00-goals.md#5-성공실패의-판정-형태)).

**원인** — 결박 단위가 라인이면 공백 한 줄에 켜진다. 그래서 정규화된 `body_digest`를 쓰는데, 정규화가 불충분하면 같은 일이 일어난다.

**대응**
1. **`body_digest`는 구문 트리에서 주석·공백·포매팅을 제거한 정규형의 해시.** 변수명은 **스코프 해소가 가능한 언어에서만** 정규형에서 제거한다(못 하는 언어에서 제거하면 서로 다른 코드가 같은 digest를 갖는다).
2. **속성 기반 테스트로 상시 검사** — `proptest`로 무작위 포매팅 변형(들여쓰기·줄바꿈·주석 삽입·세미콜론)을 가해 digest 불변을 검사하고, 식별자 변경에는 digest가 **변하는지**도 검사한다(양방향).
3. **실측**: 코퍼스에서 "포매팅만 바꾼 커밋"을 골라 그 커밋이 켜는 `stale` 수를 센다. 0이 아니면 정규화 결함이다.
4. **`stale`이 켜졌을 때 무엇이 켰는지 함께 출력한다.** "본체가 변해서"와 "감시 집합의 호출자가 변해서"는 사람이 다르게 처리한다.

**대응이 실패하면** — 제품이 성립하지 않는다. 정규화를 더 공격적으로 하거나(의미 변화를 놓칠 위험이 커짐), 결박 단위를 더 크게(파일) 잡는다.

**판정** — F03(정규화 속성 검사) · F09(코퍼스 거짓 양성률).

## R-08 {#r-08}
### 파일 이동·리네임이 전 심볼 정체성을 끊는다 · **높음**

**증상** — 디렉터리 하나를 옮겼더니 그 안의 모든 결박이 `orphaned`가 된다. 대규모 리팩터링 후 의도층이 통째로 떨어져 나간다.

**원인** — `symbol_id = hash(repo_id, 정규화 경로, 컨테이너 체인, 이름, 판별자)`. 경로가 성분이다.

**대응**
1. **`orphaned`는 조용한 실패가 아니라 사람을 부르는 사건이다.** 그것이 설계의 의도다 — 정체성이 끊긴 것을 조용히 새 심볼로 만드는 것보다 낫다.
2. **재결박 제안**: `orphaned`가 발생하면 같은 `body_digest`를 가진 새 심볼을 찾아 "이것으로 옮길까요?"를 제안한다. digest가 같으면 내용이 같다는 뜻이므로 정확도가 높다. **자동 재결박은 하지 않는다**(승인 필요) — 자동으로 하면 의미가 다른 동일 코드에 잘못 붙는다.
3. **일괄 재결박**: 한 커밋에서 N개가 동시에 `orphaned`이고 전부 같은 경로 접두사 변경이면, 한 번의 승인으로 N개를 옮긴다.
4. `repo_id`는 경로도 원격 URL도 아닌 **매니페스트가 발급하는 안정 식별자**이고, 저장소 재배치는 별칭 테이블이 흡수한다.

**판정** — F03·F09. 코퍼스의 대규모 이동 커밋에서 재결박 제안의 정확도를 잰다.

## R-09 {#r-09}
### 서술물의 좌표 해소가 안 될 수 있다 · **높음**

**증상** — 기존 ADR·설계 문서를 인입했는데 대부분이 "어느 코드에 대한 것인지" 해소되지 않아 `pending`으로 쌓인다. 그러면 결박이 없고, 결박이 없으면 `touch`가 빈 답을 낸다 — **제품의 심장이 공회전한다.**

**원인** — 사람이 쓴 문서는 심볼을 정확히 안 가리킨다. "주문 취소 로직", "결제 모듈"처럼 쓴다.

**대응 — 해소 신호를 강한 것부터 계단식으로**

| 신호 | 강도 | 예 |
|---|---|---|
| 코드 블록 안의 경로·심볼명 | 강 | `` `src/order/cancel.ts` `` |
| 인라인 코드 스팬의 식별자가 심볼 인덱스에 유일하게 존재 | 강 | `` `OrderService.cancel` `` |
| 문서와 같은 커밋에서 변경된 파일 | 중 | git 이력에서 계산 |
| 문서 경로의 디렉터리 근접성 | 약 | `docs/order/` ↔ `src/order/` |
| 본문 자연어의 이름 유사도 | **쓰지 않는다** | 거짓 결박을 만든다 |

- **해소 실패는 실패로 남긴다.** `narrative.unbound` 질의가 미결박 서술물 목록을 내고, 그것이 사람이 손으로 붙일 작업 목록이 된다.
- **제안은 하되 확정하지 않는다** — 후보를 제시하고 승인으로 결박한다(`inferred` → 승인 → `asserted`).

**대응이 실패하면** — 해소율이 낮으면 [F12(계획-구현 결박)](features/F12-plan-binding.md)의 비중을 올린다. 계획 문서는 **쓰는 시점에 좌표를 요구할 수 있으므로** 소급 해소보다 정확도가 높다. 즉 과거 문서 인입이 실패해도 앞으로 쓰는 문서로는 성립한다.

**판정** — F10. 자기 저장소 + 코퍼스에서 해소율 측정.

## R-10 {#r-10}
### 사람의 승인 노동이 감당되지 않는다 · **치명**

**증상** — 가드/효과 라벨을 사람이 승인해야 감사(목표 4)가 서는데, 라벨 하나당 몇 분이 걸리면 아무도 안 한다. 라벨이 없으면 판정이 전부 `Residual`이고 산출이 무의미해진다.

**원인** — 이 설계에는 사람의 노동을 요구하는 뿌리가 셋이고 **곱해진다** — ① 라벨 승인 ② 규칙 팩 저작 ③ (온톨로지를 붙인다면) 개념 저작. 각각 절반씩만 일어나면 남는 것은 8분의 1이다.

**대응**
1. **코드 이전에 손으로 잰다** — [P0-preflight](features/P0-preflight.md). 실제 코퍼스에서 라벨 30건을 손으로 승인하고 건당 시간과 재질문 발생률을 측정한다. 이것이 이 프로젝트의 첫 작업인 이유다.
2. **단가를 내리는 장치 넷을 분리 측정** — 이미 지불되는 승인에 올라타기 / 일괄 승인 / 진척 가시화 / 거부도 기록(재질문 제거가 절감의 대부분).
3. **규칙 파생**: 라벨 300개를 규칙 한 줄이 파생시키면 재승인도 한 번이다. 규칙 좌표에 결박되므로 규칙이 바뀌면 파생 전부가 `stale`이 된다.

**대응이 실패하면** — **감사(목표 4)를 산출 목록에서 내린다.** 큐레이션·컨설팅만 남긴다. 그것으로도 제품이다. 이 판정을 코드 이전에 하는 것이 P0-preflight의 존재 이유다.

**판정** — P0-preflight, 코드 0줄 시점.

## R-11 {#r-11}
### 응답이 에이전트 컨텍스트를 잡아먹는다 · **높음**

**증상** — `touch` 응답에 `Envelope`(대장·커버리지·절단 기록)가 매번 붙는다. 정직하지만, 에이전트 컨텍스트는 유한하고 길수록 성능이 떨어진다. 지식 베이스를 아무리 잘 만들어도 통째로 밀어 넣으면 쓸모를 잃는다.

**원인** — 첨부 필수라는 계약과 컨텍스트 예산이 정면으로 부딪힌다.

**대응**
1. **`Envelope`의 표현을 두 겹으로.** 기본은 **요약 한 줄**(`"parsed 1180/1204 · unresolved 2 · L0언어 1"`)이고, 전체 대장은 별도 질의(`ledger.snapshot`)로 뺀다. 첨부 필수는 지키되 부피를 옮긴다.
2. **응답 예산을 표면 계약에 넣는다.** MCP 툴 응답에 노드 상한(기본 500)·토큰 추정치를 걸고, 초과분은 `elision`에 건수와 사유로 남긴다. 잘렸다는 사실은 항상 보인다.
3. **점진 회상**: `touch`는 요약을 주고 상세는 후속 질의로. 한 번에 전부 싣지 않는다.

**판정** — F06. 실제 MCP 세션에서 응답 토큰을 잰다.

## R-12 {#r-12}
### 캐시·인덱스가 디스크를 잡아먹는다 · **중간**

**증상** — 10⁵ 파일 × 여러 커밋의 부분 그래프가 쌓여 `.palimpsest/`가 수 GB가 된다. 설치 비용이 1급 제약인데 정면으로 위반한다.

**원인** — 콘텐츠 주소 캐시는 지우지 않으면 단조 증가한다. `observed` 관측·`UnresolvedRef`·`Residual`도 지우지 않기로 설계되어 있다.

**대응**
1. **1층 값은 zstd 압축.** 부분 그래프는 반복이 많아 압축률이 높다.
2. **LRU 축출** — 1층은 순수 캐시이므로 지워도 정확성에 영향이 없다(재파싱될 뿐). 기본 상한을 두고(예: 2GB) 접근 시각 기준으로 축출.
3. **단조 증가하는 셋에는 보존 정책** — `observed`는 좌표별 최근 M=10개 + 환경 지문별 최소 1개. **접는 것과 지우는 것을 구별한다**(접힌 것은 "여기 관측이 있었다"를 여전히 말한다).
4. **실측을 먼저**: 10⁵ 파일 TypeScript 저장소에서 1층 크기를 재고, 파일당 바이트가 목표(< 2KB 압축 후)를 넘으면 부분 그래프 스키마를 줄인다.

**판정** — F04.

## R-13 {#r-13}
### 데이터플로우(효과 집합)가 가장 비싼 미지다 · **높음**

**증상** — "이 심볼이 무엇을 쓰는가"(`writes`)를 계산하려면 정의-사용(L3) 층이 필요하다. 빌드 없는 환경에서 이것이 얼마나 정확할지 아무도 모른다.

**원인 — 선례가 경고한다.** 같은 기반(tree-sitter) 위에서 이름 해소를 프로덕션 규모로 돌린 stack-graphs조차 **데이터플로우는 미해결로 남겼다.**

**대응**
1. **경로 곱이 아니라 합집합으로 계산한다.** "진입점에서 이 지점까지의 모든 경로"는 후보 폭발에 지수적이지만, "이 심볼이 도달 가능한 쓰기의 합집합"은 도달 가능 집합의 크기에 선형이다. 판정 술어를 `writes(P1) ⊋ writes(P2)`(포함 관계)로 잡은 것이 이 성질을 쓰기 위해서다.
2. **필드 단위가 아니라 선언된 효과 어휘로 시작한다.** 임의 표현식의 별칭 분석(alias analysis)을 하지 않는다. `state.x = ...`, ORM 호출, HTTP/큐 발신 같은 **인식 가능한 형태**만 효과로 세고, 나머지는 `UnresolvedRef`로 환원한다.
3. **판정 기준을 먼저 정한다** — 코퍼스의 실제 과거 결함 하나를 이 술어로 재현 검출할 수 있는가. 못 하면 이 능력을 내린다.

**대응이 실패하면** — 효과 집합을 독립 능력에서 내리고, 감사의 전제층으로만 둔다. 되돌리는 비용은 문서 한 행이다(번호를 옮기지 않았으므로).

**판정** — F13.

## R-14 {#r-14}
### 멀티레포 스티칭에 선례가 없다 · **중간**

**증상** — `Snapshot = {(repo_id, commit_sha)}`이고 저장소 경계를 넘는 엣지를 세워야 하는데, 두 저장소의 "지금"이 언제인지, 한쪽만 갱신되면 어떻게 되는지가 미정이다.

**원인** — stack-graphs도 단일 커밋 분석에 초점이고 크로스 저장소를 다루지 않는다. 선례가 비워둔 칸.

**대응**
1. **경계 엣지는 이름 일치로 세우지 않는다.** 계약 아티팩트(OpenAPI·protobuf·GraphQL SDL) 증거가 있어야 하고, 증거가 없으면 `unresolved-boundary`로 대장에 남는다.
2. **`Snapshot`의 부분 갱신을 1급으로.** 저장소 A는 최신이고 B는 3일 전이면 그 사실이 `Envelope`에 실린다. 동기화를 강요하지 않는다.
3. **P0/P1에서는 단일 저장소만 다룬다.** 타입은 처음부터 집합(`Snapshot`)으로 두되, 원소가 1개인 경우만 구현한다. 확장 시 타입이 안 바뀌는 것이 핵심.

**판정** — F14.

## R-15 {#r-15}
### `gix` API가 진화 중이다 · **중간**

**증상** — 버전을 올렸더니 컴파일이 깨진다. gitoxide는 활발히 개발되고 있고 여러 크레이트가 아직 1.0 이전이다.

**대응** — **`pal-git` 크레이트로 격리하고 접촉면을 좁게 유지한다.** 실제로 필요한 것은 다섯뿐이다.

```rust
pub trait GitAccess {
    fn head(&self) -> Result<CommitSha>;
    fn list_tree(&self, at: &TreeRef) -> Result<Vec<(PathBuf, BlobHash)>>;
    fn read_blob(&self, h: BlobHash) -> Result<Vec<u8>>;
    fn worktree_digest(&self) -> Result<(CommitSha, Blake3)>;   // R-06
    fn changed_between(&self, a: &TreeRef, b: &TreeRef) -> Result<Vec<PathBuf>>;
}
```

이 다섯 뒤에서 gix가 깨지면 고칠 곳이 한 파일이고, 최악의 경우 `git` CLI 호출로 대체할 수도 있다(정적 바이너리 목표를 잃지만 살아는 있다).

**판정** — F01.

## R-16 {#r-16}
### L1 언어에서 오버로드 재정렬이 조용한 재결박을 만든다 · **중간**

**증상** — L1(스코프 해소 불가) 언어에서는 오버로드 판별자가 "파라미터 개수 + 선언 순서"다. 같은 파라미터 개수의 오버로드 둘이 순서를 바꾸면 정체성이 끊기는 게 아니라 **각 좌표가 상대 심볼을 가리킨다.** `stale`은 켜지지만 그 뜻이 "결박한 코드가 변했다"가 아니라 "이제 다른 함수를 가리킨다"이고, 산출에서 둘이 구별되지 않는다. 사람은 재확인하러 가서 엉뚱한 함수를 읽는다.

**원인** — 거짓 `orphaned`는 관측 가능하지만 이것은 평범한 낡음으로 위장한다.

**대응** — L1에서 컨테이너 내 오버로드 집합의 **집합 digest**를 함께 감시해 순서 변경을 별도 사건으로 띄운다. **다만 스키마로 먼저 고정하지 않는다** — L1 언어에서 오버로드 재정렬이 실제로 얼마나 일어나는지 아무도 세어본 적이 없다. F03에서 코퍼스로 세고, 유의미하면 넣는다.

**판정** — F03의 측정 항목.

## R-17 {#r-17}
### 1인 개발 대역폭 · **높음**

**증상** — 기능 20개 중 규모 L 이상이 열둘이다. 게이트는 능력을 검사하지 **속도를 검사하지 않는다.** 속도로 무너지면 게이트는 아무것도 말해주지 않는다.

**대응**
1. **우선순위를 P0~P3으로 굳히고 P0+P1(12개)에서 멈출 수 있게 설계한다.** 목표 §2의 1·2번 산출만으로 제품이 성립한다고 미리 정의해 둔 것이 이 대응이다.
2. **각 기능 문서에 "여기서 멈춰도 되는가"를 적는다.**
3. **일정을 두지 않는다.** 절대 시간을 적으면 그것이 곧 게이트를 우회할 압력이 된다. 상대 규모(S/M/L/XL)만 붙인다.

**판정** — F11(적시 제시)에 도달하는 시점에 실측하고 그때 범위를 재조정한다.

## R-18 {#r-18}
### 게이트를 스스로 판정한다 · **구조적·영구**

성공 기준을 등록하는 사람과 판정하는 사람이 같다. 이 설계는 다른 곳에서 "생산자와 검증자의 분리"를 요구하는데, **이 계획 자신에게는 그것을 적용할 수단이 없다.**

**완화** — ① 성공 기준을 **코드 이전에** `corpus/criteria.toml`로 커밋한다(커밋 해시가 등록 증거) ② 판정 기록을 `docs/gates/`에 남기고 통과·반증·**대조 불가** 셋 중 하나를 명시한다 ③ 생략하고 다음으로 가는 것이 가장 조용한 실패 경로임을 여기 적어 둔다.

**닫히지 않는다.** 영구 잔여로 기록한다.

## R-19 {#r-19}
### 자기 저장소 자기적용은 편향된 표본이다 · **영구**

첫 실사용을 이 저장소 자신으로 하는데(문서를 코드 좌표에 걸기), palimpsest 저장소는 문서 대 코드 비율이 극단적이라 서술물 인입의 성적이 실제 프로젝트와 다를 것이 거의 확실하다. **편의 표본임을 게이트 기록에 명시한다.** 자기적용은 개발용 피드백 루프이지 증거가 아니다.
