# palimpsest 개요 — 처음 보는 사람을 위한 안내

> 이 문서는 **이 저장소를 처음 여는 사람**을 위한 것이다. 사전 지식을 전제하지 않는다.
>
> 이 문서는 **소개**이고 결정의 정본이 아니다. 결정은 [`docs/adr/`](adr/), 목표는
> [`docs/plan/00-goals.md`](plan/00-goals.md), 스택은
> [`docs/plan/00-stack.md`](plan/00-stack.md), 회차 절차는 `/round` 스킬이 정한다.
> 여기 적힌 것과 저기 적힌 것이 다르면 **저쪽이 맞다.**

---

## 0. 읽기 전에 — 이 문서에 나오는 기술 용어

본문에 라이브러리와 도구 이름이 몇 개 나온다. 여기서 한 번에 정리한다.

| 용어 | 무엇인가 |
|---|---|
| **Rust** | 이 프로젝트를 구현한 프로그래밍 언어. 컴파일 시점에 타입을 엄격하게 검사하는 것이 특징이고, 이 저장소는 그 성질을 설계의 도구로 쓴다 |
| **crate(크레이트)** | Rust의 코드 묶음 단위. 다른 언어의 모듈·패키지·라이브러리에 해당한다. 하나의 프로그램은 여러 크레이트를 조합해 만든다 |
| **워크스페이스(workspace)** | 여러 크레이트를 한 저장소에서 함께 빌드하는 Rust의 구성 방식. 크레이트끼리 누가 누구를 참조할 수 있는지가 여기서 정해진다 |
| **CLI** | 명령줄 프로그램(Command Line Interface). 터미널에 `pal ...`이라고 입력해 실행하는 형태를 말한다 |
| **`gix`** | Rust로 작성된 Git 라이브러리(gitoxide 프로젝트). Git 명령을 별도로 설치하지 않고도 커밋·파일 트리·파일 내용을 직접 읽는다. 이 프로젝트는 `git` 실행 파일을 호출하지 않고 이것을 쓴다 |
| **`redb`** | Rust로 작성된 내장형 키-값 데이터베이스. 서버 없이 파일 하나로 동작한다. SQLite와 비슷한 위치이고, 이 프로젝트에서는 색인과 의도 저장소를 담는다 |
| **`tree-sitter`** | 소스 코드를 구문 트리로 바꾸는 파서 라이브러리. 컴파일이나 빌드 없이 파일 내용만으로 파싱하고, 문법 오류가 있어도 나머지 부분을 계속 읽어 나가는 성질이 있다 |
| **`xtask`** | Rust 생태계에서 널리 쓰이는 관행. 프로젝트 전용 검사·빌드 스크립트를 **Rust 코드로 작성해** `cargo xtask <이름>`으로 실행하는 방식이다. 셸 스크립트 대신 쓰면 운영체제마다 다르게 동작할 위험이 줄어든다. 이 저장소의 자체 CI 검사가 전부 여기에 있다 |
| **CI** | 지속적 통합(Continuous Integration). 코드를 올릴 때마다 자동으로 빌드와 검사를 실행하는 장치. 이 저장소는 GitHub Actions를 쓴다 |

## 1. 한 문장으로

**코드에서 사실을 뽑아 그래프로 만들고, 사람이 쓴 결정·설계·계획을 그 코드 위치에 연결해,
누군가 그 코드를 고치려는 순간에 "여기에 무엇이 걸려 있고 그중 무엇이 낡았는지"를 알려 주는
도구.**

`palimpsest`는 양피지를 긁어내고 그 위에 다시 쓴 문서를 가리키는 말이다. 지워진 옛 글씨가
아래에 남아 비쳐 보이는 그 상태가 이 프로젝트가 다루는 대상이다 — 코드에는 지금의 모습만
남지만, 그렇게 된 이유와 그때의 판단은 아래에 깔려 보이지 않는다.

## 2. 어떤 문제를 푸는가

### 2.1 상황

어떤 팀이 2년 전에 이런 결정을 내렸다고 하자.

> "주문 취소는 **여러 번 호출돼도 결과가 같아야 한다**. 결제 취소가 두 번 일어나면 안 되니까."

이 결정은 회의록에, 위키에, ADR 문서에, 슬랙 스레드에 적힌다. 그리고 코드는 `OrderService.cancel()`
안에 구현된다.

1년 뒤 신입 개발자가 `OrderService.cancel()`을 고친다. 그는 그 결정을 모른다.
문서를 찾아보려 해도 **어느 문서가 이 함수에 관한 것인지 알 방법이 없다.** 문서는 함수
이름을 적어 두지 않았고, 적어 뒀더라도 그 사이에 함수 이름이 바뀌었을 수 있다.

그래서 세 가지가 일어난다.

| 무엇 | 왜 |
|---|---|
| **같은 버그가 다시 난다** | 예전에 왜 그렇게 고쳤는지 아무도 모른다 |
| **고치면 엉뚱한 데가 깨진다** | 무엇이 이 코드에 의존하는지 안 보인다 |
| **문서가 조용히 거짓말을 한다** | 코드는 바뀌었는데 문서는 그대로다. 낡았다는 표시가 없다 |

세 번째가 가장 심각하다. **낡은 문서는 없는 문서보다 위험하다** — 없으면 사람이 코드를 읽지만,
낡은 문서가 있으면 사람이 그것을 믿는다.

### 2.2 그래서 무엇을 하나

두 가지를 한다.

**첫째, 코드를 읽어서 "무엇이 어디에 있고 무엇이 무엇을 부르는지"를 기계가 다룰 수 있는
형태로 만든다.** 이것을 **그래프**라고 부른다 — 점(함수·클래스·파일)과 선(호출·참조)의 모음이다.

**둘째, 사람이 쓴 글을 그 그래프의 점에 연결해 둔다.** "이 결정은 `OrderService.cancel`에
관한 것이다"를 기계가 다룰 수 있는 형태로 기록한다. 이 연결하는 행위를 이 프로젝트는
**결박(binding)** 이라고 부른다.

그러면 세 번째 문제가 기계적으로 풀린다. `OrderService.cancel`의 코드가 바뀌면, 거기 연결돼
있던 결정에 **`stale`(낡음) 표시**가 자동으로 붙는다. 사람이 문서를 갱신하도록 강제할 수는
없지만, **낡았다는 사실을 알려 주는 것은 기계가 할 수 있다.**

### 2.3 그러면 무엇이 달라지나

이 프로젝트가 스스로 정한 채점 기준이 있다([`00-goals.md §0.1`](plan/00-goals.md)):

> **역사·결정을 알게 하는 것은 목적이 아니라 수단이다. 상위 가치는 그 결과로 더 나은 코드가
> 나오는 것이다.**

즉 "산출이 정확하다"는 합격 사유가 아니다. **그 산출을 본 뒤의 코드가 실제로 달라져야** 한다.
재발이 줄고, 고칠 때 엉뚱한 데가 안 깨져야 한다.

## 3. 다 만들면 어떻게 쓰이나

에이전트(또는 사람)가 `OrderService.cancel()`을 고치려 한다. 손대기 **전에** 이 화면이 뜬다.
([`00-goals.md §1`](plan/00-goals.md)에서 가져왔다. 아직 전부 만들어지지 않았다.)

```
$ pal touch order-svc:OrderService.cancel

■ 이 좌표에 걸린 것 (3)
  ADR-0042  취소는 멱등해야 한다              live      symbol 반경
  ADR-0031  정산 경계 밖으로 나가지 않는다     stale     ← 감시 집합 중 SettlementGate.check 가 12커밋 전 변경
  PLAN §4-2 재고 복원은 이번 범위 아님         pending   ← 예상 좌표에 아직 코드가 없음

■ 이 심볼이 하는 것
  writes  order.status · inventory.reserved · outbox.event
  호출자  7  (exact 5 · scoped 0 · candidate 2)

■ 여기서 났던 일 (2)
  Defect  #218  중복 취소로 재고가 두 번 복원됨      도입 4a91f2 → 해소 c7d033

■ 내가 모르는 것 (2)
  UnresolvedRef  PaymentGateway.refund   사유=동적 디스패치   at cancel.ts:88

■ 판정
  Residual  2  (사유=미해소 참조 경유 — 위 두 건이 해소되면 재판정)
  ※ "이상 없음"이라고 말하지 않습니다. 위 2건은 보지 않은 것입니다.
```

읽는 법:

- **`live`** — 이 결정이 걸린 코드는 결박한 이후로 안 변했다.
- **`stale`** — 변했다. 그러니 이 결정이 아직 유효한지 **사람이 확인해야 한다.**
- **`pending`** — 문서가 가리키는 코드가 **아직 존재하지 않는다.** 계획이 구현을 앞선 자리다
  (§6.3의 「계획 결박」).
- **`내가 모르는 것`** — 기계가 못 푼 참조를 숨기지 않고 보여 준다.
- **`판정`에 "이상 없음"이 없다** — 못 본 것을 "괜찮다"로 바꾸지 않는다.

마지막 두 줄이 이 프로젝트의 성격을 가장 잘 보여 준다. **모르는 것을 안다고 말하지 않는다.**

> ⚠ 화면의 `live`·`stale` 같은 영어 표기는 **바뀔 예정이다.** 상태 이름은 코드에서는 영어로
> 두되 사용자 화면에서는 사용자 언어를 함께 표기하기로 정했고(§8 머리말), 특히 `live`는
> 한국어권에서 "방송 중"으로 읽히는 문제가 있다. 개명 범위는 [#108](https://github.com/hskim-ecoletree/palimpsest/issues/108) 과
> [#110](https://github.com/hskim-ecoletree/palimpsest/issues/110) 이 다룬다.

## 4. 왜 기존 도구로는 안 되나

| 기존 도구 | 왜 부족한가 |
|---|---|
| `grep` · 코드 검색 | 문자열을 맞힐 뿐 관계를 모른다. 이름이 안 걸리면 없는 것이 된다 |
| 위키 · ADR 문서 | 코드와 연결이 없다. 낡아도 낡았다는 표시가 없다 |
| 코드 그래프 도구 (LSP, SCIP 등) | 관계는 알지만 **사람의 결정을 담지 않는다.** 그리고 대개 빌드를 요구한다 |
| 정적 분석기 (SAST, 린터) | 규칙 위반은 잡지만 "이 팀이 왜 이렇게 정했는지"는 모른다 |

이 프로젝트가 다른 지점 넷([`00-goals.md §3`](plan/00-goals.md)):

1. **모르는 것을 안다고 하지 않는다** — 못 푼 참조가 1급 데이터로 남는다.
2. **`clean`(이상 없음)을 출력하지 않는다** — 판정 결과에 그런 값이 아예 없다.
3. **낡음이 표시된 상태다** — 그것도 줄 번호가 아니라 **의미 단위**로. 코드 서식만 바꿔서는
   낡음 표시가 붙지 않는다.
4. **대상 프로젝트를 빌드하지 않는다** — 남의 프로젝트의 툴체인·비밀키·환경변수를 가질 수
   없고, 3년 전 커밋이 지금 빌드된다는 보장도 없다.

## 5. 전체 구조

### 5.1 두 층으로 되어 있다

```
┌─────────────────────────────────────────────────────────┐
│  하네스 (harness)   — 에이전트가 일하는 절차              │
│  · 회차를 어떻게 도는가 (스킬)                            │
│  · 역할·경계 (에이전트 정의)                              │
│  · 우회하면 피해가 큰 경계 (훅)                            │
└─────────────────────────────────────────────────────────┘
                        ↕  그래프에 묻고, 결정을 결박한다
┌─────────────────────────────────────────────────────────┐
│  코어 (core)        — `pal` 이라는 CLI 실행 파일 하나      │
│  · 코드를 읽어 그래프를 만든다                             │
│  · 사람의 글을 좌표에 결박한다                             │
│  · 물으면 봉투(Envelope)에 담아 답한다                     │
└─────────────────────────────────────────────────────────┘
```

**코어는 대화하지 않는다.** JSON을 받고 JSON을 반환한다. 스크립트에서도 CI에서도 그대로 동작한다.

**하네스는 Claude Code 전용이다.** 원래는 어느 도구에서든 쓸 수 있게 만들려 했는데,
2026-08-18에 방침을 뒤집었다([ADR-0025](adr/0025-the-harness-that-reads-the-graph-is-the-same-product.md)).
이유는 표현력이다 — 하네스의 본체는 **절차**인데, MCP 같은 프로토콜은 개별 도구만 제공할 수
있고 스킬은 절차를 제공할 수 있다. 다만 **코어는 하네스와 무관하게 단독으로 동작한다**
(`crates/pal-cli/tests/host_free.rs`가 그것을 검사한다).

### 5.2 데이터는 세 곳에 나뉘어 있다

이 구분이 이 설계에서 가장 중요한 것 하나다.

```
git (코드의 진실)                     사람의 승인 (의도의 진실)
   │                                          │
   ▼                                          ▼
┌─ 1층 · 추출 캐시 ──────────┐       ┌─ 의도 저장소 ────────────┐
│ 파일 하나 → 파싱한 결과     │       │ 결박 · 승인/거부 이력     │
│ 지워도 됨 (다시 파싱)       │       │ 지우면 **영영 잃는다**    │
└────────────────────────────┘       └──────────────────────────┘
   │                                          │ 읽기만
   ▼                                          ▼
┌─ 2층 · 질의 투영 ───────────────────────────────────────────┐
│ 심볼 색인 · 인접 리스트 · 역방향 색인                          │
│ 통째로 지워도 1층 + 의도 저장소에서 다시 만들어진다             │
└─────────────────────────────────────────────────────────────┘
```

왜 이렇게 나누나:

- **1층이 있으면 "3년 전 커밋을 여는 비용"이 바뀐 파일 수에 비례한다.** 캐시 열쇠에 커밋이
  들어가지 않기 때문이다 — 열쇠는 `(파일 내용 해시, 추출기 버전, 경로, 언어, 능력 축)`이다.
  브랜치를 바꿔도 내용이 같은 파일은 이미 캐시에 있다.
- **의도 저장소를 따로 두지 않으면 "캐시를 지우고 다시 만든다"가 사람의 승인 노동을 지우는
  명령이 된다.** 그래서 이 크레이트에는 **지우는 API가 아예 없고**, 그 사실을 CI가 검사한다.
- **의도의 정본은 `.palimpsest/intent/*.jsonl` 텍스트 파일이고 git에 커밋된다.** 그래서
  `git clone` 만으로 복원되고, 팀에 공유되고, 결박이 코드 변경과 같은 리뷰를 받는다.

### 5.3 크레이트 구성

Rust 워크스페이스이고 크레이트가 7개다.

| 크레이트 | 하는 일 | 의존 |
|---|---|---|
| `pal-core` | 도메인 타입·불변식·판정. **이 프로젝트의 어휘가 전부 여기에 정의된다** | 워크스페이스 내부 의존 **0** |
| `pal-git` | git 접근. `gix` 크레이트를 이 안에만 가둔다 | `pal-core` |
| `pal-extract` | tree-sitter로 소스를 파싱해 심볼을 뽑는다 | `pal-core` |
| `pal-store` | 1층 캐시 + 2층 투영. **지우는 API를 가진 유일한 크레이트** | `pal-core` |
| `pal-intent` | 의도 저장소. **지우는 API가 없다** | `pal-core` |
| `pal-query` | 이름 붙은 질의 실행. 예산 초과 시 생략 처리와 봉투 조립 | `pal-core`, `pal-store` |
| `pal-cli` | `pal` 실행 파일. 사람이 보는 화면과 설치·훅·회차 | 위 전부 |

의존 방향은 **CI가 기계로 검사한다**(`xtask/src/main.rs`의 검사 1):

- `pal-core`는 워크스페이스의 **어떤** 크레이트에도 의존하지 않는다 — 도메인이 저장 기술을
  내부화하는 것을 막는다.
- `pal-core`는 `tree-sitter`·`redb`·`gix`에 의존하지 않는다 — 파서와 저장 기술이 좌표계에
  새어 드는 것을 막는다.
- `pal-store`는 `pal-intent`에 쓰기 의존하지 않는다 — 캐시 폐기 경로가 사람의 노동에 닿는
  것을 막는다.

적는다.

### 6.1 좌표 — "같은 심볼인가"와 "변했는가"를 가른다

#### 개념

문서를 코드에 연결하려면 코드의 한 지점을 가리키는 **주소**가 필요하다. 줄 번호는 안 된다 —
위에 한 줄만 추가돼도 전부 밀린다.

그래서 값을 **둘** 계산한다.

| 값 | 묻는 것 | 바뀌면 |
|---|---|---|
| `symbol_id` | **같은 심볼인가** | 정체성이 끊긴다 (`orphaned`) |
| `body_digest` | **내용이 변했는가** | 결박이 `stale`이 된다 |

이 둘을 나눈 것이 핵심이다.

- 파일을 옮기면 `symbol_id`는 바뀌지만 `body_digest`는 그대로다 → **"이 함수가 여기로
  옮겨 온 것 같다"는 재결박 제안이 가능하다.**
- 코드 서식만 바꾸면 `body_digest`가 그대로다 → **서식 정리 커밋에는 낡음 표시가 붙지 않는다.**

하나로 합치면 둘 중 하나를 잃는다.

`symbol_id`의 재료는 `(저장소, 파일 경로, 컨테이너 체인, 이름, 구분자)`다. **컨테이너 체인**은
`파일 → 클래스 → 중첩 클래스` 같은 포함 관계다. 이것이 없으면 같은 파일의
`class A { m() {} }`와 `class B { m() {} }`가 선언 순서로만 구별되고, 순서를 바꾸는 것만으로
정체성이 서로 뒤바뀐다.

#### 코드

`crates/pal-core/src/coord.rs`

```rust
pub enum SymbolIdentity {
    Exact(SymbolId),      // 스코프 해소로 유일하다
    Ordinal(SymbolId),    // 선언 순서에 의존한다 — 조금 덜 믿을 만하다
    Unavailable,          // 좌표가 성립하지 않는다 (텍스트만 읽은 언어)
}
```

**여기서 "타입으로 강제한다"가 무슨 뜻인지 볼 수 있다.** `Unavailable` 변형에는 값을 담을
자리가 없다. 그래서 거기서 `SymbolId`를 **꺼낼 수 없다.** 결박을 만드는 `Binding::new`는
`SymbolId`를 요구하므로, **좌표가 없는 심볼에 결박을 거는 코드는 컴파일 자체가 안 된다.**

문서에 "이러면 안 된다"고 적는 대신 언어가 막는다. 이 방식이 이 저장소 전체에 적용돼 있고,
Rust를 고른 첫 번째 이유이기도 하다.

### 6.2 관측 원장 — "무엇을 보았고 무엇을 보지 않았는가"

#### 왜 필요한가

코드 분석 도구가 "이 저장소에 위반이 3건 있습니다"라고 말할 때, 사용자는 두 가지를 알 수 없다.

1. 이 도구가 저장소의 **모든 파일**을 봤는가, 아니면 읽을 수 있는 것만 봤는가?
2. 못 읽은 파일에는 위반이 **없는가**, 아니면 **못 본 것인가**?

"전부 검사했다"는 주장은 그 자체로는 검사할 방법이 없다. 그래서 이 프로젝트는 주장의 형태를
바꾼다.

> 기계는 **선언한 범위 안에서만** 관측하고 그 범위 안에서 빠짐없이 보았음을 보증한다.
> 범위 밖에 대해서는 "없다"가 아니라 **"보지 않았다"** 라고 사실대로 산출한다.

이 선언을 담은 것이 **관측 원장(ledger)** 이다. 모든 답에 함께 붙는다.

> ⚠ 회차 쪽에도 "원장"이 있는데 **다른 것이다.** 여기 원장은 *"어느 파일을 어떻게 읽었나"* 의
> 기록이고, 회차 원장(§6.9)은 *"완수 조건을 어떤 명령으로 검증했나"* 의 증거 기록이다.
> 영어로는 둘 다 `ledger`라 혼동하기 쉽다.

#### 무엇에 상태를 붙이나 — 저장소의 파일 하나하나

`pal ledger`를 실행하면 이 프로젝트는 **git HEAD 트리에 있는 파일 전부**를 대상으로 삼는다.
그리고 파일마다 상태를 하나씩 붙인다. 상태가 성공/건너뜀/실패 3값이 아니라 **7종**인 것이
위 태도의 실물이다.

| 상태 | 언제 이 값이 되나 | 사용자가 할 일 |
|---|---|---|
| `Parsed` | 언어를 알아봤고 파서가 파일 전체를 읽었다 | 없음 |
| `Partial` | 파싱은 했는데 일부 구문에서 오류 회복이 일어났다 | 그 파일의 심볼 일부가 빠졌을 수 있다 |
| `Unsupported` | 언어는 알아봤는데 **이 빌드에 그 언어 추출기가 없다** (사유 포함) | 로드맵을 확인한다 |
| `Unrecognized` | 확장자로도 내용으로도 **무슨 언어인지 판단하지 못했다** | **설정을 고친다** |
| `Excluded` | 설정으로 제외했다 (어느 규칙이 제외했는지 ID 필수) | 의도한 제외인지 확인 |
| `Binary` | 텍스트가 아니다 (이미지·압축 파일 등) | 없음 |
| `Generated` | 생성된 파일이다 (그렇게 판단한 증거 둘과 함께) | 없음 |

**파싱(parsing)** 은 소스 코드 텍스트를 프로그램이 다룰 수 있는 구조(구문 트리)로 바꾸는
작업이다. **오류 회복(error recovery)** 은 파서가 문법에 안 맞는 부분을 만나도 거기서
멈추지 않고 나머지를 계속 읽는 성질을 말한다 — tree-sitter가 가진 이 성질 덕분에
"반쯤 읽었다"(`Partial`)를 정직하게 표현할 수 있다.

`Unrecognized`와 `Unsupported`를 하나로 뭉개면 원장이 거짓말을 하게 된다. 전자는 **설정
문제**이고 후자는 **로드맵 문제**인데, 뭉개면 사용자가 고칠 자리를 엉뚱한 데서 찾는다.

#### 언어마다 읽어 낼 수 있는 깊이가 다르다

같은 "파싱 성공"이라도 언어별로 뽑아낼 수 있는 정보의 깊이가 다르다. 그래서 **능력 등급**을
따로 기록한다.

| 등급 | 무엇까지 알아내나 |
|---|---|
| `L0` | 텍스트로만 읽었다. 심볼을 구분하지 못한다 |
| `L1` | 구조를 안다 — 어디에 어떤 함수·클래스가 있는지 |
| `L2` | 참조를 스코프까지 해소한다 — 이 호출이 어느 정의를 가리키는지 |
| `L3` | 읽기/쓰기 집합을 안다 — 이 함수가 어떤 상태를 건드리는지 |
| `L4` | 제어 흐름을 안다 |

여기서 중요한 것은 **이 등급이 도구 전체에 하나로 정해지지 않고 언어마다 따로 기록된다**는
사실이다. Kotlin은 `L2`인데 JavaScript는 `L1`이라면, 그 차이가 답에 데이터로 실려 나간다.
"이 도구는 최소한 여기까지는 보장한다"는 **최소 보장 수준**이 언어마다 다르다는 뜻이다.

#### 코드

- `crates/pal-core/src/ledger.rs` — `FileState` 7값, `ExtractGrade` L0~L4, `IdentityGrade`
- `crates/pal-cli/src/ledger.rs` — `pal ledger` 화면
- `crates/pal-extract/src/recognize.rs` — 확장자 → 언어 인식

#### 흐름

```
pal ledger
  → pal-git 이 HEAD 트리의 파일 목록을 가져온다
  → 파일마다 언어를 인식한다 (recognize)
  → 인식된 언어에 추출기가 있으면 파싱하고, 없으면 Unsupported 로 기록한다
  → 파싱 결과를 1층 캐시에 저장한다 (열쇠에 커밋이 들어가지 않는다)
  → 7종의 상태로 집계해 관측 원장을 만든다
```

### 6.3 결박 — 이 프로젝트의 심장

#### 개념

**결박(binding)** 은 "사람이 쓴 글 한 조각"과 "코드 좌표 하나"를 연결한 기록이다.

```
결박 = { 무엇이(subject) · 내용(note) · 어디에(target) · 언제(bound_at)
        · 무엇까지 지켜보나(radius) · 감시 집합(watch) · 어떻게 만들어졌나(promoted_by) }
```

여기서 **반경(radius)** 이 흥미롭다. 이런 문제가 있다.

> `OrderService.cancel`에 걸린 결정이 있다. `cancel` 자체는 안 변했는데, 그것을 호출하는
> `checkout`이 변해서 결정이 무효가 됐다. 기계는 이것을 알 수 있나?

**원리적으로 알 수 없다.** "이 결정과 관련 있는 코드 전부"를 자동으로 판별하는 것은 결정
불가능한 문제다. 그래서 이 프로젝트는 **문제를 자동으로 해결하려 하지 않고, 사용자가
범위를 선언하게 한다.**

| 반경 | 무엇까지 지켜보나 | 판정 비용 |
|---|---|---|
| `symbol` (기본) | 대상 심볼 하나 | 상수 |
| `callers` | + 그 심볼을 직접 호출하는 것들 | 인접 조회 1회 |
| `closure:k` | + k단계까지 거슬러 올라간 호출자 전체 | 그 집합의 크기에 비례 |
| `files:a,b` | + 지정한 파일에 있는 심볼 전부 | 나열한 길이 |

`closure`는 수학의 **전이적 폐쇄(transitive closure)** 에서 온 말이다. `closure:2`는
"나를 부르는 것, 그리고 그것을 부르는 것"까지를 뜻한다.

**그래서 위 질문의 답은 이렇다.** 반경을 `symbol`로 선언했다면 기계는 `checkout`의 변경을
**알지 못하고**, 그 결박은 `live`로 남는다. 반경을 `callers`로 선언했다면 `checkout`이
감시 집합에 들어가므로 그것이 변한 순간 결박이 `stale`이 된다. **기계가 알 수 있는 범위는
사용자가 선언한 만큼이고, 그 선언이 판정 결과에 함께 출력된다.**

> "이 결정은 `symbol` 반경에서 `live` 다"

이 문장은 "이 결정은 유효하다"와 **다른 문장**이다. 앞의 문장은 무엇을 안 봤는지까지
말하고 있다. 그 차이가 화면에 남는 것이 이 설계의 요구다. 선언은 문제를 해결하지 않지만
**문제를 숨기지도 않는다.**

#### 상태는 몇 개인가 — 축이 둘이고, 계획 결박은 별개다

먼저 **코드 신선도**다. `crates/pal-core/src/binding.rs`의 `CodeFreshness`:

| 값 | 뜻 |
|---|---|
| `Live` | 좌표가 있고 감시 집합 전체가 그대로다 |
| `Stale { triggered_by }` | 감시 집합의 무언가가 변했다. **무엇이 이를 유발했는지 함께 싣는다** |
| `Orphaned { missing }` | 좌표가 사라졌다. `Stale`과 **다른 사건이다** — 구현이 제거된 것은 사람의 판단을 요구한다 |
| `Undeterminable { reason, at }` | **판정할 수 없다.** `Live`로 처리하지 않는다 |

넷째가 이 열거의 요점이다. 판정 불가를 `Live`로 처리하면 **"못 봤다"가 "괜찮다"로 둔갑한다.**
사유는 넷이다 — 정체성 등급 부족 · 부분 파싱 · 감시 대상이 사라짐 · 투영이 낡음.

**그러나 결박의 상태는 이 넷이 전부가 아니다.** 같은 파일의 `BindingStatus`는 축을 **둘**
가진다.

```rust
pub struct BindingStatus {
    pub code: CodeFreshness,   // 코드가 변했는가
    pub lineage: Lineage,      // 이 결박 자체가 다른 것으로 대체됐는가
}
```

`Lineage`는 `Current`(현행)와 `Superseded { by }`(다른 개체가 이것을 대체함) 둘이다.
축을 나눈 이유가 주석에 적혀 있다 — 하나의 열거에 합치면 **"대체됐고 코드도 변했다"** 를
표현할 수 없기 때문이다.

**그리고 계획 결박은 아예 다른 열거를 쓴다.** §3 화면 예시에 나온 `pending`이 그것이다.
`crates/pal-core/src/plan.rs`의 `PlanBindingState`:

| 값 | 뜻 |
|---|---|
| `Bound { targets }` | 좌표가 확정됐다. 여기서부터는 위의 `CodeFreshness`가 계산된다 |
| `Pending { why }` | **가리키는 코드가 아직 없다.** 계획이 구현을 앞선 자리 |
| `Unresolved { why, candidates }` | 후보가 여럿이라 하나로 좁혀지지 않았다. **기계가 임의로 고르지 않는다** |

이것을 `CodeFreshness`에 다섯째 값으로 더하지 않은 이유도 주석에 있다. `CodeFreshness`를
만드는 자리는 `BindingStatus::evaluate` 하나이고 그 입력인 `Binding`은 **정의상 좌표를
가지고 있다** — 좌표 없는 결박은 타입상 만들 수 없기 때문이다. 값을 더하면 아무도 만들 수
없는 변형이 생기거나, 하나의 열거가 서로 다른 두 모집단 위에 서게 된다.

**정리하면 "상태 4개"는 정확한 표현이 아니다.** 코드 신선도 4값 × 계보 2값이고, 계획
결박은 3값짜리 별도 열거다. 지금 시점에서 "4개로 충분한가"에 대한 답은 **필요한 구분은
이미 축을 나누는 방식으로 표현돼 있다**이다.

#### 코드

- `crates/pal-core/src/binding.rs` — `Binding`, `CodeFreshness`, `Lineage`, `BindingStatus::evaluate`
- `crates/pal-core/src/plan.rs` — `PlanBindingState`
- `crates/pal-core/src/radius.rs` — 반경 4종과 확장
- `crates/pal-intent/src/store.rs` — 결박의 실제 저장
- `crates/pal-cli/src/bind.rs` — `pal bind`

#### 흐름

```
pal bind OrderService.cancel --note "취소는 멱등해야 한다" --radius callers
  → 이름을 심볼로 해소한다. 후보가 여럿이면 **거부한다** (기계가 임의로 고르지 않는다)
  → 반경을 펼쳐 감시 집합을 만든다 (지금의 body_digest 를 함께 저장)
  → 의도 저장소에 결박을 기록한다

pal touch OrderService.cancel   (나중에)
  → 의도 저장소에서 이 좌표에 걸린 결박을 꺼낸다
  → 결박마다 감시 집합의 현재 digest 와 저장된 digest 를 대조한다
  → 다르면 Stale, 좌표가 없으면 Orphaned, 판정 못 하면 Undeterminable, 아니면 Live
```

### 6.4 정직함을 타입으로 만드는 장치 셋

이 프로젝트의 성격을 가장 잘 보여 주는 부분이다. **"모르는 것을 안다고 하지 않는다"를
문서에 적는 대신 타입으로 만든다.**

#### 장치 ① `Capable<T>` — "없음"과 "아직 안 만듦"을 가른다

기능을 점진적으로 만들면 문제가 생긴다. 감사 기능을 아직 안 만들었을 때 화면에 뭐라고
쓸 것인가?

| 후보 | 왜 안 되나 |
|---|---|
| `Option<T>`의 `None` | "값이 없다"인지 "안 만들었다"인지 구별이 안 된다 |
| 빈 목록 | **거짓 안전.** `Finding 0`(위반 없음)과 "감사를 안 만들었음"이 같은 화면이 된다 |

```rust
// crates/pal-core/src/capable.rs
pub enum Capable<T> {
    Present(T),
    NotBuilt { capability: CapabilityId },
}
```

출력은 이렇게 된다.

```
■ 판정
  (이 빌드에는 감사 능력이 없습니다 — F15 미구축)
```

`Finding 0`이라고 말하지 않는다.

#### 장치 ② `Judgment` — `clean`이 타입에 없다

```rust
pub enum Judgment { Finding(Finding), Residual(Residual), OutOfScope(OutOfScope) }
//                  위반 확정          판정 불가            범위 밖
```

**넷째 변형이 없다.** "이상 없음"이라는 값이 타입에 존재하지 않으므로, 그렇게 출력하고
싶어도 방법이 없다.

`Residual`(잔여)에는 **왜 판정 못 했는지**와 **무엇이 있으면 판정 가능한지**가 실린다.
그리고 잔여는 목록이 아니라 **좌표에 결박된다** — 그 좌표를 다시 만지는 순간 잔여가 사람
앞에 다시 나타난다. 선행 하네스가 잔여 개념을 갖고도 실패한 이유가 여기 있었다:
*표시는 목록으로 존재했고, 목록은 아무도 다시 열지 않았다.*

#### 장치 ③ `Envelope<T>` — 답만 단독으로 반환할 방법이 없다

```rust
// crates/pal-core/src/envelope.rs
pub struct Envelope<T> {
    answer: T,
    snapshot: Snapshot,                // 어느 커밋 기준인가
    projection: ProjectionFreshness,   // 이 색인이 워킹트리와 일치하나
    coverage: Coverage,                // 미해소 N · 범위 밖 N · 경유한 언어 등급
    capabilities: CapabilitySet,       // 이 빌드가 실제로 답할 수 있는 것
    ledger: LedgerRef,                 // 관측 범위
    elision: Elision,                  // 예산에 걸려 생략된 것
}
```

질의 실행기(`pal-query`)의 진입점이 **`Envelope`만 반환한다.** 그래서 "답만 돌려주는
경로"가 타입 수준에 존재하지 않는다.

`elision`(생략)이 특히 중요하다. 탐색이 예산 한도에 걸려 중간에 잘렸으면 **얼마나 무슨
이유로 생략했는지가 답에 함께 실린다.** 이것이 그래프 데이터베이스를 안 쓴 결정적 이유이기도
하다 — SQL에도 Cypher에도 `LIMIT`은 있지만 *"한도에 걸린 지점을 사유별로 분해해서
돌려달라"* 는 표현이 없다.

### 6.5 출처 — 이 값을 무엇으로 믿을 수 있나

#### 왜 필요한가

그래프에 `checkout → cancel` 이라는 호출 관계가 하나 있다고 하자. 이 선은 어떻게 생겼을까?
가능성이 몇 가지다.

- 소스 코드에 `cancel()` 호출이 있어서 파서가 뽑았다.
- 실행 로그에서 두 함수가 이어 호출된 것을 관측했다.
- 사람이 "이 둘은 연결돼 있다"고 판단해 직접 등록했다.
- 모델이 코드 주변을 보고 추론했다.

**넷 다 같은 선처럼 보이지만 신뢰도가 전혀 다르다.** 특히 마지막 것을 앞의 것과 구별하지
않으면, 추측이 조용히 사실이 된다. 그래서 그래프의 모든 값은 **어디서 왔는지**를 항상
가지고 다닌다.

| 출처 | 뜻 | 성질 |
|---|---|---|
| `extracted` | 코드에서 결정론적으로 계산됨 | 같은 입력 → 같은 답 |
| `observed` | 실행·빌드·계측에서 얻음 | **재현 보증이 없다.** "있다"는 주장에만 쓸 수 있고 "없다"는 주장에는 못 쓴다 |
| `asserted` | 사람이 승인해 확정함 | 결박 필수 |
| `inferred` | 합성·추론의 산물 | **근거·공백·확신도가 필수** |

`observed`의 성질을 한 번 더 보자. 실행 로그에서 어떤 호출을 봤다면 그 호출은 **확실히
존재한다.** 그러나 로그에 없다고 해서 그 호출이 **없는 것은 아니다** — 그 경로가 이번 실행에서
지나가지 않았을 뿐일 수 있다. 그래서 `observed`는 존재 주장에만 강하다.

**이 출처 값은 불변이다.** 추론을 승인해서 확정으로 만드는 것은 값을 고쳐 쓰는 게 아니라
**새 노드를 만드는 것**이다. 원본은 `promoted_by`(무엇에서 승격됐는지)와 함께 남는다.

```rust
impl Inferred {
    // self 를 소비하지 않는다 — 원본이 남아야 한다
    pub fn promote(&self, approval: Approval) -> (AssertedNode, PromotedByEdge);
}
```

값을 바꾸는 함수(setter)가 없고 덮어쓰는 경로가 없다. **그 자체가 "세탁 방지"의 구현
형태다** — 에이전트가 추측한 것이 조용히 사실로 승격되는 길이 아예 없다.

#### 참조를 얼마나 확실하게 풀었는가

같은 자리에 **해소 등급**도 있다. 코드에서 `foo()`라는 호출을 봤을 때, 그 `foo`가 어느
정의를 가리키는지 얼마나 확실히 알아냈는지의 등급이다.

| 등급 | 뜻 | 예 |
|---|---|---|
| `exact` | import·정의가 해소되어 대상이 유일하다 | `import { foo } from './a'` 가 있고 거기 `foo`가 하나 있다 |
| `scoped` | 스코프 해소로 후보가 유일하다 | 같은 파일 안에 `foo`가 하나뿐이다 |
| `candidate` | 후보가 여럿이다. **엣지 N개가 아니라 후보 집합 하나로 저장된다** | 프로젝트에 `foo`라는 이름이 다섯 군데 있고 어느 것인지 모른다 |
| `contract` | 모듈·서비스 경계를 넘는 계약 매칭. 증거 필수 | HTTP 경로나 이벤트 이름으로 이어진 관계 |

셋째가 중요하다. 이름이 같은 것 전부에 선을 그으면 그래프는 가득 차고 신호는 사라진다.
**거짓 엣지는 없는 엣지보다 나쁘다** — 없으면 사람이 확인하지만, 있으면 사람이 믿는다.

#### 코드

`crates/pal-core/src/graph.rs` — `Provenance`, `Producer`, `ResolutionGrade`

### 6.6 단일 진실 파일 둘 — 데이터가 코드를 검사한다

#### 왜 필요한가

프로젝트가 커지면 흔히 일어나는 일이 있다. 코드에는 어떤 기능이 들어갔는데 스키마 문서에는
안 적혀 있거나, 문서에는 "이런 질의를 지원한다"고 적혀 있는데 코드에는 그런 게 없다.
둘 다 조용히 일어나고, 발견되는 것은 사용자가 그것을 쓰려다 실패했을 때다.

그래서 이 저장소에는 **코드가 아니라 데이터인데 코드보다 상위에 있는 파일**이 둘 있다.

| 파일 | 정하는 것 | 지금 담고 있는 것 |
|---|---|---|
| `schema/graph.toml` | **무엇이 존재하는가** — 노드·엣지·속성·생산자 | 노드 10종, 엣지 8종 |
| `surface/queries.toml` | **무엇을 물을 수 있는가** — 질의 목록 | 질의 10종 |

규칙은 양방향이다. **코드에만 있고 파일에 없으면 CI 실패. 파일에만 있고 코드에 없어도 CI 실패.**

#### 실제로 어떻게 걸리나 — 양쪽 방향 모두 사례가 있다

**한쪽 방향.** 스키마에 `UnresolvedRef`(미해소 참조) 노드가 선언돼 있는데 상태가
`not_built`(아직 안 만듦)로 적혀 있다. 코드에 짝이 없는데 왜 CI가 통과하는가? 코드에 짝이
**있고**, 그 타입이 값을 만들 수 없게 되어 있기 때문이다(Rust에서 `uninhabited`, 즉 어떤
값도 존재할 수 없는 타입). 자리만 선언해 두고 값을 만들 수 있으면 그것은 *"기능이 있다고
적혀 있는데 실제로는 아무것도 안 나오는"* 상태가 된다.

**반대 방향도 실제로 걸렸다.** `pal touch` 명령은 오래전부터 동작하고 있었는데
`surface/queries.toml`에 해당 항목이 없었다. 그러면 양방향 대조 검사가 그 이름에
대해서는 **아무것도 검사하지 않은 채로 통과한다.** 대상이 없어서 검사가 통과한 것을
"이상 없음"으로 읽으면 안 된다 — **동작하지 않은 검사는 "해당 없음"이 아니라 실패다.**

#### 코드

- `crates/pal-core/src/schema.rs` — 스키마를 읽는 **유일한** 경로
- `xtask/src/main.rs` 검사 7 — 스키마 정합
- `xtask/src/main.rs` 검사 11 — 카탈로그 정합

검사가 자기 파서를 따로 만들면 **CI를 통과한 스키마가 실행 시점에 거부되는** 상황이 생길 수
있다. 그래서 `xtask`는 자기 파서를 만들지 않고 `pal-core::schema`를 호출한다.

### 6.7 CI 검사 — 규율 대신 기계

#### 왜 이런 형태인가

"의존 방향을 지키자", "상수를 한곳에 모으자" 같은 규칙은 대개 문서에 적히고 리뷰에서
확인된다. 그러면 리뷰어가 놓치는 만큼 규칙이 새어 나간다. 이 저장소는 그런 규칙을
**Rust로 짠 검사 프로그램**으로 바꿔서 `cargo xtask check` 하나가 전부 실행하게 한다.
검사가 몇 개인지는 실행하면 마지막 줄에 출력되므로 여기에 적지 않는다. 몇 개만 봐도
성격이 보인다.

| 검사 | 무엇을 막나 |
|---|---|
| 의존 방향 | 도메인이 저장 기술을 내부화하는 것 |
| **코어 어휘 금지** | `pal-core` 소스에 `claude`·`mcp`·`redb`·`cypher`·`gate` 같은 말이 나오면 실패 |
| 의도 저장소 폐기 경로 부재 | 캐시를 지우는 코드가 사람의 승인 노동에 닿는 것 |
| `gix` 격리 | git 라이브러리가 여러 크레이트로 퍼지는 것 |
| 선택 필드 금지 | 응답에 실리는 타입에 `Option<T>`가 생기는 것 |
| **예산 상수 단일 위치** | 상한값이 코드 여기저기에 숫자로 흩어지는 것 |
| 재구축 등가성 | 2층을 지우고 다시 만들었을 때 답이 달라지는 것 |

**코어 어휘 금지**가 왜 필요한지가 이 목록의 성격을 잘 보여 준다. `pal-core`는 도메인 개념만
담아야 하는데, 개발하다 보면 "이건 Claude Code에서 이렇게 쓰이니까"라는 이유로 특정 호스트나
특정 저장 기술의 이름이 도메인 타입 안으로 스며든다. 한번 들어가면 그 기술을 갈아 끼울 때
도메인까지 고쳐야 한다. 그래서 **단어 자체를 금지**하고, 예외가 필요하면
허용 목록(`xtask/vocab.toml`)에 명시적으로 등록하게 한다. 허용 목록에 항목이 늘어나는 것
자체가 관측 대상이다.

**예산 상수**는 이런 것들이다 — 후보 집합 상한 32, 경로 곱 예산 10⁴, 탐색 깊이 3,
화면 노드 500. 이 숫자들 중 **실측에서 나온 것은 하나도 없다.** 그래서 이름에
`PROVISIONAL_`(잠정) 접두어를 붙이고, 각각 "어느 측정이 이 값을 확정하는가"를 주석으로
적어 둔다. 그리고 어느 상한에 걸렸는지가 답의 `elision`(생략)에 실려 나간다.

### 6.8 하네스 — 에이전트가 일하는 절차

#### 개념

원래 이건 목표가 아니었다. 2026-08-18에 목표로 옮겼다
([ADR-0025](adr/0025-the-harness-that-reads-the-graph-is-the-same-product.md)).

옮긴 이유는 이 저장소 자신이 겪은 세 가지다.

1. **사전부검이 영향 범위를 상상했다** — 조회할 그래프가 붙어 있지 않으면 모델의 추정이
   유일한 수단이 된다.
2. **회차가 끝날 때마다 잔여가 남았다** — 완료 항목 넷을 닫고 「다음으로 넘기는 것」 열 개를
   새로 만들었다.
3. **결정이 그래프로 안 들어갔다** — 회차가 만든 판정이 문서로 12,818줄 쌓였다. 사람이
   읽어야만 꺼내지고, 조용히 낡고, 결박이 없어 낡음이 표시되지 않는다.

세 번째가 가장 심각하다. 이 제품이 지적한 문제를 **자기 저장소의 판정 기록이 그대로 저지르고
있었다.**

#### 표면은 4종이고 그 이상 늘리지 않는다

| 표면 | 하는 일 |
|---|---|
| 스킬 | 회차를 어떻게 도는가 |
| 에이전트 정의 | 역할·경계·반환 형식 |
| 훅 | 우회하면 피해가 큰 경계 |
| `pal` CLI | 상태 관리자 — **대화하지 않는다** |

#### 역할은 5종이고 단계에 고정되지 않는다

| 역할 | 하는 일 |
|---|---|
| **사관** | 결정·의도를 코드 좌표에 결박해 남긴다 |
| **사서** | 물으면 찾아 준다 — 영향 범위 · 낡음 · 걸린 결정 |
| **큐레이터** | 전부 내놓지 않고 지금 필요한 것을 고른다 |
| **서사자** | 흩어진 사실을 읽을 수 있는 이야기로 엮는다 |
| **동료** | 같이 판단한다 |

**"사서는 착수 단계, 서사자는 종료 단계" 같은 배치를 하지 않는다.** 그렇게 묶으면 정의된
곳에서만 쓰게 된다. 가장 자주 필요한 자리는 회차 밖에 있다 — **`grep`을 실행하려는 순간에
그래프에 먼저 묻는다.** `grep`은 문자열을 맞히고 그래프는 관계를 안다.

#### 코드

- `crates/pal-cli/src/install.rs` — `pal install`. **대상 프로젝트 바깥을 건드리지 않는다**
  (`$HOME` 읽기와 `~` 경로 전개가 소스에 하나도 없고, CI가 그 사실을 검사한다)
- `crates/pal-cli/src/install/layout.rs` — 설치되는 리소스 목록 (스킬·에이전트 정의)
- `crates/pal-cli/src/hook.rs` — 훅이 호출하는 자리
- `crates/pal-cli/src/round/` — 회차 상태 관리
- `.claude/skills/round/SKILL.md` — 회차 절차의 정본

### 6.9 회차 — 일을 시작하고 끝내는 단위

#### 개념

**회차(round)** 는 이 프로젝트에서 작업의 단위다. 디렉터리 하나가 회차 하나다 —
`.palimpsest/rounds/<이름>/`에 `intent.md`(잠긴 의도)와 `state.md`(교대용 상태)를 두고
둘 다 커밋한다.

```
인터뷰 → 사전부검 → 완수 조건 → 승인 → 루프 → 완료 · 차단 · 철회
```

- **인터뷰** — 소유자가 무엇을 하려는지, **말하지 않은 것과 모호한 것**을 질문으로 끌어낸다.
- **사전부검(pre-mortem)** — 착수 전에 실패할 지점을 미리 찾는다. 원 의도와 계획만 주고
  대화 기록은 주지 않는다(독립성).
- **완수 조건** — 검증 가능한 것만 적는다. 각 조건에 **RED**(시작 시점에 실제로 실패하는지
  관측)와 **음성 대조**(검사가 고장 났다면 그 사실이 드러나는 조건)를 함께 등록한다.
- **루프** — 실행 → 검증 → 처리. 처리 방침은 4종이다: 정정 · 확대 · 축소 · 전환.
  앞 둘은 자율 판단으로, 뒤 둘은 소유자 승인을 받아 진행한다.
- **나가는 문은 셋** — 완료(다 했다) · 차단(하려는데 안 된다) · 철회(안 하기로 정했다).

> 위의 「처리 방침」·「철회」는 이 문서가 쓰는 말이고, 스킬 문서는 각각 「처분」·「접힘」이라고
> 부른다. 스킬 쪽 어휘를 사용자에게 이해되는 말로 바꾸는 작업은
> [#111](https://github.com/hskim-ecoletree/palimpsest/issues/111) 이 다룬다.

핵심 규칙 하나: **회차가 끝날 때 「나중에」가 0이다.** 회차 중에 나온 발견은 그 회차 안에서
처리된다. 다만 **철회는 「나중에」가 아니다** — 「나중에」는 하겠다고 해 놓고 안 하는 것이고,
철회는 안 하기로 정하고 **왜인지를 기록하는 것**이다.

왜 사유를 강제하나. 선행 하네스에는 작업을 중단하는 기능이 있었고 실제로 **열일곱 번
중단됐는데, 사유 필드가 없어 왜 중단했는지 하나도 확인할 수 없다.** 같은 저장소가 반론
하나를 기각할 때는 근거를 요구했다. **반론은 근거 필수, 작업 전체는 근거 불필요** — 그
비대칭이 실패의 지점이었다.

#### 정반합 — 판정을 혼자 하지 않는다

결정론적인 조건(CI가 성공/실패로 답하는 것)은 기계가 판정한다. **해석이 들어가는
조건**에만 세 역할을 쓴다.

| 역할 | 누가 | 받는 것 |
|---|---|---|
| **정(正)** | 메인 에이전트 | 전부 |
| **반(反)** | `pal-decision-opponent` | **초안과 근거만** — 대화 기록도 사고 과정도 받지 않는다 |
| **합(合)** | `pal-decision-synthesizer` | 초안 + 반론 |

**합을 메인이 겸하지 않는다.** 초안을 쓴 쪽이 판정하면 자기 확신이 깨지지 않는다.

그리고 통과 여부는 판정값이 아니라 **해악도**로 가른다. 선행 하네스의 기록을 재 보니 판정값
필드가 15건 전부 같은 값이었다 — 그 필드는 아무 정보도 담고 있지 않았다. 실제 변별력은
심각도에 있었다.

> ⚠ **현재 설계와 소유자 의도가 갈리는 지점이 둘 있다.**
>
> 1. **정(正)을 메인 에이전트가 맡고 있다.** 소유자 의도는 토론 설계·정·반·합·종료 판단·결과
>    취합을 **전부 서브에이전트가 수행**하고, 메인은 스킬을 발동하고 결과를 받는 역할만 하는
>    것이다. 메인이 초안을 쓰면 메인의 컨텍스트 오염과 자기 확신이 판정에 그대로 들어간다.
>    → [#112](https://github.com/hskim-ecoletree/palimpsest/issues/112)
> 2. **완수 조건이 잘 설계됐는지 평가하는 단계가 없다.** 현재 절차는 완수 조건을 적고 바로
>    승인으로 넘어간다. 이 루프에서 가장 중요한 것이 의도 파악과 완수 조건 설계인데, 그것을
>    검증하는 자리가 비어 있다. 또한 "체크 가능한 것만"의 기준도 명시돼야 한다 —
>    **결정론적·기계적 검증(E2E·통합·단위 테스트)이 가능하면 무조건 작성하고, 그것이
>    어렵더라도 의미론적으로 검증할 방법이 있으면 검증한다.**
>    → [#113](https://github.com/hskim-ecoletree/palimpsest/issues/113)

#### 코드

- `crates/pal-intent/src/round_condition.rs` — `intent.md`의 완수 조건 파싱
- `crates/pal-cli/src/round/status.rs` — 검증 상태 읽기 (실행하지 않는다)
- `crates/pal-cli/src/round/approval.rs` — 판정 명령(oracle) 승인
- `crates/pal-cli/src/round/verify.rs` — 승인된 명령 실행 + 추가 전용 증거 기록
- `crates/pal-cli/src/round/stop.rs` — Stop 훅 정책

**승인과 실행이 분리돼 있다.** `pal round approve`는 실행하지 않고 승인만 기록하고,
`pal round verify`만 실제로 명령을 돌려서 증거를 덧붙인다. 회차 원장은 **추가 전용**이라
지난 기록을 고칠 수 없다.

## 7. 실제로 어떻게 동작하는가 — 두 흐름

### 7.1 코어: 설치부터 조회까지

```
① pal install --target ../their-project
     └ .claude/ 아래에 스킬·에이전트 정의를 놓는다
     └ settings.json 에 훅을 exec form 으로 등록한다
     └ 매니페스트(sha256)를 남긴다 — 나중에 사람이 고친 것을 덮어쓰지 않으려고
     └ ★ 검증이 끝나기 전에는 한 바이트도 쓰지 않는다 (부분 설치 금지)

② pal ledger
     git HEAD 트리 → 파일 목록
       → 언어 인식 → 추출기가 있으면 tree-sitter 파싱
       → 파일 부분 그래프를 1층 캐시에 저장 (열쇠에 커밋 없음)
       → 7종의 상태로 집계

③ pal bind <심볼> --note "..." --radius callers
     이름 → 심볼 해소 (후보가 여럿이면 거부)
       → 반경을 펼쳐 감시 집합 + 현재 digest 기록
       → 의도 저장소(재생성 불가)에 기록한다
       → 정본은 .palimpsest/intent/*.jsonl 이고 git 에 커밋된다

④ pal touch <심볼>
     1층 캐시 → 스티칭 → 2층 투영
       → 2층에서 심볼·참조를 읽는다
       → 의도 저장소에서 걸린 결박과 지켜보는 결박을 읽는다
       → 결박마다 신선도 판정 (Live/Stale/Orphaned/Undeterminable)
       → 못 만든 능력은 Capable::NotBuilt 로 자리를 채운다
       → 전부 Envelope 에 담아 반환한다

⑤ pal doctor
     저장된 그래프가 자기 규칙(불변식 8종)을 지키는지 확인한다
       → 검사 대상이 하나도 없는 불변식은 "위반 0" 이 아니라 Residual 이다
```

⑤의 마지막 줄이 이 프로젝트의 태도를 압축한다. 검사할 대상이 하나도 없었으면
"통과"가 아니라 **"측정하지 못했다"** 이다([ADR-0002](adr/0002-empty-population-is-not-zero-violations.md)).

### 7.2 하네스: 회차 한 바퀴

```
/round 를 연다
  ① 인터뷰      — 안 물은 것을 먼저 발굴한다. 끝은 상한이 정한다
  ② 사전부검    — pal-premortem-sweeper 가 실패 시나리오를 제시한다
                  영향 범위는 상상하지 말고 그래프에 묻는다
  ③ 완수 조건   — intent.md 에 검증 가능한 것만. RED · 음성 대조 · 대안 경로를 함께 등록
  ④ 승인        — 소유자가 잠긴 의도를 승인한다
  ⑤ 루프        — 실행 → 검증 → 처리
                  · 의도를 향해 가는 변경은 자율 판단
                  · 의도에서 멀어지는 변경은 소유자 승인 (승격)
                  · 해석이 필요한 판정은 정반합 셋으로
  ⑥ 완료        — pal round verify --all 로 승인된 명령을 전부 재실행
                  독립 리뷰가 라운드를 돈다 (대화 기록 없이 산출물만 본다)
                  회차 보고를 쓰고 결정을 결박한다
```

## 8. 용어집

> **이 절이 사용자와 합의할 어휘의 초안이다.** 같은 개념을 다른 이름으로 부르면 대화가
> 어긋나므로, 이 저장소가 실제로 쓰는 말을 그대로 적는다.
>
> **표기 원칙** — 상태값이나 코드에 그대로 등장하는 식별자는 **영어를 원 표기로 삼는다.**
> 번역하면 코드와 화면과 문서가 서로 다른 이름을 쓰게 되기 때문이다. 다만 그것이 **사용자
> 화면에 나갈 때는 사용자 언어를 함께 표기한다** — 예: `최신 상태 아님(stale)`.
> 개념을 가리키는 일반 용어는 한국어를 쓰고 원어를 괄호로 병기한다.
>
> ⚠ 아래 표기 중 일부는 이 원칙에 아직 맞춰지지 않았다. 정리 작업은
> [#107](https://github.com/hskim-ecoletree/palimpsest/issues/107) 이 다룬다.

### 8.1 가장 자주 쓰는 열 개

| 용어 | 뜻 | 왜 이 용어가 필요한가 |
|---|---|---|
| **결박** (binding) | 사람이 쓴 글 조각을 코드 좌표에 연결한 기록 | 이 제품의 핵심 그 자체다. 문서와 코드를 잇는 유일한 연결 |
| **좌표** (coord) | 코드의 한 지점을 가리키는 주소 `(저장소, 트리, 추출기 버전, 심볼)` | 줄 번호는 밀린다. 밀리지 않는 주소가 있어야 결박이 성립한다 |
| **낡음** (stale) | 결박이 걸린 코드가 결박 이후로 변했다는 상태 | 문서가 낡는 것은 못 막지만 **낡았다는 사실의 감지**는 기계가 한다 |
| **관측 원장** (ledger) | "무엇을 보았고 무엇을 보지 않았는가"의 선언 | "전부 검사했다"는 검사할 수 없다. 범위를 선언해야 빠짐없음 주장이 성립한다 |
| **봉투** (`Envelope`) | 모든 답을 감싸는 공통 구조 — 스냅샷·커버리지·능력·생략 정보 | 답만 단독으로 반환하는 경로가 **타입에 존재하지 않게** 만든다 |
| **출처** (provenance) | 그 값을 무엇으로 믿을 수 있나 — 4값 | 추측이 조용히 사실이 되는 것을 막는다 |
| **잔여** (residual) | 판정하지 못한 것 + 사유 + 무엇이 있으면 판정 가능한지 | "이상 없음"이라고 말하지 않기 위한 자리 |
| **능력 부재** (`Capable::NotBuilt`) | 이 빌드가 그것을 답하지 않는다 | "없음"과 "안 만듦"이 같은 화면이 되는 것을 막는다 |
| **생략** (elision) | 예산 한도에 걸려 잘라 낸 것 + 얼마나 · 왜 | 조용한 생략을 금지하는 것이 이 제품의 정체성이다 |
| **회차** (round) | 일을 여는 단위. 의도를 잠그고 끝날 때까지 반복한다 | 「나중에」를 0으로 만드는 장치 |

### 8.2 좌표와 정체성

| 용어 | 뜻 |
|---|---|
| **`symbol_id`** | "같은 심볼인가"에 답하는 값. `(저장소, 경로, 컨테이너 체인, 이름, 구분자)`에서 계산 |
| **`body_digest`** | "내용이 변했는가"에 답하는 값. `symbol_id`와 **다른 축이다** |
| **컨테이너 체인** | `파일 → 클래스 → 중첩 클래스` 같은 포함 관계. `symbol_id`의 성분 |
| **정체성 등급** | `exact`(스코프로 유일) · `ordinal`(선언 순서 의존) · `unavailable`(좌표 불가) |
| **스냅샷** (snapshot) | 이 답이 어느 `(저장소, 커밋)` 기준인가 |
| **트리 참조** (`TreeRef`) | 커밋 또는 워킹트리. 둘 다 1급이다 |
| **추출기 버전** | `(문법 버전, 추출기 코드 버전)`. 좌표의 성분이고 캐시 열쇠의 성분 |

### 8.3 관측 범위

| 용어 | 뜻 |
|---|---|
| **파일 상태** (`FileState`) | 7종 — `Parsed`·`Partial`·`Unsupported`·`Unrecognized`·`Excluded`·`Binary`·`Generated` |
| **추출 등급** | `L0`(텍스트) · `L1`(구조) · `L2`(스코프 참조) · `L3`(읽기/쓰기) · `L4`(제어흐름) |
| **커버리지** (coverage) | 미해소가 몇 건 · 범위 밖이 몇 건 · 어느 언어 등급을 경유했나 |
| **미해소 참조** (`UnresolvedRef`) | 기계가 못 푼 참조. **버리지 않고 1급 데이터로 남긴다** |

### 8.4 결박과 낡음

| 용어 | 뜻 |
|---|---|
| **반경** (radius) | 무엇까지 지켜보나. `symbol` · `callers` · `closure:k` · `files:...` |
| **감시 집합** (watch) | 반경을 펼친 결과 + 그 시점의 digest. **결박 자신의 내용이다** |
| **`live`** | 감시 집합이 그대로다 |
| **`stale`** | 감시 집합의 무언가가 변했다. **무엇이 그것을 유발했는지 함께 실린다** |
| **`orphaned`** | 좌표가 사라졌다. `stale`과 다른 사건이다 |
| **`undeterminable`** | 판정할 수 없다. **`live`로 처리하지 않는다** |
| **계보** (`Lineage`) | 이 결박이 다른 것으로 대체됐는가. `Current` · `Superseded`. 코드 신선도와 **다른 축이다** |
| **계획 결박 상태** (`PlanBindingState`) | `Bound` · `Pending`(가리키는 코드가 아직 없다) · `Unresolved`(후보가 여럿) |
| **승격** (`promoted_by`) | 결박이 만들어진 경로 — 직접 등록(`hand`) 또는 제안 승인(`proposal`) |

### 8.5 출처와 등급

| 용어 | 뜻 |
|---|---|
| **`extracted`** | 코드에서 결정론적으로 계산됨 |
| **`observed`** | 실행·빌드·계측에서 얻음. 재현 보증이 없어 **"없다"는 주장에 못 쓴다** |
| **`asserted`** | 사람이 승인해 확정함 |
| **`inferred`** | 합성·추론의 산물. 근거·공백·확신도 필수 |
| **해소 등급** | `exact` · `scoped` · `candidate` · `contract` |
| **생산자** (producer) | 그 속성을 채운 주체. 노드의 출처와 정합해야 로딩을 통과한다 |

### 8.6 판정

| 용어 | 뜻 |
|---|---|
| **`Finding`** | 위반이 확정된 것. 반례가 첨부된다 |
| **`Residual`** | 판정할 수 없는 것. **좌표에 결박된다** |
| **`OutOfScope`** | 범위 밖. 관측 원장을 참조한다 |
| **불변식** (invariant) | `pal doctor`가 그래프에 대해 검사하는 규칙 8종. 스키마에서 파생되며 손으로 세지 않는다 |
| **빈 모집단** | 검사 대상이 하나도 없었던 상태. **"위반 0"이 아니라 잔여다** |
| **음성 대조** | "검사가 고장 났다면 그 사실이 드러나는 조건". 합격선에 미리 등록한다 |

### 8.7 저장

| 용어 | 뜻 |
|---|---|
| **1층 · 추출 캐시** | 파일 하나의 파싱 결과. 내용으로 주소를 만든다. **지워도 된다** |
| **2층 · 질의 투영** | 심볼 색인·인접 리스트·역방향 색인. **지워도 된다** |
| **의도 저장소** | 결박·승인·거부의 원본. **지우면 영영 잃는다.** 지우는 API가 없다 |
| **스티칭** (stitching) | 파일별 부분 그래프를 질의 시점에 이어 붙이는 것 |
| **역방향 색인** | "이것을 가리키는 것들". `touch`의 근간 |
| **재구축 등가성** | 2층을 지우고 다시 만들었을 때 모든 자리에서 같은 값이 나오는가 |

### 8.8 하네스와 회차

| 용어 | 뜻 |
|---|---|
| **하네스** (harness) | 그래프를 읽어 회차를 진행하는 층. Claude Code 전용 |
| **코어** (core) | `pal` CLI. 하네스 없이 단독으로 동작한다 |
| **표면** (surface) | 사용자·에이전트가 닿는 자리. **4종이고 그 이상 늘리지 않는다** |
| **역할** | 사관 · 사서 · 큐레이터 · 서사자 · 동료 5종. **단계에 고정되지 않는다** |
| **의도** (intent) | 회차가 잠근 것. 원문은 소유자 문장 그대로 두고 요약하지 않는다 |
| **완수 조건** | 검증 가능한 것만. 항목에 체크가 됐다는 것은 "됐다"가 아니라 **"측정했다"** 는 뜻이다 |
| **RED** | 시작 시점에 실제로 실패하는 것을 관측하는 것. 대상 0건을 훑고 통과하는 검사는 아무것도 측정하지 않는다 |
| **대안 경로** (스킬 용어: 퇴로) | "X가 안 되면 약하게 선언하고 Y에 집중한다". 미리 등록하면 나중에 쓸 때 별도 승인이 필요 없다 |
| **처리 방침** (스킬 용어: 처분) | 정정 · 확대 · 축소 · 전환 4종. 앞 둘은 자율 판단, 뒤 둘은 소유자 승인 |
| **승격** (promotion) | 의도에서 멀어지는 변경을 소유자에게 올리는 것 |
| **차단** (스킬 용어: 막힘) | 하려는데 안 된다. 같은 실패가 3회 반복되거나 원인을 규명하지 못하는 상태 |
| **철회** (스킬 용어: 접힘) | 안 하기로 정하는 것. **사유를 기록해야 철회다** |
| **정반합** | 판정을 세 역할로 나눈 것. **합을 메인이 겸하지 않는다** |
| **판정 명령** (oracle) | 완수 조건의 충족 여부를 실제로 판정하는 명령. 승인과 실행이 분리돼 있다 |
| **회차 원장** (ledger) | 검증 증거의 기록. **추가 전용** |

> ⚠ **"관측 원장"과 "회차 원장"은 다른 것이다.** 앞은 코어가 무엇을 읽었는지의 범위 선언
> (`Ledger`)이고 뒤는 회차가 완수 조건을 어떤 명령으로 검증했는지의 증거 기록이다.
> 영어로는 둘 다 `ledger`라 혼동하기 쉽다.

## 9. 지금 어디까지 만들어졌나

**진행 상태는 문서가 아니라 이슈로 확인한다.** 어디까지 왔는지는 이렇게 본다.

```bash
./scripts/frontier.sh
```

지금 시점에서 확실히 말할 수 있는 것만 적는다.

| | 상태 |
|---|---|
| 동작하는 것 | 관측 원장 · 좌표 · 1층 캐시 · 2층 투영 · 결박과 낡음 판정 · `touch` · 설치 · 회차 상태 관리 |
| 1급 언어 | 5종 (Kotlin·Java·JavaScript·TypeScript·Rust) — 그러나 **추출기는 3종**(Kotlin·TypeScript·Rust). 나머지 둘은 `NotBuilt` |
| 답하는 질의 | `surface/queries.toml`에 등록된 10종 |
| 그래프 | 스키마에 선언된 노드 10종, 엣지 8종. **파일 경계를 넘는 참조는 아직 없다** |
| 아직 안 만든 것 | 미해소 참조(`UnresolvedRef`) 값 생성 · 판정(`Finding`) · 여정(`Journey`) · 외부 분석기 연동 |
| Windows | **지원 대상이고 CI가 검사한다.** 다만 `core.autocrlf=true`가 매니페스트 대조를 깨는 문제가 열려 있다 |
