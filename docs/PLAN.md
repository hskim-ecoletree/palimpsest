# palimpsest 구현 계획 — 설계를 어떤 순서로 어떤 코드로 세우는가

> **이 문서의 지위**
>
> - **성격**: **실행 문서**(when·what·how-built). [`DESIGN.md`](DESIGN.md)가 *백서의 계약을 어떤 구조로 만족시키는가*를 정했다면 이 문서는 *그 구조를 어떤 순서로, 어떤 코드 단위로, 무엇으로 판정하며 세우는가*를 정한다.
> - **권위**: 설계 결정에 대해서는 없다. **설계 결정은 이 문서에 살지 않는다** — 전부 `DESIGN §`로 가리킨다. 이 문서가 소유하는 것은 **구현 결정 I1~I14**(스택·경계·검사 장치·순서)뿐이며, 그것들은 설계 결정이 아니라 그것을 실현하는 수단이다.
> - **입력**: [`DESIGN.md`](DESIGN.md)(결정) + [`evidence-map.md`](evidence-map.md)(근거) + 지시 문서 [U1~U9](instructions/2026-08-03-owner-direction.md)·[U10](instructions/2026-08-04-owner-direction.md)(요구사항) + **2026-08-03 시점의 도구 지형 조사**(§3.4 — 이것은 `docs/research/`의 연구가 아니며 그 지위를 갖지 않는다).
> - **자기제약**: 설계와 충돌하면 설계가 이긴다. 단 **구현이 설계 결정의 전제를 무너뜨리는 지점**(저장 기술·언어 능력·예산)은 이 문서가 관측하고 §13에 "설계 갱신 필요"로 올린다 — 고치는 것은 이 문서가 아니라 `DESIGN.md`다.
> - **분할 규칙**: `DESIGN.md`의 규칙을 그대로 승계한다. **결정은 설계 문서에, 근거는 근거 대장에, 실행은 이 문서에.** 같은 것을 두 곳에 적으면 그것이 곧 drift이며 이 저장소에서 이미 두 번 일어났다.
> - **기호 규약**: `DESIGN.md`의 규약을 승계하고 둘을 더한다 — **`In`은 구현 결정**, **`T-<슬라이스>-<번호>`는 작업 단위**. `Sn`(슬라이스)·`Dn`(설계 결정)·`Rn`(연구 관측)·`Un`(지시)·`Pn`(백서 원리)·`Cn`/`E`/`O`(능력)는 전부 기존 뜻 그대로다. 접두어 없는 `§`는 이 문서, `DESIGN §`는 설계 문서, `백서 §`는 백서다.
> - **갱신 조건**: 슬라이스가 게이트를 통과하거나 반증될 때. 그리고 구현 결정이 뒤집힐 때. **설계가 갱신되면 이 문서는 따라서 갱신된다**(역방향은 없다).

## 0. 이 계획이 답하는 것과 답하지 않는 것

### 0.1 답하는 것

| 질문 | 자리 |
|---|---|
| 무엇으로 만드는가 — 언어·저장·파서 | §3 (I1·I3·I7) |
| 코드의 경계가 어디이고 그 경계가 어떻게 **기계적으로** 지켜지는가 | §4 (I2·I10) |
| `DESIGN §`의 형식 제약이 어떤 타입·검사로 바뀌는가 | §5 (I4·I5) |
| 표면 계약(명명된 질의)의 실제 목록 — `DESIGN §15-33`이 잔여로 남긴 것 | §6 (I6) |
| `DESIGN §1.1`의 타입 전부가 물리적으로 어디에 어떻게 앉는가 | §7 |
| 무엇이 첫날부터 CI에서 상시 도는가 | §8 (I10·I11) |
| 슬라이스마다 어떤 작업을 하고 **무엇으로 반증되는가** | §9 (S-1~S12) |
| 26건의 ADR 후보가 언제 발행되는가 | §10 |
| R8 기준선의 대조 장치를 어떻게 사전 등록하는가 | §11 |

### 0.2 답하지 않는 것

1. **일정과 날짜.** 이 계획에 착수일도 마감일도 없다. 순서를 정하는 것은 게이트이고(`DESIGN §13`), 게이트는 시간이 아니라 판정으로 열린다. 대신 각 작업에 **상대 규모**(S/M/L/XL)만 붙인다. 절대 시간을 적으면 그것이 곧 게이트를 우회할 압력이 된다.
2. **팩의 내용.** 해석기 팩에 어떤 규칙이 들어가는지는 프로젝트가 정한다(`DESIGN §7.3` — 백서 §12-3의 소진). 이 문서는 팩 **스키마**의 자리와 로딩 경로만 정한다.
3. **설계 결정의 재서술.** `Dn`을 다시 설명하지 않는다. 왜 그렇게 정했는지가 궁금하면 `DESIGN §`으로, 무엇을 보고 정했는지가 궁금하면 [`evidence-map.md`](evidence-map.md)로 간다.
4. **거버넌스 층의 구현.** 그것은 이 층 위에 서고 이 층이 아니다(`DESIGN §12.6`). 이 계획은 S12에서 **경계와 소비 계약**까지만 만든다.

## 3. 스택 — I1·I3·I7·I8

### 3.1 I1 — Rust

`DESIGN §12.1`이 고른 세 가지(단일 정적 바이너리 · 빌드 없는 다언어 파싱 · 재구축 가능한 투영)를 동시에 만족하는 언어는 사실상 둘(Rust·Go)이고 셋째 근거가 갈랐다.

| 근거 | 내용 |
|---|---|
| **형식 제약의 타입화** | §5가 이 결정의 실질이다. `DESIGN §3.1`(선택 필드 금지)·§9.1(`evidence_refs` 저장 거부)·§3.1(출처 불변)은 전부 *"이런 값은 애초에 만들어질 수 없다"*로 표현될 때만 규율에서 벗어난다. Rust의 뉴타입·소유권·`#[non_exhaustive]`·private 생성자가 그것을 컴파일 타임으로 옮긴다. Go에서는 같은 것이 런타임 검사(= 규율)로 남는다 |
| **파서 생태계** | tree-sitter는 Rust 네이티브이고 CGO 없이 정적 링크된다. Go 바인딩은 CGO를 요구해 "단일 정적 바이너리"의 비용이 올라간다 |
| **선례와의 거리** | R10(stack-graphs)이 Rust이므로 대조·부분 채택의 비용이 낮다(I8) |

**대가는 정직하게 적는다 — 소유자가 Rust에 미숙하다.** 이것은 이 계획에서 가장 큰 단일 실행 위험이며 §12-1에 잔여로 올린다. 완화는 셋이고 전부 S0 안에 있다.

1. **S0의 범위가 언어 입문의 범위와 겹친다** — 좌표·해시·파일 상태 열거·테이블 출력. 소유권과 수명이 얕게만 걸리는 구간이고, `Coord`·`body_digest`가 값 타입이라 참조 그래프가 거의 생기지 않는다.
2. **의존 크레이트를 최소로 고정한다** — S0에서 쓰는 외부 크레이트는 넷을 넘기지 않는다(파서·해시·직렬화·CLI). 크레이트 선택이 학습을 대체하는 것을 막는다.
3. **`unsafe` 금지, `clippy::pedantic` 상시** — 초심자의 실수가 조용히 통과하지 않게. §8의 CI에 들어간다.

**뒤집히는 조건**: S0 완료가 언어 때문에 막히면 I1을 재론한다. 그때 바뀌는 것은 언어이지 §4~§8의 경계·검사 설계가 아니다 — 그 설계는 언어 중립으로 적혀 있다.

### 3.2 I3 — 저장은 2층이고 백엔드는 포트 뒤에 있다

소유자의 방향은 그래프 DB(Neo4j 계열)이고 `DESIGN §12.1`의 초기 제안은 단일 파일 임베디드 DB였다. **둘은 화해 가능하며 화해의 형태는 이미 설계 안에 있다** — D2("투영은 캐시이며 재구축 가능")와 `DESIGN §12.5`("질의 언어는 표면 계약이 아니다"). 저장 기술은 교체 가능한 자리이므로 **고르는 것이 아니라 포트를 긋고 실측으로 정한다.**

```
                 ┌─ 추출 캐시 (1층) ─────────────────────────────┐
git (SoT)  ──►   │ 키: (blob 해시, extractor_version)            │
                 │ 값: 파일 단위 부분 그래프 (직렬화)             │  ← 백엔드 무관·항상 존재
                 └───────────────────────────────────────────────┘
                                    │  질의 시점 스티칭 (Snapshot 단위)
                                    ▼
                 ┌─ 질의 투영 (2층) ────────────────────────────┐
                 │ trait GraphStore  ← 포트                      │
                 │   ├ embedded  (기본)                          │
                 │   ├ sqlite    (대조군·최소 설치)              │
                 │   └ server    (옵션 — Neo4j 등)               │
                 └───────────────────────────────────────────────┘
```

**1층이 있어야 하는 이유는 성능이 아니라 계약이다.** `DESIGN §12.3`의 지연 평가(임의 과거 커밋을 변경 파일 수에 비례하는 비용으로 여는 것)는 콘텐츠 주소 캐시 위에서만 성립하고, 그것은 어떤 그래프 DB의 기능도 아니다. R10이 관측한 stack-graphs의 구조(파일 단위 사전계산 + 질의 시점 스티칭 + 증분)와 같은 형태이며, **2층을 통째로 버리고 다시 만들어도 1층이 있으면 재구축이 파일 재파싱 없이 끝난다** — P5가 실물이 되는 지점.

| 백엔드 | 자리 | 대가 |
|---|---|---|
| **임베디드 그래프** (기본) | 그래프 질의를 그래프 어휘로 쓰면서 P12를 지킨다. Cypher 계열 방언을 쓰면 소유자의 질의 경험이 그대로 산다 | §3.4의 지형 변동 위험 — 이 부류는 2025~2026에 소유권이 한 번 뒤집혔다 |
| **SQLite 재귀 CTE** (대조) | 설치 비용의 하한이자 백엔드 추상화가 새지 않았는지의 검사. `DESIGN §12.1`의 원안 | 경로 질의가 깊어질수록 표현이 나빠진다. 그 지점이 S1의 판정 대상 |
| **서버 그래프 DB** (옵션) | 팀 공유·대규모·기존 Neo4j 자산 활용. `DESIGN §12.1`이 이미 "전용 그래프 엔진을 투영으로 추가"로 열어둔 자리 | **기본이 될 수 없다** — 상주 프로세스·별도 런타임은 P12와 정면 충돌하고, "그것이 없으면 코어가 답하지 못한다"가 되는 순간 P7도 함께 깨진다 |

**포트가 지켜야 하는 규칙 셋**(S1의 백엔드 대조가 검사한다):

1. **표면에 새지 않는다.** 명명된 질의(§6)의 이름·인자·응답 스키마는 백엔드와 무관하다. Cypher 문자열이 `pal-query` 밖으로 나가면 그 자체가 위반이다(`DESIGN §12.5`).
2. **같은 질의 집합이 두 백엔드에서 같은 답을 낸다.** 골든 테스트가 백엔드별로 갈리면 그것은 추상화 실패이고 P5가 거짓이 된다.
3. **2층 삭제 후 1층만으로 완전 재구축된다.** CI에서 상시 검사(§8.1-5).

**백엔드는 성능만으로 고르지 않는다.** 평가 축은 넷이며 넷째(개념·관계·제약의 표현력)는 온톨로지 방향이 세운 것이다 — §3.5.

> **이 결정은 `DESIGN §12.1` 저장소 행을 갱신해야 한다** — 원안이 "단일 파일 임베디드 DB"였고 이 계획은 "포트 + 세 백엔드, 기본은 임베디드 그래프"로 바꾼다. §13에 갱신 필요 항목으로 올린다.

### 3.5 I15 — 온톨로지: 지금 만들지 않되 지금 자리를 비워 둔다 (U10)

지시 원문과 조항별 판정은 [2026-08-04 지시 문서](instructions/2026-08-04-owner-direction.md)에 있고 여기는 결과만 옮긴다.

**먼저 이것이 새 방향이 아님을 확인한다.** 백서의 제목이 *"코드를 근거로 삼는 프로젝트 온톨로지와 그 위의 에이전트"*이고, 백서 §2.1은 palimpsest를 *"설치된 그 프로젝트의 온톨로지를 만드는 도구"*로, 백서 §3은 *"palimpsest의 온톨로지는 두 층으로 나뉜다"*로 규정한다. 백서 §7은 결정→코드→여정→가치를 두고 *"각 링크가 온톨로지의 엣지다"*라고 적는다.

> **관측: `DESIGN.md`에 "온톨로지"라는 낱말이 한 번도 나오지 않는다. 이 계획서도 §3.5 이전까지 그랬다.**

낱말이 없는 것 자체는 결함이 아니다 — 설계는 그것을 노드·엣지·좌표·출처로 구체화했고 이름 없이도 만들고 있는 것이 그것이다. **결함은 낱말과 함께 빠진 하나에 있다.**

#### 무엇이 실제로 빠졌는가 — 개념 노드의 자리

`DESIGN §1.1`이 열거한 타입 전부는 둘 중 하나다 — **코드 좌표를 갖는 것**(심볼·엣지·`UnresolvedRef`·대장) 또는 **코드 좌표에 결박되는 것**(라벨·결정·계획·잔여·축소·합성물). **프로젝트의 도메인 개념 자체가 노드가 되는 자리는 없다.** "주문", "정산 경계", "멱등 처리 대상" 같은 것은 라벨의 대상으로만 존재하고 그 자신은 존재하지 않는다.

그리고 이 공백은 이미 문서화되어 있다 — [`evidence-map.md §3`](evidence-map.md)의 유일한 미답 항목: *"코어가 팩 스키마에서 어떤 원시 개념까지 표현 가능하게 할 것인가 — 팩이 자유 형식이면 코어가 그 위에서 아무 판정도 못 하고, 코어가 어휘를 고정하면 백서 §12-3을 소진한 의미가 사라진다."*

> **온톨로지는 그 딜레마의 제3의 답 후보다: 코어가 *어휘*를 고정하지 않고 *메타 어휘*를 고정한다.** 코어는 "개념·관계·제약을 어떻게 선언하는가"의 문법만 알고, 어떤 개념이 있는지는 프로젝트가 정한다. D17이 규칙에 대해 한 것을 개념에 대해 하는 것이며 P7을 깨지 않는 유일한 형태다.

#### 온톨로지가 요구하는 넷과 설계의 대응 상태

| 요구 | 설계의 현재 상태 | 처분 |
|---|---|---|
| **개념이 1급 노드다** | **없다.** `DESIGN §1.1`에 자리가 없다 | 신설 필요. 개념은 코드 좌표를 갖지 않으므로 **P3 위반이 하나 는다** — `DESIGN §0.7`의 기획이 만든 것과 정확히 같은 형태이고 처분도 같다: **2단 결박**(개념은 코드 좌표에, 결박 못 하면 `pending`) |
| **개념↔코드 결박과 낡음** | **이미 있다.** 결박 5상태·반경·`stale` 전파가 그대로 걸린다 | 새 장치 불필요 |
| **규칙 추론**(포함관계·전이·분류) | **이미 자리가 있다.** `asserted_via = rule(규칙 좌표)`(`DESIGN §3.2`)가 규칙 파생 사실의 배정을 이미 정했다 | **출처 축을 늘리지 않는다.** 추론 산물은 `asserted`이며 규칙 좌표에 결박된다. 공리가 틀리면 파생 전부가 `stale`이 되고 파급 범위가 계산된다 — `DESIGN §3.2`가 라벨 300개에 대해 적은 것과 같다 |
| **어휘의 소유권** | 백서 §12-3을 D17이 "프로젝트 정의"로 닫았고, 남은 미답이 위의 메타 어휘 질문 | 팩 스키마를 **메타 어휘로** 설계한다(아래 4항) |

#### 지금 하는 것 — 되붙이는 비용이 0인 넷

지금 온톨로지 층을 만들지 않는다. 사실층 하한이 서기 전에 개념을 세우면 결박할 좌표가 없고, 그것은 `DESIGN §13`이 S9를 S1·S2 뒤에 둔 이유와 같다. **대신 나중에 못 붙이게 만드는 결정을 지금 하지 않는다.**

| # | 조치 | 지금 안 하면 |
|---|---|---|
| 1 | **비코드 개체 식별자 체계를 S0에서 정한다.** `Coord`는 코드 전용이고(`repo_id, commit_sha, extractor_version, symbol_id`), 결정·계획·잔여·라벨·개념은 자기 식별자가 필요한데 **설계에 그 규정이 없다** | S2 이후 전 의도층 개체의 마이그레이션. 온톨로지가 붙는 시점에는 이미 늦다 |
| 2 | **노드·엣지 타입을 닫힌 열거로 하드코딩하지 않는다.** 코어가 아는 것은 타입의 *구조*이고 타입의 *목록*은 데이터다 | 개념 노드를 추가할 때마다 코어 개정. P7이 프로젝트 어휘 쪽에서 깨진다 |
| 3 | **팩 스키마를 메타 어휘로 설계한다**(S9) — 규칙만이 아니라 개념·관계·제약을 선언할 수 있는 문법 | 팩이 규칙 전용으로 굳으면 개념 층이 팩 밖에 따로 서고 두 어휘 체계가 생긴다 |
| 4 | **백엔드 선택 기준에 표현력 축을 추가한다**(§3.2·S1) | S1에서 성능만 보고 고르면 온톨로지가 붙는 시점에 백엔드를 다시 고른다 |

#### 그래프 DB 선택에 대해 온톨로지가 바꾸는 것 — 정직하게

**온톨로지는 그래프 저장의 필요성을 강화하지만 특정 제품을 정당화하지는 않는다.** 그리고 방향이 조금 다르다.

- **속성 그래프**(Cypher 계열)는 인스턴스 그래프와 경로 질의에 강하고 **클래스 계층·공리·제약의 표현은 관례로 흉내 낸다.**
- **RDF/OWL 계열**은 그 반대다 — 개념 체계·추론·상호운용에 강하고 대신 이 설계가 매 질의에 요구하는 것들(`Envelope`·등급·출처)을 얹는 비용이 다르다.

그러므로 **"온톨로지 → 그래프 DB → 특정 제품"의 사슬은 자동으로 이어지지 않으며**, I3의 포트 분리가 이 사실 때문에 더 필요해진다. S1의 백엔드 대조에 축을 하나 더 세운다.

> **백엔드 평가 축 4** — ① 규모 목표에서의 경로 질의 성능 ② 설치 비용(P12) ③ 표면 누출 없음(§3.2의 규칙 셋) ④ **개념·관계·제약과 규칙 파생의 표현력**(I15)

넷째 축의 판정은 S1에서 잠정, **S9(팩이 메타 어휘가 되는 시점)에서 본판정**한다. 그 사이에 축이 뒤집히면 바뀌는 것은 백엔드이지 포트도 데이터 모델도 아니다 — 그것이 포트를 그은 이유다.

#### 이것이 만드는 새 위험

**온톨로지 저작은 사슬 A의 세 번째 뿌리가 될 수 있다.** `DESIGN §15.1`의 사슬 A는 뿌리 둘(승인 노동 §11.4, 팩 저작 §7.3)에 잎 여섯이 매달려 있다고 적는다. 개념 체계를 사람이 저작해야 한다면 그것은 팩 저작보다 **더 앞선 노동**이고 같은 방식으로 무너진다 — 개념이 없으면 개념 결박이 없고, 없으면 온톨로지 질의가 전부 공백이다. **그러므로 S-1의 측정에 항목이 하나 는다**(T-S-1-7). 코드 없이 검사할 수 있고, 검사하지 않으면 가장 비싼 층을 가장 늦게 검사하게 된다.

**의존 방향 규칙 — CI가 검사한다(§8.1-1)**

| 규칙 | 무엇을 막는가 |
|---|---|
| `pal-core`는 워크스페이스 내 어떤 크레이트에도 의존하지 않는다 | 도메인이 저장·전송·호스트 개념을 내부화하는 것 |
| 어떤 크레이트도 `pal-cli`·`pal-mcp`에 의존하지 않는다 | 소비자 어휘의 역류(`DESIGN §12.2`) |
| `pal-core`는 백엔드 크레이트·tree-sitter에 의존하지 않는다 | 파서·저장 기술이 좌표계에 새는 것 |
| `pal-intake`는 `pal-extract`에 의존하지 않는다 | `observed`가 `extracted` 경로를 재사용해 배정이 흐려지는 것(`DESIGN §3` 배정 규칙 2) |

**어휘 금지 목록 — `pal-core` 소스에 나타나면 CI 실패(§8.1-2)**

- 호스트: `claude`, `mcp`, `tool_call`, `session`, `prompt`(단 `produced_by.prompt_hash`는 허용 목록)
- 거버넌스: `gate`, `risk_level`, `block`, `approve_and_merge`, `completion`, `change_contract` — `DESIGN §12.6`이 그은 경계의 실물
- 저장 기술: `cypher`, `sql`, `table`, `node_label` — `DESIGN §12.5`

허용 목록은 `xtask/vocab.toml`에 있고 추가는 커밋으로 남는다. **허용 목록에 줄이 늘어나는 것 자체가 관측 대상이다** — 그것이 드리프트의 형태다.

## 5. I4·I5 — 설계 제약을 타입으로 옮긴다

지시 문서 §U8-c는 형식 제약 다섯을 *"하나라도 완화하면 설계의 뼈대가 무너지는 것"*으로 적었다. 다섯 전부가 **런타임 검증이 아니라 타입 구성으로** 표현된다.

| 설계 제약 | 자리 | 구현 형태 | 위반이 잡히는 시점 |
|---|---|---|---|
| `evidence_refs`가 비면 저장하지 않는다 | `DESIGN §9.1` | `Synthesis::new(body, NonEmpty<Coord>, …)` — 빈 벡터로는 값을 만들 수 없다 | 컴파일 |
| 선택 필드를 두지 않는다 | `DESIGN §3.1` | 도메인 타입에 `Option<T>` 금지. 위반은 `xtask lint-schema`가 AST로 검출. 예외(기계가 채우며 못 채우면 쓰기 실패)는 `#[machine_filled]` 표식 + 허용 목록 | CI |
| 출처 필드는 불변, 승격은 새 노드 | `DESIGN §3.1` | `Provenance`는 생성자에서만. setter 없음. `Inferred::promote(self, approval) -> Asserted`가 **원본을 소비하지 않고** 새 노드와 `promoted_by` 엣지를 반환 | 컴파일 |
| 판정은 `clean`을 내지 않는다 | `DESIGN §8` | `enum Judgment { Finding, Residual, OutOfScope }` — 넷째 변형이 없고 `#[non_exhaustive]`도 아니다. "위반 없음"은 빈 `Vec<Finding>` + 비지 않은 `Vec<Residual>`로만 표현된다 | 컴파일 |
| 조용한 절단 금지 | `DESIGN §5.1`·§12.5 | `ViewModel::new(..., Elision)` 필수. 절단이 없으면 `Elision::none()`도 **명시적으로** 만들어야 한다 | 컴파일 |

### 5.1 좌표와 정체성 — 타입 수준의 두 구별

```rust
// DESIGN §2.1 — span은 Coord에 없다. 라인이 필요한 자리는 별도 타입.
pub struct Coord { repo: RepoId, commit: CommitSha, extractor: ExtractorVersion, symbol: SymbolId }
pub struct Site  { coord: Coord, span: Span }          // span 필수

// DESIGN §2.2 — identity_grade는 좌표와 함께 실린다. 없는 등급이 타입으로 구별된다.
pub enum SymbolIdentity { Exact(SymbolId), Ordinal(SymbolId), None }   // L0은 SymbolId를 못 만든다
```

`SymbolIdentity::None`이 값으로 존재하므로 **L0 언어에서 결박을 시도하는 코드는 컴파일되지 않는다** — 사슬 C(`DESIGN §15.1`)가 "그 언어에서 조용히 죽는" 것을 막는 형태다.

### 5.2 I5 — Envelope

```rust
pub struct Envelope<T> {
    answer: T,
    snapshot: Snapshot,
    projection: ProjectionFreshness,   // stale-projection 여부 (DESIGN §2.3)
    coverage: Coverage,                // 미해소 참조 수·범위 밖 파일 수·경유 언어 등급 (DESIGN §4.2)
    ledger: LedgerRef,
    elision: Elision,                  // 예산에 걸려 잘린 것 (DESIGN §5.1)
}
```

**모든 명명된 질의의 반환 타입이 `Envelope<_>`다.** 첨부를 빠뜨린 응답 경로가 타입 수준에 존재하지 않으므로 `DESIGN §4.2`가 규율에서 벗어난다. `pal-cli`·`pal-mcp`는 `Envelope`를 벗길 수 없고 직렬화만 한다.

## 7. 데이터 모델 → 물리 배치

`DESIGN §1.1`의 타입 전부가 어디에 앉는지. **1층(추출 캐시)에 앉는 것과 2층(질의 투영)에 앉는 것의 구별이 D2의 실물이다.**

| 설계 타입 | 1층(콘텐츠 주소 캐시) | 2층(그래프 투영) | 비고 |
|---|---|---|---|
| `Coord`·`Site`·`Snapshot` | 파일 부분 그래프의 키 | 노드 속성 | `span`은 `Site`에서만 |
| 심볼(C1) | ✅ 파일 단위로 완결 | `(:Symbol)` + `CONTAINS` | 재구축 가능 |
| 엣지(C2) + 해소 등급 | ✅ 파일 내 참조까지 | `REFERENCES {grade, provenance}` | 파일 간 해소는 스티칭 시점 |
| `candidate` 후보 집합 | ✅ | 엣지 1개 + 후보 배열 속성 | 엣지 N개가 아니다(`DESIGN §5.1`) |
| `UnresolvedRef` | ✅ | `(:UnresolvedRef)` + `AT` → `Site` | 해소돼도 지우지 않는다 |
| 대장 항목 | ✅ 파일 상태 | `(:LedgerEntry)` per Snapshot | 매 Snapshot 재계산 |
| `Label`(규약층) | ❌ — `asserted` | `(:Label)` + `BOUND_TO` + `DERIVED_FROM(rule)` | `asserted_via` 필수 |
| 결박·5상태·반경 | ❌ | `BOUND_TO {radius, state, watch_set}` | 상태는 계산값, 감시 집합은 저장값 |
| `Finding`·`Residual`·`OutOfScope` | ❌ | `(:Judgment)` 서브레이블 + 결박 엣지 | `Residual`은 목록이 아니라 결박물(`DESIGN §8.1`) |
| `ScopeReduction` | ❌ | `(:ScopeReduction)` + 사라진 좌표 결박 | 판정 산출에 동반 필수 |
| `Synthesis`·`Narration` | ❌ — `inferred` | `(:Synthesis)` + `EVIDENCE_OF` → `Coord[]` | `evidence_refs` 없으면 애초에 생성 불가(§5) |
| `ViewModel` | ❌ | 저장하지 않는다 — 질의 산출 | `elision`은 응답에 실린다 |
| `Plan`·`Deviation`·`Briefing` | ❌ | `(:Intent)` 계열 | `pending` 결박 허용 |
| 관측(`observed`) | ❌ | `(:Observation)` + 환경 지문·조달 절차 기록 | 보존 정책 M(`DESIGN §12.4`) |
| 질의 로그 | ❌ | 별도 append-only 테이블 | 커버리지 계산의 입력 |

> **1층에 앉는 것은 전부 `extracted`다.** 이 대응이 우연이 아니라 배정 규칙 1(`(커밋, 추출기 버전)`만으로 재현)의 물리적 표현이며, `observed`·`asserted`·`inferred`가 1층에 앉을 수 없다는 것이 **캐시 삭제 후 재구축 시 무엇이 사라지면 안 되는지**를 정한다(§8.1-5의 검사).

### 8.2 I11 — 판정 오라클 셋

## 10. ADR 발행 계획

`DESIGN §16`은 26건의 ADR 후보를 남겼다. **ADR은 슬라이스 착수 시점이 아니라 종료 시점에 발행한다** — 착수 시점의 ADR은 결정이 아니라 계획의 복사본이고, 그것이 이 저장소에서 이미 두 번 일어난 이중화다.

## 11. R8 기준선의 사전 등록 (S-1의 핵심 산출)

`DESIGN §13`은 R8 기준선의 규정 여섯(대조군 1·2, 과제, 판정, n, 기권)을 이미 정했다. 이 절은 **그 규정을 어느 파일에 어떤 형태로 고정하는가**만 정한다.

```
corpus/
├── manifest.toml        # 코퍼스 — 저장소·커밋·언어 구성·규모
├── tasks/               # 과제 5건 이상. 각 과제: 질문, 기대 산출의 형태, 채점 절차
├── arms.toml            # 대조군 정의 — ① 문서 한 장 ② 기성 그래프 MCP 도구 ③ (S6·S7·S11) 기존 정적 분석 도구
└── criteria.toml        # 성공 기준 — 슬라이스별, 사전 등록 시점 커밋 해시가 곧 등록 증거
```

| 규정 | 이 계획의 집행 |
|---|---|
| **사후에 과제를 고르지 않는다** | `corpus/`의 커밋 시점이 S-1이고, 슬라이스 게이트 판정은 그 커밋을 참조한다. **과제를 슬라이스 진행 중에 바꾸면 그것이 `DESIGN §10`이 정의한 게이트 오염이며 이 설계 자신에게 일어나는 것이다** |
| **n ≥ 5** | 6/6 대 5/6 같은 판정을 반복하지 않는다(R8 자신이 사실상 n=1이었다) |
| **기권을 명시한다** | S9처럼 대조가 성립하지 않으면 `docs/gates/S9.md`에 "대조 불가"를 적는다. 생략하고 통과로 처리하는 것이 이 계획의 가장 조용한 실패 경로다 |
| **코퍼스 후보** | boxwood(Kotlin/Spring/Exposed + Svelte — R1·S4의 판정 대상) · ditto(TypeScript — R5·R6·S2·S3의 판정 대상) · palimpsest 자신(I12) · 규모 목표 검사용 대형 OSS 1건(S-1에서 선정) |

## 12. 이 계획의 잔여 — 설계 잔여와 구별되는 것
