# 도메인 문서

엔지니어링 스킬이 이 저장소를 탐색할 때 도메인 문서를 어떻게 읽어야 하는가.

## 탐색 전에 읽을 것

- 저장소 루트의 **`CONTEXT.md`** — 용어집. 아직 없다.
- **`docs/adr/`** — 착수할 영역에 걸리는 ADR. **열 있다**(F22 종료 시 둘 · F01 종료 시 둘 · F02 종료 시 둘 · F03 종료 시 둘 · **F05 종료 시 둘**). F04 는 발행하지 않았다 — 판단 셋이 전부 기존 ADR 의 **적용**이었다.

`CONTEXT.md` 가 없으면 **조용히 진행한다.** 부재를 지적하지 말고, 미리 만들자고 제안하지도 말 것. `/domain-modeling`(‌`/grill-with-docs`·`/improve-codebase-architecture`를 통해 도달)이 용어나 결정이 실제로 확정될 때 게으르게 만든다.

**이 저장소에서 ADR은 기능 착수가 아니라 종료 시점에 발행한다** ([docs/plan/README.md §7.6](../plan/README.md)). 착수 시점의 ADR은 결정이 아니라 계획의 복사본이다.

## 구조

단일 컨텍스트다. 모노레포가 아니다.

```
/
├── CONTEXT.md        ← 용어집 (아직 없음)
├── docs/
│   ├── adr/          ← 결정 기록 (기능 종료 시 발행. 지금 0001~0006)
│   ├── DESIGN.md     ← 설계 결정과 그 근거
│   ├── evidence-map.md
│   ├── plan/         ← 무엇을 어느 순서로 만드는가
│   └── research/     ← 관측 기록 (R번호)
└── WHITEPAPER.md
```

## 이 저장소의 문서 분업 — 같은 것을 두 곳에 적지 않는다

[계획 §7.4](../plan/README.md)가 정한 규칙이다. 산출물을 쓰기 전에 어디에 속하는지 판정할 것.

| 무엇 | 어디 |
|---|---|
| 결정 | `docs/DESIGN.md` |
| 근거·관측 | `docs/evidence-map.md` · `docs/research/` |
| 실행 순서와 상태 | GitHub Issues (`docs/plan/`은 각 기능을 *어떻게* 만드는가) |
| 용어의 정의 | `CONTEXT.md` |
| 수치 합격선 | `corpus/criteria.toml` (단일 진실) |

## 용어집의 어휘를 쓸 것

산출물이 도메인 개념을 지칭할 때(이슈 제목, 가설, 테스트 이름) `CONTEXT.md`에 정의된 용어를 쓴다. 용어집이 명시적으로 피하는 동의어로 흘러가지 말 것.

필요한 개념이 용어집에 없다면 그것 자체가 신호다 — 프로젝트가 쓰지 않는 말을 지어내고 있거나(재고할 것), 진짜 공백이거나(`/domain-modeling`을 위해 기록할 것).

## ADR 충돌은 드러낼 것

산출물이 기존 ADR과 모순되면 조용히 덮어쓰지 말고 명시할 것:

> _ADR-0007과 모순 — 그러나 다시 열어 볼 값이 있다. 왜냐하면…_
