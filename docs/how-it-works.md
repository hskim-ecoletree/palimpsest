# palimpsest는 실제로 어떻게 동작하는가

> **이 문서의 지위**
>
> - **성격**: 안내 문서. 완성된 palimpsest가 남의 프로젝트에 설치됐을 때 **무슨 일이 일어나는지**를 장면으로 보여준다.
> - **왜 있나**: [백서](../WHITEPAPER.md)는 *왜 이래야 하는가*를 논증하고, [설계](DESIGN.md)는 *어떤 구조인가*를 정하고, [계획](plan/README.md)은 *무엇을 어느 순서로 만드는가*를 센다. **셋 다 제품이 실제로 어떤 모습인지는 보여주지 않는다.** 이 문서가 그 자리를 메운다.
> - **권위 아님**: 여기 나오는 출력 예시는 **아직 존재하지 않는 것의 스케치**다. 구현과 다르면 구현이 맞다. 계약의 권위는 백서에, 구조의 권위는 설계에 있다.
> - **읽는 법**: 앞에서 뒤로 시간순이다. §1부터 §8까지가 한 프로젝트의 이야기이고, §9~§11이 그 이야기를 백서의 용어로 되짚는다.
> - **⚠️ 이 문서는 2026-08-10 지시를 아직 담지 않았다.** [설계](DESIGN.md)와 [계획](plan/README.md)이 먼저 갱신됐고 이 이야기는 그 전 판이다. 어긋나는 곳 넷을 아래에 적어 두고, 개정은 별도 커밋으로 한다 — **어긋난 채로 조용히 두는 것이 이 저장소에서 이미 두 번 일어난 drift다.**
>
> | 이 문서가 아직 안 담은 것 | 어디에 |
> |---|---|
> | 채점 기준이 산출에서 **결과**로 올라간 것 | [DESIGN §0.8](DESIGN.md) · [goals §0.1](plan/00-goals.md) |
> | 외부 엔진(SAST·린터) 조달이 **P1**이 된 것 — §5.3의 감사 장면이 라벨만으로 서 있다 | [F16](plan/features/F16-observation-intake.md) |

## 0. 한 문장으로

> **남의 프로젝트에 설치하면, 그 프로젝트의 코드에서 사실을 뽑아 그래프로 만들고, 사람이 쓴 결정·설계·계획을 그 코드 좌표에 못 박아, 코드를 만지려는 순간에 무엇이 걸려 있고 무엇이 낡았는지를 내놓아 — 그래서 다음 변경이 더 나아지게 하는 도구.**

파는 것은 그래프가 아니다. 코드 그래프는 이미 여럿 있다. 파는 것은 **"이 코드에 걸린 결정이 아직 유효한가"에 기계가 답한다**는 것이고, 그 답이 누군가 코드를 만지려는 **바로 그 순간에** 온다는 것이다.

**그리고 그것은 수단이다.** 목적은 그 답을 받은 사람과 에이전트가 **더 나은 코드를 쓰는 것**이고, 이 도구는 그것으로 채점된다([DESIGN §0.8](DESIGN.md)).

이 문서는 그 문장이 실제로 무슨 뜻인지를 하나의 프로젝트를 따라가며 보여준다.

---

## 1. 무대 — `luma`

가상의 회사에 `luma`라는 커머스 백엔드가 있다. 이 문서 내내 이 프로젝트를 따라간다.

| | |
|---|---|
| 스택 | TypeScript · NestJS · Postgres. 프론트엔드는 `luma-web` 저장소에 따로 있다 |
| 나이 | 4년 |
| 규모 | 파일 3,400개 · 심볼 2만여 개 |
| 팀 | 개발자 6명. **초기 설계자 2명은 퇴사했다** |
| 문서 | ADR 12건(마지막 작성이 2년 전) · Notion 위키 · README · 여기저기 흩어진 주석 |
| 에이전트 | 팀이 Claude Code를 쓴다. 코드의 상당량이 에이전트가 쓴 것이다 |

**이 프로젝트의 병은 흔한 것이다.** 코드는 돌아간다. 아무도 왜 그렇게 돌아가는지 전부 알지는 못한다. ADR 12건은 읽을 수 있지만 그것이 지금 코드에도 해당하는 이야기인지 아무도 모른다. 새 사람이 들어오면 "이건 원래 이래요"라는 말을 듣고, 그 말을 한 사람도 사실 이유는 모른다.

그리고 최근 6개월 사이 같은 종류의 사고가 세 번 났다. 세 번 다 **"고치면 안 되는 걸 몰라서 고쳤다"**는 형태였다.

## 2. 설치 — 첫 5분

### 2.1 설치하면 무슨 일이 일어나나

```
$ claude plugin install palimpsest
$ pal init

luma 를 살펴보는 중…
  파일 훑기        3,412개                          0.4초
  파싱             3,388개 (rayon 8 워커)           38초
  좌표 만들기      21,904 심볼
  인덱스           엣지 84,302개

완료. 41초.
.palimpsest/ 가 생겼습니다 (캐시 180MB · 인덱스 24MB)
```

**41초다.** 빌드하지 않기 때문이다. `npm install`도, 툴체인도, 환경변수도 필요 없다. blob 하나를 읽어 파싱하는 것이 전부이므로 **아무 커밋에서나 똑같이 돈다**. 3년 전 커밋으로 체크아웃해도 같은 41초가 아니라 **바뀐 파일 수만큼의 시간**이 든다. 파일 내용이 같으면 캐시가 그대로 맞기 때문이다.

이것이 백서가 "균일성"(횡단 요구 U)이라고 부른 것의 실물이다. 빌드에 기대는 도구는 정밀하지만 **어떤 커밋에서는 되고 어떤 커밋에서는 안 된다.** 그러면 "이 결정이 3년 전 그 커밋에도 유효했는가"라는 질문에 답할 수 없다.

### 2.2 첫 화면은 답이 아니라 **대장**이다

```
$ pal ledger

Snapshot  luma@8f3c21a  (워킹트리와 일치)
저장소    1 (선언됨)

파일      3,412
  parsed          3,388
  partial            11    회복 지점 기록됨
  unsupported         9    언어 인식됨(SQL 7 · Dockerfile 2), 추출기 없음
  unrecognized        0
  excluded            4    규칙: vendor(3) · oversize(1)
  binary/generated    0

언어      TypeScript   L2   identity: exact 21,180 · ordinal 724    3,388 파일
          SQL          L0   결박 불가                                  7 파일
                            ← 이 파일들에는 좌표가 없습니다

감지기    마지막 추출 8f3c21a · 이후 커밋 0개
```

**대부분의 도구는 이 화면을 보여주지 않는다.** 곧바로 "심볼 21,904개를 찾았습니다"라고 말한다. 그 말은 참이지만, 듣는 사람은 그것이 **전부**인지 **찾은 것뿐**인지 알 수 없다.

palimpsest의 첫 화면이 대장인 이유가 그것이다. 이 표는 이렇게 읽힌다:

- **`unsupported 9`** — SQL 파일 7개를 우리는 읽지 못한다. 그러니 SQL 안에서 일어나는 일은 앞으로 어떤 답에도 안 나온다. 그것이 "없다"가 아니라 **"안 봤다"**로 기록되어 있다.
- **`ordinal 724`** — 심볼 2만여 개 중 724개는 스코프 해소가 안 돼서 정체성이 선언 순서에 의존한다. 그 심볼들에 건 결박은 조금 덜 믿을 만하고, **그 사실이 각 답에 함께 실린다.**
- **`excluded 4 · 규칙 vendor(3) · oversize(1)`** — 제외된 파일에는 **왜 제외됐는지 규칙 ID가 붙는다.** 나중에 누군가 제외 규칙을 넓혀서 문제가 사라지면, 그것이 "해결됨"이 아니라 "범위 축소"로 잡힌다.

이 마지막 항목이 이 도구의 성격을 잘 보여준다. **범위를 줄여서 깨끗해지는 길을 막아둔 것이다.**

### 2.3 그런데 아직 아무 값도 없다

설치 직후 `touch`를 불러보면 이렇게 나온다.

```
$ pal touch OrderService.cancel

■ 이 좌표에 걸린 것 (0)
  아직 없습니다.
  미결박 서술물 12건이 대기 중입니다 → pal narrative unbound

■ 이 심볼이 하는 것
  호출자  9  (exact 7 · candidate 2)
  호출   14  (exact 11 · candidate 1 · 미해소 2)

■ 내가 모르는 것 (2)
  UnresolvedRef  PaymentGateway.refund   사유=동적 디스패치   cancel.ts:88
  UnresolvedRef  handler                 사유=문자열 기반     registry.ts:14

■ 판정
  (이 빌드에는 감사 능력이 없습니다 — F15 미구축)

■ 이 답의 근거
  parsed 3388/3412 · unresolved 2 · L0언어 1  ·  능력: 큐레이션·컨설팅
```

**사실층은 첫날에 선다. 의도층은 비어 있다.** 백서 §2.3이 "성숙 프로젝트의 콜드스타트"라고 부른 상태가 정확히 이것이다.

여기서 이 도구가 하지 **않는** 일이 하나 있다. 에이전트에게 git 이력을 읽혀서 "이 코드는 아마 멱등성 때문에 이렇게 짰을 것"이라고 채워 넣는 것. 그렇게 하면 첫인상은 훨씬 좋다. 화면이 그럴듯하게 찬다. 그리고 **그 순간부터 어디까지가 기록이고 어디부터가 지어낸 것인지 아무도 모르게 된다.** 백서는 이것을 "세탁"이라 부르고 금지한다.

대신 비어 있다고 말하고, **다음에 할 일을 알려준다** — 미결박 서술물 12건.

마지막 줄도 눈여겨볼 만하다. `판정` 자리가 **비어 있지 않고** "감사 능력이 없습니다"라고 적혀 있다. 이 빌드는 아직 감사(F15)를 만들지 않았다. 그때 `Finding 0`이라고 출력하면 그것은 "검사해 봤는데 문제 없음"으로 읽힌다. **없는 능력과 없는 문제는 다른 것이고, 그 둘이 같은 화면을 만들면 이 도구는 자기가 고발한 문제를 스스로 저지르는 것이다.**

## 3. 첫 주 — 의도층을 채운다

### 3.1 이미 있는 문서를 끌어온다

```
$ pal narrative intake docs/adr/ docs/design/

문서 14개에서 조각 63개를 읽었습니다.

  결박됨      31   강한 신호로 좌표가 잡혔습니다
  후보 있음   18   후보를 제시합니다. 승인이 필요합니다
  미결박      14   신호가 없습니다 → pal narrative unbound

승인 대기 18건 → pal approve
```

문서를 섹션 단위로 잘라서 각 조각이 **어느 코드에 대한 이야기인지**를 찾는 작업이다. 찾는 방법은 강한 신호부터 차례로 내려간다.

| 신호 | 예 | 처분 |
|---|---|---|
| 프론트매터에 좌표를 직접 씀 | `grounds: ["src/order/cancel.ts#OrderService.cancel"]` | **확정** |
| 코드 블록 안의 파일 경로 | `` `src/order/cancel.ts` `` | 강함 — 대장에 그 경로가 있으면 확정 |
| 인라인 코드가 심볼 인덱스에 유일 | `` `OrderService.cancel` `` | 강함 — 정확히 1건이면 확정 |
| 문서와 같은 커밋에서 바뀐 파일 | git 이력에서 계산 | 중간 — 후보로 제시 |
| 문서 경로가 가까움 | `docs/order/` ↔ `src/order/` | 약함 — 후보로만 |
| **본문 자연어가 비슷함** | "주문 취소 로직" | **쓰지 않는다** |

마지막 줄이 중요하다. "주문 취소 로직"이라는 말이 `cancelOrder`인지 `OrderCanceller`인지 `OrderService.cancel`인지 **기계는 모른다.** 임베딩으로 유사도를 재면 셋 다 비슷하게 나오고, 그중 하나를 골라 결박하면 **틀린 결박**이 생긴다.

그리고 틀린 결박은 없는 결박보다 나쁘다. 없으면 사람이 찾아보지만, 틀린 게 있으면 사람은 그것을 믿는다.

### 3.2 승인 — 사람이 하는 일

```
$ pal approve

[1/18]  ADR-0042 「취소는 멱등해야 한다」  §3 재시도 안전성

  본문 발췌:
    "결제 취소는 네트워크 재시도로 두 번 호출될 수 있다. 취소 처리는
     반드시 멱등 키를 확인하고 이미 취소된 주문은 조용히 성공을 반환한다."

  제안 좌표 (신호: 인라인 코드 스팬이 심볼 인덱스에 유일)
    → luma:src/order/cancel.ts#OrderService.cancel

  감시 반경  symbol (기본)  ·  callers 로 넓히려면 [w]

  [y] 승인   [n] 거부   [e] 좌표 수정   [w] 반경 넓히기   [s] 건너뛰기
```

이 한 화면이 이 제품에서 **가장 비싼 것**이다. 사람의 시간이 들어가는 유일한 자리이기 때문이다. 백서 §12-8이 "승인 자체가 노동이면 아무도 하지 않고 의도층은 영원히 비어 있게 된다"고 적어둔 그 지점이다.

그래서 이 화면에는 비용을 낮추는 장치가 붙어 있다.

- **일괄 승인** — 같은 문서에서 나온 조각들, 같은 규칙이 파생시킨 라벨들은 한 번에.
- **거부도 기록된다.** 이게 의외로 크다. 거부를 기록하지 않으면 다음 인입 때 **같은 것을 또 묻는다.** 재질문을 없애는 것이 승인 비용 절감의 대부분이다.
- **진척이 보인다.** `[1/18]`. 끝이 안 보이는 큐는 아무도 끝내지 않는다.

승인하면 무슨 일이 일어나냐면 — `inferred`(기계가 제안한 것)가 **`asserted`(사람이 확정한 것)로 바뀌는 게 아니다.** 새 `asserted` 노드가 생기고, 원래의 `inferred`는 "누구의 추론이었는지"를 달고 **그대로 남는다.**

왜 그렇게 하냐면 되돌릴 수 있어야 하기 때문이고, 나중에 "이거 누가 정한 거야?"에 답할 수 있어야 하기 때문이다.

### 3.3 붙지 않은 것들

```
$ pal narrative unbound

미결박 서술물 14건 — 좌표를 못 찾았습니다

  ADR-0007  「우리는 이벤트 소싱을 쓰지 않는다」          사유: 코드 참조 없음
  ADR-0011  「팀 간 API는 버전을 붙인다」                  사유: 조직 규칙, 코드 대상 아님
  DESIGN §2 「전체 아키텍처 개요」                          사유: 대상이 너무 넓음
  …

이 목록이 당신의 작업 목록입니다.
좌표를 직접 붙이려면:  pal bind <문서#섹션> <좌표>
```

**해소 실패를 실패로 남긴다.** 억지로 붙이지 않는다. 그리고 이 목록은 버려지는 게 아니라 **사람이 손으로 붙일 것들의 목록**이 된다.

여기 있는 것 중 일부는 영원히 안 붙는다. "우리는 이벤트 소싱을 쓰지 않는다"는 **어떤 코드도 가리키지 않는 결정**이다. 그건 정상이다. 그런 결정이 있다는 것과, 그것이 코드에 결박되지 않았다는 것 둘 다 기록되면 된다.

### 3.4 일주일 뒤의 상태

```
$ pal status

의도층
  결박된 항목    49    (asserted 49 · inferred 0 대기)
  미결박         14
  반경 분포      symbol 41 · callers 7 · files 1

사실층
  심볼        21,904
  엣지        84,302   exact 61,208 · scoped 14,377 · candidate 8,717
  미해소       9,431   ← pal refs unresolved --by reason 으로 지도를 봅니다

이 프로젝트에서 답할 수 있는 것: 큐레이션 · 컨설팅
```

## 4. 어느 화요일 오후 — **이 장면이 제품이다**

지수(개발자)가 Claude Code에게 말한다.

> "주문 취소할 때 재고 복원이 안 되는 버그가 있어. `OrderService.cancel` 고쳐줘."

에이전트가 코드를 읽기 **전에** `touch`를 부른다. (MCP 툴로 등록되어 있다.)

```
$ pal touch OrderService.cancel

■ 이 좌표에 걸린 것 (3)
  ADR-0042  취소는 멱등해야 한다              live      symbol 반경
  ADR-0031  정산 경계 밖으로 나가지 않는다     stale     ← 감시 집합 중
                                                          SettlementGate.check 가
                                                          12커밋 전 변경됨
  PLAN §4-2 재고 복원은 이번 범위 아님         pending   ← 예상 좌표에 아직 코드가 없음

■ 이 심볼이 하는 것
  writes  order.status · inventory.reserved · outbox.event
  호출자  9  (exact 7 · scoped 0 · candidate 2)

  UnresolvedRef  PaymentGateway.refund   사유=동적 디스패치   cancel.ts:88

```

에이전트는 코드를 고치기 전에 이걸 읽고 지수에게 말한다.

> 고치기 전에 세 가지를 짚고 가겠습니다.
>
> **① `PLAN §4-2`에 "재고 복원은 이번 범위 아님"이 있습니다.** 상태가 `pending`이니 아직 구현 안 된 계획 항목입니다. 지금 요청하신 게 정확히 그 범위인데, 계획을 바꾸시는 건지 아니면 계획을 못 보고 요청하신 건지 확인이 필요합니다.
>
> **② `ADR-0031`이 `stale`입니다.** "정산 경계 밖으로 나가지 않는다"는 결정인데, 12커밋 전에 `SettlementGate.check`가 바뀌면서 낡음 표시가 켜졌습니다. 이 함수는 `cancel`이 정산 쪽으로 나갈 때 통과해야 하는 관문입니다. 재고 복원을 넣으면 이 경계를 건드릴 수 있으니, 먼저 ADR-0031이 아직 유효한지 확인하는 게 좋겠습니다.
>
> **③ 이 심볼은 `outbox.event`를 씁니다.** 취소 이벤트가 나가고 있습니다. 재고 복원을 추가하면 이벤트 순서에 영향이 갈 수 있는데, `PaymentGateway.refund`가 동적 디스패치라서 **그쪽 경로는 제가 못 봤습니다.**

지수는 여기서 멈춘다. 계획을 다시 본다. ②가 진짜 문제였다는 걸 안다.

### 4.1 무슨 일이 일어난 것인가

**이 대화가 이 제품의 전부다.** 나머지 모든 기능은 이 3분을 만들기 위한 것이다.

주목할 부분이 넷 있다.

**① 지식이 사람을 찾아왔다.** 지수는 ADR-0031을 몰랐다. 그걸 쓴 사람은 2년 전에 퇴사했다. 검색해서 찾을 수도 있었지만, **검색하려면 그런 게 있다는 걸 먼저 알아야 한다.** 백서가 말하는 진짜 문제는 "지식이 없다"가 아니라 **"지식이 필요한 순간에 도달하지 않는다"**이다.

**② `stale`이 무엇 때문에 켜졌는지가 붙어 있다.** 그냥 "낡음"이면 지수는 ADR-0031을 열어 읽고 "음... 아직 맞는 것 같은데?" 하고 닫는다. **"`SettlementGate.check`가 12커밋 전에 변했다"**가 붙어 있으니 어디를 볼지 안다.

**③ `pending`과 `stale`이 구별된다.** "아직 안 만들었다"와 "만든 뒤 어긋났다"는 사람이 완전히 다르게 처리한다. 둘을 같은 색으로 칠하면 신생 프로젝트에서는 모든 게 빨간불이 되고, 그러면 아무도 안 본다.

**④ 모르는 걸 모른다고 했다.** `PaymentGateway.refund`는 동적 디스패치라 못 따라갔다. 그래서 판정이 `Residual 2`다. **`Finding 0`만 보고 "안전하다"고 결론 내릴 수 없게** 되어 있다.

### 4.2 이 도구는 "이상 없음"을 말하지 않는다

마지막 항목을 조금 더 파고들 만하다. 판정 결과의 타입에는 값이 셋뿐이다.

| | 뜻 | 반드시 달고 다니는 것 |
|---|---|---|
| **Finding** | 위반이 존재한다 | **반례 경로** — 어디를 보면 확인되는지 |
| **Residual** | 판정할 수 없었다 | 사유 · 술어 · 결박 좌표 · 언제 · 무엇이 있으면 풀리는지 |
| **OutOfScope** | 범위 밖이다 | 대장 참조 |

**넷째 값이 없다.** "위반 없음"이라는 값이 타입에 존재하지 않는다. "괜찮다"에 가장 가까운 표현은 **"Finding이 비었고 Residual이 비지 않았다"**이고, 이건 사람이 읽으면 자연히 "그래서 못 본 게 뭔데?"로 이어진다.

왜 이렇게까지 하냐면, 보안·정합성 맥락에서 최악의 실패는 틀린 경고가 아니라 **틀린 안심**이기 때문이다. 경고가 틀리면 사람이 확인하고 걷어낸다. 안심이 틀리면 **사람이 확인을 그만둔다.**

그리고 `Residual`은 목록에 적히고 잊히는 게 아니라 **좌표에 결박된다.** 즉 나중에 누가 그 코드를 `touch`하면 "여기 아직 판정 못 한 게 있다"가 **다시 사람 앞에 온다.**

그런데 그 도구가 말하지 않는 것이 있다. **나머지 17개를 어떻게 처리했는가.** 라벨이 없어서 검사 자체가 안 된 8개는 "통과"로 셌을까, 아니면 조용히 목록에서 빠졌을까? 동적 디스패치를 지나는 4개는? 대부분의 도구에서 이 둘은 **구별되지 않고 "이상 없음"에 합산된다.**

기준을 낮춰서 통과하는 길을 막는 것 — 백서 §12-5가 "게이트 오염"이라 부른 것에 대한 대응이다.

## 6. 반년 뒤 — 프로젝트가 움직인다

### 6.1 대개편이 일어난 날

팀이 `src/order/`를 `src/domain/order/`로 옮기는 대규모 리팩터링을 했다. 파일 214개가 움직였다.

```
$ pal status

⚠ 결박 47건이 orphaned 입니다 — 좌표가 사라졌습니다

  같은 내용의 새 심볼을 찾았습니다:
    43건  경로 접두어 변경 src/order/** → src/domain/order/**
           body_digest 일치 · 이름 일치 · 컨테이너 일치
    3건   개별 확인 필요 (내용도 함께 변경됨)
    1건   대응 심볼 없음 — 실제로 삭제된 것 같습니다

  pal rebind --batch    ← 43건을 한 번에 승인
  pal rebind --review   ← 3건을 하나씩
```

**정체성이 끊긴 걸 조용히 넘기지 않는다.** 새 심볼로 자동으로 옮겨 붙이면 편하지만, **의미가 다른 동일 코드에 잘못 붙을 수 있다.** 그래서 제안까지만 하고 승인을 받는다.

다만 승인 비용은 낮춰준다. 43건이 전부 같은 경로 접두어 변경이면 **승인 한 번**이다. 그리고 `body_digest`(코드 내용의 해시)가 같다는 게 제안의 근거라서 정확도가 높다.

여기서 `body_digest`가 두 번째 일을 한다. 처음 만든 이유는 **낡음 감지**였다 — 포매팅만 바뀐 커밋에 `stale`이 켜지면 안 되니까 주석·공백·변수명을 지운 정규형의 해시를 쓴다. 그런데 **파일이 옮겨졌을 때 "같은 코드"를 찾는 데도 같은 값이 쓰인다.**

### 6.2 포매터를 돌린 날

누군가 prettier 설정을 바꾸고 전체 파일에 돌렸다. 커밋 하나에 3,388개 파일이 바뀌었다.

```
$ pal status

의도층
  결박된 항목    112
  live           112
  stale            0     ← 포매팅 커밋이 낡음을 켜지 않았습니다
```

**아무 일도 일어나지 않는 것이 여기서의 정답이다.**

이게 안 되면 제품이 죽는다. 포매팅 커밋 하나에 결박 112개가 전부 `stale`로 켜지면, 사람은 그날부터 낡음 표시를 무시한다. 한 번 무시하기 시작하면 진짜 낡음도 같이 무시된다.

그래서 결박의 단위가 라인이 아니라 **정규화된 심볼**이다. 들여쓰기·줄바꿈·주석·따옴표 종류·후행 쉼표는 digest에서 지워진다. 지역 변수명도 (스코프 해소가 된 심볼에서만) 지워진다.

```
원본:    function add(a: number, b: number) { const s = a + b; return s }
정규형:  function add(#0: number, #1: number){const #2=#0+#1;return #2}
```

반대로 **지우지 않는 것**도 명확하다. 리터럴 값(`TIMEOUT = 30` → `300`은 의미 변경), 연산자, 호출 대상 이름, 필드·메서드 이름, 타입 주석. 이건 바뀌면 `stale`이 켜져야 하는 것들이다.

### 6.3 계획대로 됐는지 본다

```
$ pal plan deviation --plan docs/plans/2026-q3-refund.md

계획 항목 14건 · base 8f3c21a → head 4b91e07

  계획대로            9
  계획에 없던 변경     5
    src/domain/order/mapper.ts#OrderMapper.toDto      (리팩터링으로 보임)
    src/shared/logger.ts#configure                     (무관해 보임)
    …
  계획했으나 없는 변경  2
    §3-1 "환불 사유 코드 정규화"
    §5-2 "관리자 CLI에 인가 추가"       ← audit 의 Finding 1 과 같은 자리입니다
  판정 불가            3
    좌표로 해소되지 않은 계획 항목입니다
    §2 "성능 개선"  §4 "문서 정리"  §6 "모니터링 보강"
```

**"판정 불가"를 따로 세는 것이 이 화면의 요점이다.** "성능 개선"은 어떤 좌표도 가리키지 않는다. 그걸 "미구현"에 합산하면 이탈률이 거짓말이 된다. 못 잰 건 못 쟀다고 적는다.

그리고 `계획에 없던 변경 5`는 **나쁜 게 아니다.** 이 도구는 그것을 관측할 뿐 평가하지 않는다. 리팩터링은 원래 계획에 안 적힌다. 판정은 사람이 한다.

한 가지 더 — `§5-2 "관리자 CLI에 인가 추가"`가 계획됐는데 안 됐고, 그게 §5.3의 `Finding 1`과 같은 자리다. **의도층과 사실층이 같은 좌표에서 만나면 이런 것이 보인다.** 계획만 보면 "안 했네"이고, 감사만 보면 "구멍이 있네"인데, 둘을 겹치면 **"하기로 했는데 안 해서 구멍이 남았다"**가 된다.

## 7. 내부에서는 무슨 일이 — 얕게

여기까지가 사용자가 보는 것이다. 아래는 그게 어떻게 가능한지의 요약이다.

### 7.1 세 개의 저장소

```
git (코드의 진실)                       사람의 승인 (의도의 진실)
  │                                              │
  ▼                                              ▼
┌─ 1층 · 추출 캐시 ────────────┐   ┌─ 의도 저장소 ────────────────┐
│  파일 하나 = 캐시 항목 하나   │   │  결박 · 승인한 라벨 · 관측     │
│  키가 파일 내용의 해시라서    │   │  승인/거부 이력               │
│  내용이 같으면 항상 적중       │   │  ★ 재생 불가. 지우면 끝.      │
│  지워도 됨 (다시 파싱)        │   │  JSONL 로 내보내집니다        │
└──────────────────────────────┘   └──────────────────────────────┘
  │                                        │
  ▼        질의 시점에 이어 붙임             │ 읽기만
┌─ 2층 · 질의 인덱스 ────────────────────────┴──────┐
│  심볼 · 엣지 · 역방향 색인 · 결박 색인              │
│  지워도 됨 (1층 + 의도 저장소에서 다시 만듦)        │
└───────────────────────────────────────────────────┘
```

**왼쪽 둘의 성격이 정반대**라서 파일을 갈라 놓았다.

- 캐시와 인덱스는 언제든 지워도 된다. 지우면 다시 만든다. 원본이 git에 있다.
- **의도 저장소는 지우면 끝이다.** 사람이 몇 주에 걸쳐 승인한 것이 거기 있고, 코드에서도 git에서도 복원되지 않는다.

그래서 `pal cache prune`이 의도 저장소에 닿는 코드 경로가 **아예 없다.** 그리고 승인이 처음 생기는 순간 "내보내기 해 두세요"라고 권한다. 내보낸 JSONL을 저장소에 커밋해 두면 의도층의 이력이 코드의 이력과 같은 도구로 관리된다.

### 7.2 낡음은 어떻게 감지되나

결박 하나에 이런 게 들어 있다.

```
ADR-0042 → luma:src/order/cancel.ts#OrderService.cancel
  반경: symbol
  결박 시점의 감시 집합 digest: { OrderService.cancel: a3f2… }
```

코드가 바뀌면 재추출이 돌고, digest가 바뀐 심볼 목록이 나온다. 그 목록으로 **역방향 조회**를 해서 영향받는 결박만 다시 계산한다. 전체를 다시 세지 않는다.

**반경**은 "이 결정이 무엇을 감시하는가"다.

| 반경 | 감시하는 것 | 비용 |
|---|---|---|
| `symbol` (기본) | 그 심볼 하나 | 상수 |
| `callers` | + 직접 호출자들 | 조회 1회 |
| `closure(k)` | + k홉 의존 폐포 | 폐포 크기만큼 — **너무 크면 결박 저장 자체를 거부한다** |
| `files` | + 지정한 파일들 (설정·스키마·마이그레이션) | 나열한 만큼 |

**반경이 있는 이유는 이 문제가 원리적으로 안 닫히기 때문이다.** "이 결정과 관련 있는 코드 전부"는 계산할 수 없다. 좌표 바깥이 변해서 결정이 무효가 돼도 `live`로 남는 경우가 반드시 있다.

그래서 닫는 대신 **선언한다.** `"이 결정은 symbol 반경에서 live"`는 `"이 결정은 유효하다"`와 다른 문장이고, 그 차이가 화면에 남는다. 해결이 아니라 정직이다 — 하지만 숨기는 것보다는 낫다.

### 7.3 못 푼 참조가 로드맵이 된다

```
$ pal refs unresolved --by reason

문자열 기반      4,102   ← 라우트 레지스트리 패턴.
                            프레임워크 인식기를 만들면 대부분 해소됩니다
동적 디스패치    2,871   ← 실행 관측의 1순위 표적
정의 없음        1,560   ← 그중 890건이 DI 컨테이너. 팩 규칙 후보
후보 과다          672   ← 수신자 타입 추론이 있으면 줄어듭니다
언어 등급 미달     226   ← SQL 파일. 추출기 추가 또는 표준 인덱스 수용
```

못 푼 것을 조용히 버리지 않고 **노드로 만들어 두니까**, 그것들이 저절로 이런 표가 된다. **다음에 무엇을 만들지를 사람이 감으로 정하지 않는다. 밀도가 정한다.**

그리고 이 표는 두 번째 일도 한다. 실행 관측(트레이스·DI 덤프·SCIP 인덱스)을 받아들일 때, **전수로 돌릴 필요가 없다.** 이 지도를 따라 좁게 조달하면 된다. "어디서 한 번 돌리면 가장 많이 밝혀지는가"가 이미 계산되어 있으니까.

### 7.4 실행이 필요한 것은 이렇게 들어온다

palimpsest는 **대상 프로젝트를 실행하지 않는다.** 툴체인도 비밀도 없고, 남의 머신에서 임의의 코드를 돌리는 건 신뢰 문제이기도 하다.

대신 **수용 창구**를 연다.

```
$ pal observation intake --kind call-trace --file trace.json \
    --procedure "npm test 실행, OTel 수집기로 캡처" \
    --env "node 20.11 / linux-x64 / deps-lock a3f2…"

수용됨. 출처: observed
  미해소 참조 87건이 해소됐습니다 (동적 디스패치 61 · 문자열 기반 26)
  기존 정적 엣지와 어긋나는 것: 2건 → pal observation conflicts

⚠ 이 관측은 좌표 87개에 결박됩니다.
   그중 하나라도 코드가 바뀌면 stale-observation 이 되고,
   그때부터 이 관측에 기대던 판정은 Residual 로 떨어집니다.
```

누가 이걸 만들었는지는 **묻지 않는다.** Claude Code가 돌렸든, CI가 돌렸든, 사람이 로그를 붙여넣었든 출처 배정은 똑같이 `observed`다. 대신 **어떤 절차로 얻었는지는 반드시 적어야 한다** — 그게 없으면 값을 만들 수조차 없다.

이 구분이 "호스트를 통해 실행에 닿는다"가 "호스트에 의존한다"로 미끄러지는 걸 막는 유일한 장치다.

그리고 마지막 경고가 중요하다. **관측은 네 가지 출처 중 가장 빨리 낡는다.** 코드는 바뀌면 다시 파싱되지만, 3주 전 트레이스는 그대로 남아 있다. 낡은 관측이 계속 판정에 쓰이면 **낡은 서술이 거짓 신호가 되는 문제가 사실층 안에서 재생산된다.** 그래서 자동으로 배제하고, 대신 "여기 한 번 더 돌리면 회복됩니다"라는 큐에 넣는다.

## 8. 그런데 P1까지만 만들면?

계획은 P1(기능 12개)에서 멈출 수 있게 짜여 있다. 그 상태에서도 제품이다 — **큐레이션과 컨설팅**이 선다. 위 이야기 중 §3·§4·§5.1·§6이 그대로 돌아간다.

없는 것은 감사(§5.3)와 효과 집합(`writes` 줄)과 진입점 목록(§5.2)이다. 그때 화면은 이렇게 된다.

```
■ 이 심볼이 하는 것
  호출자  9  (exact 7 · candidate 2)
  호출   14  (exact 11 · candidate 1 · 미해소 2)
  (효과 집합 없음 — F13 미구축)

■ 판정
  (이 빌드에는 감사 능력이 없습니다 — F15 미구축)

■ 이 답의 근거
  … · 능력: 큐레이션 · 컨설팅   /   미구축: 감사 · 효과 · 진입점
```

**빈 자리가 "이상 없음"으로 보이지 않게 하는 것**이 이 설계에서 제일 신경 쓴 부분 중 하나다. 미완성 제품이 완성된 척하는 가장 흔한 방식이 빈 목록을 성공으로 보여주는 것이다.

## 9. 백서의 여섯 산출이 이 이야기의 어디였나

백서 §8이 여섯 가지를 열거한다. 이 문서의 장면과 대응시키면 이렇다.

| 산출 | 질문 | 이 문서에서 | 언제 켜지나 |
|---|---|---|---|
| **큐레이션** | "왜 이렇게 되어 있나 / 이게 아직 맞나" | §4 화요일 오후 | **P1 — 첫 번째 목표.** 대체재가 없다 |
| **컨설팅** | "여기 바꾸면 뭐가 깨지나" | §5.1 브리핑 | **P1.** 같은 장치 위에 서므로 거의 공짜 |
| **온보딩** | "이 기능은 어디서 시작해 어디로 흐르나" | §5.2 환불 흐름 | P2 — 진입점 인식기가 자라야 한다 |
| **감사** | "이 흐름에 구멍이 있나" | §5.3 인가 검사 | P2 — **가장 비싼 베팅** |
| **중재** | "내 브랜치와 팀 브랜치 중 어느 쪽이 최신인가" | (좌표계가 서면 거의 따라온다) | P3 |
| **질의** | 임의의 프로젝트 질문 | 위 전부의 조합 | P3 — 산출이 아니라 표면 |

**첫날에 여섯 개가 다 유용한 척하지 않는다.** 성숙 프로젝트에서는 사실층이 즉시 서니까 컨설팅·온보딩이 먼저 쓸모 있고, 큐레이션은 의도층이 쌓이면서 자란다. 신생 프로젝트는 정확히 반대다 — 결박할 코드가 아직 없으니 `pending`이 대부분이고, 코드가 생기면서 하나씩 `live`로 바뀐다.

## 10. 설계 원리가 화면에서 어떻게 보이는가

백서 §9의 원리 14개는 추상적으로 읽힌다. 그런데 전부 **화면의 어느 한 줄**로 나타난다.

| 원리 | 화면에서 |
|---|---|
| **P1** 코드가 근거의 원본 | 모든 답이 `Snapshot luma@8f3c21a`를 달고 나온다 |
| **P2** 사실과 추론을 분리 | 브리핑의 `■ 제안` 블록이 따로 있고 `inferred`라고 적혀 있다 |
| **P3** 근거 없는 답을 안 냄 | `Finding`에 반례 경로가 `cli/admin.ts:212`처럼 붙는다 |
| **P4** 공백을 정직하게 | `■ 내가 모르는 것`, `Residual 14`, 대장의 `unsupported 9` |
| **P5** git이 원본, 그래프는 투영 | `.palimpsest/`를 지워도 41초면 복구된다 (의도 저장소만 빼고) |
| **P6** 완전성이 정밀도보다 앞 | `candidate` 엣지를 버리지 않고 **후보 집합째** 들고 있다 |
| **P7** 환경에 종속되지 않음 | Claude Code 없이 `pal` CLI만으로 전부 된다 |
| **P8** 생성형 큐레이션은 1급 | `■ 제안`이 존재한다. 다만 근거 좌표 없이는 저장되지 않는다 |
| **P9** 점진 회상 | `touch`가 상위 10건 + 요약만 준다. 나머지는 후속 질의 |
| **P10** 생성자와 검증자 분리 | 합성물에 `produced_by {모델, 프롬프트 해시, 스냅샷}`이 붙는다 |
| **P11** 빌드하지 않음 | 41초 설치. 3년 전 커밋도 같은 방식으로 열린다 |
| **P12** 설치 비용이 1급 제약 | 캐시 상한 기본 2GB · LRU 축출 · `pal cache stats` |
| **P13** 책임은 사람의 자리 | 승인 없이 `inferred`가 `asserted`가 되는 경로가 없다 |
| **P14** 판정은 통독이 아니라 대조 | 지수가 diff를 다 읽지 않고 세 줄을 보고 멈췄다 (§4) |

**P14가 §4 장면의 요점이다.** 지수는 에이전트가 쓴 코드를 통독해서 문제를 찾은 게 아니다. 기계가 들고 있는 기준(`ADR-0031`이 `stale`이고 `SettlementGate.check`가 변했다)에 **대조**해서 멈췄다. 통독이 검토의 정의면 검토 속도가 전체 처리량의 천장이 되고, 그 천장은 에이전트가 코드를 더 많이 쓸수록 낮아진다.

## 11. 그래서 기존 도구와 뭐가 다른가

정직하게 말하면 **겹치는 게 많다.** 코드 그래프, 호출 관계, 진입점 목록 — 이건 여러 도구가 한다. 어떤 건 palimpsest보다 정밀하게 한다(빌드를 하니까).

다른 것은 넷뿐이다. **이 넷 중 하나라도 안 지켜지면 만들 이유가 없다.**

### ① 모르는 것을 안다고 하지 않는다

대부분의 코드 그래프 도구는 못 푼 참조를 **조용히 버린다.** 그러면 그래프가 깨끗해 보인다. 그리고 `"닿는 경로 없음"`과 `"가는 참조 12건이 미해소"`가 같은 답이 된다. 앞의 것은 안전이고 뒤의 것은 무지인데.

palimpsest에서 `UnresolvedRef`는 **1급 노드**다. 지우지 않고, 이유를 달고, 집계되고, 나중에 실행 관측으로 해소돼도 **원본은 남는다**(다른 환경에서는 다시 못 풀 수 있으니까).

### ② `clean`을 출력하지 않는다

판정 타입에 "위반 없음"이라는 값이 **아예 없다.** 271개 엔드포인트에 "전부 위험"도 "이상 없음"도 말하지 않는다. 못 판정한 것은 `Residual`로 남고, **그 잔여가 좌표에 결박되어 나중에 사람 앞에 다시 온다.**

### ③ 낡음이 표시된 상태다

문서가 낡는 건 못 막는다. **낡았다는 사실의 감지는 기계적으로 가능하다.** 그리고 그 감지의 단위가 라인이 아니라 정규화된 심볼이라서 포매팅 커밋에 `stale`이 켜지지 않는다 — 그게 안 되면 사람이 표시를 무시하고, 무시되는 순간 제품이 죽는다.

### ④ 빌드하지 않는다

이건 약점처럼 보이고 실제로 정밀도를 잃는다. 그런데 **잃는 것은 정밀도이지 완전성이 아니다.** 넓게 잡는 것은 빌드 없이도 할 수 있고, 좁히는 것은 근거를 보며 에이전트와 사람이 한다.

그리고 빌드하지 않기 때문에 **임의의 과거 커밋에서 균일하게 돈다.** 그게 없으면 계보를 못 따라간다 — "이 결정이 3년 전 그 커밋 기준으로 쓰였다"는 말은, 3년 전 커밋에 대해 지금과 같은 방식으로 답할 수 있을 때만 뜻이 있다.
