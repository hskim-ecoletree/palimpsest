# palimpsest는 실제로 어떻게 동작하는가

> **이 문서의 지위**
>
> - **성격**: 안내 문서. 완성된 palimpsest가 남의 프로젝트에 설치됐을 때 **무슨 일이 일어나는지**를 장면으로 보여준다.
> - **왜 있나**: [백서](../WHITEPAPER.md)는 *왜 이래야 하는가*를 논증하고, [설계](DESIGN.md)는 *어떤 구조인가*를 정하고, [계획](plan/README.md)은 *무엇을 어느 순서로 만드는가*를 센다. **셋 다 제품이 실제로 어떤 모습인지는 보여주지 않는다.** 이 문서가 그 자리를 메운다.
> - **권위 아님**: 여기 나오는 출력 예시는 **아직 존재하지 않는 것의 스케치**다. 구현과 다르면 구현이 맞다. 계약의 권위는 백서에, 구조의 권위는 설계에 있다.
> - **읽는 법**: 앞에서 뒤로 시간순이다. §1부터 §8까지가 한 프로젝트의 이야기이고, §9~§11이 그 이야기를 백서의 용어로 되짚는다.
> - **개정 이력**: 2026-08-11에 [2026-08-10 지시](instructions/2026-08-10-owner-direction.md)(U11~U18)와 [선행 구현체 관측](research/2026-08-11-legacy-freshness-anchor-observation.md)을 반영했다. 바뀐 곳은 **§0의 채점 기준 · §2의 provider · §4의 결함 계보와 두 축 · §5.3의 외부 엔진 조달 · §6.4의 PR 델타 · §7.1의 정본 · §7.2의 앵커와 판정 불가 · §7.5의 provider**다.

## 0. 한 문장으로

> **남의 프로젝트에 설치하면, 그 프로젝트의 코드에서 사실을 뽑아 그래프로 만들고, 사람이 쓴 결정·설계·계획을 그 코드 좌표에 못 박아, 코드를 만지려는 순간에 무엇이 걸려 있고 무엇이 낡았는지를 내놓아 — 그래서 다음 변경이 더 나아지게 하는 도구.**

파는 것은 그래프가 아니다. 코드 그래프는 이미 여럿 있다. 파는 것은 **"이 코드에 걸린 결정이 아직 유효한가"에 기계가 답한다**는 것이고, 그 답이 누군가 코드를 만지려는 **바로 그 순간에** 온다는 것이다.

**그리고 그것은 수단이다.** 목적은 그 답을 받은 사람과 에이전트가 **더 나은 코드를 쓰는 것**이고, 이 도구는 그것으로 채점된다([DESIGN §0.8](DESIGN.md)).

이 문서는 그 문장이 실제로 무슨 뜻인지를 하나의 프로젝트를 따라가며 보여준다.

---

## 1. 무대 — `luma`

가상의 회사에 `luma`라는 커머스 백엔드가 있다. 이 문서 내내 이 프로젝트를 따라간다.

| | |
|---|---|
| 스택 | TypeScript · NestJS · Postgres. 프론트엔드는 `luma-web` 저장소에 따로 있다 |
| 나이 | 4년 |
| 규모 | 파일 3,400개 · 심볼 2만여 개 |
| 팀 | 개발자 6명. **초기 설계자 2명은 퇴사했다** |
| 문서 | ADR 12건(마지막 작성이 2년 전) · Notion 위키 · README · 여기저기 흩어진 주석 |
| 에이전트 | 팀이 Claude Code를 쓴다. 코드의 상당량이 에이전트가 쓴 것이다 |

**이 프로젝트의 병은 흔한 것이다.** 코드는 돌아간다. 아무도 왜 그렇게 돌아가는지 전부 알지는 못한다. ADR 12건은 읽을 수 있지만 그것이 지금 코드에도 해당하는 이야기인지 아무도 모른다. 새 사람이 들어오면 "이건 원래 이래요"라는 말을 듣고, 그 말을 한 사람도 사실 이유는 모른다.

그리고 최근 6개월 사이 같은 종류의 사고가 세 번 났다. 세 번 다 **"고치면 안 되는 걸 몰라서 고쳤다"**는 형태였다.

## 2. 설치 — 첫 5분

### 2.1 설치하면 무슨 일이 일어나나

```
$ pal init

luma 를 살펴보는 중…
  파일 훑기        3,412개                          0.4초
  파싱             3,388개 (rayon 8 워커)           38초
  좌표 만들기      21,904 심볼
  인덱스           엣지 84,302개

완료. 41초.
.palimpsest/ 가 생겼습니다 (캐시 180MB · 인덱스 24MB)
  intent/     ← 여기가 원본입니다. git 에 커밋하세요
  cache/ index.redb intent.redb   ← 전부 파생. gitignore 에 넣었습니다
```

**41초다.** 빌드하지 않기 때문이다. `npm install`도, 툴체인도, 환경변수도 필요 없다. blob 하나를 읽어 파싱하는 것이 전부이므로 **아무 커밋에서나 똑같이 돈다**. 3년 전 커밋으로 체크아웃해도 같은 41초가 아니라 **바뀐 파일 수만큼의 시간**이 든다. 파일 내용이 같으면 캐시가 그대로 맞기 때문이다.

이것이 백서가 "균일성"(횡단 요구 U)이라고 부른 것의 실물이다. 빌드에 기대는 도구는 정밀하지만 **어떤 커밋에서는 되고 어떤 커밋에서는 안 된다.** 그러면 "이 결정이 3년 전 그 커밋에도 유효했는가"라는 질문에 답할 수 없다.

**설치한 것은 CLI 하나다.** 에이전트에 물리려면 `pal serve`로 MCP 서버를 띄우거나 플러그인을 얹으면 되지만, **둘 다 없어도 능력이 하나도 죽지 않는다.** CI에서 돌리든 git 훅에서 부르든 스크립트에서 파이프로 받든 같은 답이 나온다 — 상주 프로세스가 없다는 것이 설치 비용 제약(P12)의 실질이고, 특정 호스트가 있어야 답하는 도구가 되지 않는다는 것이 P7이다.

### 2.2 첫 화면은 답이 아니라 **대장**이다

```
$ pal ledger

Snapshot  luma@8f3c21a  (워킹트리와 일치)
저장소    1 (선언됨)

파일      3,412
  parsed          3,388
  partial            11    회복 지점 기록됨
  unsupported         9    언어 인식됨(SQL 7 · Dockerfile 2), 추출기 없음
  unrecognized        0
  excluded            4    규칙: vendor(3) · oversize(1)
  binary/generated    0

언어      TypeScript   L2   identity: exact 21,180 · ordinal 724    3,388 파일
          SQL          L0   결박 불가                                  7 파일
                            ← 이 파일들에는 좌표가 없습니다

provider  0/7 설정됨   ← 이 프로젝트에 대해 우리가 모르는 것을
                          프로젝트가 알려줄 수 있는 자리입니다
조달      없음         ← CI·SAST·린터 산출이 아직 들어오지 않았습니다

감지기    마지막 추출 8f3c21a · 이후 커밋 0개
```

**대부분의 도구는 이 화면을 보여주지 않는다.** 곧바로 "심볼 21,904개를 찾았습니다"라고 말한다. 그 말은 참이지만, 듣는 사람은 그것이 **전부**인지 **찾은 것뿐**인지 알 수 없다.

palimpsest의 첫 화면이 대장인 이유가 그것이다. 이 표는 이렇게 읽힌다:

- **`unsupported 9`** — SQL 파일 7개를 우리는 읽지 못한다. 그러니 SQL 안에서 일어나는 일은 앞으로 어떤 답에도 안 나온다. 그것이 "없다"가 아니라 **"안 봤다"**로 기록되어 있다.
- **`ordinal 724`** — 심볼 2만여 개 중 724개는 스코프 해소가 안 돼서 정체성이 선언 순서에 의존한다. 그 심볼들에 건 결박은 조금 덜 믿을 만하고, **그 사실이 각 답에 함께 실린다.**
- **`excluded 4 · 규칙 vendor(3) · oversize(1)`** — 제외된 파일에는 **왜 제외됐는지 규칙 ID가 붙는다.** 나중에 누군가 제외 규칙을 넓혀서 문제가 사라지면, 그것이 "해결됨"이 아니라 "범위 축소"로 잡힌다.

이 마지막 항목이 이 도구의 성격을 잘 보여준다. **범위를 줄여서 깨끗해지는 길을 막아둔 것이다.**

그리고 아래 두 줄 — `provider 0/7`과 `조달 없음` — 은 **이 도구가 자기 무지의 종류까지 센다**는 뜻이다. `luma`가 NestJS를 쓴다는 것, 데코레이터 하나가 인가 가드라는 것, `@InjectRepository`가 무엇에 묶이는지 — 코어는 이걸 모르고 **알 방법도 없다.** MSA인지 모놀리스인지, 이벤트 기반인지, 모노레포인지도 모른다. 그런데 `luma` 팀은 안다. 그 자리가 [provider 포트](plan/features/F21-provider-ports.md)이고, **비어 있으면 비어 있다고 적힌다**(§7.5).

### 2.3 그런데 아직 아무 값도 없다

설치 직후 `touch`를 불러보면 이렇게 나온다.

```
$ pal touch OrderService.cancel

■ 이 좌표에 걸린 것 (0)
  아직 없습니다.
  미결박 서술물 12건이 대기 중입니다 → pal narrative unbound

■ 이 심볼이 하는 것
  호출자  9  (exact 7 · candidate 2)
  호출   14  (exact 11 · candidate 1 · 미해소 2)

■ 내가 모르는 것 (2)
  UnresolvedRef  PaymentGateway.refund   사유=동적 디스패치   cancel.ts:88
  UnresolvedRef  handler                 사유=문자열 기반     registry.ts:14

■ 판정
  (이 빌드에는 감사 능력이 없습니다 — F15 미구축)

■ 이 답의 근거
  parsed 3388/3412 · unresolved 2 · L0언어 1  ·  능력: 큐레이션·컨설팅
```

**사실층은 첫날에 선다. 의도층은 비어 있다.** 백서 §2.3이 "성숙 프로젝트의 콜드스타트"라고 부른 상태가 정확히 이것이다.

여기서 이 도구가 하지 **않는** 일이 하나 있다. 에이전트에게 git 이력을 읽혀서 "이 코드는 아마 멱등성 때문에 이렇게 짰을 것"이라고 채워 넣는 것. 그렇게 하면 첫인상은 훨씬 좋다. 화면이 그럴듯하게 찬다. 그리고 **그 순간부터 어디까지가 기록이고 어디부터가 지어낸 것인지 아무도 모르게 된다.** 백서는 이것을 "세탁"이라 부르고 금지한다.

대신 비어 있다고 말하고, **다음에 할 일을 알려준다** — 미결박 서술물 12건.

마지막 줄도 눈여겨볼 만하다. `판정` 자리가 **비어 있지 않고** "감사 능력이 없습니다"라고 적혀 있다. 이 빌드는 아직 감사(F15)를 만들지 않았다. 그때 `Finding 0`이라고 출력하면 그것은 "검사해 봤는데 문제 없음"으로 읽힌다. **없는 능력과 없는 문제는 다른 것이고, 그 둘이 같은 화면을 만들면 이 도구는 자기가 고발한 문제를 스스로 저지르는 것이다.**

## 3. 첫 주 — 의도층을 채운다

### 3.1 이미 있는 문서를 끌어온다

```
$ pal narrative intake docs/adr/ docs/design/

문서 14개에서 조각 63개를 읽었습니다.

  결박됨      31   강한 신호로 좌표가 잡혔습니다
  후보 있음   18   후보를 제시합니다. 승인이 필요합니다
  미결박      14   신호가 없습니다 → pal narrative unbound

승인 대기 18건 → pal approve
```

문서를 섹션 단위로 잘라서 각 조각이 **어느 코드에 대한 이야기인지**를 찾는 작업이다. 찾는 방법은 강한 신호부터 차례로 내려간다.

| 신호 | 예 | 처분 |
|---|---|---|
| 프론트매터에 좌표를 직접 씀 | `grounds: ["src/order/cancel.ts#OrderService.cancel"]` | **확정** |
| 코드 블록 안의 파일 경로 | `` `src/order/cancel.ts` `` | 강함 — 대장에 그 경로가 있으면 확정 |
| 인라인 코드가 심볼 인덱스에 유일 | `` `OrderService.cancel` `` | 강함 — 정확히 1건이면 확정 |
| 문서와 같은 커밋에서 바뀐 파일 | git 이력에서 계산 | 중간 — 후보로 제시 |
| 문서 경로가 가까움 | `docs/order/` ↔ `src/order/` | 약함 — 후보로만 |
| **본문 자연어가 비슷함** | "주문 취소 로직" | **쓰지 않는다** |

마지막 줄이 중요하다. "주문 취소 로직"이라는 말이 `cancelOrder`인지 `OrderCanceller`인지 `OrderService.cancel`인지 **기계는 모른다.** 임베딩으로 유사도를 재면 셋 다 비슷하게 나오고, 그중 하나를 골라 결박하면 **틀린 결박**이 생긴다.

그리고 틀린 결박은 없는 결박보다 나쁘다. 없으면 사람이 찾아보지만, 틀린 게 있으면 사람은 그것을 믿는다.

### 3.2 승인 — 사람이 하는 일

```
$ pal approve

[1/18]  ADR-0042 「취소는 멱등해야 한다」  §3 재시도 안전성

  본문 발췌:
    "결제 취소는 네트워크 재시도로 두 번 호출될 수 있다. 취소 처리는
     반드시 멱등 키를 확인하고 이미 취소된 주문은 조용히 성공을 반환한다."

  제안 좌표 (신호: 인라인 코드 스팬이 심볼 인덱스에 유일)
    → luma:src/order/cancel.ts#OrderService.cancel

  감시 반경  symbol (기본)  ·  callers 로 넓히려면 [w]

  [y] 승인   [n] 거부   [e] 좌표 수정   [w] 반경 넓히기   [s] 건너뛰기
```

이 한 화면이 이 제품에서 **가장 비싼 것**이다. 사람의 시간이 들어가는 유일한 자리이기 때문이다. 백서 §12-8이 "승인 자체가 노동이면 아무도 하지 않고 의도층은 영원히 비어 있게 된다"고 적어둔 그 지점이다.

그래서 이 화면에는 비용을 낮추는 장치가 붙어 있다.

- **일괄 승인** — 같은 문서에서 나온 조각들, 같은 규칙이 파생시킨 라벨들은 한 번에.
- **거부도 기록된다.** 이게 의외로 크다. 거부를 기록하지 않으면 다음 인입 때 **같은 것을 또 묻는다.** 재질문을 없애는 것이 승인 비용 절감의 대부분이다.
- **진척이 보인다.** `[1/18]`. 끝이 안 보이는 큐는 아무도 끝내지 않는다.

승인하면 무슨 일이 일어나냐면 — `inferred`(기계가 제안한 것)가 **`asserted`(사람이 확정한 것)로 바뀌는 게 아니다.** 새 `asserted` 노드가 생기고, 원래의 `inferred`는 "누구의 추론이었는지"를 달고 **그대로 남는다.**

왜 그렇게 하냐면 되돌릴 수 있어야 하기 때문이고, 나중에 "이거 누가 정한 거야?"에 답할 수 있어야 하기 때문이다.

### 3.3 붙지 않은 것들

```
$ pal narrative unbound

미결박 서술물 14건 — 좌표를 못 찾았습니다

  ADR-0007  「우리는 이벤트 소싱을 쓰지 않는다」          사유: 코드 참조 없음
  ADR-0011  「팀 간 API는 버전을 붙인다」                  사유: 조직 규칙, 코드 대상 아님
  DESIGN §2 「전체 아키텍처 개요」                          사유: 대상이 너무 넓음
  …

이 목록이 당신의 작업 목록입니다.
좌표를 직접 붙이려면:  pal bind <문서#섹션> <좌표>
```

**해소 실패를 실패로 남긴다.** 억지로 붙이지 않는다. 그리고 이 목록은 버려지는 게 아니라 **사람이 손으로 붙일 것들의 목록**이 된다.

여기 있는 것 중 일부는 영원히 안 붙는다. "우리는 이벤트 소싱을 쓰지 않는다"는 **어떤 코드도 가리키지 않는 결정**이다. 그건 정상이다. 그런 결정이 있다는 것과, 그것이 코드에 결박되지 않았다는 것 둘 다 기록되면 된다.

### 3.4 이미 돌고 있는 것을 끌어온다

`luma`의 CI는 이미 무언가를 돌리고 있다. eslint, `tsc --noEmit`, 그리고 작년에 붙인 semgrep. **그 산출물은 매번 새로 나고 아무 데도 결박되지 않는다** — PR이 닫히면 사라진다.

```
$ pal observe --from-ci .github/workflows/ci.yml --dry-run

이 저장소에서 도는 것을 찾았습니다
  eslint    JSON 리포터    파일:라인 있음    ✓ 수용 가능
  tsc       텍스트         파일:라인 있음    ✓ 수용 가능
  semgrep   SARIF          파일:라인 있음    ✓ 수용 가능 · taint 경로 포함

$ pal observe --from-ci .github/workflows/ci.yml

수용됨 — 3개 조달원
  semgrep@p/security-audit  alert 23  → 좌표 결박 21 · 미결박 2
  eslint                    진단 118  → 좌표 결박 118
  tsc                       진단 0    → 범위: src/**/*.ts (3,388 파일)

  ⚠ 억제 6건을 발견했습니다. 근거와 만료가 없으면 수용하지 않습니다:
      cancel.ts:61  // nosemgrep         → pal suppress review
```

세 가지가 여기서 일어난다.

- **alert가 좌표에 결박된다.** `파일:라인`을 심볼 좌표로 옮기고, 옮기지 못한 2건은 **버리지 않고 미결박으로 남는다.**
- **`tsc 진단 0`이 "이상 없음"이 아니다.** 옆에 범위가 붙어 있다 — `src/**/*.ts` 3,388 파일. 그 밖은 `OutOfScope`다. **범위 없는 "0건"은 수용하지 않는다.**
- **억제가 심사 대상이 된다.** `// nosemgrep` 한 줄이 코드에 있는데 왜 붙었는지, 언제까지 유효한지 아무 데도 없다. palimpsest는 그것을 **근거와 만료를 요구하는 승인 항목**으로 만든다. 아무도 세지 않던 자리다.

> **여기서 palimpsest가 하는 일은 분석이 아니다.** semgrep이 semgrep보다 잘할 방법은 없다. 하는 일은 **그 산출을 좌표에 못 박고, 낡으면 낡았다고 말하고, 못 본 범위를 함께 세고, 억제의 이력을 남기고, 두 엔진이 어긋나면 그것을 신호로 만드는 것**이다([DESIGN §7.5](DESIGN.md)).

### 4.1 무슨 일이 일어난 것인가

**이 대화가 이 제품의 전부다.** 나머지 모든 기능은 이 3분을 만들기 위한 것이다.

그리고 이 장면이 이 도구가 채점되는 자리다. 화면이 정확했는지가 아니라 **지수가 다른 코드를 쓰게 됐는지**로 채점된다([DESIGN §0.8](DESIGN.md)) — 역사를 알게 하는 것은 수단이고, 목적은 다음 변경이 나아지는 것이다.

주목할 부분이 여섯 있다.

**⓪ 같은 자리에서 났던 사고가 따라왔다.** 이게 없으면 지수는 5개월 전 인시던트를 모른 채 같은 코드를 고친다. `#218`은 이슈 트래커에 있었지만 **그 코드를 만지는 순간에 오지 않았다.** 결함이 좌표에 결박된다는 것은 "재발"을 셀 수 있게 된다는 뜻이고, 재발을 세지 못하면 이 도구가 실제로 코드를 나아지게 했는지도 잴 수 없다.

**① 지식이 사람을 찾아왔다.** 지수는 ADR-0031을 몰랐다. 그걸 쓴 사람은 2년 전에 퇴사했다. 검색해서 찾을 수도 있었지만, **검색하려면 그런 게 있다는 걸 먼저 알아야 한다.** 백서가 말하는 진짜 문제는 "지식이 없다"가 아니라 **"지식이 필요한 순간에 도달하지 않는다"**이다.

**② `stale`이 무엇 때문에 켜졌는지가 붙어 있다.** 그냥 "낡음"이면 지수는 ADR-0031을 열어 읽고 "음... 아직 맞는 것 같은데?" 하고 닫는다. **"`SettlementGate.check`가 12커밋 전에 변했다"**가 붙어 있으니 어디를 볼지 안다.

**③ `pending`과 `stale`이 구별된다.** "아직 안 만들었다"와 "만든 뒤 어긋났다"는 사람이 완전히 다르게 처리한다. 둘을 같은 색으로 칠하면 신생 프로젝트에서는 모든 게 빨간불이 되고, 그러면 아무도 안 본다.

**④ 모르는 걸 모른다고 했다.** `PaymentGateway.refund`는 동적 디스패치라 못 따라갔다. 그래서 판정에 `Residual 2`가 남는다. **`Finding`만 보고 "나머지는 안전하다"고 결론 내릴 수 없게** 되어 있다.

**⑤ `Finding 1`을 우리가 찾은 게 아니다.** semgrep이 찾았다. palimpsest가 한 일은 그 alert를 **좌표에 못 박고, 2일 전 것이라 아직 유효하다고 말하고, `tsc`의 진단은 12커밋 전 것이라 `stale-observation`으로 내리고, 억제 하나가 6개월 뒤 만료된다는 걸 함께 띄운 것**이다. 이 다섯 중 어느 것도 엔진 자신은 하지 못한다 — alert는 실행마다 새로 나고 어디에도 결박되지 않기 때문이다.

**⑥ 결박 상태가 두 칸이다.** `live`/`stale`은 **코드 대비**이고 `current`/`superseded`는 **계보 대비**다. 둘은 독립이라 `superseded`인데 `stale`인 결정("대체됐고 코드도 변했다")과 `superseded`인데 `live`인 결정("대체됐지만 코드는 그대로")이 구별된다. 한 칸으로 뭉개면 대체된 결정의 코드 신선도가 사라지고, **그러면 "이 결정은 폐기됐는데 그 코드는 아직 그대로인가?"에 답할 수 없다.**

### 4.2 이 도구는 "이상 없음"을 말하지 않는다

마지막 항목을 조금 더 파고들 만하다. 판정 결과의 타입에는 값이 셋뿐이다.

| | 뜻 | 반드시 달고 다니는 것 |
|---|---|---|
| **Finding** | 위반이 존재한다 | **반례 경로** — 어디를 보면 확인되는지 |
| **Residual** | 판정할 수 없었다 | 사유 · 술어 · 결박 좌표 · 언제 · 무엇이 있으면 풀리는지 |
| **OutOfScope** | 범위 밖이다 | 대장 참조 |

**넷째 값이 없다.** "위반 없음"이라는 값이 타입에 존재하지 않는다. "괜찮다"에 가장 가까운 표현은 **"Finding이 비었고 Residual이 비지 않았다"**이고, 이건 사람이 읽으면 자연히 "그래서 못 본 게 뭔데?"로 이어진다.

왜 이렇게까지 하냐면, 보안·정합성 맥락에서 최악의 실패는 틀린 경고가 아니라 **틀린 안심**이기 때문이다. 경고가 틀리면 사람이 확인하고 걷어낸다. 안심이 틀리면 **사람이 확인을 그만둔다.**

그리고 `Residual`은 목록에 적히고 잊히는 게 아니라 **좌표에 결박된다.** 즉 나중에 누가 그 코드를 `touch`하면 "여기 아직 판정 못 한 게 있다"가 **다시 사람 앞에 온다.**

    └─ (위와 같은 경로로 합류)

  CLI    luma-admin refund --order-id    AdminCli.refund
    └─ OrderService.refund  ⚠ 인가 가드를 통과하지 않습니다
                              → 의도된 것인지 확인이 필요합니다 (Residual)

■ 이 흐름에 걸린 결정 (2)
  ADR-0042  취소는 멱등해야 한다              live
  ADR-0019  환불은 원 결제수단으로만          live

■ 못 본 것
  · PaymentGateway.refund 이후 — 동적 디스패치
  · luma-web 으로 나가는 경계 — OpenAPI 등 계약 아티팩트가 없어 엣지를 세우지 않았습니다
```

민준은 30초 만에 세 개의 진입점이 있다는 걸 알았다. 그리고 마지막 줄에서 **CLI 경로가 인가 가드를 안 지난다**는 걸 봤다. 4년 된 프로젝트에서 아무도 몰랐던 사실이다.

**"환불"이라는 이름은 코드에서 나오지 않는다.** 진입점 셋은 추출되지만 *"이 셋이 한 여정이다"*는 사람이 선언한 것이다 — 그래서 여정은 `asserted`이고, 선언되지 않은 프로젝트에서는 이 질문에 답하지 못한다(진입점 목록까지만 나온다). E2E 테스트가 있으면 그것이 여정의 근사가 되므로 거기서 끌어오는 것이 첫 시도다.

주목할 곳은 **"못 본 것"** 항목이다. `luma-web`으로 나가는 호출은 저장소 경계를 넘는다. 이름이 같다는 이유로 엣지를 세우지 않는다 — **이름의 우연한 일치로 세운 엣지는 순수한 거짓말**이기 때문이다. OpenAPI 스펙이나 protobuf 같은 **계약 아티팩트가 증거로 있을 때만** 경계 엣지가 선다. 없으면 없다고 적는다.

### 5.3 "인가 빠진 데 있어?" (감사)

이 질문이 가장 어렵고, 답도 가장 낯설다.

```
$ pal audit --rule "결제 관련 엔드포인트는 인가 가드로 지배되어야 한다"

대상: 진입점 271개 중 결제 관련으로 라벨된 34개

■ Finding  3
  [자체 판정]  AdminCli.refund → OrderService.refund
    이 경로에는 인가 가드가 없습니다.
    반례 경로: cli/admin.ts:212 → order/service.ts:88
    (직접 확인하실 수 있습니다)

  [조달]  semgrep@p/security-audit · 2일 전 · live         2건
    taint: req.body.reason → order.cancelReason   cancel.ts:52
    taint: req.query.id → rawQuery                 admin.ts:140

■ Residual  14
  라벨 없음               8   가드 라벨이 승인되지 않은 진입점
  미해소 참조 경유         4   동적 디스패치를 지나는 경로
  candidate 집합 과다      2   후보가 K=32를 넘어 탐색을 중단했습니다

■ OutOfScope  2
  SQL 마이그레이션이 직접 상태를 바꿉니다 — 이 언어에는 좌표가 없습니다

■ 조달의 침묵                                ← "검사했는데 없음"이 아닙니다
  semgrep  범위 안 34개 중 31개 스캔 · 3개는 룰셋 대상 언어 밖
  tsc      stale-observation (12커밋 전) — 이 판정에서 배제됨

■ 범위 변동                                  ← 없으면 위 숫자가 거짓말을 합니다
  지난 판정 이후 없음
  억제 6건 중 1건이 3개월 뒤 만료 예정

34개 중 20개를 판정했습니다.
```

**`Finding 3` 중 둘은 우리가 찾은 게 아니다.** 그리고 그 사실이 화면에 적혀 있다. 조달 경유 판정은 라벨 저작을 요구하지 않으므로 **가드 라벨이 하나도 승인되지 않은 프로젝트에서도 선다** — 이것이 [2026-08-10에 F16을 P1로 올린 이유](plan/features/F16-observation-intake.md)이고, 감사가 "가장 비싼 베팅"(라벨·제어흐름·승인 노동이 전부 필요한 자체 판정)과 "조달하면 오늘 되는 것"으로 갈리는 지점이다.

> **⚠ 이 화면은 P1에서 뜨지 않는다 — 2026-08-11.**
> [T9 실측](gates/preflight.md#t9--조달-가능성-실측)이 코퍼스 넷에서 **SAST 조달원 0/4**를
> 확인해 [F16이 P2로 되돌아갔다](plan/features/F16-observation-intake.md).
> 위 판정 블록의 성질(*라벨 없이 `Finding`이 선다*)은 그대로지만, **받을 alert가 있는
> 프로젝트에서만 뜬다.** 문서 머리가 말하는 "아직 담지 않은 것"에 이것이 하나 더 붙는다 —
> **이 화면은 조달원이 있는 프로젝트의 화면이다.**

**그런데 조달은 새 거짓 안전을 하나 들여온다.** semgrep 리포트에 아무것도 없으면 사람은 "안전하다"고 읽는다. 그래서 `■ 조달의 침묵` 블록이 있다.

- **`31개 스캔 · 3개는 룰셋 대상 언어 밖`** — 침묵한 3개는 "통과"가 아니라 **안 본 것**이다.
- **`tsc stale-observation`** — 12커밋 전 진단이라 **판정에서 자동 배제된다.** 표시만 하지 않는 이유는 사람이 표시를 무시하기 때문이다.
- 그리고 여기 안 보이는 것 하나 — **엔진이 실패한 경우.** 빌드가 깨져서 semgrep이 0건을 뱉었으면 그건 "위험 없음"이 아니라 조달 실패다. 종료 코드를 보지 않으면 **실패가 침묵으로, 침묵이 안전으로 두 번 미끄러진다.** 선행 구현이 이것을 *"보안 니치 최악의 false-clean"*이라 부르며 착수 조건으로 못 박았다([연구 G](research/2026-08-11-legacy-freshness-anchor-observation.md)).

**이 화면을 처음 보면 실망스럽다.** "34개 중 20개"라니. 다른 도구는 "34개 검사 완료, 취약점 3건"이라고 말한다. 그게 훨씬 보기 좋다.

그런데 그 도구가 말하지 않는 것이 있다. **나머지 14개를 어떻게 처리했는가.** 라벨이 없어서 검사 자체가 안 된 8개는 "통과"로 셌을까, 아니면 조용히 목록에서 빠졌을까? 동적 디스패치를 지나는 4개는? 대부분의 도구에서 이 둘은 **구별되지 않고 "이상 없음"에 합산된다.**

그리고 마지막 항목 — **범위 변동**. 이게 이 도구에서 가장 조용하지만 중요한 장치다.

> 누군가 `Residual 14`가 보기 싫어서 제외 규칙을 넓히거나, 판정을 못 하는 진입점을 대상 라벨에서 뺀다. 그러면 다음 실행에서 `Residual`이 3으로 줄어든다. **숫자만 보면 진전이다.**

그래서 판정 결과에는 **범위가 어떻게 변했는지가 반드시 함께 나온다.** 제외 규칙이 넓어졌는지, 언어 등급이 떨어졌는지, 라벨이 지워졌는지, 예산이 줄었는지. 그리고 그렇게 **판정 대상에서 사라진 좌표에도 결박이 걸려서**, 나중에 누가 그 코드를 `touch`하면 "여기는 판정 대상에서 빠졌습니다"가 뜬다.

기준을 낮춰서 통과하는 길을 막는 것 — 백서 §12-5가 "게이트 오염"이라 부른 것에 대한 대응이다.

## 6. 반년 뒤 — 프로젝트가 움직인다

### 6.1 대개편이 일어난 날

팀이 `src/order/`를 `src/domain/order/`로 옮기는 대규모 리팩터링을 했다. 파일 214개가 움직였다.

```
$ pal status

⚠ 결박 47건이 orphaned 입니다 — 좌표가 사라졌습니다

  같은 내용의 새 심볼을 찾았습니다:
    43건  경로 접두어 변경 src/order/** → src/domain/order/**
           body_digest 일치 · 이름 일치 · 컨테이너 일치
    3건   개별 확인 필요 (내용도 함께 변경됨)
    1건   대응 심볼 없음 — 실제로 삭제된 것 같습니다

  pal rebind --batch    ← 43건을 한 번에 승인
  pal rebind --review   ← 3건을 하나씩
```

**정체성이 끊긴 걸 조용히 넘기지 않는다.** 새 심볼로 자동으로 옮겨 붙이면 편하지만, **의미가 다른 동일 코드에 잘못 붙을 수 있다.** 그래서 제안까지만 하고 승인을 받는다.

다만 승인 비용은 낮춰준다. 43건이 전부 같은 경로 접두어 변경이면 **승인 한 번**이다. 그리고 `body_digest`(코드 내용의 해시)가 같다는 게 제안의 근거라서 정확도가 높다.

여기서 `body_digest`가 두 번째 일을 한다. 처음 만든 이유는 **낡음 감지**였다 — 포매팅만 바뀐 커밋에 `stale`이 켜지면 안 되니까 주석·공백·변수명을 지운 정규형의 해시를 쓴다. 그런데 **파일이 옮겨졌을 때 "같은 코드"를 찾는 데도 같은 값이 쓰인다.**

### 6.2 포매터를 돌린 날

누군가 prettier 설정을 바꾸고 전체 파일에 돌렸다. 커밋 하나에 3,388개 파일이 바뀌었다.

```
$ pal status

의도층
  결박된 항목    112
  live           112
  stale            0     ← 포매팅 커밋이 낡음을 켜지 않았습니다
```

**아무 일도 일어나지 않는 것이 여기서의 정답이다.**

이게 안 되면 제품이 죽는다. 포매팅 커밋 하나에 결박 112개가 전부 `stale`로 켜지면, 사람은 그날부터 낡음 표시를 무시한다. 한 번 무시하기 시작하면 진짜 낡음도 같이 무시된다.

그래서 결박의 단위가 라인이 아니라 **정규화된 심볼**이다. 들여쓰기·줄바꿈·주석·따옴표 종류·후행 쉼표는 digest에서 지워진다. 지역 변수명도 (스코프 해소가 된 심볼에서만) 지워진다.

```
원본:    function add(a: number, b: number) { const s = a + b; return s }
정규형:  function add(#0: number, #1: number){const #2=#0+#1;return #2}
```

반대로 **지우지 않는 것**도 명확하다. 리터럴 값(`TIMEOUT = 30` → `300`은 의미 변경), 연산자, 호출 대상 이름, 필드·메서드 이름, 타입 주석. 이건 바뀌면 `stale`이 켜져야 하는 것들이다.

### 6.3 계획대로 됐는지 본다

```
$ pal plan deviation --plan docs/plans/2026-q3-refund.md

계획 항목 14건 · base 8f3c21a → head 4b91e07

  계획대로            9
  계획에 없던 변경     5
    src/domain/order/mapper.ts#OrderMapper.toDto      (리팩터링으로 보임)
    src/shared/logger.ts#configure                     (무관해 보임)
    …
  계획했으나 없는 변경  2
    §3-1 "환불 사유 코드 정규화"
    §5-2 "관리자 CLI에 인가 추가"       ← audit 의 Finding 1 과 같은 자리입니다
  판정 불가            3
    좌표로 해소되지 않은 계획 항목입니다
    §2 "성능 개선"  §4 "문서 정리"  §6 "모니터링 보강"
```

**"판정 불가"를 따로 세는 것이 이 화면의 요점이다.** "성능 개선"은 어떤 좌표도 가리키지 않는다. 그걸 "미구현"에 합산하면 이탈률이 거짓말이 된다. 못 잰 건 못 쟀다고 적는다.

그리고 `계획에 없던 변경 5`는 **나쁜 게 아니다.** 이 도구는 그것을 관측할 뿐 평가하지 않는다. 리팩터링은 원래 계획에 안 적힌다. 판정은 사람이 한다.

한 가지 더 — `§5-2 "관리자 CLI에 인가 추가"`가 계획됐는데 안 됐고, 그게 §5.3의 자체 판정 `Finding`과 같은 자리다. **의도층과 사실층이 같은 좌표에서 만나면 이런 것이 보인다.** 계획만 보면 "안 했네"이고, 감사만 보면 "구멍이 있네"인데, 둘을 겹치면 **"하기로 했는데 안 해서 구멍이 남았다"**가 된다.

### 6.4 리뷰가 열리는 날 — 판정의 단위는 브랜치다

지수가 PR을 연다. CI가 `pal`을 부른다.

```
$ pal conformance --base main

feature/refund-inventory  (17 커밋 · 파일 23)

  새 위반           1   AdminOrderController.forceCancel 이 가드를 우회합니다
  해소된 위반       2   semgrep taint 2건이 이 브랜치에서 사라졌습니다
  새 잔여           3   추가된 동적 디스패치 경유
  해소된 잔여       0
  범위 변동         ⚠ semgrep 룰셋이 p/security-audit → p/ci 로 바뀌었습니다
                       (룰 14개 감소 · alert 2건이 이 변경으로 사라졌습니다)

  ↑ "해소된 위반 2"와 "룰셋 축소로 사라진 2"가 같은 건입니다.
    고쳐서 사라진 것이 아닙니다.
```

**마지막 두 줄이 이 화면의 전부다.** 룰셋을 줄이면 alert가 사라지고 숫자만 보면 진전이다. 델타에 **범위 변동이 필수 성분**인 이유이고, 그것이 없으면 "위반 2건 해소"가 거짓말이 된다.

그리고 이 판정은 **절대값이 아니라 이 브랜치가 만든 순증**이다. 4년 된 프로젝트에 처음 설치한 날의 절대 평가는 "전부 위반"이고 그 산출은 아무도 안 읽는다. `--base main` 하나가 브리핑·구조 평가·계획 이탈률의 기준선을 동시에 정한다.

지수가 결박을 하나 더 만들고 커밋한다.

```
$ pal bind ADR-0042 OrderService.cancel --print-trailer
Palimpsest-Binds: ADR-0042@luma:src/order/cancel.ts#OrderService.cancel

$ git commit   # 트레일러를 커밋 본문에 붙인다
```

**결박이 변경과 같은 리뷰를 받는다.** 그리고 승인의 정본은 `.palimpsest/intent/*.jsonl`이라 **git에 커밋되고 팀이 공유한다** — 지금까지 이 산업의 어떤 도구도 승인 노동을 한 사람의 로컬 파일에 두고 팀에 전달하지 못했다. 몇 주에 걸쳐 지불한 판정이 그 사람 노트북에만 있으면 그것은 자산이 아니다.

파일 형식은 **추가 전용에 한 줄 한 레코드**다. 두 사람이 같은 주에 승인해도 머지 충돌이 라인 단위로 풀리고, 대개는 양쪽을 다 취하는 것이 정답이다.

└──────────────────────────────┘   └──────────────────────────────┘
  │                                        │
  ▼        질의 시점에 이어 붙임             │ 읽어서 색인
┌─ 2층 · 질의 인덱스 + intent.redb ─────────┴──────┐
│  심볼 · 엣지 · 역방향 색인 · 결박 색인              │
│  지워도 됨 (1층 + intent/*.jsonl 에서 다시 만듦)   │
└───────────────────────────────────────────────────┘
```

**왼쪽 둘의 성격이 정반대**라서 파일을 갈라 놓았다.

- 캐시와 인덱스는 언제든 지워도 된다. 지우면 다시 만든다. 원본이 git에 있다.
- **의도는 사람이 몇 주에 걸쳐 승인한 것이고 코드에서 복원되지 않는다.** 그래서 정본을 **텍스트로 두고 git에 커밋한다.**

정본을 바이너리 DB가 아니라 텍스트로 둔 이유가 셋이다.

| | |
|---|---|
| **지워도 돌아온다** | `.palimpsest/`를 통째로 지워도 `git checkout` 하나면 복구된다. "지우는 코드 경로가 없다"는 방어는 사용자가 디렉터리째 지우는 것까지는 막지 못한다 |
| **팀이 공유한다** | 승인 노동이 한 사람의 노트북에 갇히지 않는다 |
| **리뷰된다** | 결박이 diff로 보이고 PR에서 검토된다 |

그리고 `pal cache prune`이 의도에 닿는 코드 경로는 **아예 없다.** `intent.redb`는 이제 색인일 뿐이라 그것도 지워도 된다 — **지워도 되는 것과 안 되는 것의 경계가 파일 확장자에서 보인다.**

### 7.2 낡음은 어떻게 감지되나

결박 하나에 이런 게 들어 있다.

```
ADR-0042 → luma:src/order/cancel.ts#OrderService.cancel
  반경: symbol
  결박 시점의 감시 집합 digest: { OrderService.cancel: a3f2… }
                                 ↑ 기계가 코드에서 읽은 값입니다
```

코드가 바뀌면 재추출이 돌고, digest가 바뀐 심볼 목록이 나온다. 그 목록으로 **역방향 조회**를 해서 영향받는 결박만 다시 계산한다. 전체를 다시 세지 않는다.

**저 화살표가 이 절에서 가장 중요하다.** 결박을 만든 쪽이 *"이건 커밋 8f3c21a 기준이야"*라고 신고해도 **그 신고가 기준점이 되지 않는다.** 기준점은 결박 시점에 기계가 대상 코드에서 직접 읽은 digest다. 신고는 기록되고 어긋나면 그것 자체가 신호가 되지만, 유효기간을 정하는 권한은 없다.

가장 무겁게 걸리는 곳은 §3.4의 조달이다 — semgrep이 *"이 alert는 이 커밋 기준"*이라 신고하는데, 그것을 앵커로 쓰면 **엔진이 자기 산출물의 유효기간을 스스로 정하게 된다.**

그리고 **낡음은 탐지만 한다.** `stale`이 떴다고 요약을 다시 만들거나 결박을 옮기지 않는다. 그렇게 하면 세 가지가 동시에 깨진다 — 낡았다고 판정한 쪽과 다시 만든 쪽이 같아지고, 기록하는 층이 고치는 층이 되고, **사람이 승인한 것이 승인 없이 교체된다.** `stale`이 하는 일은 재판정 큐에 올려 다음에 그 좌표를 만질 때 사람 앞에 가져오는 것까지다.

#### 그리고 판정할 수 없을 때가 있다

```
■ 이 좌표에 걸린 것 (1)
  ADR-0055  마이그레이션은 되돌릴 수 있어야 한다   undeterminable   current
                                                   ← 감시 집합에 SQL 파일이 있고
                                                     그 언어에는 좌표가 없습니다
```

`live`도 `stale`도 아니다. **모르는 것이다.** 이걸 `live`로 세면 "이 결정은 유효합니다"와 "유효한지 알 수 없습니다"가 같은 화면이 되고, 그것은 이 도구가 `clean`을 없앤 것과 정확히 같은 실패다.

판정 불가는 네 가지 사유로 생긴다 — 좌표가 없는 언어(L0), 파싱이 부분 실패한 파일, 감시 집합의 원소가 사라진 경우, 투영이 아직 그 스냅샷을 안 본 경우. **그리고 이것이 몰린 곳이 다음에 무엇을 만들지의 지도가 된다** — §7.3의 미해소 참조가 하는 일과 같다.

**반경**은 "이 결정이 무엇을 감시하는가"다.

| 반경 | 감시하는 것 | 비용 |
|---|---|---|
| `symbol` (기본) | 그 심볼 하나 | 상수 |
| `callers` | + 직접 호출자들 | 조회 1회 |
| `closure(k)` | + k홉 의존 폐포 | 폐포 크기만큼 — **너무 크면 결박 저장 자체를 거부한다** |
| `files` | + 지정한 파일들 (설정·스키마·마이그레이션) | 나열한 만큼 |

**반경이 있는 이유는 이 문제가 원리적으로 안 닫히기 때문이다.** "이 결정과 관련 있는 코드 전부"는 계산할 수 없다. 좌표 바깥이 변해서 결정이 무효가 돼도 `live`로 남는 경우가 반드시 있다.

그래서 닫는 대신 **선언한다.** `"이 결정은 symbol 반경에서 live"`는 `"이 결정은 유효하다"`와 다른 문장이고, 그 차이가 화면에 남는다. 해결이 아니라 정직이다 — 하지만 숨기는 것보다는 낫다.

### 7.3 못 푼 참조가 로드맵이 된다

```
$ pal refs unresolved --by reason

문자열 기반      4,102   ← 라우트 레지스트리 패턴.
                            프레임워크 인식기를 만들면 대부분 해소됩니다
동적 디스패치    2,871   ← 실행 관측의 1순위 표적
정의 없음        1,560   ← 그중 890건이 DI 컨테이너. 팩 규칙 후보
후보 과다          672   ← 수신자 타입 추론이 있으면 줄어듭니다
언어 등급 미달     226   ← SQL 파일. 추출기 추가 또는 표준 인덱스 수용
```

못 푼 것을 조용히 버리지 않고 **노드로 만들어 두니까**, 그것들이 저절로 이런 표가 된다. **다음에 무엇을 만들지를 사람이 감으로 정하지 않는다. 밀도가 정한다.**

그리고 이 표는 두 번째 일도 한다. 실행 관측(트레이스·DI 덤프·SCIP 인덱스)을 받아들일 때, **전수로 돌릴 필요가 없다.** 이 지도를 따라 좁게 조달하면 된다. "어디서 한 번 돌리면 가장 많이 밝혀지는가"가 이미 계산되어 있으니까.

### 7.4 환경이 필요한 것은 이렇게 들어온다

palimpsest는 **대상 프로젝트를 실행하지도 빌드하지도 않는다.** 툴체인도 비밀도 없고, 남의 머신에서 임의의 코드를 돌리는 건 신뢰 문제이기도 하다. §3.4의 semgrep도, 아래의 트레이스도, §7.5의 provider도 **전부 밖에서 돌고 결과만 들어온다.**

대신 **수용 창구**를 연다.

```
$ pal observation intake --kind call-trace --file trace.json \
    --procedure "npm test 실행, OTel 수집기로 캡처" \
    --env "node 20.11 / linux-x64 / deps-lock a3f2…"

수용됨. 출처: observed
  미해소 참조 87건이 해소됐습니다 (동적 디스패치 61 · 문자열 기반 26)
  기존 정적 엣지와 어긋나는 것: 2건 → pal observation conflicts

⚠ 이 관측은 좌표 87개에 결박됩니다.
   그중 하나라도 코드가 바뀌면 stale-observation 이 되고,
   그때부터 이 관측에 기대던 판정은 Residual 로 떨어집니다.
```

누가 이걸 만들었는지는 **묻지 않는다.** Claude Code가 돌렸든, CI가 돌렸든, 사람이 로그를 붙여넣었든 출처 배정은 똑같이 `observed`다. 대신 **어떤 절차로 얻었는지는 반드시 적어야 한다** — 그게 없으면 값을 만들 수조차 없다.

이 구분이 "호스트를 통해 실행에 닿는다"가 "호스트에 의존한다"로 미끄러지는 걸 막는 유일한 장치다.

그리고 마지막 경고가 중요하다. **관측은 네 가지 출처 중 가장 빨리 낡는다.** 코드는 바뀌면 다시 파싱되지만, 3주 전 트레이스는 그대로 남아 있다. 낡은 관측이 계속 판정에 쓰이면 **낡은 서술이 거짓 신호가 되는 문제가 사실층 안에서 재생산된다.** 그래서 자동으로 배제하고, 대신 "여기 한 번 더 돌리면 회복됩니다"라는 큐에 넣는다.

**두 엔진이 같은 것을 다르게 말하면 덮어쓰지 않는다.** 둘 다 남고 불일치가 보고된다. 그러려면 두 산출이 **애초에 다른 노드로 서야** 한다 — 파생 노드의 정체성에 출처와 생산자가 들어가는 이유다. 이것을 속성으로만 두면 같은 자리의 두 판정이 하나로 접히고 나중 것이 앞의 것을 덮는다. **붕괴한 것은 어긋날 수 없다.** 선행 구현이 정확히 그 자리에서 자기 설계를 뒤집었다([연구 G](research/2026-08-11-legacy-freshness-anchor-observation.md)).

### 7.5 코어가 모르는 것은 프로젝트가 채운다

`luma`가 NestJS라는 것, `@Roles()`가 인가 가드라는 것, `@InjectRepository`가 무엇에 묶이는지 — **코어는 모르고 알 방법도 없다.** 대상이 MSA인지 모놀리스인지, 이벤트 기반인지, 모노레포인지, 어떤 언어인지 가정하지 않는 것이 이 도구의 전제이기 때문이다.

그런데 `luma` 팀은 안다. 그것을 받는 자리가 **포트 일곱**이고, **절반 이상은 코드가 아니라 선언으로 채워진다.**

```toml
# .palimpsest/packs/nestjs.toml   — 코드 한 줄 없이
[[recognizer]]
kind = "entrypoint"
match = { decorator = ["@Get", "@Post", "@Delete"] }
yields = "http-route"

[[rule]]
id = "R-7"
match = { decorator = "@Roles" }
yields = { label = "guard", kind = "authorization" }
```

```
$ pal pack load .palimpsest/packs/nestjs.toml

인식기 3 · 규칙 5 · 개념 0
  진입점        +47   (HTTP 라우트)
  가드 라벨    +112   asserted_via = rule(R-7)
  미해소 참조  -4,102 → -3,880   문자열 기반 라우트 레지스트리가 풀렸습니다

⚠ 규칙 R-7 하나가 라벨 112개를 파생시킵니다.
   R-7 을 고치면 112개가 전부 stale 이 되고 파급 범위가 계산됩니다.
```

**규칙 한 줄의 승인이 라벨 112개를 세운다.** 이것이 승인 노동의 단가를 내리는 가장 강한 장치이고, 동시에 가장 위험한 장치다 — R-7이 틀리면 112개가 전부 틀리기 때문이다. 그래서 파생 라벨은 **규칙 좌표에 결박된다.** 규칙을 고치면 파생된 것 전부가 `stale`이 되고, 규칙을 지우면 그것은 "해결됨"이 아니라 **범위 축소**로 잡힌다.

선언으로 안 되는 것 — 코어가 모르는 언어의 추출기, CI·SAST 조달자 — 은 **실행 파일**로 붙는다. 표준 입출력으로 JSON을 주고받고, **코어는 그것을 실행하지 않는다.** 호출은 CLI나 CI가 하고 결과는 §7.4의 창구로 들어오며, 그 산물은 전부 `observed`다. 프로젝트가 짠 코드의 재현성을 코어가 검사할 수 없기 때문이고, 그 선을 넘으면 "기계가 결정론적으로 계산했다"는 계약이 남의 코드로 넘어간다.

**포트가 전부 비어 있어도 모든 질의가 답한다.** §2.2의 대장에 `provider 0/7`로 적혀 있던 것이 그 뜻이다 — 팩이 있으면 하한이 올라가고, 없으면 하한이 낮은 채로 그 사실이 보인다.

## 8. 그런데 P1까지만 만들면?

계획은 P1에서 멈출 수 있게 짜여 있다. 그 상태에서도 제품이다 — **큐레이션 · 컨설팅 · 조달 경유 감사**가 선다. 위 이야기 중 §3·§4·§5.1·§6이 그대로 돌아가고, §5.3도 **`[조달]` 줄만** 돌아간다.

없는 것은 **자체 판정** 감사와 효과 집합(`writes` 줄)과 진입점 목록(§5.2)이다. 그때 화면은 이렇게 된다.

```
■ 이 심볼이 하는 것
  호출자  9  (exact 7 · candidate 2)
  호출   14  (exact 11 · candidate 1 · 미해소 2)
  (효과 집합 없음 — F13 미구축)

■ 판정
  Finding   1  semgrep@p/security-audit · 2일 전 · live      ← 조달 경유는 선다
  (자체 판정 능력이 없습니다 — F15 미구축)
  ※ 위 1건은 외부 엔진이 찾은 것이며, 이 빌드는 스스로 판정하지 않습니다.

■ 이 답의 근거
  … · 능력: 큐레이션 · 컨설팅 · 감사(조달)   /   미구축: 감사(자체) · 효과 · 진입점
```

**두 줄이 나란히 있는 것이 요점이다.** `Finding 1`이 떴다고 해서 "검사가 돌았다"가 아니고, 자체 판정 능력이 없다고 해서 "아무것도 못 본다"도 아니다. **무엇이 본 것이고 무엇이 안 만든 것인지가 화면에서 갈린다.**

**빈 자리가 "이상 없음"으로 보이지 않게 하는 것**이 이 설계에서 제일 신경 쓴 부분 중 하나다. 미완성 제품이 완성된 척하는 가장 흔한 방식이 빈 목록을 성공으로 보여주는 것이다.

## 9. 백서의 여섯 산출이 이 이야기의 어디였나

백서 §8이 여섯 가지를 열거한다. 이 문서의 장면과 대응시키면 이렇다.

| 산출 | 질문 | 이 문서에서 | 언제 켜지나 |
|---|---|---|---|
| **큐레이션** | "왜 이렇게 되어 있나 / 이게 아직 맞나" | §4 화요일 오후 | **P1 — 첫 번째 목표.** 대체재가 없다 |
| **컨설팅** | "여기 바꾸면 뭐가 깨지나" | §5.1 브리핑 | **P1.** 같은 장치 위에 서므로 거의 공짜 |
| **온보딩** | "이 기능은 어디서 시작해 어디로 흐르나" | §5.2 환불 흐름 | P2 — 진입점 인식기가 자라야 한다 |
| **감사** | "이 흐름에 구멍이 있나" | §5.3 인가 검사 | **둘로 갈린다** — 조달 경유는 **P1**, 자체 판정은 P2(**가장 비싼 베팅**) |
| **중재** | "내 브랜치와 팀 브랜치 중 어느 쪽이 최신인가" | §6.4 `--base` 델타 | P3 |
| **질의** | 임의의 프로젝트 질문 | 위 전부의 조합 | P3 — 산출이 아니라 표면 |

**첫날에 여섯 개가 다 유용한 척하지 않는다.** 성숙 프로젝트에서는 사실층이 즉시 서니까 컨설팅·온보딩이 먼저 쓸모 있고, 큐레이션은 의도층이 쌓이면서 자란다. 신생 프로젝트는 정확히 반대다 — 결박할 코드가 아직 없으니 `pending`이 대부분이고, 코드가 생기면서 하나씩 `live`로 바뀐다.

**감사가 둘로 갈린 것이 이 표에서 2026-08-10에 바뀐 유일한 칸이다.** 자체 판정은 제어흐름·가드 라벨·사람의 승인 노동이 전부 필요하고 하나만 무너져도 산출 전체가 `Residual`이 된다. 조달 경유는 그 사슬을 우회한다 — **남이 이미 돌리고 있는 것을 좌표에 못 박는 데는 라벨이 필요 없다.** 다만 그 대가로 능력의 존재가 대상 환경에 걸린다: CI도 SAST도 없는 프로젝트에서는 이 칸이 빈다.

## 10. 설계 원리가 화면에서 어떻게 보이는가

백서 §9의 원리 14개는 추상적으로 읽힌다. 그런데 전부 **화면의 어느 한 줄**로 나타난다.

| 원리 | 화면에서 |
|---|---|
| **P1** 코드가 근거의 원본 | 모든 답이 `Snapshot luma@8f3c21a`를 달고 나온다 |
| **P2** 사실과 추론을 분리 | 브리핑의 `■ 제안` 블록이 따로 있고 `inferred`라고 적혀 있다 |
| **P3** 근거 없는 답을 안 냄 | `Finding`에 반례 경로가 `cli/admin.ts:212`처럼 붙는다 |
| **P4** 공백을 정직하게 | `■ 내가 모르는 것`, `Residual 14`, 대장의 `unsupported 9` |
| **P5** git이 원본, 그래프는 투영 | `.palimpsest/`를 지워도 `git checkout` + 41초면 전부 복구된다 (§7.1) |
| **P6** 완전성이 정밀도보다 앞 | `candidate` 엣지를 버리지 않고 **후보 집합째** 들고 있다 |
| **P7** 환경에 종속되지 않음 | Claude Code 없이 `pal` CLI만으로 전부 된다. provider가 0개여도 답한다 |
| **P8** 생성형 큐레이션은 1급 | `■ 제안`이 존재한다. 다만 근거 좌표 없이는 저장되지 않는다 |
| **P9** 점진 회상 | `touch`가 상위 10건 + 요약만 준다. 나머지는 후속 질의 |
| **P10** 생성자와 검증자 분리 | 합성물에 `produced_by {모델, 프롬프트 해시, 스냅샷}`이 붙는다. 그리고 **낡음이 재생성을 부르지 않는다** (§7.2) |
| **P11** 빌드하지 않음 | 41초 설치. 3년 전 커밋도 같은 방식으로 열린다. semgrep도 provider도 **밖에서** 돈다 |
| **P12** 설치 비용이 1급 제약 | 캐시 상한 기본 2GB · LRU 축출 · `pal cache stats` · 상주 프로세스 없음 |
| **P13** 책임은 사람의 자리 | 승인 없이 `inferred`가 `asserted`가 되는 경로가 없다. 억제도 근거·만료 없이는 수용되지 않는다 |
| **P14** 판정은 통독이 아니라 대조 | 지수가 diff를 다 읽지 않고 네 줄을 보고 멈췄다 (§4) |

**P14가 §4 장면의 요점이다.** 지수는 에이전트가 쓴 코드를 통독해서 문제를 찾은 게 아니다. 기계가 들고 있는 기준(`#218`이 같은 자리에서 났고, `ADR-0031`이 `stale`이고, `SettlementGate.check`가 변했다)에 **대조**해서 멈췄다. 통독이 검토의 정의면 검토 속도가 전체 처리량의 천장이 되고, 그 천장은 에이전트가 코드를 더 많이 쓸수록 낮아진다.

**그리고 P14는 이 도구가 채점되는 방식이기도 하다.** 화면이 얼마나 정확했는지가 아니라 **지수가 다른 코드를 쓰게 됐는지**로 채점된다. 정확한데 아무것도 바꾸지 않는 산출은 통과가 아니다([DESIGN §0.8](DESIGN.md) · [goals §0.1](plan/00-goals.md)).

## 11. 그래서 기존 도구와 뭐가 다른가

정직하게 말하면 **겹치는 게 많다.** 코드 그래프, 호출 관계, 진입점 목록 — 이건 여러 도구가 한다. 어떤 건 palimpsest보다 정밀하게 한다(빌드를 하니까). 그리고 취약점은 **semgrep이 우리보다 잘 찾는다** — 그래서 우리가 찾지 않고 받는다(§3.4).

다른 것은 다섯뿐이다. **이 다섯 중 하나라도 안 지켜지면 만들 이유가 없다.**

### ① 모르는 것을 안다고 하지 않는다

대부분의 코드 그래프 도구는 못 푼 참조를 **조용히 버린다.** 그러면 그래프가 깨끗해 보인다. 그리고 `"닿는 경로 없음"`과 `"가는 참조 12건이 미해소"`가 같은 답이 된다. 앞의 것은 안전이고 뒤의 것은 무지인데.

palimpsest에서 `UnresolvedRef`는 **1급 노드**다. 지우지 않고, 이유를 달고, 집계되고, 나중에 실행 관측으로 해소돼도 **원본은 남는다**(다른 환경에서는 다시 못 풀 수 있으니까).

### ② `clean`을 출력하지 않는다

판정 타입에 "위반 없음"이라는 값이 **아예 없다.** 271개 엔드포인트에 "전부 위험"도 "이상 없음"도 말하지 않는다. 못 판정한 것은 `Residual`로 남고, **그 잔여가 좌표에 결박되어 나중에 사람 앞에 다시 온다.**

### ③ 낡음이 표시된 상태다

문서가 낡는 건 못 막는다. **낡았다는 사실의 감지는 기계적으로 가능하다.** 그리고 그 감지의 단위가 라인이 아니라 정규화된 심볼이라서 포매팅 커밋에 `stale`이 켜지지 않는다 — 그게 안 되면 사람이 표시를 무시하고, 무시되는 순간 제품이 죽는다.

### ④ 빌드하지 않는다

이건 약점처럼 보이고 실제로 정밀도를 잃는다. 그런데 **잃는 것은 정밀도이지 완전성이 아니다.** 넓게 잡는 것은 빌드 없이도 할 수 있고, 좁히는 것은 근거를 보며 에이전트와 사람이 한다.

그리고 빌드하지 않기 때문에 **임의의 과거 커밋에서 균일하게 돈다.** 그게 없으면 계보를 못 따라간다 — "이 결정이 3년 전 그 커밋 기준으로 쓰였다"는 말은, 3년 전 커밋에 대해 지금과 같은 방식으로 답할 수 있을 때만 뜻이 있다.

### ⑤ 남이 찾은 것도 낡는다

이게 마지막이고, 앞의 넷이 없으면 성립하지 않는다.

semgrep의 alert는 **실행할 때마다 새로 나고 어디에도 결박되지 않는다.** PR이 닫히면 사라지고, 3개월 뒤 같은 코드를 만지는 사람은 그런 게 있었는지 모른다. 억제 주석 `// nosemgrep`은 코드에 영원히 남지만 **왜 붙었는지는 아무 데도 없다.**

palimpsest가 그 산출에 하는 일은 다섯이다 — **좌표에 못 박고, 낡으면 낡았다고 말하고, 엔진이 못 본 범위를 함께 세고, 억제에 근거와 만료를 요구하고, 두 엔진이 어긋나면 그것을 신호로 만드는 것.** 어느 것도 엔진 자신은 하지 못한다. 그리고 **이 다섯이 안 되면 그냥 semgrep을 돌리는 편이 낫다** — 그게 이 능력의 반증 조건이다.

## 12. 한 장으로

```
설치 41초
   ↓
대장이 먼저 나온다 — 무엇을 보았고 무엇을 안 보았는가
   ↓
기존 문서·결함 기록을 끌어와 코드 좌표에 못 박는다 (사람이 승인)
이미 돌고 있는 CI·SAST 산출도 같은 좌표로 들어온다
   ↓
누군가 그 코드를 만지려는 순간 ─────────────┐
   ↓                                        │
touch 가 뜬다                                │  ← 여기가 제품
  · 걸린 결정 (live/stale/pending × current/superseded)
  · 여기서 났던 일 (결함 계보)                │
  · 이 심볼이 하는 것                         │
  · 내가 모르는 것                            │
  · 판정 (Finding / Residual — clean 없음)   │
  · 외부 엔진이 본 것 (그리고 못 본 범위)     │
  · 이 답의 근거 (대장 요약)                  │
   ↓ ───────────────────────────────────────┘
사람이 통독이 아니라 대조로 판정한다
   ↓
그래서 **다음 변경이 달라진다**  ← 이것으로 채점된다
   ↓
코드가 변하면 무엇이 낡았는지 기계가 말한다 (탐지만. 고치지 않는다)
   ↓
낡은 것이 다시 사람 앞에 온다
   ↓
승인은 텍스트로 git 에 남아 팀이 공유한다
```
