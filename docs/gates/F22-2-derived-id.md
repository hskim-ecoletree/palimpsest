## 이 조각이 이 저장소에서 처음 하는 일

F22 문서 §1 은 *"F01 이 첫 노드를 만드는 순간 스키마가 있어야 한다. 나중에 만들면 그것은
스키마가 아니라 이미 만들어진 것의 목록이다"* 라고 적었다. 슬라이스 넷은 그 순서를 지키지
못했고 [F22-1](F22-1-schema.md)은 그래서 **정본화**였다.

**여기서는 순서가 맞다.** `Synthesis`(F17) · `Finding`(F15) · `Observation`(F16)을 만드는
기능이 하나도 없는 상태에서 그것들의 정체성 규칙이 먼저 선다. `pal-core::derived` 를
지금 아무도 부르지 않는 것은 결함이 아니라 **이 기능의 목적 그 자체다.**

## ④ 음성 대조가 실물 결함을 잡았다 — **이 게이트에서 가장 중요한 사건**

`scripts/f22-2-verify.sh` 는 **선행 구현이 무너진 방식을 코드에 그대로 재현**한다 —
성분을 하나씩 빼고 픽스처가 실제로 무너지는지 본다.

첫 실행에서 **하나가 통과했다**:

```
✗ 생산자를 성분에서 뺌 (연구 G §2 의 재현)
    derived::tests::두_엔진의_같은_판정이_두_노드로_선다 가 여전히 통과한다
```

### 무엇이 잘못돼 있었나

초안 픽스처는 판정 **둘**이었다 — 정적 엔진(`observed` · `provider("sast")`)과
에이전트(`inferred` · `agent`). **그 둘은 출처도 다르다.** 그래서 생산자를 해시에서
빼도 출처만으로 갈라졌고, 픽스처는 초록이었다.

즉 **[R14] 가 지목한 성분(생산자)을 격리하지 못했고, 선행 구현의 고장을 그대로
재현해도 통과하는 픽스처**였다. 그것은 붕괴 픽스처가 아니라 붕괴 픽스처의 모양을 한
것이다.

### 고친 형태

셋으로 늘렸다 — **출처를 고정한 채 생산자만 바꾸는 셋째**를 넣었다.

| | 출처 | 생산자 |
|---|---|---|
| 정적 엔진 A | `observed` | `provider(sast-a)` |
| **정적 엔진 B** | `observed` | **`provider(sast-b)`** |
| 에이전트 | `inferred` | `agent` |

셋이 세 노드로 서야 하고, 생산자가 성분에서 빠지면 **셋이 둘로 접혀** 시험이 무너진다.
이것이 [F16 §1.2](../plan/features/F16-observation-intake.md)의 다섯째 몫(엔진 간
불일치)이 성립하는 조건이다 — **붕괴한 것은 어긋날 수 없다.**

### 그리고 그것이 이 규율의 값이다

음성 대조가 없었다면 이 게이트는 **통과로 기록됐을 것이다.** 픽스처는 초록이었고,
`[f22.2]` 의 ①②③④ 도 전부 초록이었다. 잡은 것은 *"이 검사가 고장 났다면 어떻게
드러나는가"* 하나뿐이었다.

```
── 성한 상태 ──
  ✓ 파생 정체성 시험 12 건 전부 통과
── 성분을 빼면 픽스처가 무너지는가 ──
  ✓ 생산자를 성분에서 뺌 (연구 G §2 의 재현)   무너졌다
  ✓ 출처를 성분에서 뺌                          무너졌다
  ✓ 재현 입력을 성분에서 뺌                     무너졌다
  ✓ 대상 정렬을 없앰                            무너졌다
  ✓ 길이 접두어를 없앰                          무너졌다
── 본문 ──
  ✓ compute 의 인자에 본문이 없다
```

**본문 방향만 변이로 시험하지 않았다.** 넣을 자리 자체가 없기 때문이고, **그것이 강제의
형태다** — `DerivedId::compute` 의 시그니처에 본문이 없으므로 본문을 성분으로 만들려면
API 를 바꿔야 한다. 스크립트는 시그니처를 확인하고, `본문만_다른_둘은_한_노드다` 가
같은 인자로 두 번 부른 결과가 한 노드이고 **둘째 쓰기가 갱신**임을 센다.

## 성분 다섯 — 그리고 넷이 아닌 이유

DESIGN §1.2 D33 은 넷을 적었다(대상 좌표 · 출처 · 생산자 · 재현 입력). 구현은 **다섯**을
쓴다 — 앞에 **라벨**이 붙는다.

`Finding` 과 `Synthesis` 가 같은 대상·출처·생산자·입력을 가질 수 있고, 그 둘이 한 노드로
접히면 *"판정"* 과 *"요약"* 이 서로를 덮는다. 라벨을 넣는 것은 규칙의 확장이 아니라
네임스페이스 접두어(§2.2)를 종류 단위까지 내린 것이다.

**그리고 생산자는 이름만이 아니라 인자까지 성분이다.** `provider(sast-a)` 와
`provider(sast-b)` 가 접히면 엔진 간 불일치가 성립하지 않는다 — 위 픽스처의 셋째가
정확히 그것을 시험한다.

## 붕괴의 반대편 고장도 시험했다

등록값에 없던 둘을 더 넣었다. 성분 민감도만 보면 **너무 민감한** id 가 만점을 받기 때문이다.

| 시험 | 왜 |
|---|---|
| `대상의_순서는_정체성을_바꾸지_않는다` | 같은 집합을 다른 순서로 준 두 산출이 갈리면 계보가 소음이 된다 |
| `목록의_경계가_없으면_다른_집합이_하나가_된다` | 길이 접두어가 없으면 `["ab"]` 와 `["a","b"]` 가 같은 바이트열이 된다 — `SymbolId` 의 `\0` 만으로는 **가변 길이 목록**에서 부족하다 |

## 이 게이트가 판정하지 않는 것

- **파생 노드가 실물로 서는 것이 아니다.** 만드는 기능(F15 · F16 · F17)이 없다.
  시험은 전부 픽스처 위에서 일어났고, 그것이 이 조각의 성격이다.
- **계보가 아니다.** `promoted_by` · `superseded` 축은 F12 다. 여기서는 *"승격된 노드가
  원본과 다른 id 를 갖는다"* 까지다(출처가 성분이므로 자동으로 성립한다).
- **불변식 3 이 아니다.** *"id 가 같은데 출처가 다르면 스키마 위반"* 을 **잡는 것**은
  [`doctor`](../plan/features/F22-graph-schema.md) 의 몫([#45](https://github.com/hskim-ecoletree/palimpsest/issues/45))이다. 여기서는 그런 값이
  **애초에 계산될 수 없다**는 데까지다 — `compute` 가 출처 없이는 부를 수 없다.
- **`NodeRef` 가 완전하지 않다.** 변형이 `Symbol` 과 `Derived` 둘뿐이다. `Change` ·
  `Actor` 를 가리킬 자리는 [#44](https://github.com/hskim-ecoletree/palimpsest/issues/44)가 그것을 만들 때 는다 — **없는 것을 미리 두지 않는다.**
