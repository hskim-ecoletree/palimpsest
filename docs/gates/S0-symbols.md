## 대조 회차 — 2026-08-12

### 방법 — 왜 바이너리를 1,122번 부르는가

전수 대조를 ⓐ **바이너리를 파일마다 부르는 스크립트**로 할지 ⓑ 서브커맨드를 하나 더 둘지가
착수 시점의 미정 사항이었다. **ⓐ 를 택했다.** 도구는
[`scripts/s0-compare.py`](../../scripts/s0-compare.py).

1. **대조 전용 경로를 하나도 만들지 않는다.** 합격선이 묻는 것은 *"출하되는 코드가 레퍼런스와
   같은 값을 내는가"* 이고, ⓐ 는 출하물(`pal` 바이너리) 그 자체를 몬다. ⓑ 는 판정을 위해
   새 경로를 추가하고, 그 경로가 검사받지 않는다.
2. **게이트를 통과시키려고 1급 표면을 늘리지 않는다.** S0 이 뚫기로 한 것은 서브커맨드
   하나(`pal symbols`)다. 대조용 명령을 더 두면 그 명령의 존재 이유가 게이트가 된다.
3. **대조의 양쪽이 같은 층위에 선다.** 레퍼런스도 스크립트(`s0-reference.py`)가 CLI 를 몰아
   만들었다. 한쪽만 바이너리 내부로 들어가면 비교가 비대칭이 된다.
4. **비용이 문제가 아니었다.** 재고 결정했다 — 1,122회 호출에 **18.1초**.

파일 목록 규칙(`sorted(rglob("*.kt"))`)과 경로 표기(코퍼스 상대)는 레퍼런스 생성기와 **같은
코드 모양**으로 맞췄다. 선언 수는 `pal symbols --json` 이 낸 **JSON 배열의 길이**이고,
레퍼런스 쪽 단위(쿼리 매치 하나 = 선언 하나)와 같다.

### 환경 — 재현 좌표

```
코퍼스   corpus/manifest.toml [corpus.pin] @ a29cad0bf6a8 · 10185f804ad8 · 2e9198716796
         ./scripts/s0-corpus.sh /tmp/s0-corpus ~/dev/projects/boxwood   → 671+434+17 = 1122
바이너리 target/release/pal (e0f6c42 + 작업트리 무변경) · rustc 1.94.1
문법     tree-sitter-kotlin-ng 3dea6df · tree-sitter 런타임 0.26.12
쿼리     crates/pal-extract/queries/kotlin/top-level.scm  — **이 회차에서 손대지 않았다**
```

**쿼리 파일에 diff 가 없다는 것이 이 대조의 전제다.** 한쪽만 고치고 대조하면 그것은 판정이
아니라 사후 조정이다. `git diff HEAD -- crates/pal-extract/queries/` 가 비어 있음을 확인했다.

### 결과

```
./scripts/s0-compare.py --corpus /tmp/s0-corpus
```

| | 관측 | 기대 |
|---|---|---|
| 관측 파일 | 1,122 | 1,122 |
| **불일치** | **0** | **0 (합격선)** |
| 실행 실패 | 0 | 0 |
| 레퍼런스에만 있는 경로 | 0 | 0 |
| 관측에만 있는 경로 | 0 | 0 |

종료 코드 `0`. 관측 벡터는 레퍼런스 1,122행과 **전 항목 일치**한다.

### 이 대조가 고장이 아님을 보인 것 — 음성 대조

**통과를 보고하는 도구가 아무것도 하지 않는 도구일 수 있다.** 판정이 그 위에 서면 안 되므로
레퍼런스를 일부러 세 곳 틀어 놓고 같은 도구를 다시 돌렸다.

| 주입한 변조 | 잡혔는가 |
|---|---|
| 어떤 파일의 선언 수 `1` → `2` | ☑ 불일치로 나옴 (`2 → 1`) |
| 다른 파일의 선언 수 `1` → `8` | ☑ 불일치로 나옴 (`8 → 1`) |
| 경로 끝에 `.bogus` 를 붙임 | ☑ *레퍼런스에만 있음* 1 · *관측에만 있음* 1 |

변조본에서 종료 코드 `1`, 정본에서 `0`. **도구는 차이를 본다.**

### 부차 확인 — 최적화 수준이 값을 바꾸지 않는다

`target/debug/pal` 로도 전수 대조를 돌렸다. **불일치 0건이고, 관측 벡터 1,122행이
release 의 것과 바이트까지 같다**(헤더의 바이너리 경로만 다름). 최적화가 추출 결과를 바꾸면
그것이 곧 결함이므로 확인했고, 바꾸지 않았다.

## R-01 판정 — 무엇이 관측됐고 무엇이 아직 아닌가

**막히지 않았다.** [R-01](../plan/00-risks.md#r-01)의 증상은 *"소유권·수명·트레잇 객체에서
막히면 **며칠이 사라진다**"* 이고, 합격선 등록(`14dc336` · 15:57)에서 이 판정(20:16)까지
**4시간 19분**이다. 기한 3일의 6분의 1이다. 며칠은 사라지지 않았다.

**그러나 이 판정이 덮는 범위는 좁다. 그 좁음을 여기 적는다.**

1. **R-01 의 판정 시점은 원래 "F01~F03 완료 여부"다**([00-risks.md](../plan/00-risks.md) 위험
   표). S0 은 그 앞의 관통 슬라이스이므로 이것은 R-01 의 **첫 관측이지 종결이 아니다.**
2. **위험이 겨눈 난소가 이 슬라이스에 거의 등장하지 않았다.** `dyn` 을 쓰지 않았고 수명
   파라미터가 나오지 않는다 — `extract` 를 트레잇 객체 대신 `match` 로 가른 결과다
   (R-01 §대응1 이 의도한 형태이기도 하다). 즉 **막히지 않은 것과 시험되지 않은 것이 여기서
   겹친다.** 수명 파라미터의 첫 시험대는 `EdgeCursor`(P0 후반)이고 아직 오지 않았다.
3. **[R-18](../plan/00-risks.md#r-18)(게이트를 스스로 판정한다 · 구조적·영구)이 그대로
   걸려 있다.** 대조 도구를 만든 쪽과 판정하는 쪽이 같다. 위의 음성 대조는 그 위험을
   없애지 못하고 **줄이기만 한다** — 도구가 차이를 본다는 것까지만 보이고, 합격선이 옳게
   골라졌는지는 보이지 않는다. 합격선을 소유자가 결과 이전에 정한 것이 그 자리의 방어다.

**결론 — stack §1 의 Rust 결정은 재론하지 않는다.** 재론 조건(기한 초과 · 언어 때문에 막힘)
어느 쪽도 발생하지 않았다.

## 정정 — 관측 회차가 성립하지 않는다 (2026-08-12, 착수 직후)

**등록에 "판정용 3dea6df · 관측용 최신"이라고 적었고 그것은 같은 것을 둘로 적은 것이었다.**

```
git rev-list --count 3dea6df..origin/HEAD   →  0
최신 태그 v1.1.0                             =  3dea6df
crates.io tree-sitter-kotlin-ng 1.1.0        =  3dea6df
마지막 커밋 2025-01-16                        →  19개월째 정지
```

**결과를 보기 전에 고쳤다** — [§5.1](../plan/features/P0-preflight.md)의 규율은
*"커밋 이후 불변"*이 아니라 **"결과 이전"** 이다. 조용히 고치지 않고 여기 적는다.

**이것이 드러낸 것 — S0 을 막지는 않지만 기록되어야 한다.**
T7 이 관측한 결함 둘은 **문법 업그레이드로 고쳐질 수 없다.** 최신이 곧 T7 이 쓴 그것이다:

| 결함 | 규모 |
|---|---|
| Exposed `} get` 파싱 실패 | **73파일** — T7 실패 87건의 84% |
| 조용한 오파싱 | **17파일** |

crates.io 에 포크가 여섯 있다(`-sg` · `-codanna` *"includes unreleased fixes from upstream"* ·
`brokk-` · `-sqry` · `-updated` · `tree-sitter-kotlin`). **포크가 그만큼 생겼다는 것이
upstream 이 멈췄다는 신호다.** Kotlin 은 1급 지원 대상인데 그 문법이 유지보수되지 않는다.

**처분은 F02 가 진다** — 포크 채택 · 자체 패치 · 관용구 우회 중 무엇인지 지금 정하지 않는다.
**S0 에서 손대지 않았다.** 손댔으면 이 게이트가 재는 것(Rust 경로 == CLI 경로)이 오염된다.

## 부차 관측 — 판정에 쓰지 않고 기록만 한다

레퍼런스의 `parse` 컬럼과 이번 관측 벡터를 교차해서 얻었다.

| | 관측 | T7 |
|---|---|---|
| 선언 총수 | 2,241 | 2,241 ☑ |
| 선언 ≥1 파일 | 1,058 (**94.30%**) | 1,058 (94.30%) ☑ |
| 파싱 실패 파일 | 56 | 56 ☑ |
| 파싱 성공했는데 선언 0건 (조용한 오파싱) | 17 | 17 ☑ |

**T7 이 다섯 값에서 그대로 재현됐다.** 재현이 정상이다 — 같은 문법 · 같은 쿼리이므로 결함도
같이 재현되어야 하고, 재현되지 않았다면 그것이 이상 신호였을 것이다.

한 가지 새로 보인 것: **파싱 실패 56파일 중 9파일은 그래도 선언을 낸다.** 부분 트리에서
뽑히기 때문이고, 레퍼런스도 같은 값을 냈다. 이 9파일의 선언이 옳은지는 **재지 않았다** —
그것은 추출 품질이고 아래가 말하는 대로 이 게이트의 질문이 아니다.

## 이 게이트가 판정하지 않는 것

**추출 품질이다.** 벡터가 완전히 일치해도 증명되는 것은 **"Rust 경로 == CLI 경로"** 까지이고,
둘은 같은 방식으로 틀릴 수 있다 — T7 이 발견한 조용한 오파싱 17건은 파서가 오류를 내지
않으므로 양쪽에서 똑같이 사라진다. T7 이 뽑은 선언 **2,241건 중 사람이 세어 본 것은 41건(1.8%)** 뿐이다.

**선언의 *이름*도 판정하지 않았다.** 오라클이 선언 **수** 벡터이기 때문이다. 개수가 같고
이름이 다른 경우는 이 대조를 통과한다. 합격선을 사후에 넓히지 않기 위해 그대로 둔다.

품질은 [계획 §5](../plan/README.md)의 오라클 *"심볼 리콜 표본"* 이 지며 **소유 기능은 아직 미정**이다.
근거는 [`criteria.toml`](../../corpus/criteria.toml) `[s0.does_not_prove]`.

**Java · JavaScript · TypeScript 도 판정하지 않는다.** 셋은 1급 지원 대상이지만
([지시 §1](../instructions/2026-08-12-owner-direction.md)) 사전 등록된 대조값이 없다.
S0 에서 셋의 자리는 `Capable::NotBuilt` 이고, 각각의 게이트는 따로 선다.

## 이 게이트를 닫으면서 남기는 빚

**`cargo-deny` 가 아직 켜지지 않았다.** [stack §4.3](../plan/00-stack.md) 단계 1 에 등록돼
있으나 S0 의 커밋들에 없다. S0 의 합격선이 아니므로 이 판정을 막지 않지만, 등록된 검사가
빠진 채로 다음 기능이 시작되면 그것이 곧 drift 다.
