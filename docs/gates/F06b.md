**판정: 통과.** 반증 **0** · **대조 불가 0**. ⚠ **등록 문장과 산출이 어긋난 자리 넷**
(③⑥⑦⑨)이 있고 **고치지 않고** §판정-나 에 적는다 — 문장을 지금 고치면 「재기로 한
것」이 「잰 것」에 맞춰 움직인다.

★ **이 문서는 두 층이다.** 아래 「판정」 절이 이 회차의 산출이고, §1~§5 는 **등록 그대로**

## ★ 판정 — 합격선 아홉에 대해

**어떻게 쟀나.** 아래 전부를 **이 회차가 직접 실행해서** 관측했다 — 남의 보고를 근거로
쓰지 않았다. 재는 자리는 셋이다:

  · **실 MCP 세션** — 같은 SDK(`rmcp` 3.1.2)의 **클라이언트**가 자식 프로세스
    `pal serve` 를 몰고 `initialize`→`tools/list`→`tools/call` 을 완주한다
    (`crates/pal-cli/tests/mcp_session.rs`). 손으로 만든 JSON 을 파이프에 붓지 않았다.
  · **밖에서 망가뜨리기** — `scripts/f06b-verify.py` 가 카탈로그를 변형하고 **매번
    복원하며** 세션 시험을 돌린다. 그리고 어댑터를 뺀 빌드를 실제로 세운다.
  · **정적 검사** — `cargo xtask check` 16 개.

**이 회차의 게이트값**(전부 이 기계에서 쟀다 · 2026-08-17):

### 판정-나 — **등록 문장과 산출이 어긋난 자리 넷**

**고치지 않는다.** 무엇을 재기로 했었는지가 판정을 읽는 근거다.

**③ — 인자의 「타입」은 안 댔다.** 등록은 *"이름만이 아니라 **인자 이름과 필수 여부**도
같아야 한다"* 이고 잰 것이 정확히 그 둘이다. 그런데 카탈로그는 `type`(`SymbolName` ·
`RepoPath`)도 적고 어댑터는 그것을 스키마의 `description` 에 싣는다 — **그 값이 카탈로그와
같은지는 아무도 안 댔다.** 등록 문장은 지켰고, **등록이 좁았다.**

**⑥ — 「전건」이 워크스페이스가 아니다.** 등록은 *"어댑터 없는 빌드에서 `cargo test` 전건
통과"* 인데 실제로 돌린 것은 **`cargo test -p pal-cli --no-default-features`** 다.
`--no-default-features` 를 워크스페이스에 걸면 **다른 크레이트의 기본 feature 까지** 끄고,
그러면 재는 것이 *"어댑터 부재"* 가 아니라 *"모든 기본값 부재"* 가 된다. 그래서 어댑터를
가진 크레이트 하나로 좁혔다. **381 은 769 의 부분집합이고, 그 차이가 무엇인지 이 게이트는
안 잰다.**

**⑦ — 등록이 적은 음성 대조가 성립하지 않았다.** 등록은 *"어댑터에 `pal-cli` 의존을
넣으면 검사 1 이 빨개져야 한다"* 인데, 넣어 보니 **`cargo` 가 먼저 막았다**:

```
error: cyclic package dependency: package `pal-cli` depends on itself
```

**검사 1 은 도달조차 못 했다.** `pal-cli` 는 최상위라 그것에 의존하면 **언제나 순환**이고,
그 방향은 빌드 시스템이 이미 막는다. 그래서 규칙 3 이 **살아 있는지를 다른 방향으로**
쟀다 — `xtask` 에 `pal-cli` 의존을 넣으니(순환 아님) 검사 1 이 **rc=1 로
`xtask 가 pal-cli 에 의존한다 — 소비자 어휘의 역류`** 를 냈고, 되돌린 뒤 작업 트리가
깨끗했다. **규칙 3 은 산다. 다만 등록이 고른 변형으로는 그것이 안 보인다.**

**⑨ — 기계가 상시로 안 잰다.** 방향 4 의 스캔은 `rust_sources` 를 타므로 `.json`·`.md`
를 안 본다. 등록이 이 경우의 처분을 미리 적었고(*"그러면 눈으로 읽은 것이지 잰 것이
아니고, 그 사실을 판정에 적는다"*) **그대로 따랐다** — 스캔을 넓히는 것은 등록에 없는
새 측정이고 운영 순서 4 가 금한다. 지금 상태: **손으로 돌린 대조에서 0 건.** 내일 누가
`plugin.json` 에 질의 이름을 넣으면 **아무것도 안 운다.**

### 판정-다 — 회차 중에 드러난 것 셋

**(1) ★ 검증 중에 커밋하면 `버전에_커밋이_실려_있다` 가 거짓 실패한다.**
백그라운드로 `cargo xtask test` 를 돌리는 동안 커밋을 두 번 냈다. 시험은 **빌드 시점의
커밋**(`842c840`)이 박힌 바이너리를 쓰는데 **실행 시점의 `HEAD`**(`9928b58`)를 읽어
어긋났다. `build.rs` 는 `.git/HEAD`·ref 에 `rerun-if-changed` 를 제대로 걸어 두었고,
`cargo build` 를 부르니 재빌드되어 값이 맞았다 — **제품의 결함이 아니라 검증 순서의
문제다.** 바이너리를 `HEAD` 에 맞춘 뒤 다시 돌려 **rc=0** 을 얻었다.
⚠ **그러나 이것은 밟기 쉬운 함정이다** — §다음으로 넘기는 것.

**(2) `host_free.rs` 의 락 시험이 한 번 깨졌다 — 재현 안 됨.**
`cargo test --workspace --all-targets` 를 **`--no-fail-fast` 없이** 돌린 회차에서
`읽기_전용_여럿이_동시에_붙고_쓰기는_배타다` 가 `Database already open. Cannot acquire
lock` 으로 실패했다. **단독 3 회 전부 통과**했고, `--no-fail-fast` 를 붙인 전체 회차와
`cargo xtask test`(게이트 명령)에서도 **통과**했다. **재현이 안 되므로 고치지 않는다.**
이 시험은 F06 소유이고 이 회차가 건드리지 않았다.

**(3) CI 스텝에 셸 변수명을 한국어로 썼다가 되돌렸다.** bash 의 식별자는 비ASCII 를 못
받아 `없는쪽=x` 가 `command not found` 로 죽는다 — **재현해서 확인**했다(rc=127).
⚠ **같은 자리에서 의심한 둘째는 재현이 안 됐다**: `set -euo pipefail` 아래 `grep -q … &&
{ exit 1; }` 가 좌변 실패로 스크립트를 죽일 것이라 봤는데 **rc=0 으로 그대로 지난다**.
**재현 안 된 것은 안 고쳤다.**

### 다음으로 넘기는 것

**새 이슈를 열지 않는다**(운영 순서 1). 여기가 발견의 단일 진실이다.

1. **⑨ 를 기계가 재려면** 방향 4 의 스캔이 `.rs` 밖(`plugin.json`·`commands/*.md`)을
   봐야 한다. 지금은 **눈으로 읽은 것**이다.
2. **③ 의 인자 타입 대조** — 카탈로그의 `type` 이 MCP 스키마에 실린 값과 같은지 아무도
   안 댄다. 등록이 좁았던 자리다.
3. **⑥ 의 「전건」을 워크스페이스로 넓히려면** `--exclude pal-mcp` 같은 축이 필요하고,
   그것이 무엇을 재는지 먼저 정해야 한다.
4. **검증 순서의 함정**(판정-다-1) — *"빌드 → 커밋 → 시험"* 순서면 누구든 밟는다.
   시험이 **바이너리에 박힌 커밋과 `HEAD` 가 다르다**는 것을 *"두 빌드가 같은 값을 낸다"*
   와 다른 문장으로 낼 수 있는지는 **F24 소유**다.
5. **`host_free` 의 락 시험**(판정-다-2) — 재현되면 그때 F06 이 진다.

⚠ **넷과 다섯은 이 게이트가 만든 것이 아니다.** 넘기는 이유가 *"내 것이 아니라서"* 가
아니라 **재현이 안 되거나 소유가 다른 기능**이기 때문이다.

## 0. 등록 — 이 문서가 어떻게 태어났나

★ **왜 등록이 단독 커밋인가.** [F24 게이트](F24-install-distribute.md) §7.5-3 이 앞
회차의 발견으로 이렇게 적었다:

> *"두 새 게이트 문서에 「등록이 결과보다 먼저」라는 증거가 없다 — 두 문서는 등록이
> 아니라 판정과 함께 태어났다."*

**그 형태를 반복하지 않는다.** 이 커밋 시점에 산출은 하나도 없고(§4 가 그것을 실측으로
박는다), 판정은 다음 커밋들 뒤에 이 문서에 **더해진다.** 아래 §2 의 합격선 문장은
판정할 때 **한 글자도 안 고친다** — 문장을 나중에 고치면 「재기로 한 것」이 「잰 것」에
맞춰 움직인다.

⚠ **합격선의 정본은 이 문서가 아니다.** [`corpus/criteria.toml`](../../corpus/criteria.toml)
의 `[f06b]` · `[f06b.pass]` · `[f06b.does_not_prove]` 가 정본이고 이 문서는 그것을
**가리킨다.** F24 는 게이트 문서가 정본을 졌고 그 자리에서 *"두 곳에 적으면 그것이 곧
drift"*(진행 규칙 4)를 스스로 §5 에 넘겼다 — 그 부채를 새로 만들지 않는다. F06 계열은
이미 `[f06]`·`[f06.1]`·`[f06.2]`·`[f06.3]` 이 `criteria.toml` 에 산다.

**합격선을 정한 것도 판정할 것도 에이전트다** — [R-18](../plan/00-risks.md#r-18)은
닫히지 않는다.

## 1. 무엇을 묻는가


> **`pal` 을 사람이 아닌 것이 부를 수 있는가. 그리고 그 표면이 CLI 와 갈릴 수 있는가.**

[F06 문서 §1.1](../plan/features/F06-surface.md) 이 지위를 정했다 — ***"1급은 CLI 다.
프로토콜은 어댑터다."*** 그러므로 이 조각이 무언가를 **더한다면 그것은 능력이 아니라
경로다.** 능력을 더하는 순간 어댑터가 아니라 두 번째 코어가 된다.

그래서 이 게이트의 한가운데는 *"MCP 가 도는가"* 가 아니라 ***"MCP 가 CLI 와 갈릴 수
있는가"*** 다. 갈릴 수 있으면 카탈로그는 단일 진실이 아니고, 문서 §2 규칙 1 과
`[f06.1.pass]` 의 방향 넷이 **MCP 표면에 대해서는 꺼진 채로** 돈다.

### 1.1 ★ 스케치를 그대로 따르지 않는다 — 그리고 그것이 설계대로다

문서 §4.2 의 예시는 `#[tool_router]` + **질의마다 함수 하나**다:

```rust
#[tool_router]
impl PalimpsestServer {
    #[tool(description = "…")]
    async fn touch(&self, Parameters(a): Parameters<TouchArgs>) -> … { … }
}
```

**이 형태는 질의 열 개에 함수 열 개를 손으로 적는다 — 그것이 곧 두 번째 목록이다.**
그리고 그 목록은 `queries.toml` 이 변해도 안 따라온다. 문서 §2 규칙 1(*"질의 추가는
`queries.toml` 변경으로만 일어난다"*)과 정면으로 부딪힌다.

[문서 머리](../how-it-works.md)가 자기 지위를 *"아직 존재하지 않는 것의 스케치.
구현과 다르면 구현이 맞다"* 로 적었고, 같은 자격이 여기 붙는다. **규칙 1 이 이긴다.**
이 게이트는 툴 목록이 `QueryName::ALL` **에서 나오는 것**을 요구하고, 그것을 `[f06b.pass]`
③④⑤ 가 잰다.

> **실현 가능성은 착수 전에 쟀다** — `rmcp` 3.1.2 의 `ServerHandler` 를 직접 구현해
> `list_tools` 를 런타임에 만드는 최소 서버가 이 기계에서 **컴파일된다**(스파이크 ·
> 경고 0). 그러므로 이 요구는 *"되면 좋겠다"* 가 아니라 **된다고 확인한 것**이다.
> ⚠ 스파이크는 **API 형태만** 확인했다. 세션이 왕복하는지는 ①이 잰다.

## 2. 합격선 아홉 — 정본은 `criteria.toml`

| | 무엇을 재는가 | 음성 대조 — 검사가 고장이면 어떻게 드러나나 |
|---|---|---|
| **①** | 실 MCP 세션이 왕복한다 (`initialize`→`tools/list`→`tools/call`) | ②가 없는 이름을 부른다 |
| **②** | ★ **없는 툴 이름은 오류다** | 무엇을 불러도 성공이면 ①은 메아리를 잰 것 |
| **③** | 툴 목록 ↔ 카탈로그 **양방향** + 인자까지. 하한 6 | ④가 카탈로그를 실제로 망가뜨린다 |
| **④** | ★ **카탈로그를 망가뜨리면 ③이 실패한다** (변형 셋 · 매번 복원) | 변형이 아무것도 안 바꾸면 실패로 적는다 |
| **⑤** | 어댑터 소스에 질의 이름 리터럴 **0** — 방향 4 의 스캔을 넓힌다 | 리터럴을 심으면 `xtask check` 가 빨개진다 |
| **⑥** | 어댑터 **뺀** 빌드에서 전건 통과 + 그 빌드에 `serve` 가 **없다** | 두 빌드의 `--help` 를 각각 떠서 대 본다 |
| **⑦** | 어댑터가 `pal-cli` 에 의존하지 않는다 (검사 1 규칙 3) · 크레이트 8→9 | 의존을 넣으면 검사 1 이 빨개진다 |
| **⑧** | 응답 크기를 **실 세션에서** 재고 잰 것/가정한 것을 가른다 | 한 필드로 뭉개지면 실패 · 고정값이면 실패 |
| **⑨** | 플러그인에 로직 없음 · 질의 이름 리터럴 0 | 스캔이 `.rs` 만 보면 **눈으로 읽은 것**이라고 적는다 |

전문은 [`corpus/criteria.toml`](../../corpus/criteria.toml) `[f06b.pass]`. **여기 표는
요약이고 정본이 아니다** — 어긋나면 `criteria.toml` 이 맞다.

### 2.1 ⑦ 이 왜 합격선인가 — 가장 짧은 길이 규칙을 깬다

어댑터가 질의를 돌리려면 **조립**이 필요하다. 그런데 그 조립은 지금 `pal-cli` 안에
산다 — `query.rs` 가 대장을 만들고(`ledger::compute`) 2층에 붙고(`attach::attach`)
의도 저장소를 열고 예산을 세워 `QueryCtx` 를 만든다. 어댑터에서 그것을 쓰는 **가장
짧은 길은 `pal-mcp → pal-cli` 의존**이고, 그것이 정확히 검사 1 의 규칙 3 —
*"소비자 어휘의 역류"* — 이 금하는 것이다.

**그래서 이 자리를 미리 합격선으로 세운다.** 세우지 않으면 구현 중에 가장 짧은 길이
선택되고, 그 선택은 검사가 잡기 전까지 보이지 않는다.

### 2.2 ⑧ 이 상한을 안 세우는 이유

운영 순서 4 — *"완벽에 수렴하는 장치를 새로 만들지 않는다. 추가 측정 · 합격선 상향
금지."* ⑧이 요구하는 것은 **기록이 존재하고 두 값이 분리되어 있는 것**이지 어떤 수
아래인 것이 아니다. 상한은 `PROVISIONAL_VIEW_NODE_MAX` 가 이미 지고 있다.
