# palimpsest 설계 — 백서의 계약을 만족하는 구조

> **이 문서의 지위**
>
> - **성격**: 결정 문서(how). 백서가 *무엇이 성립해야 하는가*를 정했다면 이 문서는 *그것을 어떤 구조로 성립시키는가*를 정한다. 결정만 담고, 근거는 [`evidence-map.md`](evidence-map.md)(연구·백서 자기모순)와 [`instructions/2026-08-03-owner-direction.md`](instructions/2026-08-03-owner-direction.md)(지시 원문·조항 대조)에서 가리키기만 한다.
> - **권위**: 아직 없다. 코드도 ADR도 없으므로 이 문서는 ADR 후보의 묶음이다(§16).
> - **입력**: [`WHITEPAPER.md`](../WHITEPAPER.md)(계약) + [`docs/research/`](research/README.md)(증거) + 소유자 방향 지시(2026-08-03). 연구는 요구사항이 아니므로(research/README 33장) 능력 계약을 늘리는 데 쓰지 않았고 백서가 이미 연 질문에 답을 고르는 근거로만 썼다. 지시는 요구사항이다(§0.6).
> - **자기제약**: 백서와 충돌하면 백서가 이긴다. 단 백서가 자기 안에서 충돌하는 지점([`evidence-map.md §2`](evidence-map.md))은 이 문서가 우선순위를 정한다 — 그것이 이 문서의 존재 이유다.
> - **분할 규칙**: **결정은 이 문서에만 살고 근거 문서는 결정을 담지 않는다.** 반대도 같다. 이중화는 곧 drift이며 이 저장소에서 이미 두 번 일어났다(별도 파일 판에서 어긋난 자리 11건, 부록 흡수 판에서 같은 결정의 이중 서술). **경계는 파일이 아니라 "결정이냐 근거냐"다.**
> - **미판정 입력**: 연구 C(적대적 감사) 32군집은 판정되지 않은 산출이다(research/README 28장). 인용한 군집은 전부 백서 원문 좌표를 대조해 오독이 아님을 확인한 것이고 대조하지 않은 것은 인용하지 않는다. 21개 대조, 11개 잔여(§15-18).
> - **기호 규약**: `§N.M`은 절, `§N-M`은 번호 매겨진 항목. 백서는 언제나 `백서 §…`로 적고 접두어가 없으면 이 문서다. 연구 C 군집과 백서 능력이 `C1~`을 공유하므로 군집은 "군집 Cn", 능력은 `Cn`으로 적는다. `A*`·`B*`는 군집 전용. 신설 능력은 `E`(효과 집합)·`O`(실행 관측)(§7).
> - **갱신 조건**: 결정이 뒤집힐 때. 구현 진척으로는 고치지 않는다.

## 0. 이 설계가 답해야 하는 것

### 0.1 백서가 준 것 — 협상 대상이 아닌 입력

능력 계약 C1~C6 + 횡단요구 U, 설계 원리 P1~P14, 두 층(사실/의도)과 결박, 세 자리(사람/기계/에이전트). 이 설계는 그것들을 재론하지 않고 만족시킨다.

### 0.2 근거의 두 종류 — 원문은 별도 대장에

- **연구 관측 R1~R12** — 요구사항은 아니지만 백서가 열어둔 질문의 답을 고를 근거는 준다. 열둘 중 열하나가 설계를 바꾸고 R12는 바꾸지 않는다.
- **백서 자기모순 군집 21건** — 연구 C의 32군집 중 원문 대조를 통과한 것.

둘 다 [`evidence-map.md`](evidence-map.md)에 있다. 이 문서는 기호(`R1`·`A2`·`B4`·`군집 C9`)로만 인용하며 **그 기호가 대장에 없으면 인용 자체가 규율 위반이다.**

**의도적으로 답하지 않는 것**: B10의 상태기계·트랜잭션 의미론을 어떤 어휘로 담을지. 자리는 규약층(§7.1), 소유자는 프로젝트(§7.3 — 백서 §12-3의 소진). 코어가 팩 스키마에서 어떤 원시 개념까지 표현 가능하게 할 것인가는 열려 있다(§14-3).

### 0.4 백서 §12-2가 남긴 자리 — 코어는 실행하지 않지만 시스템은 실행에 닿는다

백서는 실행 조달을 금지한 적이 없다. 네 곳에서 열어 두었다.

| 백서 좌표 | 원문 |
|---|---|
| §2.2-1 | "빌드를 요구하는 정밀 분석은 **주경로가 될 수 없다.** 정밀도가 모자라서가 아니라, 균일하게 돌지 않아서다" |
| §5 U | "균일성을 포기하고 얻을 수 있는 것은 정밀도다. **그 교환은 금지되지 않지만**, 주경로가 아니라 **보조로만** 허용되고, 그 산물은 적용 범위를 명시적으로 달고 다녀야 한다" |
| §9 P11 | "균일하지 않은 정밀도는 **보조이지** 주경로가 아니다" |
| §12-2 | "빌드 의존 외부 엔진은 대체 불가한 니치를 위한 **옵션 보조로만 유예되어 있다.** 남은 질문은 **범위와 깊이**다" |

백서 §2.2-1의 논거(임의의 과거 커밋이 빌드된다는 보장이 없다)를 이 설계는 반박하지 않고 인정한다 — 실행은 현재 환경·현재 HEAD 근방에서만 성립한다. 그 위에서 하는 것은 둘이다.

1. §12-2가 "남은 질문"이라 부른 범위와 깊이에 답을 하나 넣는다 — O(§7.2).
2. **백서가 열거하지 않은 보조 후보를 추가한다.** 백서의 보조 후보(§12-2 "빌드 의존 외부 엔진", §10 "정밀 분석 엔진")는 전부 정적이고 동적 관측(트레이스·DI 컨테이너 덤프·기동 후 라우트 테이블·테스트 결과)은 목록에 없다. 군집 C6이 같은 곳을 겨눴다.

후보가 실재하는 근거: palimpsest는 플러그인/MCP로 설치되므로(백서 §2.1) **호스트 에이전트가 이미 사용자의 머신·툴체인 안에 서 있다** — 빌드·테스트·구동·트레이스의 조달자는 코어가 아니라 호스트다. 수용 경로도 열려 있다(백서 §2.4의 "출처 중립적 수용" → §12.2의 관측 수용 API).

| 바뀌지 않는 것 | 바뀌는 것 |
|---|---|
| **U** — 주경로는 여전히 빌드 비의존. 임의 과거 커밋은 여전히 빌드되지 않는다 | **A1의 완전성 손실이 부분 회복된다** — 생성 코드·DI·리플렉션은 정적으로 안 보이지만 실행 중에는 보인다. §5.3의 `UnresolvedRef`가 해소 경로를 얻는다 |
| **P7** — 코어는 호스트 없이도 모든 질의에 답한다. 실행 조달은 입력이지 전제가 아니다 | **연구 5장의 "행동 하네스 미개발" 칸에 닿는다** |
| **P11**("변형하지 않는다") — 실행은 부작용을 낳으므로 여기서 더 무거워진다 | **연구 D §8.4(마이크로월드↔빌드 불가)의 전제가 부분적으로 풀린다.** "대상마다 새로 지어야 한다"는 비용은 그대로 |
| **P2** — 실행에서 온 사실은 결정론적 추출이 아니다 | **파티션 값이 하나 는다** — `observed`(§3) |

**실행 계약**

1. **사람의 승인 아래에서만.** 실행은 되돌릴 수 없는 부작용(마이그레이션·외부 호출·과금)을 낳는다. 실행 범위는 `asserted` 설정이다.
2. **관측은 환경 좌표를 단다** — `(Snapshot, 환경 지문, 실행 시각, 명령)`. 같은 커밋도 환경이 다르면 다른 사실이고 그 차이가 감춰지면 §4의 대장이 거짓말을 한다.
3. **재현 보증이 없다.** `extracted`의 결정론 계약을 `observed`에 확장하지 않는다 — 확장하면 P5가 깨진다.
4. **주경로를 대체하지 않는다.** 실행 가능한 프로젝트에서만 나오는 답은 "때때로 있는 능력"이고 언제 유효한지 알 수 없다(백서 §5 U).
5. **무한히 쌓이지 않는다.** 좌표에 실행 시각이 들어가 `observed`는 단조 증가한다. 보존 정책은 §12.4이며 정책 없이 켜는 것은 P12 위반이다.
6. **수용 API는 조달자의 정체를 묻지 않되 조달 절차의 기록은 요구하고, 없으면 수용하지 않는다** — `(명령·도구 식별, 환경 지문, 산출 아티팩트 해시)`. 이 요구가 없으면 §3 배정 규칙 2("환경 의존 절차가 실제로 산출했는가")를 검사할 방법이 없고 에이전트가 자기 추론을 관측으로 신고하는 경로가 열린다 — `inferred`가 승인 없이 `observed`의 권한(존재 주장·§8의 `Finding`)을 얻는 것이며 백서 §4.4가 금지한 세탁의 정확한 형태다. §3.1이 막는 것은 저장 이후의 승격, 이 조항이 막는 것은 **입력 시점의 사칭**이다.

**백서에 대한 귀결: 없다.** §12-2가 이미 보조를 유예했고 O는 그 "범위와 깊이"에 대한 답이다(§14-2). 남는 것은 백서의 보조 후보 목록에 동적 기법이 없다는 관찰 하나이며, **(c) 설계 미결**이므로 §16-2가 권고가 아니라 관찰로 적는다.

### 0.5 경계 — palimpsest는 하네스가 아니다

§0.4가 실행 접근을 열었으므로 반대편 말뚝을 박는다. **"실행에 닿을 수 있다"가 "실행을 몬다"로 미끄러지면 이 설계는 ditto가 실패한 자리로 들어간다.**

[E](research/2026-08-02-ditto-harness-failure-observation.md)가 관측한 실패는 능력 부족이 아니다. 소유자의 진술은 *"이해가 병목이 되어 전부 맡겼고, 그게 내가 원한 결과가 아니어서 목적지까지 가지 못했다"*이고, 그 저장소에는 위임을 규율로 박은 불변식(자율 실행·무축소 게이트·완료 계약·fresh-context 검증)이 그대로 남아 있다. **작동하지 않아서가 아니라 작동하면서 판정을 사람 손에서 떼어냈기 때문에** 소유자가 자기 시스템을 모르게 됐다.

| palimpsest가 하는 것 | 하지 않는 것 |
|---|---|
| 좌표를 들고 있는다 | 작업을 몬다 |
| 무엇이 결박됐고 무엇이 낡았는지 계산한다 | 무엇을 할지 정한다 |
| 잔여와 공백을 사람이 있는 곳으로 가져온다 | 잔여를 대신 닫는다 |
| 관측을 수용한다(§5.3) | 실행을 자율로 트리거한다(§0.4) |
| 승인의 대상을 좌표로 만든다 | 승인을 대행한다 |

백서 P13·P14가 이미 이것을 적었다. 이 절이 더하는 것은 그 원리가 깨졌을 때의 관측된 사례가 이제 있다는 것, 그리고 원리를 깬 것이 나쁜 의도가 아니라 **좋은 자동화**였다는 것이다.

### 0.6 소유자의 방향 지시 — 이 설계가 반영하는 것

2026-08-03에 세 차례 들어온 지시를 조항 단위로 정규화하면 아홉(U1~U9)이다. 연구는 증거이지만 지시는 요구사항이다. 그러나 백서도 같은 소유자의 계약이므로 **지시가 백서와 어긋나는 지점은 "지시가 이긴다"가 아니라 "어느 쪽을 고칠 것인가"가 열리는 지점**이다. 원문·정규화·조항별 판정은 [지시 문서](instructions/2026-08-03-owner-direction.md)에 있고 여기는 결과만 옮긴다.

| 지시 | 반영 |
|---|---|
| **U1** 프로젝트별 해석기·분석기 | D17 해석기 팩(§7.3) + 규칙 파생 사실 배정(§3.2) |
| **U2** 변경 전 분석과 시각화 | D18 사전 브리핑(§11.5) + D19 뷰 모델 표면(§12.5) |
| **U3** 변경 후 구조 평가 | D20 적합성 델타(§11.6) + §10 손잡이 표 여섯째 행 |
| **U4·U8** ACG를 개념으로 수입 | D21 거버넌스 층의 경계(§12.6) + §14-1 처분 변경 |
| **U5** 서술은 그래프를 경유한다 | D22 서술 경로 선언(§9.4) |
| **U6** 결정론 주장 | §9.4의 6단계 대조 — 방향은 지지되고 낱말은 과장이다 |
| **U7** 병목에 대한 아쉬움 | §11.4 — 병목 완화의 형태를 판정 단가 인하로 못 박는다 |
| **U9** 사관·서사자·큐레이터·동료 | §0.7 정체성 정렬 |
| **U11** 목적의 순위 — 더 나은 코드 | D23 채점 기준의 승격(§0.8) |
| **U12** 정적 분석의 재판정 | D24 조달과 다섯 몫(§7.5) + §7.2 조달원 확장 |
| **U13** 엔티티 설계 | D25 그래프 스키마 파일(§1.2) + D26 노드 넷 신설(§1.1) |
| **U14** 속성값의 생성 주체 | D27 출처 동질성과 `producer`(§3.4) + 재현 입력 명세(§3) |
| **U15** KG의 신선도·일관성 | D29 무결성 계약(§12.7) + 낡음 전파(§6.4) |
| **U16** 프로젝트가 만드는 구현체 | D28 `provider` 포트(§7.4) |
| **U17** MCP가 필수는 아니다 | D30 표면 우선순위(§12.2) |
| **U18** git 개발 방법론 | D31 git 결합(§12.8) |

**U10**(온톨로지)은 [2026-08-04 지시](instructions/2026-08-04-owner-direction.md)이고 처분은 §7.3·F18에 있다. U13이 그 실질을 앞당긴다 — 개념 노드를 P3에 둔 채로 그래프 스키마가 없던 것이 U10이 요구한 것의 실제 공백이었다.

세 가지를 먼저 못 박는다.

1. **백서 조항을 고쳐야만 성립하는 지시는 하나도 없다.** 대신 열린 질문 셋이 소진된다 — §12-1(승계 범위), §12-3(서사 규칙 소유자), §12-4 계열. 소진은 개정이 아니므로 백서 갱신 규칙에 걸리지 않는다.
2. **긴장 일곱 곳이 지시의 형태를 바꿨다**(U1-c·U2-a·U3-a·U4-b·U5-b·U8-c·U9-d — [지시 문서 §3](instructions/2026-08-03-owner-direction.md)). 가장 무거운 둘: "영향 범위"는 전칭 주장이므로 3분할로(§11.5), ACG의 fail-closed는 게이트의 논리이므로 `Residual`로 형태를 바꿔 수입(§12.6).
3. **새 잔여 아홉 개가 §15에 들어갔다**(§15-19~27). 그중 §15-22(해석기 팩 저작)가 사슬 A의 두 번째 뿌리가 된다 — 승인 노동이 일어나지 않는 것과 정확히 같은 방식으로 산출 전체를 `Residual`로 만든다.

### 0.7 정체성 정렬 — 사관이라는 은유가 결정하는 것

U9는 palimpsest를 *"프로젝트의 모든 역사(기획·설계·구현 의도·결정·코드 형상)를 서사적으로 담는 기록이자, 사관이자 서사자이자 큐레이터이자 동료"*로 규정한다. 능력 요구가 아니라 다른 결정들이 어느 쪽으로 읽혀야 하는지를 정하는 진술이므로 §0에 둔다.

| 은유 | 설계에서의 뜻 | 자리 |
|---|---|---|
| **사관** | **기록하되 통치하지 않는다.** §0.5의 표를 한 낱말로 요약한 것이며 §12.6의 게이트 집행 기각을 정체성 층에서 다시 세운다 | §0.5 |
| **서사자·큐레이터** | 생성형 큐레이션은 1급이되 결박·공백·확신도를 단다 | P8 · §9 |
| **동료** | 코어의 성질이 아니라 **코어 위에 서는 에이전트의 성질**이다(백서 §4의 가운데 자리는 기계이고 백서 제목이 이미 "그 위의 에이전트"를 가리킨다). 채택 형태는 §11.3 적시 제시 — 묻지 않아도 알고 있고 필요한 순간에 꺼내며 결정은 하지 않는다 | 백서 §4 · §11.3 |

**사관과 큐레이터는 자원에서 충돌한다.** 사관은 전수 보존을(백서 §7), 큐레이터는 선별과 적시 제시를(P9) 요구한다. "모든 역사를 담는다"를 문자 그대로 실행하면 §12.4의 단조 증가 목록에 네 번째가 붙고 P12와 충돌한다.

**택한 독해**: U9가 요구하는 것은 무한 보존이 아니라 **공백이 조용해지지 않을 것**이다. §12.4가 이미 그 형태다 — *접는 것과 지우는 것은 다르다.* 이 독해가 틀리면 D16의 보존 정책 전체가 다시 열린다(§15-27).

**역사에 기획이 들어오면 사슬이 한 마디 길어진다.** 백서 §7은 `결정 → 코드 → 여정 → 가치`이고 기획은 결정의 상류다.

```
기획 → 결정 → 계획 → 코드 → 여정 → 가치
```

기획은 정의상 코드 좌표를 갖지 않으므로 P3 위반이 하나 는다 — 군집 C10이 "여정 → 가치"에 대해 지적한 것과 같은 형태이고 처분도 같다: **2단 결박**(§14-6). 기획은 결정 좌표에, 결정은 코드에 결박되고, 결박되지 못한 기획은 `pending`(§6.1)으로 남는다 — 백서 §2.3이 신생 프로젝트를 위해 정의한 상태의 두 번째 쓰임.

### 0.8 목적의 순위 — 이 설계가 무엇으로 채점되는가 (U11)

2026-08-10 지시가 목적의 순위를 뒤집었다. 원문·정규화·조항 대조는 [지시 문서](instructions/2026-08-10-owner-direction.md)에 있고 여기는 이 설계가 지는 결과만 적는다.

> **역사·결정을 알게 하는 것은 목적이 아니라 수단이고, 상위 가치는 그 결과로 더 나은 코드가 나오는 것이다.**

§0.7이 정체성을 정했다면 이 절은 **채점 기준**을 정한다. 둘은 충돌하지 않는다 — 사관은 통치하지 않지만, 아무도 읽지 않는 사관은 만들 이유가 없다.

| 이 지시가 바꾸는 것 | 이 지시가 바꾸지 않는 것 |
|---|---|
| **산출의 정당화가 한 단 올라간다.** "결박이 계산된다"는 더 이상 통과 사유가 아니고 "그 결박이 코드를 바꿨다"가 통과 사유다 | **§0.5의 경계.** 결과를 목적으로 삼는 것과 작업을 모는 것은 다르다. 채점 기준이 올라간 것이지 이 층이 실행자가 된 것이 아니다 |
| **P1의 내용이 아니라 P1의 검사가 바뀐다** — [계획 G2](plan/00-goals.md)가 재는 "다음 행동의 변화"에 결과 축이 하나 선다 | **P1에서 멈출 수 있다는 성질**(R-17). 결과 축이 붙는다고 미완성 상태가 거짓말을 하게 되지는 않는다 — `Capable<T>`가 그대로 선다 |

**지시가 든 네 형태와 이 설계의 자리**

### 1.1 데이터 모델 — 이 설계가 만드는 타입 전부

구현은 여기서 시작한다. 논거와 경계 사례는 정의 절에 있고 이 표는 **무엇이 존재하고 무엇이 비면 저장이 거부되는가**만 모은다. §3.1의 규칙(*필수이거나 없거나, 선택 필드를 두지 않는다*)이 표 전체에 걸린다.

**좌표**

| 타입 | 정의 | 절 |

**표 전체에 걸리는 강제 규칙 일곱**

위 타입들은 규율로 지켜지지 않는다. **"그런 값은 애초에 만들 수 없다"로 표현될 때만** 규칙이 사람의 주의력에서 벗어난다. 일곱 중 다섯은 타입으로, 둘은 검사로 강제된다.

### 1.2 D25 — 그래프 스키마는 문서가 아니라 파일이다

§1.1은 **타입 표**이고 그래프 스키마가 아니다. 노드 라벨의 집합, 엣지 타입의 집합, 각 엣지의 도메인·레인지·카디널리티, 속성별 필수 여부와 **생성 주체**(§3.4)가 어디에도 없었다 — U10이 온톨로지를 목표로 세웠는데 그 실질이 비어 있던 자리다.

> **스키마는 `schema/graph.toml` 하나에 있고 코드·JSON 스키마·문서 표·`pal export`의 매핑이 전부 거기서 파생된다. 코드에만 있고 스키마에 없는 노드·엣지는 CI 실패.**

`surface/queries.toml`이 질의에 대해 하는 일([stack §6](plan/00-stack.md))을 노드·엣지에 대해 하는 것이며 새 원리가 아니다.

```toml
[node.Symbol]
provenance = "extracted"                  # 이 노드의 모든 속성이 지는 출처 (§3.4)
key        = ["coord"]
attrs      = [
  { name = "name",          type = "string",   producer = "extractor", required = true },
  { name = "body_digest",   type = "digest",   producer = "extractor", required = true },
  { name = "identity_grade",type = "enum",     producer = "extractor", required = true },

[edge.CALLS]
from        = "Symbol"
to          = ["Symbol", "UnresolvedRef"]
cardinality = "many-to-many"

**모든 엣지가 공통으로 지는 넷**(U13-c가 연 것): `해소 등급`(§5.1) · `출처`(§3) · `근거`(§5.2, `inferred`일 때 필수) · `발생 Snapshot`. 이 넷이 없는 엣지 타입은 스키마에 등록되지 않는다.

#### D33 — id 산출 규칙: 출처는 속성이 아니라 정체성의 성분이다 (R14)

§3.1이 *"출처 필드는 불변이고 승격은 새 노드 생성"*을 정했다. 그 규칙은 **필드를 고쳐 쓰는 것**을 막지만 **두 노드가 하나로 병합되는 것**은 막지 못한다 — 후자에서는 아무도 필드를 고치지 않았는데 값이 바뀐다.

선행 구현이 정확히 그 자리에서 자기 설계를 unsound로 판정했다([G §2](research/2026-08-11-legacy-freshness-anchor-observation.md)): 파생물 id가 `제목 + 대상 커밋 + 대상 집합`만 해시하고 생산자를 제외해서, **정적 엔진이 만든 판정과 에이전트가 만든 판정이 같은 노드로 붕괴하고 last-writer-wins로 생산자 표시가 덮어써졌다.** 마커는 저장됐으나 정체성을 지지 않았고, 그래서 소멸했다.

> **파생 노드의 id = hash(대상 좌표, 출처, 생산자, 재현 입력).** 넷 중 하나라도 다르면 다른 노드다.

| 규칙 | 왜 |
|---|---|
| **출처·생산자가 id 성분** | 두 엔진의 같은 판정이 **나란히 선다.** 이것이 없으면 §7.5의 다섯째 몫(엔진 간 불일치)이 성립하지 않는다 — **붕괴한 것은 어긋날 수 없다** |
| **재현 입력이 id 성분**(§3의 `ReproInput`) | 같은 대상에 대한 다른 시점·다른 범위의 산출이 덮어쓰지 않고 쌓인다. 계보가 생기는 것이 §12.4의 보존 정책이 접을 대상을 갖는 조건이다 |
| **네임스페이스 접두어** | 파생 노드의 id가 코드 좌표와 우연히 같아질 수 없다 |
| **본문은 id 성분이 아니다** | 같은 근거로 다시 만든 요약이 문장만 달라졌다고 새 노드가 되면 계보가 소음이 된다. 본문 변경은 같은 노드의 갱신 |

**병합 규칙도 함께 못 박는다**: id가 같으면 갱신이고 다르면 새 노드다. **id가 같은데 출처가 다른 상황은 스키마 위반이며** §12.7의 불변식 3이 그것을 잡는다.

**스키마가 자라는 것 자체가 관측 대상이다.** 노드 라벨 수·엣지 타입 수가 대장에 적히고, 늘어난 커밋은 [`vocab.toml` 허용 목록](plan/00-stack.md#42-어휘-금지-목록--pal-core-소스에-나타나면-ci-실패)이 늘어난 커밋과 같은 자격으로 검토된다 — 온톨로지의 팽창은 조용히 일어나는 종류의 비용이다.

**아직 정하지 않은 것**: §12.5가 표면을 "명명된 질의 + JSON"으로 계약했으나 그 질의 목록이 이 문서에 없다. 표면이 계약이면 목록도 계약이므로 F06이 산출로 확정한다(§15-33).

## 2. 좌표계 — 무엇이 무엇을 가리키는가

결박(백서 §3)과 낡음 감지 전체가 좌표 위에 선다. 백서는 좌표를 요구했지만 입도를 정의하지 않았다(A3).

### 2.1 D1 — 3축 좌표

```
Coord = (repo_id, TreeRef, ExtractorVersion, symbol_id)
Site  = (Coord, span)          // 라인 범위가 필요한 자리에서만 쓰는 별도 타입
```

- **`repo_id`** — 매니페스트가 선언한 저장소 식별자. 멀티레포가 기본 가정이므로(백서 §2.2-3) 단일 저장소는 원소 1개인 특수 케이스다. 매니페스트는 `asserted`이며 그 사실이 대장에 표시된다(§4.3).
- **`TreeRef`** — 시간축. **커밋 하나가 아니다**(아래 §2.1-1). 멀티레포의 "지금"은 그 집합이며 `Snapshot = {(repo_id, TreeRef)}`로 부른다.
- **`ExtractorVersion`** — B6에 대한 답. 이 축이 없으면 P5("같은 커밋은 같은 그래프")는 문자 그대로 거짓이고, 넣으면 "같은 `(트리, 추출기 버전)`은 같은 그래프"로 참이 되어 능력 향상이 좌표 변경으로 관측된다. **단 이 축에 무엇을 합성할지가 정해져야 한다**(아래 §2.1-2).
- **`symbol_id`** — §2.2. 계산 가능성이 언어 능력 등급에 의존하며 그 사실이 좌표에 함께 실린다.
- **`span`은 `Coord`에 없다.** 라인 범위는 결박의 기본 단위가 아니고(§2.2) 선택 필드 금지(§3.1)에도 걸린다. 라인이 실제로 필요한 자리 — `partial`의 회복 지점(§4.1), `UnresolvedRef`의 참조 지점(§5.3), 반례 경로(§8) — 는 `Site`를 쓰고 거기서 `span`은 필수다.

#### 2.1-1 시간축은 커밋만이 아니다 — 워킹트리에 좌표가 없으면 1순위 장면이 죽는다 ([R-06](plan/00-risks.md#r-06))

초안은 시간축을 `commit_sha`로 적었다. 그런데 **이 설계의 1순위 사용 장면(§11.3 적시 제시)은 정확히 커밋 전 순간에 일어난다** — 에이전트가 편집 중에 `touch`를 부른다. 커밋되지 않은 상태에 좌표가 없으면 결박도 낡음 판정도 그 순간에 성립하지 않고, §2.3은 "워킹트리와 일치하는지 표시한다"까지만 말할 뿐 워킹트리 자체를 좌표화하지 않았다.

```
TreeRef = Committed(commit_sha)
        | Worktree { base: commit_sha, tree_digest }   // 추적 파일 blob 해시들의 머클 루트
```

**이것이 성립하는 이유는 1층 캐시의 성질에 이미 있다.** 캐시 키가 `(blob 해시, 추출기 버전)`이지 커밋이 아니므로(§2.3), 워킹트리 파일의 blob 해시를 직접 계산하면 캐시가 **아무 변경 없이 그대로 적중한다.** 파싱 파이프라인은 커밋을 모른다.

- 내용이 같으면 `tree_digest`가 같다 → 편집이 멈춘 동안 워킹트리 좌표는 **안정적인 식별자**다.
- `stale-projection`(§2.3)이 "낡음"이 아니라 **"워킹트리 좌표로 계산됨"**이라는 1급 상태가 된다.
- 결박은 커밋 좌표에 걸리고, 워킹트리 질의는 *"이 결박이 지금 편집 중인 코드 기준으로도 live인가"*에 답한다.

#### 2.1-2 버전 축은 하나가 아니라 셋이다 — 합치면 캐시가 상시 전량 무효화된다

초안은 *"해석기 팩이 들어오면 `extractor_version`의 성분이 하나 는다"*고 적었다(§7.3). **그러면 팩 규칙 한 줄을 고칠 때마다 10⁵ 파일이 재파싱된다** — 팩은 대개 심볼의 존재를 바꾸지 않는데도. 무엇이 무엇을 무효화하는지가 다르므로 축을 가른다.

| 축 | 성분 | 바뀌면 무효화되는 것 | 좌표에 실리나 |
|---|---|---|---|
| **`ExtractorVersion`** | 문법 버전 + 추출기 코드 버전 | **1층 캐시 전량** · 2층 · 좌표 이동 | **예** — `Coord`의 성분 |
| **`ProjectionVersion`** | 해소 로직 버전 + 정규화 등급 | 2층만 (재파싱 없음) | 아니오 — `Envelope`에 실린다 |
| **`PackFingerprint`** | 팩 규칙·인식기·개념 선언의 해시 | 팩이 파생시킨 **라벨·판정·개념 관계**만 | 아니오 — 라벨·판정에 실린다 |

**팩 지문이 `Coord`에 들어가지 않는 것이 여기서의 결정이다.** 팩은 심볼의 존재나 정체성을 바꾸지 않고 그것에 **붙는 것**을 바꾼다. 팩이 자라도 좌표는 제자리이고 움직이는 것은 파생 라벨의 결박 상태다 — 규칙 좌표에 결박되어 `stale`이 되는 것이 §3.2의 장치이며, 관측 가능성은 좌표를 움직여서가 아니라 **붙는 것에 실어서** 얻는다.

**예외 하나**: 팩이 언어 문법이나 심볼 추출 규칙 자체를 바꾸는 경우. 그런 팩은 스키마에서 `affects = "extraction"`으로 **분류를 요구**하고 그때만 `ExtractorVersion`에 합성된다. 분류 없는 팩은 추출에 닿을 수 없으며 로딩 시점에 거부된다.

#### 2.1-3 `EntityId` — 좌표를 갖지 않는 것들의 식별자

`Coord`는 **코드 전용**이다. 그런데 결박의 주체 — 결정·계획 항목·라벨·잔여·범위 축소·개념·여정·결함 — 은 코드가 아니고 자기 식별자가 필요하다. 이 규정이 없으면 §6의 결박이 *무엇을* 코드에 매는지가 타입 수준에서 정해지지 않는다.

```
EntityId = (EntityKind, 안정 식별자, origin)
```

- **`EntityKind`는 닫힌 열거가 아니라 등록형이다.** 코어가 부팅 시 등록하는 것(`decision`·`plan`·`label`·`residual`·`scope-reduction`·`change`·`actor`)과 팩이 등록하는 것(`concept`·`journey` 등, §7.3)이 있다. 닫힌 열거로 적으면 §1.2가 *"노드 타입은 스키마 파일이 정한다"*고 한 것을 코드가 부정하게 된다.
- **안정 식별자는 경로 해시가 아니다.** 문서가 이동해도 유지되어야 한다. `origin`(어느 문서·어느 섹션에서 왔나)은 추적용이며 정체성의 성분이 아니다.
- **`kind`가 등록형이어도 결박·낡음 계산은 영향받지 않는다.** 그 계산은 대상 좌표와 반경만 쓰고 주체의 종류를 모른다. 종류를 아는 것은 표현 층뿐이며, 거기서 미등록 종류는 *"알 수 없는 종류의 결박 N건"*으로 **보이게** 처리한다 — 조용히 버리지 않는다.

**지금 정하는 이유**: 의도층 개체가 쌓인 뒤에 식별 체계를 바꾸면 전부 다시 결박해야 한다. 비용이 지금은 0이다.

### 2.2 D1 — 심볼 정체성과 정규화

라인 번호에 결박하면 공백 한 줄에 stale이 켜지므로 결박의 단위는 심볼이다.

```
symbol_id      = hash(repo_id, 정규화 경로, 컨테이너 체인, 이름, 판별자)
body_digest    = hash(구문 트리에서 주석·공백·포매팅을 제거한 정규형)
identity_grade = 판별자가 어느 언어 능력 등급에서 계산됐는가 — 좌표와 함께 실린다
```

- **`symbol_id`가 같으면 같은 심볼이다.** 파일 이동·이름 변경은 정체성을 끊지만 그때는 `orphaned`(§6)로 넘어가 사람의 판단을 부르므로 조용히 사라지지 않는다.
- **`body_digest`가 바뀌어야 "변했다"이다.** 포매팅·주석·변수명 변경은 digest를 바꾸지 않는다 — A3의 거짓 양성 대부분이 여기서 죽는다. 변수명은 스코프 해소가 가능한 언어에서만 정규형에서 제거되며 그 차이가 대장에 언어별로 표시된다.

#### 판별자는 언어 등급에 의존한다

판별자를 "정규화 시그니처"로 못 박으면 타입 해소를 요구하므로 L2 미만에서 계산되지 않는다(등급 §4.1). 좌표는 §6·§8·§11 전부의 전제이므로 이 의존을 감추면 좌표 없는 언어에서 설계 절반이 조용히 죽는다.

| 언어 등급 | 판별자 | `identity_grade` | 귀결 |
|---|---|---|---|
| **L2 이상** | 정규화 시그니처(해소된 파라미터 타입) | `exact` | 오버로드가 구별된다 |
| **L1** | 파라미터 개수 + 컨테이너 내 선언 순서 | `ordinal` | 같은 개수의 오버로드는 순서에 의존하므로 선언 순서 변경이 좌표를 옮긴다 |
| **L0** | 없음 — 심볼을 만들지 않는다 | 없음 | **좌표가 없다.** 결박·잔여 결박·적시 제시가 성립하지 않는다 |

**L1의 실패 양식은 `orphaned`가 아니다 — 그쪽이 덜 나쁘다.** 같은 파라미터 개수의 오버로드 둘이 순서를 바꾸면 정체성이 끊기는 것이 아니라 각 좌표가 상대 심볼을 가리킨다. `body_digest`가 달라 `stale`은 켜지지만 그것이 뜻하는 것은 *"결박한 코드가 변했다"*가 아니라 *"이제 다른 함수를 가리킨다"*이고 산출에서 둘은 구별되지 않는다 — 사람은 재확인하러 가서 엉뚱한 함수를 읽는다. 거짓 `orphaned`는 관측 가능하지만 이것은 평범한 낡음으로 위장한다.

닫는 방법은 L1에서 컨테이너 내 오버로드 집합의 집합 digest를 함께 감시해 순서 변경을 별도 사건으로 띄우는 것이다. **F03의 검사 항목으로만 올려 두고 스키마로 고정하지 않는다** — L1에서 오버로드 재정렬이 실제로 얼마나 일어나는지 아무도 세어본 적이 없다(F03 · §15-7).

**감추지 않는 형태**: 대장의 언어별 등급 표(§4.1)에 `identity_grade` 열이 서고, 모든 응답이 자기가 어느 정체성 등급 위에 있는지 동반한다(§4.2). L0 언어가 있으면 대장 머리에 "결박 불가 언어 N개"가 적힌다.

#### 정체성 규칙

| 대상 | 규칙 |
|---|---|
| **오버로드** | 위 표의 판별자로 구별 |
| **익명 함수·클로저·람다** | 독립 심볼이 아니다. 가장 가까운 이름 있는 조상에 귀속되고 그 `body_digest`에 포함 |
| **제네릭** | 선언 하나가 심볼 하나. 인스턴스화는 심볼이 아니다 |
| **매크로·애노테이션 프로세서 생성 심볼** | 파일 시스템에 없으므로 심볼이 아니라 `UnresolvedRef`(§5.3). O의 표적(§5.4) |
| **재선언·조건부 컴파일** | 같은 좌표에 둘 이상이면 후보 집합으로 저장 — `candidate` 엣지와 같은 처리(§5.1) |

#### `repo_id`를 해시에 넣는 대가

저장소를 분할·병합하면 그 안의 전 심볼 정체성이 한 번에 끊긴다. 그러므로 `repo_id`는 경로도 원격 URL도 아닌 **매니페스트가 발급하는 안정 식별자**이고 재배치는 별칭 테이블이 흡수한다. 흡수되지 않은 재배치는 전 심볼 `orphaned`라는 관측 가능한 사건이 되며 그것이 조용한 정체성 유실보다 낫다.

**이 정규화가 보증하지 않는 것**: "의도가 변하지 않았다". 보증하는 것은 "텍스트만 변했다"를 걸러낸다뿐이다. 의미가 변했는데 digest가 같은 경우(호출하는 상수 값만 변경 등)는 §6.2의 결박 반경 문제로 넘어간다.

### 2.3 D2 — 투영은 캐시다

B5가 정확하다 — 백서는 "사실층은 낡지 않는다"를 정의로 선언했지만 투영이 캐시이므로 커밋과 재추출 사이 창에서 사실층은 낡은 상태다.

- 모든 응답은 어느 `Snapshot`에서 계산됐는지와 현재 워킹 트리와 일치하는지를 함께 반환한다. 불일치하면 `stale-projection`으로 표시된다 — 답을 막지 않고 표시한다.
- 재추출 트리거는 사람의 규율에 의존하지 않는다. git 훅이 아니라 질의 시점 검사(HEAD 비교는 상수 시간)로 감지하고 증분 재추출은 변경 파일에 한정된다.
- 캐시 무효화 키는 `(파일 blob 해시, 추출기 버전)`. 콘텐츠 주소이므로 브랜치 전환·과거 커밋 조회가 대부분 캐시 적중이 되며 이것이 U를 P12 안에서 성립시키는 실질 장치다(§12.3).

## 3. D3 — 파티션은 출처 축이다

백서 P2는 "사실과 추론" 2분할을 요구했다. B2가 보인 대로 그것은 가드 라벨을 담지 못하고(추출되지 않았으므로 사실이 아니고 사람이 확정했으므로 추론이 아니다), §0.4가 연 실행 관측도 담지 못한다(추측이 아니므로 추론이 아니고 커밋에서 결정론적으로 나오지 않으므로 추출도 아니다). 4값으로 바꾸면 전체를 덮는다.

| 출처 | 정의 | 누가 만드나 | 결정론 | 신선도 규칙 | 예 |
|---|---|---|---|---|---|
| **`extracted`** | 코드에서 결정론적으로 계산됨 | 기계 | 보증 — 같은 `(커밋, 추출기 버전)`은 같은 답 | 좌표가 곧 정의. 재추출로 갱신 | 심볼, 엣지, 진입점 |
| **`observed`** | 환경에 의존하는 절차(실행·빌드·계측)에서 얻음 | 호스트가 조달, 코어가 수용 | 없음 | `(Snapshot, 환경 지문, 실행 시각)` 좌표 + 적용 범위 표시 필수 + 관측 좌표의 digest가 변하면 `stale-observation`(§3.3) | 호출 트레이스, DI 바인딩 실물, 테스트 결과, 라우트 실측, 빌드 의존 정밀 엔진의 산물 |
| **`asserted`** | 사람이 승인해 고정함 | 사람 | 해당 없음 | 결박 필수 + 만료·재확인 규칙(§10) | 가드·효과 라벨, 결정, 매니페스트, 실행 허용 범위 |
| **`inferred`** | 합성·추론의 산물 | 에이전트 | 없음 | 결박 + 공백 + 확신도 필수. 승인 없이 승격 불가 | 경계 통과 후보, 발굴된 과거 의도, 요약 |

#### 배정 규칙 — "덮고 겹치지 않는다"는 선언으로 성립하지 않는다

위 표의 "누가 만드나"(생산자)와 "정의"(인식론적 지위)는 다른 축이고 둘이 어긋나는 입력이 실재한다. 배정은 생산자가 아니라 아래 순서의 첫 참으로 결정된다.

> 1. **`(재현 입력, 추출기 버전)`만으로 재현되는가** → `extracted`
> 2. 아니면 환경 의존 절차가 실제로 산출한 것인가(누가 조달했든) → `observed`
> 3. 아니면 사람이 승인해 고정한 것인가 → `asserted`
> 4. 아니면 → `inferred`

**규칙 1의 입력 명세 — 커밋 하나가 아니다 (U14-c).** 초안은 규칙 1을 `(커밋, 추출기 버전)`으로 적었고 그러면 **저장소 안에서 결정론적으로 계산되는데 커밋 하나에서 나오지 않는 사실**이 규칙 2로 떨어진다 — 변경 결합도(co-change), 수정 빈도, 도입 커밋(bisect) 같은 git 이력 파생 사실이다. 그것들은 환경에 의존하지 않고 같은 저장소에서 언제나 같은 답을 낸다. `observed`로 배정하면 재조달을 요구하고 보존 정책(§12.4)에 걸리며 판정 입력에서 `stale-observation`으로 떨어진다 — 전부 틀린 처분이다.

```
ReproInput ∈ { Tree(TreeRef) | History(base..head) | Files(경로 집합 @ TreeRef) }   // 사실에 함께 저장 — 필수
```

`extracted` 사실은 자기 재현 입력을 실어야 한다. 그러면 규칙 1이 반증 가능해진다 — *"이 입력과 이 버전으로 다시 돌려서 다른 답이 나오면 배정이 틀린 것이다."* `History` 입력을 갖는 사실은 **범위가 좌표의 일부**이므로 base가 바뀌면 낡는다(§6.4).

| 경계 사례 | 배정 | 왜 |
|---|---|---|
| 사람이 손으로 붙여넣은 실행 트레이스 | `observed` | 사람이 만든 것이 아니라 운반한 것. 조달자는 좌표에 남되 배정을 바꾸지 않는다 |
| 빌드 의존 정밀 엔진의 산물 | `observed` | 결정론적이지만 빌드 환경이 좌표에 필요하므로 규칙 1에서 떨어진다 |
| 추출기가 파싱한 실행 로그 파일 | `observed` | 파싱은 결정론적이나 근거인 로그가 커밋에서 나오지 않는다 |
| 에이전트가 수행한 정확한 정적 분석 | `inferred` | 재현 보증이 없다. 정확할 수 있다는 것은 배정 근거가 아니다 |
| 사람이 승인한 실행 허용 범위 설정 | `asserted` | 규칙 1·2에서 떨어지고 승인이 있다 |
| **변경 결합도·수정 빈도·도입 커밋** | **`extracted`** | 재현 입력이 `History`이고 환경에 의존하지 않는다 |
| **프로젝트가 제공한 `provider`의 산물**(§7.4) | **`observed`** | 코어가 실행하지 않으므로 재현을 검사할 수 없다. provider가 결정론을 선언하면 재조달 시 대조하고 불일치를 보고할 뿐이다 |

**규칙 2를 규칙 1보다 뒤에 두면 안 된다**는 것이 이 순서의 핵심이다 — 그러면 "결정론적이므로 `extracted`"라는 경로로 빌드 의존 산물이 사실층에 들어오고 `extracted`의 재현 계약(§0.4-3)이 거짓이 된다. 네 규칙이 순서를 가지므로 겹치지 않고, 규칙 4가 무조건 참이므로 덮는다 — P2가 선언이 아니라 절차로 만족되는 지점이다.

**`observed`를 `extracted`에 합치지 않는 이유**: 합치면 `extracted`의 결정론 계약(백서 §4.2-2)이 거짓이 되고 재실행이 답을 바꾸는 사실이 "기계의 보증" 아래로 들어간다. 분리는 낮춰 보는 것이 아니라 그것이 무엇인지 감추지 않는 것이다.

**`observed`와 `inferred`도 다르다.** 트레이스가 A→B 호출을 실제로 봤다면 추측이 아니다. 다만 본 것이 전부라는 보증이 없으므로 **`observed`는 존재 주장에만 강하고 부재 주장에는 쓸 수 없다** — §8의 3분할과 정확히 맞물린다: `observed` 엣지는 `Finding`을 세울 수 있지만 `observed`의 침묵은 `Residual`이지 `clean`이 아니다.

### 3.1 필드 규칙 — 선택 필드는 비게 된다 (R7)

ditto의 work item 스키마에는 `runs`와 `child_ids` 자리가 있었고 146건 전부에서 빈 배열이었다([E §7](research/2026-08-02-ditto-harness-failure-observation.md)).

> **필수이거나 없거나. 선택 필드를 두지 않는다.**

- 필수로 둘 만큼 중요하면 비어 있을 때 저장을 거부한다(§9.1의 `evidence_refs`).
- 그만큼 중요하지 않으면 스키마에서 뺀다. 빈 필드는 "이 시스템은 이것을 다룬다"는 거짓 신호이고 백서 §1이 고발한 것과 같은 종류다.

> **예외는 하나**: 기계가 채우며 채우지 못하면 그 쓰기 자체가 실패하는 필드 — 좌표, `produced_by`, 대장 항목. "기계가 채울 예정인 필드"는 예외가 아니다 — ditto의 `runs`가 전형적인 기계 자동 기록 필드였고 146건 전부에서 비어 있었다.

- 예외 필드에도 사후 검사를 건다. 어떤 필드가 연속 N개 `Snapshot`에서 전건 공백이면 대장이 보고한다(N은 §12.4). ditto의 실패는 스키마 심사에서 잡히지 않았고 146건이 쌓인 뒤에야 보였으며 그때는 아무도 세지 않았다 — **세는 일을 기계에 맡기는 것이 이 규칙의 실질이다.**
- 이 규칙은 이 문서의 스키마 전부에 걸린다. `Coord`에서 `span`을 분리한 것(§2.1)이 첫 적용이다.

**세탁 방지의 구현 형태**: 승격은 출처 필드를 고쳐 쓰는 것이 아니다. `inferred` 노드를 승인하면 그것을 가리키는 새 `asserted` 노드가 생기고 원본은 `promoted_by`와 함께 남는다 — (1) 되돌릴 수 있어야 하고 (2) "원래 누구의 추론이었는가"가 계보에 남아야 한다. 출처 필드를 갱신하는 구현은 그 자체가 세탁 장치이므로 스키마 수준에서 금지한다(출처 필드 불변).

### 3.2 규칙이 파생시킨 사실 — 프로젝트 해석기가 만드는 것의 자리 (U1)

D17(§7.3)이 선언 팩을 들여오면 새 종류의 사실이 생긴다. 예: *"이 프로젝트에서 `@RequireAuth`가 붙은 함수는 인가 가드다"*라는 팩 규칙이 커밋되어 있고 추출기가 그것을 적용해 라벨 300개를 만든다.

배정 규칙을 순서대로 적용하면 `asserted`다 — 코어 추출기 버전만으로 재현되지 않고(팩이 있어야 한다), 환경 의존 절차도 아니며(팩은 저장소 안의 파일이고 적용은 결정론적), 팩을 쓴 것은 사람이고 팩이 틀리면 라벨 300개가 전부 틀린다.

그러나 `asserted` 안에서 둘을 구별해야 한다 — 좌표 하나하나에 붙인 라벨과 규칙 한 줄이 파생시킨 라벨은 틀렸을 때의 파급이 다르다.

```
asserted_via ∈ { direct, rule(규칙 좌표) }      // 필수 — 비면 저장 거부(§3.1)
```

1. **규칙 파생 라벨은 규칙 좌표에 결박된다.** 규칙이 바뀌면 파생된 전부가 `stale`이 되고, 규칙 하나의 재승인으로 300개가 함께 갱신되는 것이 §11.4 일괄 승인의 기계 형태다.
2. **거짓 양성의 진단이 좌표를 갖는다.** "왜 붙었나"의 답이 *"규칙 R-7이 붙였다"*가 되고 R-7이 잘못 쓰였으면 파급 범위가 즉시 계산된다.
3. **팩의 완화가 `ScopeReduction`이 된다**(§10). 규칙을 지우면 파생 라벨이 사라지고, 잔여 감소의 원인이 "판정됨"이 아니라 "범위 축소"임이 §8.1-3의 분해로 잡힌다.

**출처 축을 다섯 값으로 늘리지 않는 이유**는 §5.2와 같다 — `derived` 같은 값을 만들면 §3의 파티션 규칙이 다시 열리고 그 비용이 얻는 것보다 크다. 강도·경로는 출처가 아니라 필수 필드로 뺀다.

### 3.3 관측도 낡는다 — `observed`의 무효화 계약

`observed`는 네 출처 중 가장 빨리 낡는다. 재현 보증이 없으므로(§0.4-3) 재계산으로 갱신되지 않기 때문이다 — `extracted`는 코드가 바뀌면 다음 추출에서 새 값이 되지만 3주 전 트레이스는 그대로 남는다. 그리고 `observed`는 §8에서 `Finding`을 세울 수 있는 유일한 비-`extracted` 출처이므로, 낡은 관측이 그 권한을 유지하면 백서 §1이 고발한 *낡은 서술이 거짓 신호가 된다*가 사실층 안에서 재생산된다.

> **규칙**: 모든 `observed` 사실은 자기가 가리키는 좌표 집합에 결박된다. 그 좌표 중 하나라도 `body_digest`가 변하면 `stale-observation`이다.

1. **지워지지 않는다.** 정적 하한과 과거의 관측된 해소를 겹쳐 보여주는 것이 정직한 형태이고, 관측이 있었다는 사실 자체가 재조달의 지도다(§5.4).
2. **판정 입력에서는 자동 배제된다.** `stale-observation`에 기대던 `Finding`은 `Residual{사유=관측 낡음}`으로 떨어진다. 표시로 두지 않는 이유는 §15-9다.
3. **재조달 큐에 들어간다.** 낡은 관측의 좌표 밀도가 "여기서 한 번 더 돌리면 가장 많이 회복된다"는 지도다.

**§12.4의 보존 정책이 이 규칙을 대신하지 못한다.** 그 표는 `observed`를 "좌표별 최근 M개"로 접는데 그것은 개수 기준이지 신선도 기준이 아니다 — 코드가 열 번 바뀌는 동안 관측이 한 번도 없었으면 그 하나짜리 관측은 M에 걸리지 않고 영원히 살아남는다. 두 장치는 목적이 다르고 둘 다 필요하다.

### 3.4 D27 — 출처의 입도는 노드가 아니라 속성이다 (U14)

§3은 출처를 **노드·엣지 단위**로 정했고 §3.1은 **필드의 유무**를 정했다. 그 사이에 규칙이 없다 — *한 노드의 속성들이 서로 다른 출처를 가질 수 있는가.* 지시가 "엔티티의 각 **속성값**을 만들어 내는 주체"라고 적은 것이 정확히 이 공백을 가리켰다.

실물은 이렇게 생긴다. `Symbol` 하나에 이름(`extracted`)·요약(`inferred`)·소유자(`asserted`)·실측 호출 횟수(`observed`)가 함께 실릴 수 있고, 지금 스키마는 그것을 막지 않는다. 막지 않으면 무슨 일이 일어나나:

1. **노드의 출처 필드가 거짓이 된다.** `Symbol.provenance = extracted`인데 그 안의 요약은 에이전트가 썼다. §3의 파티션이 "덮고 겹치지 않는다"를 노드 단위로 선언했으므로 이것은 파티션의 위반이 아니라 **파티션이 잘못된 대상에 걸려 있었다**는 것이다.
2. **낡음의 단위가 계산되지 않는다.** 코드가 변하면 이름은 그대로이고 요약만 낡는데, 노드 하나에 상태가 하나뿐이면 둘을 구별할 방법이 없다.
3. **§3.1의 세탁 방지가 뚫린다.** 출처 필드는 불변인데 **다른 출처의 속성을 노드에 얹는 것**은 필드 수정이 아니므로 그 규칙에 걸리지 않는다.

> **규칙: 한 노드·엣지의 모든 속성은 같은 출처를 갖는다. 섞으려면 노드를 쪼개고 엣지로 잇는다.**

| 하나로 두면 | 쪼개면 |
|---|---|
| `Symbol{name, summary, owner}` | `Symbol{name}` ←`DESCRIBES`— `Synthesis{summary}` · ←`OWNED_BY`— `Ownership{owner}` |
| 낡음이 노드 하나에 뭉개진다 | **요약만 `stale`이 된다.** 코드가 변했을 때 무엇이 낡았는지가 데이터로 나온다 |
| 승격이 필드 수정으로 보인다 | 승격이 새 노드 생성이라는 §3.1과 같은 형태가 된다 |

그리고 스키마의 **모든 속성이 생성 주체를 선언한다**(§1.2의 `producer`).

| `producer` | 뜻 | 대응하는 출처 | 지시가 든 이름 |
|---|---|---|---|
| `extractor` | 코어 추출기의 결정론적 계산 | `extracted` | 결정론적 계산 |
| `rule(규칙 좌표)` | 선언 팩 규칙의 결정론적 적용(§3.2) | `asserted` + `asserted_via=rule` | 결정론적 추론 |
| `provider(id)` | 프로젝트 어댑터의 산물(§7.4) | `observed` | — |
| `agent` | 에이전트의 합성·추론 | `inferred` | 에이전트 추론 |
| `human` | 사람의 승인·입력 | `asserted` | — |
| `machine-record` | 기계가 자동 기록하되 채우지 못하면 쓰기 실패(§3.1의 예외) | 해당 노드를 따른다 | — |

**`producer`는 출처의 중복이 아니다.** 출처는 *인식론적 지위*(이 값을 무엇으로 믿을 수 있는가)이고 `producer`는 *생산 경로*(무엇이 이 값을 계산했는가)다. `asserted` 하나에 `rule`과 `human`이 함께 대응하는 것이 그 차이의 실물이며, 규칙이 틀렸을 때의 파급 계산(§3.2)이 그 구별 위에서만 성립한다.

**CI 검사**: 스키마의 각 노드에 대해 속성들의 `producer`가 그 노드의 `provenance`와 정합하는가. 어긋나면 로딩 시점에 거부된다 — 문서의 규율이 아니라 파일 하나의 검사다.

## 4. D4 — 관측 범위 대장

A6이 정확하다: "완전성 — 찾을 수 있는 것을 빠뜨리지 않는다"는 범위를 기계가 정의하므로 어떤 관측으로도 위반될 수 없다. 반증 가능한 형태로 바꾼다.

> **완전성(재정의)**: 기계는 선언된 관측 범위 안에서 전수임을 보증한다. 범위는 기계 판독 가능한 명세이며 범위 밖은 "없음"이 아니라 **"보지 않음"**으로 산출된다.

이제 반증 가능하다 — 범위 안인데 그래프에 없는 심볼을 하나라도 제시하면 계약 위반이다. 오라클도 있다(코퍼스 차등 재추출, 언어별 참조 구현 대조).

### 4.1 대장 스키마

`Snapshot`마다 계산되는 파일 단위 상태의 집합.

| 상태 | 뜻 |
|---|---|
| `parsed` | 파싱 성공, 선언된 언어 능력 등급까지 추출됨 |
| `partial` | 파싱은 됐으나 일부 구문에서 회복 — 회복 지점이 `Site`로 기록 |
| `unsupported` | 언어 인식됨, 추출기 없음 |
| `unrecognized` | 언어 미인식 |
| `excluded` | 설정으로 제외 — 제외 규칙 ID 함께 기록(§10) |
| `binary` / `generated` | 대상 아님, 판정 근거와 함께 |

여기에 언어별 능력 등급이 붙는다(백서 §2.2-2의 "하한은 전역이 아니라 언어별"). 등급은 `L0 텍스트 / L1 구조 / L2 스코프 해소 참조 / L3 정의-사용 / L4 제어흐름`이며 대장은 `(언어 → 추출 등급, identity_grade)` 표를 항상 동반한다.

두 값을 따로 적는 이유는 §2.2다 — 추출 등급이 심볼 정체성의 계산 가능성을 정한다. L0은 정체성이 없어 결박 자체가 성립하지 않으므로 대장 머리에 "결박 불가 언어 N개"가 적히고 그 파일들은 `unsupported`와 별개로 "좌표 없음"으로 표시된다. 사슬 C(§15.1)의 사용자 대면 형태다.

### 4.2 질의 응답에의 첨부

모든 응답은 자기 답이 어느 범위 위에서 계산됐는지를 동반한다. 예: "이 엔드포인트에 닿는 경로" 질의는 경로 집합과 함께 `{미해소 참조 12건, 범위 밖 파일 3건, L1 등급 언어 경유 2건}`을 반환한다. 백서 §4.2-4(정직한 공백)의 실제 형태이고 백서 §6.3의 "하한임이 표시되어야 한다"가 문장이 아니라 데이터가 되는 지점이다.

### 4.3 뿌리의 공백

C7이 정확하다 — "어떤 저장소들이 한 프로젝트인가"는 코드에 없다. 매니페스트는 `asserted`이며 대장은 항상 "선언된 저장소 N개"를 머리에 적는다. 저장소 하나가 빠지면 그것을 지나는 모든 경로가 조용히 사라지는 대신 대장이 계속 말한다. 완전한 해법이 아니다 — 애초에 빠뜨린 저장소는 여전히 보이지 않는다(§15-3).

## 5. D5 — 엣지 해소 등급

A2의 충돌은 실재한다. P6은 넓게 잡으라 하고 C2는 거짓 엣지가 없는 엣지보다 나쁘다고 한다. 둘 다 옳고, 화해는 "하나를 고르는 것"이 아니라 **엣지에 자격을 박는 것**이다.

### 5.1 등급

| 등급 | 성립 조건 | 출처 |
|---|---|---|
| `exact` | 임포트·정의가 해소되어 대상이 유일 | `extracted` |
| `scoped` | 스코프 해소로 후보가 유일 — L2 이상에서만 | `extracted` |
| `candidate` | 후보가 여럿. 엣지 하나가 아니라 후보 집합 하나로 저장 | `extracted` |
| `contract` | 경계를 넘는 계약 매칭. 증거 아티팩트 필수(§5.2) | `inferred` |

**핵심은 `candidate`의 표현이다.** 같은 이름의 대상 열 개에 엣지 열 개를 거는 것이 C2가 금지한 방식이고, 그것을 피하려고 엣지를 안 만드는 것이 P6 위반이다. 후보 집합을 하나의 엣지로 저장하면 둘 다 피한다 — 완전성은 집합이 지고 정밀도는 질의가 진다.

**질의가 등급을 고른다.** 감사(완전성 우선)는 `candidate`를 포함해 넓게 돌고, 컨설팅(정밀도 우선)은 `exact|scoped`만 쓰되 "제외된 `candidate` N건"을 대장으로 붙인다. P6("기계는 넓게 잡고 좁히는 것은 에이전트")을 데이터 구조로 표현한 형태다.

**후보 집합에는 상한이 있다.** B14가 지적한 폭발은 집합 저장으로 사라지지 않는다 — 경로 질의는 후보의 곱으로 자란다.

| 장치 | 규칙 |
|---|---|
| **집합 크기 상한 `K`** | 넘으면 나열하지 않고 `UnresolvedRef{사유=후보 과다}`로 강등(§5.3). 나열되지 않은 것은 "보지 않음"이지 "없음"이 아니다 |
| **경로 곱 예산 `B`** | 한 질의가 통과하는 `candidate` 엣지의 곱이 B를 넘으면 탐색을 멈추고 `Residual{사유=candidate 집합 과다}`(§8) |
| **절단은 산출에 남는다** | 상한에 걸려 잘린 것은 §4.2 첨부에 건수로 나타난다. 조용한 절단은 금지다 |

`K`·`B`의 초기값은 §12.4. 값은 실측으로 정해지지만 **값 없이 켜지지 않는다**는 것이 여기서의 결정이다.

### 5.2 경계 엣지 — B9에 대한 답

C2는 "언어를 잇는 것은 이름의 우연한 일치가 아니라 명시적 임포트여야 한다"고 하고 C4는 HTTP·큐·저장소 경계를 요구한다. 경계에는 명시적 임포트가 없다. 해소: 경계 엣지는 `extracted`가 아니라 `inferred`이며 `contract` 등급으로만 존재하고, 이름 일치가 아니라 계약 아티팩트를 증거로 요구한다.

| 증거 | 예 | 강도 |
|---|---|---|
| 선언된 스키마 | OpenAPI/AsyncAPI/protobuf/GraphQL SDL | 강 |
| 양쪽의 리터럴 경로·토픽 + 메서드 일치 | `POST /v1/tasks` ↔ 라우트 선언 | 중 |
| DTO 형태 일치 | 필드 이름·타입 집합 | 약 (단독으로는 엣지를 세우지 못함) |

증거 없이 이름만 같은 것은 엣지를 만들지 않고 `unresolved-boundary`로 대장에 남는다 — C2의 진리 명제를 지키면서 C4를 포기하지 않는 유일한 형태다.

**증거의 추출과 엣지의 성립을 구별한다.** "저장소에 OpenAPI 명세가 있고 `POST /v1/tasks`를 선언한다"는 재현되므로 증거 자체는 `extracted`다. 그러나 "이 클라이언트 호출이 저 라우트에 닿는다"는 명세로부터 따라 나오지 않는다 — 명세는 계약을 선언할 뿐 호출의 실재를 보증하지 않는다.

| | 출처 | 성질 |
|---|---|---|
| **증거 노드** | `extracted` | 좌표를 가지며 재추출로 갱신 |
| **경계 엣지** | `inferred` | `evidence: Coord[]`(비면 저장 거부) + `evidence_strength: 강\|중\|약` 필수 |
| **관측된 호출** | `observed` | 트레이스가 실제로 보면 별도 엣지가 나란히 선다. 덮어쓰지 않으며(§7.2) 어긋나면 그 불일치가 보고 대상 |

강도는 출처 축에 넣지 않고 엣지의 필수 필드로 뺀다 — 출처를 5·6값으로 늘리면 §3의 파티션 규칙이 다시 열린다.

### 5.3 D6 — 미해소 참조 노드

A1이 정확하다. 빌드하지 않으면 생성 코드·DI 바인딩·서드파티 계층은 노드 자체가 파일 시스템에 없다. 정밀도 손실이 아니라 완전성 손실이며 백서 §9의 P11/P6 화해 문단은 여기서 성립하지 않는다. 답은 없는 것을 만들어내는 것이 아니라 **없음을 노드로 만드는 것**이다.

```
UnresolvedRef { 참조된 이름, 참조 지점 Site, 실패 사유, 해소 시도 기록 }
실패 사유 ∈ { 정의 없음, 후보 과다, 언어 등급 미달, 범위 밖, 동적 디스패치, 문자열 기반 }
```

1. **거짓 안전이 관측 가능해진다.** "닿는 경로 없음"과 "가는 참조가 12건 미해소"는 다른 답이다.
2. **공백이 순위를 갖는다.** 미해소 참조가 몰린 파일이 곧 능력 확장의 우선순위다.
3. **외부 사실의 수용 지점이 생긴다.** 백서 §2.4·§10이 허용한 "출처 중립적 수용"이 `UnresolvedRef`를 해소하는 형태로 들어온다. 배정은 조달자가 아니라 §3의 규칙이 정한다 — 빌드 의존 정밀 엔진의 산물도 실행 트레이스도 둘 다 `observed`이고 재현 보증 없는 추론만 `inferred`다. 어느 쪽이든 조달 절차 기록과 적용 범위를 단다(§0.4-6). **누가 만들었는지 알 필요는 없지만 무엇이 어떤 절차로 만들었고 어디까지 유효한지는 좌표에 남는다.**

**그 수용의 첫 구체적 형태는 표준 인덱스 포맷이다 (R9).** [F §1](research/2026-08-03-precompute-code-graph-precedents.md): Glean은 C++·Hack만 자체 인덱서를 갖고 Go·Java·Rust·TypeScript는 LSIF/SCIP 수용으로 커버한다 — "빌드 통합 인덱서가 만든 정밀 사실을 포맷으로 받아 자기 fact 공간에 얹는다"가 이미 프로덕션에서 도는 형태다. 이 설계에서는 새 장치가 아니라 §12.2 수용 API의 입력 하나이며 배정은 규칙 2에서 `observed`로 떨어진다(SCIP 인덱스는 빌드 환경이 있어야 생긴다).

### 5.4 `UnresolvedRef`는 실행 관측의 작업 목록이다

A1이 지적한 완전성 손실 — DI 바인딩·리플렉션·동적 디스패치·생성 코드 — 은 전부 정적으로는 안 보이고 실행 중에는 보이는 부류이고 `UnresolvedRef`는 그 목록을 사유별로 이미 들고 있다.

| 실패 사유 | 실행 관측이 해소할 수 있는가 |
|---|---|
| `동적 디스패치` · `문자열 기반` | 예 — 트레이스가 실제 대상을 준다 |
| `정의 없음`(생성 코드·DI) | 예 — 빌드 산출물·컨테이너 덤프가 노드를 준다 |
| `후보 과다` | 부분 — 관측된 것만 확정, 나머지는 `candidate` |
| **`언어 등급 미달`** | 부분 (R9) — 실행으로는 안 되지만 그 언어의 빌드 통합 인덱서가 만든 SCIP/LSIF로는 된다. 조달원을 정적 추출기로만 상정하면 닫혀 보이는 칸 |
| `범위 밖` | 아니오 — 범위의 문제 |

그러므로 실행 조달의 우선순위는 사람이 정하지 않는다. **미해소 참조 밀도가 곧 "여기서 한 번 돌려보면 가장 많이 밝혀진다"는 지도**이며 조달은 그 지도를 따라 좁게 일어난다 — 전수가 아니라 표적이므로 P12와 충돌하지 않는다.

해소된 뒤에도 `UnresolvedRef`는 지워지지 않고 `observed` 엣지가 그것을 가리키며 붙을 뿐이다. 재현 보증이 없으므로 다른 환경에서 그 지점은 다시 미해소이고, 정적 하한과 관측된 해소를 겹쳐 보여주는 것이 정직한 형태다.

## 6. D7 — 결박과 낡음

### 6.1 5상태

백서의 3상태(살아 있음·낡음·보류)에 B13이 지적한 둘을 더한다. 상태는 결박 하나가 아니라 그 결박의 감시 집합 위에서 계산되며 감시 집합은 반경이 정한다(§6.2).

**그리고 그것은 하나의 열거가 아니라 두 축이다** — 초안은 다섯을 한 열거에 넣었고, 그러면 *"대체됐고 코드도 변했다"*를 표현할 수 없다. 선행 구현이 두 축으로 나눠 둘 다 표면화했다([G §4](research/2026-08-11-legacy-freshness-anchor-observation.md)).

**축 1 — 코드 대비 (기계가 계산한다)**

| 상태 | 조건 | 왜 구별하나 |
|---|---|---|
| `live` | 결박 좌표 존재 + 감시 집합 전체의 digest 불변 | |
| `stale` | 결박 좌표 존재 + 감시 집합 중 하나 이상의 digest 변경 | 무엇이 켰는지가 함께 출력된다(§6.2) |
| `pending` | 좌표가 아직 없음 (신생 프로젝트) | "아직 안 만들었다"와 어긋났다는 다르다 |
| `orphaned` | 좌표가 사라짐 (심볼 삭제·이동) | 구현 제거는 코드 변경과 다른 사건 |
| **`undeterminable{사유}`** | **감시 집합의 digest를 계산할 수 없음** — `partial` 파일, L0 심볼, 정체성 등급 미달 | **신설(R16).** 아래 |
| `stale-derived{경유}` | 자기는 그대로인데 입력이 낡음 | §6.4 |

**축 2 — 계보 대비 (사람 또는 승인된 추론이 만든다)**

| 상태 | 조건 |
|---|---|
| `current` | 이 의도를 대체한 것이 없다 |
| `superseded{by}` | 다른 의도로 대체됨 — B13의 핵심. 대체된 결정이 "살아 있음"으로 적극 보증되는 것이 낡음보다 강한 거짓 신호다 |

**두 축은 독립이고 둘 다 출력된다.** `superseded ∧ stale`(대체됐고 코드도 변함)과 `superseded ∧ live`(대체됐지만 코드는 그대로)는 사람이 다르게 처리한다. 그리고 **대체된 결박도 숨기지 않는다** — §11.3의 `touch`가 이미 "`superseded`된 이전 결정"을 반환한다고 적었고, 두 축으로 나눠야 그 반환값에 코드 신선도가 함께 실린다.

#### `undeterminable`이 필요한 이유 (R16)

선행 구현은 앵커나 대상 시각이 없으면 **낡지 않은 것으로 접었다**(`stale=False`). 방향은 이 설계와 같다 — 모르는 것을 낡았다고 하지 않는다. 그러나 **`false`와 "판정 불가"를 구별하지 않은 것은 백서 §4.2-4와 [목표 §3.1](plan/00-goals.md)의 정면 위반**이다. 그 접기의 결과는 *"이 결정은 유효합니다"*와 *"이 결정이 유효한지 알 수 없습니다"*가 같은 화면이 되는 것이고, 이 설계가 `Judgment`에서 `clean`을 없앤 것과 정확히 같은 실패다.

- 사유 어휘: `정체성 등급 미달`(L0·`ordinal`) · `파싱 부분 실패`(`partial`) · `감시 집합 원소 소멸` · `투영 미갱신`.
- **`live`로 세지 않는다.** 판정 입력에서는 `Residual{사유=결박 판정 불가}`가 되며 §8의 3분할과 같은 처리를 받는다.
- **밀도가 지도다** — `undeterminable`이 몰린 곳이 언어 능력 확장이나 provider 저작의 우선순위다(§5.4의 `UnresolvedRef`가 하는 일과 같다).

### 6.2 결박 반경

A3의 거짓 음성 — 좌표 바깥(호출자·설정·스키마)이 변해 결정이 무효가 돼도 `live`로 남는 것 — 은 원리적으로 닫히지 않는다("이 결정과 관련 있는 코드 전부"는 결정 불가능하다). 그러므로 닫지 않고 선언한다.

| 반경 | 감시 집합 | 크기 | 판정 비용 | 켜는 방법 |
|---|---|---|---|---|
| `symbol` (기본) | 결박된 심볼의 digest | 1 | 상수 | 기본값 |
| `callers` | + 직접 호출자 집합 | 1 + 직접 호출자 | 인접 조회 1회 | 결박 시 선택 |
| `closure(k)` | + k-홉 의존 폐포 | k-홉 폐포 | 폐포 크기에 비례 | 명시적 승인. `결박 수 × 폐포 크기`가 예산(§12.4)을 넘으면 저장 시점에 거부 |
| `files` | + 명시적으로 나열된 파일(설정·스키마·마이그레이션) | 열거 길이 | 열거 길이 | 사람이 지정 |

반경은 결박에 붙어 저장되고 낡음 판정 결과에 함께 출력된다. "이 결정은 `symbol` 반경에서 live"는 "이 결정은 유효하다"와 다른 문장이고 그 차이가 산출에 남는 것이 P4의 요구다. `stale`이 켜지면 어느 원소가 켰는지가 함께 나온다 — "호출자가 변해서"와 "본체가 변해서"는 사람이 다르게 처리할 사건이다.

§2.3의 "질의 시점 상수 시간 검사"는 투영의 신선도(HEAD 비교)에 대한 것이지 결박 상태 계산이 아니다. 결박 상태는 위 표의 비용을 지며 `closure(k)`를 무제한 허용하면 P12가 깨지므로 **런타임에 조용히 느려지는 대신 설정 시점에 실패한다.**

### 6.3 낡음 감지기가 낡는 경우

B5가 물은 것이다. 답: 감지기의 상태 자체가 대장에 있다 — 마지막 재추출 `Snapshot`, 추출기 버전, 그 이후 커밋 수. 감지기가 3주 낡았으면 낡음 표시들도 3주 낡았다는 것이 응답에 붙는다. 감지기의 신선도 검사는 상수 시간이므로 무한 후퇴하지 않는다.

### 6.4 D29 — 낡음은 전파된다. 규칙이 없으면 전파가 멈춘다 (U15-c)

§7.1이 라벨 하나에 대해 `label-stale`을 정했고 §3.3이 관측에 대해 `stale-observation`을 정했다. **일반 규칙이 없다** — 낡은 라벨에 의존한 판정, 그 판정을 근거로 쓴 서술, 그 서술을 인용한 브리핑이 각각 무엇이 되는지가 정해진 적 없다. 파생물의 파생물이 낡는 규칙은 온톨로지의 뼈대이며 그것이 비어 있으면 **KG는 자기 일부만 신선하고 나머지는 조용히 낡는다.**

> **모든 파생 노드는 자기 입력 좌표 집합에 결박된다. 입력 중 하나가 `stale`이면 파생물은 `stale-derived`다.**

| 등급 | 뜻 | 판정 입력 자격 |
|---|---|---|
| `live` | 자기 감시 집합도 입력도 전부 불변 | 있음 |
| `stale` | **자기** 감시 집합이 변했다(§6.1) | 없음 — 재판정 큐 |
| `stale-derived{경유 좌표[]}` | 자기는 그대로인데 **입력이** 낡았다 | 없음. 그러나 **재판정 비용이 다르다** — 입력을 갱신하면 자동으로 회복될 수 있다 |

> **`경유` 가 좌표가 아니라 노드 이름이다 (2026-08-12 · [F22-4 게이트](gates/F22-4-doctor.md)).** 낡은 입력이 언제나 코드 좌표를 갖는 것은 아니다 — `Change`·`Actor` 는 심볼이 아니고(§1.1) 그것들도 파생물의 입력이 될 수 있다. `경유`에 좌표만 실으면 **좌표 없는 입력이 조용히 빠지고**, 그러면 *"무엇을 갱신하면 닫히는가"* 라는 이 필드의 유일한 쓸모가 사라진다. 그래서 구현은 `(라벨, 식별자)` 를 싣는다. 파생물 자신의 **결박**은 그대로 좌표다 — 그것이 §6.5 의 신선도 앵커다.

1. **둘을 구별하는 이유는 처분이 다르기 때문이다.** `stale`은 사람이 그 결박을 다시 봐야 하고, `stale-derived`는 기계가 입력을 갱신하면 대개 닫힌다. 하나로 합치면 사람의 재판정 큐에 기계가 닫을 수 있는 것이 섞이고, 그 순간 [R-10](plan/00-risks.md#r-10)의 승인 노동이 부풀어 오른다.
2. **전파는 깊이 제한을 갖는다.** 파생 사슬은 길어질 수 있으므로 `stale` 전파에도 예산이 붙는다(§12.4). 예산에 걸리면 전파를 멈추는 것이 아니라 **`Residual{사유=낡음 전파 예산 초과}`를 낸다** — 조용한 절단 금지가 여기에도 걸린다.
3. **`History` 입력은 다르게 낡는다**(§3의 `ReproInput`). 범위가 `base..head`인 사실은 head가 움직이면 낡는 것이 아니라 **범위가 달라진 것**이다. 그러므로 `stale`이 아니라 **재계산 대상**이며, 재계산 전까지 산출에 자기 범위를 달고 나온다.

**전파를 끄는 손잡이를 두지 않는다.** 끌 수 있으면 그것은 §10의 협상 가능한 손잡이가 하나 느는 것이고, 게이트 오염의 가장 값싼 경로가 된다.

### 6.5 D32 — 신선도 앵커는 신고받지 않고, 낡음은 탐지만 한다 (R13)

§9.3이 검증 커버리지에 대해 세운 원리 — *"신고받지 않고 계산한다"* — 는 결박 층에 적용된 적이 없다. 선행 구현이 그것을 파생 타입 넷 전부에 걸어 두었고 이유를 명시했다: *"freshness must follow the code, not the generator's wall-clock"*([G §1.1](research/2026-08-11-legacy-freshness-anchor-observation.md)).

> **어떤 산출물도 자기 신선도의 기준점을 정할 수 없다. 기준점은 그 산출물이 가리키는 코드에서 나온다.**

| 생산자가 주는 것 | 기계가 계산하는 것 |
|---|---|
| `evidence_refs` — 무엇을 근거로 삼았는가 | **감시 집합과 그 시점의 digest**(§6.2의 `watch_snapshot`) |
| 어느 `Snapshot`에서 만들었다는 신고 | 그 신고와 **무관하게** 대상 좌표의 현재 digest |

**신고를 거부하는 것이 아니라 신고에 권한을 주지 않는 것이다.** 생산자의 `Snapshot` 신고는 `produced_by`에 기록되고 대조에 쓰인다 — 신고와 계산이 어긋나면 그 자체가 신호다(§7.2의 "덮어쓰지 않는다"와 같은 규칙).

**이것이 가장 무겁게 걸리는 곳은 §7.5의 조달이다.** 외부 엔진이 *"이 alert는 커밋 X 기준"*이라 신고하는데, 그 신고를 신선도 앵커로 쓰면 **엔진이 자기 산출물의 유효기간을 정하게 된다.** 앵커는 alert가 결박된 좌표의 현재 digest에서 온다.

#### 낡음은 탐지만 한다 — 자동 재생성이 없다

> **`stale`은 재생성을 트리거하지 않는다. 순수 비교이며 그 결과는 값이다.**

이 문장이 없으면 미끄러지는 방향이 하나뿐이다 — *"낡았으니 다시 만들자."* 그것이 일어나면 셋이 동시에 깨진다.

| 깨지는 것 | 어떻게 |
|---|---|
| §9.2 생산자 분리 | 재생성한 것이 자기가 낡았다고 판정한 주체와 같아진다 |
| §0.5 경계 | 기록하되 통치하지 않는다 → 자동으로 고치는 층이 된다 |
| §11.4 승인 비용 | 사람이 승인한 것이 승인 없이 교체된다. [R-21](plan/00-risks.md#r-21)이 막은 유실이 다른 경로로 재현된다 |

`stale`이 하는 일은 **재판정 큐에 올리고 §11.3으로 사람 앞에 가져오는 것**까지다. 다시 만드는 것은 사람이나 에이전트가 하고, 그 산출은 새 노드다(§1.2의 id 규칙).

## 7. D8 — 능력 확장 C1~C6 + E · O

백서 C1~C6의 기호와 뜻을 그대로 두고 R1(실측 최대 군집)과 B10(표가 요구하는 원시 개념)에 따라 능력 둘을 신설하고 착수 순서를 바꾼다.

| 능력 | 백서 대비 | 내용 | 순서 근거 |
|---|---|---|---|
| **C1 구조** | 동일 | 단위와 포함 관계 | 전제 |
| **C2 참조** | 등급화(D5) | 해소 등급 + 미해소 참조 | 전제 |
| **C3 진입점** | 동일 | 프레임워크 인식기. 인식기 버전이 좌표에 포함(B6) | 서사의 목록 |
| **C4 경계 통과** | `contract` 등급으로 한정(§5.2) | 저장소 경계를 1급으로 | 실측 8%([B §3](research/2026-08-01-boxwood-fix-taxonomy.md), 하한) |
| **E 효과 집합** | **신설** — 백서 C5의 전제층 하나를 독립 능력으로 | 어떤 경로가 어떤 필드·상태·외부 효과를 쓰는가. 술어: `writes(P1) ⊋ writes(P2)` | R1 — 백서 §6.2 표에 이 축이 없다 |
| **C5 지배관계** | 동일 | 경로 위의 가드 지배 | E보다 뒤. 제어흐름 층을 E와 공유하되 경로 열거를 더 요구 |
| **C6 시간축** | 동일 | 3축 좌표 + 신선도 | 전부에 걸림 |
| **O 실행 관측** | **신설 — 보조**(§0.4) | 호스트가 조달한 트레이스·바인딩·테스트 결과 + 빌드 산출물·표준 코드 인덱스(R9). `observed` 출처 | 주경로 아님. 정적 하한을 메우는 표적 도구(§7.2) |
| **U 균일성** | 동일 | 빌드 없이 임의 커밋. O는 U에서 면제되며 면제되었음을 산출에 단다 | §12.3에서 비용과 화해 |

**번역표를 두지 않는 것이 이 절의 결정이다.** 백서 번호를 밀어 신설 능력을 그 자리에 넣으면 같은 기호가 두 문서에서 다른 것을 가리키고 이후의 모든 ADR·코드·질의·대화가 번역표를 들고 다녀야 한다. 얻는 것은 없다 — 착수 순서는 §13 로드맵이 강제하지 번호가 강제하지 않는다. 그 결과 R1에 걸리는 무게는 "효과 집합이 독립 능력일 값이 있는가" 하나로 줄어든다(§15-16).

#### 순서를 바꾼 실제 근거

R1이 주는 것은 존재 주장뿐이다 — 18%(~19건) ↔ 21%(~22건)의 차이는 3건이고 n=104에서 구별되지 않는다. R1이 지지하는 것은 "효과 집합 축이 백서 §6.2 표에 아예 없다"이고 그것만으로는 순서가 정해지지 않는다. 순서를 정하는 것은 셋이다.

1. **의존 방향이 대등하지 않다.** 백서 §11은 제어흐름과 정의-사용을 나란히 적지만 지배관계는 정의-사용 위에 경로 열거를 더 요구한다. 정의-사용이 먼저 서는 것은 선호가 아니라 순서 강제다.
2. **하한 위에서 먼저 쓸모를 낸다.** 지배관계는 전칭 술어라 하한 위에서 `Finding`을 세우기가 원리적으로 어렵다(B4). `writes(P1) ⊋ writes(P2)`는 포함 관계이고 관측된 쓰기 집합만으로 비대칭이 보이면 그것은 존재 주장이다.
3. **`candidate` 폭발에 덜 민감하다.** 효과 집합은 경로의 곱이 아니라 심볼별 쓰기 집합의 합집합으로 자라므로 §5.1의 예산 안에서 먼저 성립한다.

**되돌리는 조건**: F13의 반증 조건(§13). 다른 코퍼스에서 효과 집합 결함이 드물면 첫째 논거만 남는데 그것은 순서만 지지하고 독립 능력으로 세울 값은 지지하지 않는다 — 그 경우 `E`를 내리고 백서 C5의 전제층으로 되돌린다. 번호를 옮기지 않았으므로 되돌리는 비용이 문서 한 행이다.

### 7.1 규약층 — B10이 요구한 원시 개념

백서 §6.2 표의 상태 전이·트랜잭션 경계·멱등 키·신뢰 경계는 능력이 아니다 — 코드에서 도출되지 않으므로 능력 목록에 넣는 순간 거짓말이 된다. 대신 규약층에 둔다.

```
Label { 종류(guard|effect|boundary|state|idempotency-key), 대상 좌표, 출처=asserted, 근거, 만료 규칙 }
```

- 라벨은 `asserted`이며 결박된다. 좌표가 변하면 라벨도 `stale`이 된다 — B2가 지적한 "라벨이 낡으면 판정은 여전히 결정론적으로 안전을 출력한다"를 이것이 닫는다. **stale 라벨에 의존한 판정은 `label-stale`을 달고 나온다.**
- 라벨 제안은 `inferred`로 에이전트가 대량 생성할 수 있고 승인만 사람이 한다(§11.4).

### 7.2 O 실행 관측 — 무엇을 하고 무엇을 하지 않는가

**하는 것**

| 용도 | 형태 | 겨냥하는 것 |
|---|---|---|
| 미해소 참조 해소 | 트레이스·컨테이너 덤프·빌드 산출물 | A1의 완전성 손실(§5.4) |
| 언어 하한 보정 (R9) | 표준 코드 인덱스(SCIP·LSIF) | §4.1의 낮은 언어 등급. 정적 하한을 코어 확장 없이 올리는 두 번째 경로이며 선언 팩(§7.3)과 달리 사람의 저작을 요구하지 않는다 |
| 라벨의 실측 확인 | "이 가드가 실제로 이 경로에서 도는가" | B2 |
| 결정의 실현 확인 | "이 결정이 말한 동작이 실제로 나는가" | 연구 5장의 행동 하네스 공백 · 연구 D §9.4-(1) |
| 진입점 실측 | 기동 후 라우트 테이블 조회 | C3의 인식기 하한 보정 |
| **정밀 분석 산물의 수용** (D24) | SAST(CodeQL·Semgrep 계열)의 alert·taint 경로, 린터·타입체커 진단, 의존 취약점 스캔 | **U11-b** — 데이터플로우(E)와 지배관계(C5)의 하한을 직접 만들지 않고 올린다. §7.5 |

**이름이 내용보다 좁다.** 위 표의 빌드 산출물·표준 인덱스는 실행이 아니라 빌드다. 배정은 정확하다 — §3의 규칙 2는 "실행"이 아니라 "환경에 의존하는 절차"로 쓰여 있고 빌드는 그 절차다. O는 `observed` 출처를 조달하는 능력의 이름이며 실행은 그 부분집합이다. ADR로 쪼갤 때 이름을 재검토한다(§16).

**하지 않는 것**

- **부재를 말하지 않는다.** 실행되지 않은 경로는 관측되지 않으므로 O의 침묵은 `Residual`이다.
- **인덱스를 `extracted`로 받지 않는다.** SCIP/LSIF는 정확하지만 빌드 환경 없이는 다시 만들어지지 않는다.
- **주경로를 대체하지 않는다.** O만으로 답이 나오는 질의는 만들지 않는다 — 실행 불가 프로젝트에서 조용히 죽고 그것이 U 위반이다.
- **자동으로 돌지 않는다.** 실행 허용 범위는 `asserted`이고 사람이 정한다(§0.4).
- **`extracted`를 덮어쓰지 않는다.** 어긋나면 양쪽을 함께 남기고 불일치를 보고한다 — 정적으로 도달 불가한 코드가 실행됐다면 추출기의 공백이고, 정적으로 존재하는 경로가 한 번도 안 돌았다면 다른 질문이 열린다.

### 7.3 D17 — 해석기 팩: 프로젝트별 계층이 서는 자리 (U1)

먼저 충돌이 아닌 것을 치운다. "해석기를 프로젝트마다 별도 구현한다"는 U와 정면 충돌로 보이지만 아니다 — U의 원문은 *"빌드하지 않고, 이력상의 임의 커밋에 대해 같은 방식으로 성립"*이며 균일성의 축은 **한 프로젝트 안의 시간축**이다. 프로젝트 사이의 능력 균일성은 백서가 요구한 적이 없고 백서 §2.2-2가 오히려 반대로 적었다 — 능력 차이는 결함이 아니고 결함은 그 차이를 숨기는 것이다. 그러므로 문제는 "허용되는가"가 아니라 **"어느 파티션에 들어가고 무엇이 그것을 감추지 못하게 하는가"**다.

#### 3층 분할

| 층 | 누가 만드나 | 출처 | 결정론 | 좌표 성분 |
|---|---|---|---|---|
| **코어 추출** | palimpsest | `extracted` | 보증 | 코어 추출기 버전 |
| **선언 팩** — 프레임워크 인식기, 가드·효과 규칙, 구조 기준, 서사 술어 | 프로젝트(사람) | `asserted` (§3.2 `asserted_via=rule`) | 팩이 고정되면 결정론적. 팩의 참값은 사람이 진다 | 팩 지문 |
| **실행 팩** — 프로젝트 전용 분석 스크립트, 외부 정밀 엔진, 빌드 산출물 덤프 | 프로젝트(도구) | `observed` | 없음 | 환경 지문 · 실행 시각 |

```
extractor_version = (코어 추출기 버전, 선언 팩 지문)
```

이 확장이 P5를 지키는 방식은 B6과 같다 — 팩이 자라면 같은 커밋이 다른 그래프를 낳지만 그것이 좌표 변경으로 관측된다. 팩 지문을 좌표에 넣지 않으면 P5는 프로젝트 단위로 문자 그대로 거짓이 된다.

#### 네 가지 제약

1. **코어는 팩 스키마만 알고 팩 내용은 모른다.** 팩은 데이터이지 코어 코드가 아니다. 프로젝트의 어휘(레이어 이름·프레임워크 개념·도메인 술어)가 코어에 들어오는 순간 P7이 깨지고 그것은 백서 §2.4가 역사적 전례까지 적어둔 드리프트다.
2. **코어는 실행 팩을 실행하지 않는다.** 실행은 호스트가 하고 코어는 §12.2의 수용 API로 결과를 받는다.
3. **팩은 필수가 아니라 점증적이다.** 팩이 0개여도 코어 하한으로 모든 질의에 답이 나온다. 팩을 써야 능력이 서면 설치 첫날 가치가 무너지고 군집 C9가 지적한 공백이 커진다.
4. **팩의 부재는 대장에 표시된다.** 대장 머리에 `(프레임워크 인식기 N개 · 규칙 M개 · 실행 팩 K개)`가 서고 팩이 없어 내려간 등급은 언어 등급과 나란히 적힌다. 팩이 없는 프로젝트와 팩이 커버하지 못한 영역이 같아 보이면 백서 §2.2-2가 깨진다.

#### 기각한 형태

- **"프로젝트마다 추출기를 새로 구현한다"** — 기각. 코어의 결정론 계약(백서 §4.2-2)을 프로젝트 코드가 지게 되고 `extracted`의 의미가 프로젝트마다 달라진다. P2를 프로젝트 단위로 무효화한다.
- **"코어가 프로젝트 분석기 코드를 실행한다"** — 기각. 임의 코드 실행은 §0.4의 실행 계약을 코어 안으로 들여오고 P11의 방어선을 코어에서 잃는다(제약 2의 다른 표현).
- **"팩 산물을 `extracted`로 받는다"** — 기각. §3.2의 배정이 막는다. 팩이 틀리면 파생 사실 전부가 틀리는데 `extracted`는 그런 실패 양식을 갖지 않는다.
- **"팩 인터페이스를 선행 자산에서 가져온다"** — 기각(U8). 개념은 수입하고 인터페이스는 여기서 짓는다(§12.6).

#### 이것이 능력표에 하는 일

**팩은 능력을 늘리지 않는다. 하한을 올린다.** C1~C6·E·O의 정의는 그대로이고 팩이 하는 것은 `UnresolvedRef`를 줄이고 `candidate`를 `scoped`로 승격시키고 라벨을 공급하는 것이다. 그러므로 팩의 값은 §5.3이 이미 준 지도로 측정된다 — 미해소 참조 밀도가 팩 저작의 우선순위이고 그 밀도의 감소가 팩의 효능이다.

**정직하게**: 팩이 실제로 저작되는지는 아무도 측정한 적 없다. §11.4의 승인 노동과 같은 종류의 미지수이며 같은 사슬로 흘러간다 — 팩이 없으면 라벨이 없고 라벨이 없으면 §8의 산출이 전부 `Residual`이다(§15.1 사슬 A).

### 7.4 D28 — `provider`: 프로젝트가 **코드로** 제공하는 것 (U16)

§7.3은 프로젝트별 계층을 셋으로 갈랐고 그중 실행 팩에 대해 *"코어는 실행하지 않고 호스트가 실행한다"*고만 적었다. **무엇을 주고받는지가 없다.** 대상 프로젝트가 MSA인지 모놀리스인지, 이벤트 기반인지, 어떤 언어·프레임워크인지 코어가 알 수 없다는 U16의 전제 아래에서 이 공백은 치명적이다 — 프로젝트가 자기 구조를 아는 유일한 주체인데 그것을 코어에 전달할 규격이 없다.

> **`provider`는 프로젝트가 자기 저장소에 두는 실행 가능한 어댑터이고, 코어는 그 산물의 스키마만 안다.**

#### 포트 일곱 — 무엇이 프로젝트마다 다른가

| # | 포트 | 프로젝트가 아는 것 | 선언(TOML)으로 되나 | 산물의 출처 |
|---|---|---|---|---|
| 1 | **언어 추출기** | 코어가 모르는 언어·DSL | 아니오 | `observed` (코어 내장 추출기만 `extracted`) |
| 2 | **진입점 인식기** | 자기 프레임워크의 라우팅·핸들러 규약 | **대개 예** — 애노테이션·경로 패턴 | 예이면 `asserted_via=rule`, 코드면 `observed` |
| 3 | **경계 계약 추출기** | 자기 IDL·스키마 위치와 방언 | 부분 | 위와 같음 |
| 4 | **효과 어휘 매퍼** | 자기 ORM·큐·캐시 호출이 무엇을 쓰는가 | **대개 예** | 위와 같음 |
| 5 | **모듈·경로 규약** | 모노레포 레이아웃, 생성 디렉터리, 별칭 | **예** | `asserted` |
| 6 | **관측 조달자** | 자기 CI·테스트·SAST를 어떻게 돌리는가 | 아니오 | `observed` (§7.5) |
| 7 | **개념·규칙 팩** | 자기 도메인 어휘 | **예** — F18의 메타 어휘 | `asserted_via=rule` |

**절반 이상이 선언으로 된다.** 그것이 D17이 이미 답한 부분이고, 코드가 필요한 것은 1·6과 2·3의 잔여뿐이다. **코드가 필요한 자리를 최소로 유지하는 것이 이 포트 설계의 목표**이지 확장점을 많이 여는 것이 목표가 아니다 — 확장점 하나는 저작 노동 하나이고 사슬 A의 뿌리 후보다.

#### 계약 — 프로세스 경계

```
palimpsest → provider :  stdin  에 JSON 요청  { kind, snapshot, inputs, budget }
provider   → palimpsest: stdout 에 JSON 응답  { schema_version, capability, facts[], unresolved[], elision }
```

1. **코어는 provider를 실행하지 않는다.** 호출은 호스트·CLI 배치 경로가 하고 코어는 §12.2의 수용 API로 받는다. §7.3의 기각 목록 두 번째(*"코어가 프로젝트 분석기 코드를 실행한다"*)가 그대로 유지된다 — 인프로세스 플러그인(동적 라이브러리·임베디드 런타임)을 열지 않는 이유가 이것이고, 부수적으로 언어 자유(어떤 언어로 짜든 된다)를 얻는다.
2. **산물은 `observed`다**(§3의 경계 사례 표). provider가 `deterministic = true`를 선언해도 배정은 바뀌지 않는다 — 코어가 재현을 검사할 수 없기 때문이다. 선언이 하는 일은 **재조달 시 대조**이고, 불일치는 지워지지 않고 보고된다(§7.2의 "덮어쓰지 않는다"와 같은 규칙).
3. **능력을 선언하지 않으면 산물이 거부된다.** provider는 자기가 무엇을 산출하는지(`capability`)와 어디까지 유효한지(적용 범위)를 매 응답에 싣는다. 없으면 §0.4-6의 절차 기록 요구에 걸려 수용되지 않는다.
4. **provider가 없어도 코어는 모든 질의에 답한다** — §7.3의 제약 3과 같다. provider의 부재는 대장에 `(provider N개 · 미설정 포트 M개)`로 적힌다.
5. **예산과 절단이 provider에도 걸린다.** 응답의 `elision`이 필수이고, 시간·크기 상한을 넘으면 호스트가 끊되 그 사실이 `Residual`이 된다. 남의 코드가 무한히 도는 것을 조용히 기다리지 않는다.

#### 언어 추출기도 포트인 이유 (U16-c)

[계획 §6](plan/00-goals.md)이 첫 언어를 TypeScript, 둘째를 Kotlin으로 적었다. **언어 목록을 늘리는 것으로는 스택 불가지에 도달하지 못한다** — 목록은 언제나 유한하고 대상 프로젝트는 그 밖에 있을 수 있다. 도달 경로는 포트 1을 여는 것이고, 그때 지켜야 할 선이 하나다: **코어 내장 추출기의 산물만 `extracted`다.** 외부 추출기의 산물은 `observed`이며 대장에 그 사실이 적힌다. 그러지 않으면 `extracted`의 결정론 계약이 프로젝트 코드로 넘어가고 §7.3이 이미 기각한 형태가 뒷문으로 들어온다.

### 7.5 D24 — 정밀 분석은 만들지 않고 조달한다 (U11-b · U12)

[계획 §4](plan/00-goals.md)가 *"정밀한 정적 분석기 — 목표가 아님"*이라 적었고 그 판정은 유지된다. 그러나 그 한 줄이 **두 문장을 묶고 있었다.**

| 문장 | 판정 |
|---|---|
| ① 우리가 정밀 분석기를 만들지 않는다 | **유지.** 빌드 의존 엔진을 내장하면 U가 그날 죽는다 |
| ② 정밀 분석의 산물이 이 제품에 들어오지 않는다 | **정정.** §7.2의 O가 이미 반대로 적고 있었고, 계획만 그 자리를 P2로 미룬 채 조달원 목록에서 SAST를 빠뜨렸다 |

**왜 지금 정정되어야 하는가.** U11이 상위 가치로 올린 (b)(c)는 이 설계에서 E(효과 집합)와 C5(지배관계)가 지고, 둘 다 **XL**이며 [R-13](plan/00-risks.md#r-13)이 "가장 비싼 미지"라 적었다. 직접 만드는 경로는 [R-17](plan/00-risks.md#r-17)(1인 대역폭)이 막는다. 조달하는 경로는 수용 API 하나이고 **이미 설계되어 있다.**

#### 그러면 palimpsest의 몫은 무엇인가 — 다섯

조달만으로는 이 제품일 이유가 없다. SAST를 그냥 돌리면 된다. 이기는 자리는 정밀도가 아니라 아래 다섯이며, **다섯 중 어느 것도 성립하지 않으면 D24는 조달 배관에 불과하다**(F16b의 반증 조건에 들어간다).

| # | 몫 | 기존 도구가 못 하는 이유 |
|---|---|---|
| 1 | **결박** — alert가 좌표에 걸리고 그 좌표를 다시 만질 때 나타난다(§11.3) | alert는 실행마다 새로 나고 어디에도 결박되지 않는다 |
| 2 | **낡음** — "이 alert가 아직 유효한가"에 답한다. 코드가 변하면 `stale`(§3.3) | 재실행이 유일한 답이고 재실행은 빌드를 요구한다 |
| 3 | **3분할 재분류** — alert 목록을 `{Finding, Residual, OutOfScope}`로 옮긴다(§8). 엔진이 보지 못한 범위가 `Residual`로 선다 | 엔진은 자기가 못 본 것을 산출하지 않는다 |
| 4 | **억제의 이력** — `// nosemgrep`·baseline·예외 목록이 **언제 왜 누가** 붙였는지가 `asserted`로 결박되고 만료를 갖는다 | 억제는 코드 주석으로 흩어지고 근거가 남지 않는다. **§10의 협상 가능한 손잡이가 하나 더 있는 자리이며 지금 아무도 세지 않는다** |
| 5 | **엔진 간 불일치** — 두 엔진이 어긋나면 그것이 신호다(§7.2) | 각 엔진은 자기 답만 안다 |

#### 그리고 조달할 것이 있는지를 쟀다 — 없었다 (2026-08-11)

**D24는 유지된다. 무너진 것은 D24가 아니라 조달의 P1 자리다.**

[T9](gates/preflight.md#t9--조달-가능성-실측)가 코퍼스 넷의 CI 설정·실행 이력·로그·아티팩트를 실측했다.

| 집계 | 값 |
|---|---|
| SAST 조달원 | **0 / 4** (GitHub 코드 스캐닝도 4개 저장소 전부 비활성) |
| 좌표 있는 진단을 실제로 내는 코퍼스 | 1 / 4 (ditto — biome lint + `tsc`) |
| 진단을 아티팩트로 보존하는 코퍼스 | **0 / 4** — 경로가 CI 실행 로그뿐이다 |
| SARIF | **0 / 4** |

**위 다섯 몫은 전부 alert가 존재한다는 가정 위에 있다.** 그 가정이 대상 환경에서 비어 있으면
다섯 몫은 반증되는 것이 아니라 **적용될 데가 없다.** 그래서 처분은 "D24 폐기"가 아니라
"[조달을 P2로 되돌리고 P1의 약속을 (a)(d)로 줄인다](plan/00-goals.md#01-무엇으로-채점되는가--산출이-아니라-결과-design-08)"이다.
그리고 그 강등이 F16을 둘로 쪼갰다 — **수용 API(F16)는 P1로 남는다.**
[F21](plan/features/F21-provider-ports.md)이 필요로 한 것이 조달이 아니라 그 문이었기 때문이다.
§15-35가 검사 가능하다고 적어 둔 그 위험이 실제로 발생했고, 검사가 코드 이전에 끝났다.

**한 가지가 특히 나쁘다** — 감사(§8·C5)의 판정 대상인 boxwood Kotlin 백엔드는
분석 CI가 하나도 없다. 조달로 우회하려던 사슬 A의 대상이 바로 거기다.

#### 이 조달이 여는 새 위험 — 가장 무겁다

**`observed`는 존재 주장에만 강하고 부재 주장에는 쓸 수 없다**(§3 말미). SAST의 "0 alerts"는 `clean`이 아니라 `Residual`이다. 이 규칙이 여기서 가장 무겁게 걸리는 이유는 SAST 산출의 형태가 **부재 주장처럼 생겼기 때문**이다 — 리포트에 아무것도 없으면 사람은 안전하다고 읽는다.

- 수용 시점에 **엔진의 적용 범위**(스캔한 경로·룰셋·언어)를 함께 받고, 그 범위 밖은 `OutOfScope`로 대장에 적힌다. 범위를 안 주는 산출은 수용하지 않는다.
- `audit.judge`가 SAST를 근거로 세우는 것은 `Finding`뿐이다. 침묵은 `Residual{사유=관측 침묵}`이며 타입 수준에서 그 경로가 없다(D9).
- **엔진의 룰셋 변경이 `ScopeReduction`이다**(§10). 룰을 끄면 alert가 사라지고, 그것은 고쳐서 사라진 것과 다르다. §10의 여섯 손잡이에 일곱째가 붙는다.

#### 이 조달은 이미 한 번 시도됐다 — 선행 시도가 남긴 다섯 (R15)

선행 구현이 같은 조달을 설계하다 **코드 0줄에서 재유예했다**([G §3](research/2026-08-11-legacy-freshness-anchor-observation.md)). 미작성의 이유가 특히 값지다 — *happy-path fixture가 hard case를 전부 우회하므로 테스트가 green이어도 실효 증거가 못 된다.* 그 pre-mortem이 남긴 선행조건 중 **이 설계가 아직 답하지 않은 다섯**을 여기 옮긴다.

| # | 조건 | 이 설계에서 어디로 |
|---|---|---|
| 1 | **실패와 침묵은 다르다.** 생산자가 exit code를 보지 않으면 빌드 실패가 "0 findings"로 위장한다 — *"보안 니치 최악의 false-clean"* | §3의 배정 이전 단계다. **조달 실패는 `observed` 사실이 아니라 조달 자체의 부재**이며, 침묵(`Residual`)과 다른 처분을 받는다: 재조달 큐로 가고 대장에 "조달 실패 N건"으로 선다. 이 구별이 없으면 실패가 침묵으로, 침묵이 안전으로 두 번 미끄러진다 |
| 2 | **위치 → 좌표 resolver가 어디 사는가.** 엔진은 `파일:라인`으로 말하고 이 설계는 심볼 좌표로 말한다 | **provider 안이 아니라 수용 경계에 산다**(§7.4의 caller-side). provider 안에 두면 프로젝트마다 다시 구현되고 그 정확도가 코어의 계약에서 사라진다. 그리고 **resolver 실패와 정당한 미결박을 구별해야 한다** — 전자는 우리 결함이고 후자는 `UnresolvedRef`다 |
| 3 | **한 지점에 여러 흐름이 있다.** 같은 sink·같은 룰의 서로 다른 taint 경로가 하나로 접히면 **조용한 과소 계상**이다 | §1.2의 id 규칙에 **흐름 식별자**가 재현 입력의 일부로 들어간다. 이것이 없으면 D33이 엔진 간 불일치는 살리고 엔진 내 다중 흐름은 잃는다 |
| 4 | **엔진의 입도가 더 잘다.** SARIF는 식(expression) 단위이고 이 설계의 최소 결박 단위는 심볼이다 | 셋 중 하나를 **미리 정해야** 한다 — 감싸는 심볼로 올림 / 파일로 올림(정밀도 상실을 표시) / 거부(`UnresolvedRef`). 정하지 않으면 드롭이 조용해진다 |
| 5 | **산출이 환경마다 다르다.** SARIF에 실행 시각·도구 버전·절대 경로·스레드 순서가 섞여 있다 | 재조달 대조(§7.4-2)가 **거짓 불일치**를 낸다. 수용 시점 정규화가 필요하고, 무엇을 정규화했는지가 조달 절차 기록에 남는다 |

**1이 가장 무겁다.** 나머지 넷은 정밀도·비용의 문제이지만 1은 이 제품의 정체성을 정면으로 겨눈다 — 실패를 안전으로 읽는 경로는 백서 §1이 고발한 것의 가장 값싼 형태다.

B4는 연구 C의 세 회차 모두 `critical`을 매긴 유일한 군집이고 원문 대조 결과 정확하다. 하한 위에서 "모든 경로가 P로 지배된다"는 전칭 판정은 근거를 가질 수 없다. 그러므로 감사는 `clean`을 출력하지 않는다.

```
Finding   — 위반이 확정된 것. 반례 경로가 Site로 첨부된다. (존재 주장)
Residual  — 판정할 수 없는 것. 사유 + 무엇이 있으면 판정 가능한지.
OutOfScope— 범위 밖. 대장 참조.
```

`Residual` 사유 어휘: `미해소 참조 경유`, `라벨 없음`, `언어 등급 미달`, `범위 밖 저장소 경유`, `동적 디스패치`, `candidate 집합 과다`, `관측 낡음`, `검증 커버리지 미달`, `탐색 예산 초과`.

> **어휘가 아홉에서 열하나로 늘었다 (2026-08-12 · [F22-4 게이트](gates/F22-4-doctor.md)).** `낡음 전파 예산 초과`(§6.4-2 가 이미 이 낱말로 요구했다)와 `표본 밖`(§12.7 의 표본 검사)이 붙는다. 위의 아홉은 **감사 판정**을 두고 쓴 목록이고 `doctor` 는 그때 존재하지 않았다 — 목록이 닫힌 것이 아니라 그 판정의 어휘였다. **어휘가 열거인 것은 그대로다**: 문자열로 두면 같은 사유가 두 이름을 갖고 사유별 정렬이 무의미해진다.

**실측 사례에서 무엇을 하는가**: 가드 없는 엔드포인트 271개([B §4](research/2026-08-01-boxwood-fix-taxonomy.md))에 대해 기존 도구는 "271개 위험" 또는 "이상 없음"을 말하고 둘 다 틀렸다. 정확한 답은 "위반 확정 N개, 잔여 271-N개, 각 잔여의 사유"이며 잔여는 사유별로 정렬되어 사람이 라벨 하나를 승인할 때마다 줄어든다 — 잔여 집합의 크기가 §11.4 승인 노동의 진척 표시가 된다.

### 8.1 잔여는 목록이 아니라 결박물이다 (R6)

**여기서 이 설계는 한 번 반증됐다.** 잔여를 1급으로 만들어 표시하는 것은 ditto가 이미 했다 — `unverified` 필드, 종료 완전성 게이트, 완료 계약의 "남은 위험" 필수 필드. 결과는 [E §4](research/2026-08-02-ditto-harness-failure-observation.md)다: 잔여 어휘를 안고 닫힌 work item 43%, 후속으로 분리된 세 건 중 두 건 폐기. 표시는 목록으로 존재했고 목록은 아무도 다시 열지 않았다.

```
Residual { 사유, 판정 대상 술어, 결박 좌표[], 발생 Snapshot, 해소 조건 }
```

1. **잔여는 §11.3의 적시 제시 대상이다.** 그 좌표를 다시 만지는 순간 나타난다 — 사람이 목록을 열어야 보이는 것이 아니라 잔여가 사람이 있는 곳으로 온다.
2. **잔여는 낡는다.** 결박 좌표가 변하면 `stale`이 되어 다시 판정돼야 하고 자동으로 사라지지 않는다.
3. **잔여의 소멸은 사건이다.** 줄었으면 원인이 셋 중 하나다 — 판정됨 / 좌표 소멸 / 범위 축소(§10). 셋째를 둘째와 섞지 않는 것이 게이트 오염 감지의 실질이다.

**B14(과다근사가 신호를 제조한다)에 대한 부분적 답**: `candidate` 집합을 통과한 경로는 `Finding`이 아니라 `Residual`로 간다. 등급 구분이 없으면 전 지점이 "구멍 있음"이 되고 등급이 그 경보 포화를 막는다. 완전히 막지는 못한다 — `scoped` 해소가 틀릴 수 있고 그 경우는 남는다(§15-6).

## 9. 합성과 검증 — 생성형 큐레이션을 1급으로 유지하면서

백서 P8은 생성형 큐레이션을 1급 능력으로 선언하고 이 설계는 그것을 결정론적 추출기의 부속품으로 축소하지 않는다. §2~§8이 전부 사실층이었던 이유는 사실층이 목적이어서가 아니라 **합성이 안전해지는 조건이 사실층에 있기 때문**이다.

### 9.1 D10 — 합성물의 저장 조건

```
Synthesis {
  본문, 출처=inferred,
  evidence_refs: Coord[]      // 비어 있으면 저장 거부
  gaps: string[]              // 무엇을 보지 못했는가
  confidence: enum
  produced_by: {모델, 프롬프트 해시, Snapshot}
}
```

`evidence_refs`가 비면 저장 자체가 실패한다 — P3("근거 없는 답을 내지 않는다")를 문장이 아니라 스키마 제약으로 만드는 지점이다.

네 필드 전부가 §3.1을 통과한다(선택 필드 없음). `gaps`는 비면 "다 봤다"는 주장이 되어 §15-1과 충돌하므로 기계가 §4.2의 첨부에서 자동으로 채우고 채우지 못하면 쓰기가 실패한다. `confidence`·`produced_by`도 기계 기록이다. `evidence_refs`가 좌표이므로 합성물도 결박되고 낡으면 낡았다고 표시된다 — 연구 D §6.4가 `/explain-diff`의 결핍으로 지목한 것(설명이 `/tmp`에 있고 자기가 낡았다고 말하지 못한다)이 여기서 구조적으로 닫힌다.

### 9.2 P10의 확장 — 설명·출제도 생성 경로 밖에 둔다

백서 P10은 생성자/검증자 분리를 검증에 적용했다. 연구 D §6.3·§7.3이 관측한 것은 설명과 출제에도 같은 원리가 걸린다는 것이다 — 설명자가 생성자면 서사가 사후 정당화 방향으로 수렴한다.

규칙: **어떤 산출이 판정의 입력이 되면 그 산출의 생산자는 판정 대상의 생산자와 달라야 한다.** 구현상 별도 컨텍스트 + 다른 세션이며 `produced_by`가 기록하므로 위반이 사후에 관측 가능하다.

### 9.3 D11 — 검증자의 커버리지를 질의 로그에서 계산한다

백서 §12-11이 연 질문: 검증자가 "무엇을 보지 않았는가"를 무엇에 기대어 말하는가. 자기 신고에 머무르면 §4.3이 거부한 자기 증언이 검증 층에서 재현된다. **답: 신고받지 않고 계산한다.** 검증자는 질의 표면을 통해서만 코드에 접근하므로(§12.2) 질의 로그가 곧 검증자가 조회한 좌표 집합이다.

```
확실히 보지 않은 집합 ⊇ (판정 대상의 관련 좌표 집합) − (질의 로그가 남긴 좌표 집합)
```

조회하지 않은 좌표는 확실히 보지 않은 것이다(이 방향은 건전하다). 조회했다고 본 것은 아니다(이 방향은 보증하지 않는다). 계산되는 것은 "보지 않은 것"의 하한이며 자기 신고보다 엄격하게 강하다.

#### 이 계산의 전제는 palimpsest가 강제할 수 없다

검증자가 자기 파일 읽기·grep으로 코드에 직접 닿으면 질의 로그는 그 접근을 담지 못한다. 코어는 라이브러리이지 샌드박스가 아니므로 막을 수단이 없고, 막을 수 있다고 적으면 R6·R7에서 두 번 배운 것(규율 의존 장치는 실패한다)을 세 번째로 어긴다. 그러므로 강제하는 대신 선언하고 대조한다. 선언값은 §9.4의 `narration_basis`와 같은 세 값이다.

| 선언값 | 계산된 값의 정확한 이름 | 성립 조건 |
|---|---|---|
| `graph-only` | "보지 않은 것의 하한" — 질의 로그가 접근의 전부이므로 여집합이 건전하다 | 없음 |
| `graph+direct-read` **(기본)** | 신고를 합치면 하한, 안 합치면 하한이 아니다 | 직접 열람 좌표를 `direct_reads`로 신고해야 `(관련 좌표) − (질의 로그 ∪ direct_reads)`가 되어 하한이 회복된다. 신고는 규율에 기대므로 하한의 자격이 `graph-only`보다 약하고 그 차이가 등급으로 붙는다 |
| `undeclared` | "palimpsest를 통해 보지 않은 것" — 약한 이름 | — |

**대조**(어느 값에서든): 호스트가 조달할 수 있으면(§12.2) 세션의 도구 호출 로그를 `observed`로 받아 신고와 대조하고 미신고 접근 건수가 산출에 붙는다. 두 값을 같은 이름으로 부르지 않는 것이 여기서 지켜야 할 전부다. 기본값이 가운데 줄이므로 §14-11이 "닫음"이 아니라 "부분"이다(§15-32).

#### 계산된 하한에는 처분이 붙는다 — 단, 존재 주장에는 걸지 않는다

값이 산출에 붙기만 하면 §15-9("표시는 읽히지 않는다")에 걸리므로 처분을 정한다. 그러나 *"미조회 비율이 임계를 넘으면 `Finding`을 세우지 못한다"*는 형태는 참 양성만 죽인다 — `Finding`은 존재 주장이고 커버리지 부족은 완전성의 문제이므로 부재 주장에만 걸려야 한다. §3 말미가 이미 같은 비대칭을 세웠고, D9에 의해 `clean`이 애초에 출력되지 않으므로 그 임계가 막을 거짓 안전은 이미 다른 장치가 막고 있다.

| 대상 | 임계 초과 시 |
|---|---|
| `Finding` | 그대로 선다. 다만 커버리지 등급이 필수 필드로 붙는다 |
| 잔여의 완결성 — "이것이 잔여의 전부다" | 세우지 못한다. `Residual{사유=검증 커버리지 미달}`이 추가되고 그 산출은 잔여를 열거했다고 말할 수 없다 |
| 후속 판정의 입력 자격 | 승인 게이트·구조 평가 델타(§11.6)의 입력이 되지 못한다 — 둘 다 완결성을 전제하는 소비처다 |

임계값은 §12.4이며 실측으로 조정되지만 임계 없이 켜지지 않는다. R2의 측정(회차당 53%·단일출현 34%)이 말한 것은 회차를 늘려도 하한이 상한이 되지 않는다는 것이고, 이 설계는 그것을 고치지 않고 **하한임을 계산 가능하게 만들 뿐이다.**

### 9.4 D22 — 서술은 질의 표면을 경유한다 (U5)

사슬 B의 뿌리는 "질의 로그 완결성을 강제할 수 없다"이고 §9.3의 선언은 관례에 기대고 있었다. U5는 그 선언을 기본값으로 올린다 — 온보딩·변경 전 계획·변경 후 리뷰의 서술은 코드를 직접 읽고 쓰는 것이 아니라 그래프 질의를 근거로 쓴다.

**그러나 하한 위의 서술은 새 거짓 안전을 만든다.** 직접 열람을 막으면 추출기가 못 본 것이 서사에서도 사라진다 — A1의 완전성 손실(생성 코드·DI·리플렉션)은 그래프에 노드가 없으므로 그래프만 읽는 서술자는 원리적으로 언급할 방법이 없다. 백서 §4.3의 경고 그대로다(*"좁히면서 버린 것이 산출에 남지 않으면 거짓 안전은 관측 불가능한 자리로 옮겨갈 뿐이다"*). 그러므로 서술물은 §9.1의 제약에 네 필드를 더 진다.

```
Narration extends Synthesis {
  coverage        // 근거로 쓴 질의들의 §4.2 첨부 합집합 — 미해소 참조 건수, 범위 밖 파일 수, 경유 언어 등급
  unresolved_refs // 서술이 지나간 경로 위의 미해소 참조 좌표. 비면 "없음"이 아니라 "미계산"이며 저장되지 않는다
  narration_basis ∈ { graph-only, graph+direct-read, undeclared }
  direct_reads: Coord[]   // 질의 표면을 거치지 않고 직접 읽은 좌표.
                          // narration_basis=graph+direct-read이면 필수이고 비면 저장 거부
}
```

- **넷 다 필수다**(§3.1). `coverage`·`unresolved_refs`는 기계가 질의 로그에서 채우며 채우지 못하면 쓰기가 실패한다.
- **`direct_reads`가 없으면 "커버리지에 반영된다"는 문장이 실현 수단을 갖지 못한다.** `coverage`가 §4.2 첨부의 합집합 = 질의 기반이므로 질의를 거치지 않은 열람을 담을 자리가 없다. 신고는 기계가 채우지 못하므로 이것만은 규율에 기대고 그 사실이 하한의 등급에 남는다.
- `narration_basis=undeclared`이면 커버리지는 약한 이름으로만 불린다(§9.3).
- **앞의 셋은 본문에 렌더링된다.** 메타데이터로만 있으면 §15-9에 걸린다 — 서사 안에 공백이 문장으로 들어가야 한다. `direct_reads`는 커버리지 계산의 입력이므로 좌표 목록은 본문 대상이 아니고 건수만 `coverage`에 실린다.

#### 어느 값이 기본인가 — R11이 이 질문을 열었다

U5의 문면대로면 기본값은 `graph-only`다. 외부 실측이 그 독해에 반대한다 — [F §4](research/2026-08-03-precompute-code-graph-precedents.md)의 31개 저장소 평가에서 그래프 경유 83% vs 파일 탐색 92%였고, 위 문단이 원리로 적은 것에 수치가 붙은 형태다.

**잠정 처분: 기본값은 `graph+direct-read`.** 그래프를 먼저 경유하고, 직접 열람이 필요하면 하되 그 사실이 선언되고 커버리지에 반영된다. 근거 셋:

1. U5가 요구한 것은 근거의 결박이지 열람의 금지가 아니다 — `graph+direct-read`도 `evidence_refs`·`coverage`·`unresolved_refs`를 그대로 지므로 잃는 것이 없다.
2. `graph-only`를 강제하면 §9.3의 질의 로그 완결성이 오히려 나빠진다 — 규율로 막을 수 없는 것을 기본값으로 요구하면 실제로 일어나는 일은 `undeclared`로의 이탈이다(R6·R7의 실패 양식).
3. 83 vs 92의 원인을 조사가 구별하지 못했다(F §4-3). "그래프가 나쁘다"인지 "그 그래프가 얕다"인지 모르는 상태에서 더 강한 쪽을 기본으로 두는 것은 근거 없는 베팅이다.

**뒤집히는 조건**: F17·F19에서 두 값의 산출 품질·커버리지를 대조해 `graph-only`가 지지 않으면 U5의 문면대로 올린다. 판정 전까지 이 설계는 U5를 "경유한다"로 읽지 "경유만 한다"로 읽지 않는다(§15-28).

#### 이 경로가 실제로 결정론적인 만큼만 그렇게 부른다 (U6)

지시의 논거는 *"추출과 쿼리는 결정론적이고 서사 부여만 비결정론이므로 전부 에이전트가 분석·서술하는 것보다 정확하다"*이다. 방향은 지지되고 낱말은 과장이다.

| 단계 | 성질 | 근거 |
|---|---|---|
| ① 추출 (코드 → 그래프) | 조건부 결정론 — `(커밋, 코어 버전, 팩 지문)`이 고정될 때만. 시점이 다른 두 그래프의 비교는 결정론이 아니다 | B6 · D1 · §7.3 |
| ② 그래프의 내용 | 하한이며 등급이 섞여 있다. `candidate`·`contract`는 결정론적으로 *계산*되지만 참이라는 보증이 없다 | D5 · §15-6 |
| ③ 질의 실행 | 결정론 — 단, 하한 위에서. 같은 답이 나온다는 것과 그 답이 완전하다는 것은 다른 문장이다 | §4.2 · B4 |
| ④ 질의 **선택** | 비결정론. 그리고 이것이 커버리지 문제의 본체다 | R2 · §9.3 |
| ⑤ 시각화 | 레이아웃은 결정론화 가능하나 무엇을 그릴지는 아니다. 그림은 잘린 것을 보여주지 않는 매체다 | §5.1 · §12.5 |
| ⑥ 서술 | 비결정론. `inferred` + `evidence_refs` + `produced_by` | §9.1 |

> **이 이득의 정확한 이름은 "결정론"이 아니다.** 비결정론이 두 곳(④ 질의 선택 · ⑥ 서술)으로 국소화되고, 그 두 곳이 각각 질의 로그와 `evidence_refs`로 관측 가능해진다.

이름을 이렇게 부르는 것이 수사가 아닌 이유: "결정론적이다"라고 부르면 ②의 등급과 ③의 하한이 시야에서 사라지고, 그 순간 이 시스템은 백서 §6.3이 최악의 실패 양식으로 지목한 거짓 안전을 더 그럴듯한 포장으로 생산한다.

#### 연구 D가 지목한 세 위험 중 둘이 닫힌다

| `/explain-diff`의 위험(연구 D §6) | 처분 |
|---|---|
| (3) 결박되지 않아 낡음이 표시되지 않는다 | 닫힌다 — `evidence_refs`가 좌표이므로 서술물도 결박된다(§9.1) |
| (2) 설명자가 생성자다 | 닫힌다 — §9.2의 생산자 분리 + `produced_by`의 사후 관측 |
| (1) 설명은 수용을 늘리지 판정을 늘리지 않는다 | **열려 있다.** 결박은 이 위험을 줄이지 않는다 — 오히려 근거가 붙은 설명은 더 그럴듯하므로 틀렸을 때 더 해롭다(§15-24) |

## 10. D12 — 기준의 변경 이력을 결박한다

백서 §12-5가 연 질문(게이트 오염에 무엇을 보장할 것인가)의 두 선택지 중 **"기준의 변경 이력 자체를 결박 대상으로 삼는다"**를 고른다. A4가 보인 대로 사실층도 면역이 아니다 — 좌표의 참값은 협상 불가능하지만 어디까지 좌표를 만들 것인가는 전부 협상 가능하다.

| 협상 가능한 손잡이 | 오염 형태 | 감지 |
|---|---|---|
| 스캔 제외 패턴 | 결함 많은 디렉터리 제외 | 대장 diff — `excluded` 증가 |
| 지원 언어 선언 | 언어를 `unsupported`로 내려 판정 대상에서 제거 | 언어별 등급 표 diff |
| 인식기·깊이 한계 | 탐색 깊이 축소로 경로 감소 | 설정 결박 + 잔여 증가 |
| 가드·효과 라벨 | 라벨 삭제로 잔여 이동 | 라벨 삭제 이벤트 |
| 서사 규칙 | 술어 약화 | 규칙 정의의 결박 |
| **구조 기준**(레이어·허용 의존 방향·모듈 경계) | 기준 완화로 §11.6의 위반이 사라짐 | 선언 팩에 있으므로 팩 지문 diff. U3가 더한 여섯째 손잡이 |
| **외부 엔진의 룰셋·억제·baseline**(§7.5) | 룰을 끄거나 `nosemgrep`·예외 목록을 늘려 alert가 사라짐 | 조달 절차 기록에 룰셋 지문이 실리므로 그 diff. 억제는 `asserted`이고 만료를 갖는다. **U12가 더한 일곱째 손잡이이며 지금 어느 도구도 세지 않는다** |

**구현 형태**: 여섯은 전부 `asserted` 설정이며 저장소에 커밋된 파일에서 온다 — 즉 그 자체가 git에 있고 결박된다. 각 `Snapshot`에서 대장이 계산되므로 범위 축소는 대장의 diff로 나타나고, 커버리지가 줄어든 커밋은 결함을 고친 커밋과 같은 자격으로 관측된다.

**축소는 diff가 아니라 결박 객체다** — R6의 일관 적용(§8.1이 `Residual`에 한 것과 같은 교훈).

```
ScopeReduction { 손잡이 종류, 변경 전/후 범위, 사라진 좌표 집합, 발생 Snapshot, 규칙 ID, 해소 조건 }
```

- **사라진 좌표에 결박된다** — 제외된 디렉터리의 심볼, `unsupported`로 내려간 언어의 파일.
- **§11.3의 적시 제시 대상이다.** 그 좌표를 다시 만지면 *"이 영역은 N일 전 스캔 범위에서 빠졌다 — 규칙 R, 커밋 C"*가 나타난다. 사람이 대장 diff를 열어야 보이는 것이 아니라 축소가 사람이 있는 곳으로 온다.
- **잔여 소멸의 원인 분해와 맞물린다**(§8.1-3) — "범위 축소"가 좌표를 가진 객체이므로 셋째를 둘째와 섞지 않는 것이 계산 가능해진다.

**보장하지 않는 것**: 축소를 막지 않는다. 정당한 축소(진짜 생성 파일 제외)와 회피(불편한 디렉터리 제외)를 기계가 구별하지 못한다. 보장하는 것은 축소가 조용하지 않고 잊히지도 않는다까지다(§15-10·§15-26).

## 11. D13 — 의도층의 입구 셋

백서 §12-8이 연 질문("승인 자체가 노동이면 아무도 하지 않고 의도층은 영원히 빈다")은 제품의 생사를 가르는 질문이고(군집 C9도 같은 곳) 연구 D가 그 답의 재료를 준다.

### 11.0 항해가 1급이다 (R5)

세 입구는 대등하지 않다. ditto는 의도 포착을 규율이 아니라 기계로 강제한 시스템이었다 — 커밋 본문 90%, ADR 49건, work item 146건 전부가 acceptance criteria 보유. 이 조사가 관측한 어느 표본보다 의도부채가 낮다. 그리고 소유자가 자기 시스템의 한 경로에 대해 이렇게 적었다: *"내가 지시하여 만들었지만 잘 모름."*

> **포착이 포화한 저장소에서 실패한 것은 항해다.**

| | 역할 | 근거 |
|---|---|---|
| **§11.3 적시 제시** | **목적** — 결박된 것이 필요한 좌표에서 나타난다 | R5·R3. 실패가 실제로 일어난 지점 |
| §11.1 계획-구현 결박 | 재료 공급 — 좌표를 가진 의도를 대량으로 만든다 | R4 |
| §11.2 서술물 인입 | 재료 공급 — 이미 있는 서술을 좌표에 건다 | 군집 C4 |

포착 장치를 하나 더 만드는 것은 이 설계의 목표가 아니다. 재료는 이미 넘친다(ditto 하나에 work item 146건·ADR 49건·설계 보고서 60여 편). 부족한 것은 그것들이 필요한 순간에 필요한 좌표에서 나타나는 경로다.

### 11.1 입구 1 — 계획-구현 결박 (R4)

**관측**: 상류 검토(RPI)를 쓰는 팀은 연구·계획 문서를 지금 대량으로 생산하고 있고 그것은 백서 §7이 말하는 "결정"의 실물이다 — 대안이 검토되고 하나가 선택되고 그것이 코드가 되는 사슬 그 자체. 그런데 마크다운으로 흘러가고 코드에 묶이지 않는다.

```
Plan { 항목[] }  →  각 항목: { 서술, 예상 좌표(파일·심볼), 검증 단계 }
                     ↓ 구현 후
Deviation = 대조(계획 항목 좌표 집합, 실제 diff 좌표 집합)
          → { 계획대로, 계획에 없던 변경, 계획했으나 없는 변경 }
```

1. **연구 D §9.4-(1)이 지목한 빈칸을 채운다** — 사람이 이해한 것(200줄 계획)과 배포되는 것(20,000줄 코드) 사이의 검사 가능한 연결.
2. **의도층 콜드스타트를 우회한다.** 새 승인 노동을 요구하지 않는다 — 이미 사람이 계획을 검토하고 승인하고 있고 palimpsest는 그 승인에 좌표를 붙일 뿐이다. 백서 §12-8("승인 비용을 어디까지 낮출 수 있는가")에 대한 답은 **"이미 지불되고 있는 승인에 올라탄다"**이다.
3. **계획-구현 이탈률이 측정된다** — 연구 D §13-8이 "실행 가치가 높은 후속 측정"으로 지목한 값.

**정직하게**: 계획 항목이 예상 좌표를 갖지 않으면 대조가 성립하지 않고 그 항목은 `pending` 결박으로 남아 이탈률 계산에서 `unmeasurable`로 빠진다.

### 11.2 입구 2 — 기존 서술물 인입 (군집 C4)

백서 §1이 고발한 낡은 README·주석·위키·티켓은 의도층 항목이 아니므로 결박되지 않고 설치 후에도 거짓 신호로 남는다. **설계**: 설치 시 저장소의 서술물(마크다운, 주석 블록, ADR 디렉터리)을 훑어 결박을 시도한다 — 코드 식별자·경로 언급을 좌표로 해소한다.

| 결과 | 처리 |
|---|---|
| 해소됨 + 좌표 `live` | `inferred` 결박 후보 → 승인 큐 |
| 해소됨 + 좌표 `stale`/`orphaned` | "낡은 서술물"로 즉시 보고 — 설치 첫날의 가장 값싼 산출 |
| 해소 실패 | "미결박 서술물" 목록에 등록 |

셋째 줄이 중요하다. 결박할 수 없는 문서를 목록으로 만드는 것 자체가 산출이다 — "이 프로젝트에서 검증되지 않은 서술이 여기 있다"는 지도이고 지금 어디에도 없다.

#### 가장 가까운 선례가 어디까지 갔고 어디서 멈췄는지

Meta의 pre-compute engine은 §11.2가 하려는 것을 생성 쪽에서 이미 했다 — 50+ 에이전트가 4,100여 파일을 읽고 모듈마다 다섯 질문에 답해 25~35줄(~1,000토큰) 컨텍스트 파일을 만들고, opt-in으로만 싣고, 몇 주마다 자동 job이 경로를 검증하고 stale 참조를 고친다([F §5](research/2026-08-03-precompute-code-graph-precedents.md)).

**그 자가유지가 멈춘 지점이 이 설계의 자리다.** Meta의 job이 검증하는 것은 파일 경로의 실재이고, 이 문서의 어휘로는 `orphaned` 판정만 하고 `stale` 판정을 하지 않는다 — 경로는 그대로인데 `body_digest`가 바뀐 경우, 즉 서술이 낡는 가장 흔한 방식을 보지 못한다.

> **palimpsest가 이 선례에 대해 주장할 수 있는 차이는 정확히 하나 — 서술이 좌표에 결박되고 그 좌표의 내용이 변하면 낡았다고 말한다.** 그 이상(더 나은 요약, 더 넓은 커버리지)을 주장하면 50+ 에이전트가 한 일을 더 잘한다는 주장이 되고 근거가 없다.

같은 출처가 반대 방향의 증거도 준다 — Meta 자신이 적기를, AI 생성 컨텍스트 파일이 Django·matplotlib 같은 유명 OSS에서 에이전트 성공률을 떨어뜨렸다(사전학습에 이미 있어 중복 노이즈였다는 설명). **생성된 서술의 순효능이 음수인 조건이 실재한다**는 1차 자인이며(§15-24), §11.5의 브리핑과 §9.4의 서술이 정확히 그 부류다.

### 11.3 입구 3 — 적시 제시 (R3의 항해 문제)

연구 D §11.1이 실측한 것: 그 표본은 의도를 상당히 잘 기록하면서도 같은 결함을 다섯 번 반복했다. 규칙은 커밋 본문에 쓰여 있었고 아무도 그것에 도달하지 못했다. 의도층을 채우는 것만으로는 부족하고 **좌표를 건드리는 순간 그 좌표에 결박된 것이 나타나야 한다.**

```
질의: touch(좌표)  →  { 이 좌표에 결박된 결정, superseded된 이전 결정, 이 좌표에 걸린 라벨,
                        이 좌표를 포함하는 계획 항목, 이 좌표에서 발생한 결함 계보,
                        이 좌표에 걸린 Residual(§8.1)·ScopeReduction(§10) }
```

새 능력이 아니라 결박의 역방향 색인이다. 비용은 거의 0이고 실측된 재발 사례(같은 함수 5회)를 직접 겨눈다. P9(점진 회상)의 실제 형태이기도 하다 — 전부 싣지 않고 지금 만지는 좌표에 걸린 것만 싣는다.

**palimpsest가 인지부채를 갚는다고 주장하지 않는다**(R3). 인지부채는 사람 안에 있으므로 어떤 산출물도 직접 상환하지 못한다. 적시 제시가 하는 것은 의도부채의 상환을 필요한 시점에 도달시키는 것이며 그것이 산출물이 할 수 있는 최대다.

### 11.4 승인 비용의 설계

세 입구가 공통으로 요구하는 것이 승인이고, 백서 §12-8이 경고한 대로 승인이 노동이면 아무도 하지 않는다.

| 장치 | 내용 |
|---|---|
| **올라타기** | 새 승인을 만들지 않고 이미 있는 승인(계획 검토·PR 승인·커밋)에 좌표를 붙인다 |
| **일괄 승인** | `inferred` 라벨 제안을 종류별로 묶어 한 번에 판정. 개별 확인이 아니라 표본 확인 + 잔여 표시 |
| **진척의 가시화** | 잔여 집합 크기(§8)가 승인 하나마다 줄어드는 것을 보여준다. 노동이 아니라 계기판을 보고 하는 일이 된다 |
| **거부도 기록** | "이 엔드포인트에 가드는 불필요하다"도 `asserted` 사실이며 결박된다. 다음 회차에 다시 묻지 않는다 — 재질문의 제거가 승인 비용 절감의 대부분이다 |
| **규칙으로 묶기** | 팩 규칙 하나를 승인하면 파생 라벨 전부가 함께 선다(§3.2). 일괄 승인의 기계 형태 — 표본 확인의 대상이 라벨이 아니라 규칙이 된다 |

#### 병목 완화의 형태를 못 박는다 (U7)

백서 P14가 이미 같은 곳에 서 있다 — *"사람의 판정은 통독이 아니라 대조로 성립해야 한다. 사람이 감당하는 것은 코드의 양이 아니라 판정의 양이다."*

> **병목 완화는 "절차를 더 쌓는 것"이 아니라 "판정 단가를 낮추는 것"이다.** 절차를 쌓는 형태는 이미 관측되었고 실패했다([E](research/2026-08-02-ditto-harness-failure-observation.md) — 자율 실행·무축소 게이트·완료 계약·fresh-context 검증이 전부 작동하면서 판정을 사람 손에서 떼어냈다).

이 구별이 산출 전체에 걸린다. 브리핑(§11.5)·구조 평가(§11.6)·그래프 경유 서술(§9.4)은 대조 재료의 단가를 낮추는 장치로만 정당화되며 새 승인 단계로 기능하는 순간 §0.5가 막아둔 방향이다. **반대 위험이 같은 무게로 걸린다** — 브리핑과 시각화는 그 자체가 새 절차이기도 하다. 세 검사가 §13·§15에 있다: R8 기준선(문서 한 장을 이기는가), 연구 E의 실패 양식(자동화가 판정을 대행하는가), 설명적 깊이의 착각(§15-21).

### 11.5 D18 — 변경 전 브리핑 (U2)

§11.1이 계획을 코드에 결박했다면 이 절은 그 계획이 만들어지기 전에 무엇이 제공되는가를 정한다. 브리핑은 `Plan`의 상류다.

```
좌표를 만진다 → 브리핑(사실 하한 + 후보 + 잔여) → 사람이 읽고 판단 → Plan(§11.1) → 구현 → Deviation
```

#### 이름을 먼저 고친다

지시의 원형은 "어떤 영향 범위가 있는지를 분석한다"였고 그 형태는 D9가 금지한 것이다 — "이 변경의 영향은 이것들이다"는 나열되지 않은 것에 영향이 없다는 부재 주장을 포함하고 하한 위에서 부재 주장은 근거를 가질 수 없다(B4). 그러므로 산출의 이름은 **"영향 범위"가 아니라 "영향 하한과 그 잔여"**다. 이름을 지키는 것이 여기서 지켜야 할 전부다 — 제목이 "영향 범위"면 3분할을 붙여도 전칭으로 읽힌다.

#### 세 부분은 출처가 다르다 — 섞으면 세탁이다

| 브리핑의 부분 | 출처 | 형태 |
|---|---|---|
| **도달 하한** — 이 좌표를 만지면 무엇이 닿는가 | `extracted` (+ 팩이 있으면 `asserted`) | `{도달 확정, 잔여, 범위 밖}` 3분할(§8) |
| **활용 후보** — 어떤 메서드·추상화·기존 설계가 있는가 | `extracted`가 후보를 공급 | 후보는 사실, "이것을 쓰라"는 판단 |
| **수정 제안** — 어떻게 고칠 것인가 | `inferred` | `evidence_refs` 필수. 승인되면 `Plan` 항목이 된다 |

```
Briefing {
  대상 좌표[], 발생 Snapshot,
  reach: { findings: Coord[], residuals: Residual[], out_of_scope: 대장 참조 },
  candidates: { 재사용 후보 좌표[], 유사 구조 좌표[], 관련 결정·라벨(§11.3의 touch 결과) },
  proposal: Synthesis,          // inferred. evidence_refs 없으면 저장 거부(§9.1)
  ...Narration                  // §9.4의 네 필드 전부. 브리핑도 서술물이다
}
```

`candidates`가 §11.3의 `touch(좌표)`를 그대로 재사용한다 — **적시 제시는 새 장치가 아니라 브리핑의 재료 공급 경로이며 브리핑은 적시 제시가 변경 시점에 켜지는 형태다.**

#### P10이 부분적으로 걸린다

브리핑은 사람의 승인을 받으므로 판정의 입력이다(§9.2). 그러나 연구 D §9.2가 상류 검토에 대해 관측한 면제 논거가 일부 적용된다 — 계획 검토는 코드가 존재하기 전이므로 사후 정당화 유인이 원리적으로 없다. 정확히는 **사후 정당화 유인은 없고 사전 정당화 유인은 있다**(자기가 하려는 변경을 쉬워 보이게 하한을 좁게 그릴 유인).

- `reach` — 기계가 계산하므로 생산자와 무관하다. P10이 걸리지 않는다.
- `proposal` — `produced_by`에 기록되고 승인 게이트의 입력이면 §9.2가 그대로 걸린다.

#### 입력이 없을 때

관련 좌표가 해소되지 않거나 팩이 없어 라벨이 비면 브리핑은 빈 `reach`를 내지 않고 `Residual`을 낸다 — §12.6의 fail-closed 형태 변환과 같은 규칙이다(기계가 차단하지 않고 처분을 사람에게 가져온다).

### 11.6 D20 — 변경 후 구조 평가 (U3)

#### 평가는 절대값이 아니라 델타다

성숙 프로젝트에 설치한 첫날의 절대 평가는 "전부 위반"이고 그 산출은 읽히지 않는다(§15-9). 판정 대상은 이 변경이 만든 순증이다.

```
Conformance = 판정(Snapshot_after) ⊖ 판정(Snapshot_before)
            → { 새 위반, 해소된 위반, 새 잔여, 해소된 잔여, 범위 변동(§10) }
```

마지막 항이 없으면 §10의 게이트 오염에 무방비다 — 범위가 줄어서 위반이 사라진 것과 고쳐서 사라진 것이 같아 보인다. `ScopeReduction`이 델타의 필수 성분인 이유다.

#### 무엇을 평가하는가 — 기준 없이는 평가가 아니라 취향이다

구조 평가는 규범 판정이므로 기준을 요구한다. 기준은 규약층(§7.1)의 `asserted` 라벨과 선언 팩(§7.3)의 규칙이며 코어가 어휘를 고정하지 않는다(§14-3).

| 축 | 기준의 출처 | 판정 형태 |
|---|---|---|
| 코드·데이터 흐름 | E 효과 집합 + 효과 라벨 | `writes(P1) ⊋ writes(P2)` 비대칭(§7) |
| 함수 호출 흐름 | C2 등급 엣지 | 새로 생긴 `candidate`·`UnresolvedRef` 밀도 |
| 의존 | 선언 팩의 레이어·허용 방향 | 방향 위반 + 위반의 신규성 |
| 소유권 | 아래 | 소유자 없는 표면의 증감 |

#### 소유권 — 코드 밖에서 낡는 첫 사실

소유권은 코드에 없다. `CODEOWNERS`·디렉터리 관례·커밋 저자 분포는 증거이지 소유권이 아니다 — §5.2가 경계 엣지에 세운 구별이 그대로 적용되고 소유권 주장은 `asserted`다.

> 소유권의 무효화 원인은 코드 밖에 있다. 퇴사·팀 재편·인수인계는 `body_digest`를 바꾸지 않으므로 §6.1의 `stale`이 켜지지 않고 §6.2의 어떤 반경으로도 감시되지 않는다 — `files` 반경조차 저장소 안의 파일만 본다.

닫지 않는다. 대신 **만료 규칙을 필수로** 요구한다. §3의 `asserted` 행이 이미 "결박 필수 + 만료·재확인 규칙"을 적었고 소유권은 만료가 결박보다 앞서는 첫 사례다. 만료 없는 소유권 주장은 저장을 거부한다(§15-20).

#### 이 산출이 이겨야 할 상대

백서 §10은 "정밀 분석 엔진이 더 잘하는 영역이 있다"를 인정했고 구조 평가는 그 목록의 한복판이다(아키텍처 lint·의존 규칙 검사·순환 탐지). §13의 R8 기준선이 여기 가장 날카롭게 걸리며 이길 수 있는 지점은 정밀도가 아니라 셋뿐이다.

1. **결박된 기준** — 기준 자체가 낡으면 낡았다고 말한다(D12).
2. **3분할** — "위반 0건"이 아니라 "위반 N건, 잔여 M건, 각 잔여의 사유".
3. **적시 제시** — 평가 결과가 보고서가 아니라 좌표 결박물이 되어 그 좌표를 다시 만질 때 나타난다(§8.1·§11.3).

**셋 중 어느 것도 성립하지 않으면 이 산출은 만들 이유가 없다.** 그대로 반증 조건이 된다(F20).

## 12. D14 — 물리 설계

### 12.1 무엇을 설치하는가

P12(설치·운영 비용이 1급 제약) + P11(대상을 빌드하지 않는다) + U(임의 커밋에서 균일)가 함께 강한 제약을 건다.

| 구성 | 선택 | 근거 | 뒤집히는 조건 |
|---|---|---|---|
| 추출기 | **tree-sitter 기반 다언어 파서** | 빌드·툴체인 없이 blob 하나만으로 파싱된다 → U가 성립하는 유일한 부류. 오류 회복이 있어 `partial`을 표현할 수 있다. 외부 근거 둘(R10) — stack-graphs가 tree-sitter 위에서 빌드·설정 없이 이름 해소를 프로덕션 규모로 돌리고, Joern은 fuzzy parsing으로 빌드 환경 없이 부분 프로그램에 CPG를 세운다([F §2·§6](research/2026-08-03-precompute-code-graph-precedents.md)) | L3(정의-사용) 이상을 tree-sitter 위에서 감당 못 하는 언어가 다수로 밝혀지면 언어별 백엔드 분리. **stack-graphs가 데이터플로우를 미해결로 남긴 것이 이 조건이 실제로 걸릴 수 있다는 신호다**(F13) |
| 실행 형태 | **단일 정적 바이너리.** 구현 언어는 Rust로 확정 | 사용자 머신에 런타임을 요구하지 않는다(P12) — 언어 런타임 의존은 곧 설치 실패율. Rust인 이유는 §1.1의 강제 규칙 일곱 중 다섯을 **컴파일 타임으로 옮길 수 있는** 유일한 후보이기 때문이다. 다른 후보에서는 같은 것이 전부 검사, 즉 규율로 남는다 | 소유자의 언어 숙련이 진척을 막으면 재론. **그때 바뀌는 것은 언어이지 구조가 아니다** — 다섯이 컴파일에서 검사로 내려오고 그 손실을 명시적으로 기록한다([R-01](plan/00-risks.md#r-01)) |
| 저장소 | **파생 2층 + 재생 불가 의도.** ① 1층 콘텐츠 주소 캐시 ② 2층 임베디드 KV 인덱스 ③ **의도 — 정본은 텍스트이고 git에 커밋된다**(§12.8). 그래프 DB는 저장이 아니라 **내보내기 대상** | 셋의 성질이 다르다 — 1·2층은 지워도 재생되고 의도는 지우면 유실이다([R-21](plan/00-risks.md#r-21)). 한 파일에 두면 "지우고 재구축"이 사람의 승인 노동을 지우는 명령이 되고, **재구축 등가성 검사가 그 유실을 확인하고 통과한다.** 그래프 DB를 기본 저장으로 두지 않는 이유는 §5.1의 절단 기록을 남의 질의 엔진에서 표현할 수 없기 때문이다 | 경로 질의(C5)가 실측에서 감당 불가면 **먼저 예산을, 다음에 인덱스 레이아웃을, 마지막에 엔진을** 의심한다. 순서를 못 박는다 |
| 캐시 키 | `(blob 해시, ExtractorVersion)` | 브랜치 전환·과거 커밋 조회가 대부분 적중 → U와 P12의 화해(§12.3). **커밋이 키가 아니므로 워킹트리 좌표(§2.1-1)가 캐시를 그대로 쓴다** | — |

**이 표는 ADR 후보이지 결정이 아니다** — 백서 §12-9가 연 질문에 대한 제안이며 각 행에 뒤집히는 조건을 함께 적었다. **다만 저장소 행의 "셋으로 가른다"는 뒤집히지 않는다** — 그것은 성능 선택이 아니라 R-21에 대한 방어이고, 대안은 유실을 감수하는 것뿐이다.

### 12.2 표면은 양방향이다 — 소비자 중립 + 조달자 중립 (P7, D15)

호스트는 질의하는 쪽이기만 한 것이 아니라 관측을 조달하는 쪽이기도 하다. 표면을 한 방향으로만 그리면 그 사실이 어댑터 안에 숨는다.

```
                     ┌──────────────── 질의(consume) ──────────────┐
코어 (라이브러리)                                                    │
  ├── CLI            — JSON in/out. 스크립트·CI·임의 도구            │
  ├── MCP 서버       — 에이전트. 질의 로그가 여기서 나온다(§9.3)     │
  └── 관측 수용 API  — observation intake. 조달자 중립              ─┘
                     └──────────────── 조달(provide) ───────────────┘
                                    ↑
        Claude Code 플러그인 (어댑터) — 소비자이자 조달자. 얇게.
        그 외 조달자 — CI 산출물, 정밀 분석 엔진(SAST·린터·타입체커, §7.5),
                       프로덕션 텔레메트리, 표준 코드 인덱스(SCIP·LSIF) — R9,
                       프로젝트 provider(§7.4)
```

#### D30 — 1급은 CLI이고 프로토콜은 어댑터다 (U17)

*"MCP일 필요는 없다. 단순 하네스여도 된다"*는 이 설계를 뒤집지 않고 **우선순위 하나를 정정한다.** 계획이 MCP 서버와 플러그인을 P0에 넣었는데([F06](plan/features/F06-surface.md)) 그럴 이유가 없다.

| | 지위 | 근거 |
|---|---|---|
| **CLI (JSON in/out)** | **1급.** 이것만으로 모든 능력에 도달한다 | 스크립트·CI·git 훅·임의 도구가 쓴다. 프로토콜 SDK의 스펙 변동에 노출되지 않는다 |
| **배치·훅 경로** | CLI와 대등 | U17의 "하네스"가 가리키는 형태. 상주 프로세스가 없다는 것이 P12의 실질 |
| **MCP 서버** | **어댑터.** 질의 로그(§9.3)를 얻는 경로로서 값이 있고 그것이 유일한 고유 이득 | 없어도 코어의 어떤 능력도 죽지 않는다 |
| **플러그인** | 어댑터의 어댑터 | 전달 경로이지 코어의 정의가 아니다 |

**"하네스"의 두 뜻을 여기서 못 박는다.** U17이 쓴 하네스는 **전달 형태**(상주 서버가 아니라 불러 쓰는 도구)이고, §0.5가 거부한 하네스는 **작업을 모는 오케스트레이터**다. 전자는 채택하고 후자는 여전히 거부한다 — 같은 낱말이 다른 것을 가리키므로 이 문단이 없으면 §0.5의 말뚝이 지시로 뽑힌 것처럼 읽힌다.

경계 규칙(백서 §2.4를 그대로 강제):

- 코어의 어휘에 특정 호스트의 개념이 들어오지 않는다. 호스트 어휘로의 매핑은 어댑터 안에서만 일어난다.
- **수용 API는 조달자의 정체를 묻지 않되 조달 절차는 요구한다.** 받는 것은 `(관측 종류, 좌표, 환경 지문, 조달 절차 기록, 증거)`이며 그것을 만든 것이 Claude Code인지 CI인지 사람이 붙여넣은 트레이스인지는 배정을 바꾸지 않는다(§3). 이것이 "호스트를 통해 실행에 닿는다"가 "호스트에 의존한다"로 미끄러지지 않게 막는 유일한 장치다.
- **그러나 정체 중립과 절차 무검증은 다르다.** 앞의 것이 P7을 지키고 뒤의 것은 `observed` 파티션을 아무나 임의 사실을 넣을 수 있는 문으로 만든다. 절차 기록은 필수이며 규칙은 §0.4-6에 있다(§15-31).
- 코어는 조달된 관측이 하나도 없어도 모든 질의에 답한다. 없으면 `UnresolvedRef`가 남고 대장에 공백으로 표시될 뿐이다.
- **P7의 반증 조건**(군집 C8 중 원문 대조를 통과한 부분 — [대장 §2](evidence-map.md)): *코어 테스트 스위트가 어떤 호스트도 설치되지 않은 환경에서 전부 통과해야 하고, 관측이 0건인 상태에서도 모든 질의가 답(공백 포함)을 낸다.* 둘 중 하나가 깨지면 P7이 깨진 것이며 **이 검사는 F01부터 CI에서 상시 돌아야 한다**(§15-14).

### 12.3 U와 P12의 화해 — A7에 대한 답

A7의 충돌은 실재한다: U는 임의의 과거 커밋을 요구하고 P12는 그 비용이 사용자 것이라 하며 백서 §11 자신이 "설치 비용은 미검증"이라 자인한다. **해소: 이력은 요구가 아니라 지연 평가다.**

| 단계 | 무엇을 추출하나 | 언제 |
|---|---|---|
| 설치 | HEAD `Snapshot`만 | 즉시 |
| 결박 발생 | 그 결박이 가리키는 커밋 | 필요 시 |
| 계보 질의 | 계보가 지나는 커밋만 | 질의 시 |
| 전 이력 replay | 전부 | 옵션. 기본값 아님 |

U가 요구하는 것은 "모든 커밋이 미리 추출되어 있음"이 아니라 "임의 커밋에 대해 같은 방식으로 답할 수 있음"이다. 콘텐츠 주소 캐시가 있으면 과거 커밋 추출은 변경 파일 수에 비례하므로 계보 한 마디를 여는 비용이 커밋 하나 분량이다 — **U는 능력의 성질로 유지되고 비용은 실제 사용량에 비례한다.**

**이 형태에 선례가 있다 (R10).** stack-graphs는 파일마다 독립적으로 부분 그래프를 만들고 질의 시점에 커밋 전체로 스티칭하며 변경분만 재계산한다([F §2.2](research/2026-08-03-precompute-code-graph-precedents.md)) — 캐시 키가 `(blob 해시, 추출기 버전)`인 것과 같은 구조다. 다만 stack-graphs는 단일 커밋 분석에 초점이고 크로스 저장소를 다루지 않으므로 `Snapshot`(커밋 집합) 위의 스티칭은 여전히 선례 없는 구간이다(§14-7).

### 12.4 D16 — 예산과 수명

P12가 1급 제약이라면 숫자도 설계의 일부여야 한다(A7이 지적한 것 — 백서 §2.3의 "git 이력을 전부 읽으면 사실층은 첫날에 선다"가 규모 조건 없는 단언). 아래는 결정이 아니라 초기값이고 값은 실측으로 움직인다. 움직이지 않는 것은 **"값 없이 켜지지 않는다"**는 규칙 쪽이다.

**외부 기준선이 하나 있다 (R9).** Glean이 공개한 증분 색인 비용 — 색인 오버헤드 Python 2~3%·Hack 무시 가능, ownership 메타데이터로 DB 크기 +약 7%, 질의 오버헤드 일반 10% 미만 · 검색 집약 질의 약 3배([F §3.3](research/2026-08-03-precompute-code-graph-precedents.md)). 자릿수 감각까지만 쓴다. 그러나 마지막 값이 이 표의 형태를 지지한다 — 비싸지는 것은 저장이나 일반 질의가 아니라 탐색형 질의이고, 이 설계에서 탐색형은 `candidate` 경유 경로(`K`·`B`)와 결박 폐포(§6.2) 둘이다.

#### 수명 — 단조 증가하는 셋

세 종류가 지우지 않기로 설계되어 있고 각각 이유가 옳지만, 그대로 두면 저장소가 무한히 자라고 P12와 직접 충돌한다.

| 대상 | 왜 안 지우나 | 보존 정책 |
|---|---|---|
| `observed` 관측 | 재현 보증이 없어 과거 관측을 재계산할 수 없다(§3) | 좌표별 최근 M개 + 서로 다른 환경 지문마다 최소 1개. 초기 M=10. **개수 정책이지 신선도 정책이 아니다** — 낡음은 §3.3이 따로 잡는다 |
| `UnresolvedRef` | 해소돼도 다른 환경에서 다시 미해소(§5.4) | 좌표가 살아 있는 동안 유지. 좌표가 `orphaned`면 함께 축출 |
| `Residual` | 자동으로 사라지면 안 된다(§8.1) | 유지하되 `stale`이 된 잔여는 재판정 큐로. 재판정에서 소멸하면 사유와 함께 접힌다 |

**접는 것과 지우는 것은 다르다.** 접힌 것은 *"여기 관측이 있었고 지금 원본이 없다"*를 여전히 말한다. 그 구별이 없으면 §4의 대장이 거짓말을 한다 — 축출된 좌표와 애초에 관측된 적 없는 좌표가 같아 보인다.

#### 이 절이 뒤집히는 조건

위 숫자 중 하나라도 F01·F02 실측에서 한 자릿수 이상 어긋나면 능력이 아니라 §12.1의 저장 기술 선택이 먼저 재론 대상이다. 순서를 못 박는다 — **예산을 의심하고, 안 되면 저장 기술을 의심하고, 그래도 안 되면 그때 능력을 줄인다.**

### 12.5 D19 — 시각화: 코어는 뷰 모델까지, 픽셀은 어댑터 (U2·U5)

백서 §2.4는 소비자 중립 표면을 요구하지 표현 매체를 정하지 않는다. 시각화 자체는 계약 위반이 아니고 위반이 되는 경로는 하나뿐이다 — 특정 호스트의 렌더링 개념이 코어 어휘에 들어오는 것.

```
ViewModel {
  nodes: { 좌표, 종류, 표시 이름 }[],
  edges: { from, to, 해소 등급(§5.1), 출처(§3) }[],
  frame: { 뿌리 좌표, 깊이, 적용된 필터, Snapshot },
  elision: { 잘린 노드 수, 잘린 엣지 수, 사유별 분해, 초과한 상한 }   // 필수 — 비면 저장 거부
}
```

**`elision`이 이 결정의 전부다.** §5.1의 "조용한 절단 금지"가 시각화에서 가장 무겁게 걸린다 — 그림은 잘린 것을 보여주지 않는 매체이고 잘린 그림은 잘리지 않은 그림과 똑같이 완결돼 보인다. 노이즈를 줄이려 노드를 접는 것과 백서 §6.3의 거짓 안전을 만드는 것 사이에 기계적 구별은 없으며, 있는 것은 절단이 데이터로 남는가뿐이다.

1. **등급과 출처가 뷰 모델에 실린다.** `candidate` 엣지와 `exact` 엣지가 같은 선으로 그려지면 D5가 표현 층에서 무효가 된다. 어떻게 그릴지는 어댑터가 정하되 구별할 재료 없이 그리는 것은 불가능해야 한다.
2. 뷰 모델에 붙는 설명도 §9.4의 서술물 규칙을 진다.
3. 뷰 예산이 §12.4에 들어간다 — 뷰 노드 상한 초기값 `500`.

**질의 언어는 표면 계약이 아니다.** 지시는 cypher를 결정론의 근거로 들었지만 결정론은 질의 언어에서 오지 않고 질의가 고정되고 로그에 남는다는 데서 온다(§9.3). 코어의 표면은 명명된 질의 + JSON이며 특정 질의 언어를 계약에 넣으면 §12.1의 저장 기술 선택이 표면에 새어 나오고 P5("그래프는 교체 가능한 투영")가 깨진다. cypher를 쓰는 저장 기술을 고른다면 그것은 §12.1 표의 한 행이 바뀌는 일이지 표면이 바뀌는 일이 아니다.

### 12.6 D21 — 거버넌스는 이 층 위에 서되 이 층이 아니다 (U4·U8)

#### 무엇을 수입하고 무엇을 두고 오는가

지시는 ditto의 ACG(Agentic Change Governance)를 개념으로 가져오고 계약·인터페이스·구현은 가져오지 않는다고 정했다.

| ACG의 것 | 처분 | 근거 |
|---|---|---|
| **변경(Change)의 1급화** — 변경이 이름·명세·검증 가능성을 갖는다 | 수입 | 백서 §7의 사슬에 없던 축이고 §11.1의 `Plan`·`Deviation`과 §11.5의 `Briefing`이 이미 그 자리의 대부분이다 |
| **지속 적합성** — 한 변경의 판정이 아니라 시계열의 추세 | 수입 | §11.6의 델타와 §10의 대장 diff가 같은 형태 |
| **스펙/바인딩 2계층** | 수입 | §7.3 해석기 팩과 동형 |
| **기준의 권위를 사람에 두고 현재 위반을 규칙으로 자동 박제하지 않는다** | 수입 | §7.1 규약층 + D12와 같은 곳을 겨눈다 |
| 스키마·ledger 형식·envelope | 비수입 | 여기서 새로 짓는다 |
| **게이트 집행 배선**(훅이 ledger를 읽어 진행을 차단) | **명시적 기각** | §0.5. 연구 E가 관측한 실패의 실물 |
| **fail-closed 차단**(입력 부재 → 위험 등급 상향) | **형태를 바꿔 수입** | 아래 |
| 정적 엔진 선택(빌드 의존 엔진으로의 통일) | 비수입 | U와 충돌. 산물은 `observed`로 수용(§3) |

각 행의 판정 근거 — ditto 쪽 실물 좌표(`00-framework`·ADR-0004·ADR-0006·`src/hooks/stop.ts`) — 는 [지시 문서 §5](instructions/2026-08-03-owner-direction.md)에 있다.

**같은 규칙이 선행 palimpsest 자산에도 적용된다.** 백서 §12-1이 연 승계 질문의 답은 "개념 승계, 구현·계약 비승계"이며 백서 §11 말미가 요구한 검사("단일 저장소·개발자 머신·고정 코퍼스 전제 위에 서 있던 결정인지")를 자산 단위가 아니라 층 단위로 적용한 형태다. 백서 지위 블록의 ADR 인용 여섯 건은 여전히 가리킴이지 보증이 아니다.

#### fail-closed가 형태를 바꾸는 지점

거버넌스의 안전 규칙 *"입력이 없으면 위험으로 올리고 절대 낮추지 않는다"*는 차단 판정이므로 게이트에서만 성립한다. 같은 안전 성질을 이 층에서 내는 형태는 D9다.

> 입력이 없으면 `Finding`도 `clean`도 내지 않고 **`Residual{사유}`를 낸다.**

두 형태는 같은 실패(거짓 안전)를 막지만 책임의 소재가 다르다 — fail-closed는 기계가 막고 3분할은 사람에게 처분을 가져온다. 그리고 **이것이 이 층을 게이트가 되지 못하게 하는 구조적 장치다**: `Residual`이 섞인 산출로는 자동 차단기를 만들 수 없다. 잔여를 위반으로 세면 전부 막히고 무시하면 백서 §6.3의 거짓 안전이 돌아온다. 게이트를 세우려면 사람이 잔여를 처분해야 하고 그 노동이 §11.4로 되돌아온다 — 우회로가 없다는 것이 여기서의 이득이다.

#### 경계 — 무엇이 이 층이고 무엇이 그 위인가

| 이 층(palimpsest) | 그 위(거버넌스) |
|---|---|
| 좌표·엣지·등급·미해소 참조 | 변경의 허용/금지 범위 |
| 결박 상태·낡음·계보 | 위험 등급과 차단 |
| 잔여의 결박과 적시 제시 | 완료 판정 |
| 대장(범위·하한·언어 등급) | 사람에게 무엇을 올릴지의 정책 |
| **판정의 재료** | **판정의 처분** |

**P7의 반증 조건이 여기서 확장된다.** §12.2가 요구한 것에 한 줄이 붙는다.

> 거버넌스 층이 하나도 연결되지 않은 환경에서 코어 테스트가 전부 통과하고 모든 질의가 답을 낸다. 코어 어휘에 변경 계약·위험 등급·완료 판정의 개념이 없다.

이 검사도 F01부터 CI에서 상시 돌아야 한다 — 백서 §2.4가 역사적 전례를 적어둔 그 드리프트가 이번에는 밖이 아니라 안에서 일어날 수 있기 때문이다. 거버넌스를 여기서 새로 지으면 손잡이와 게이트가 같은 저장소에 산다(§15-25).

#### 오염의 역류

판정에 쓰이는 산출은 그 `Snapshot`의 `ScopeReduction` 집합을 필수로 동반한다(§10). 범위가 줄어서 나온 "위반 0건"과 원래 위반이 없는 "위반 0건"이 같아 보이면 백서 §1의 문제를 거버넌스 층에서 재생산한 것이다. D12는 부분 방어일 뿐이며 정당한 축소와 회피를 기계가 구별하지 못하는 것은 그대로 남는다(§15-26).

### 12.7 D29 — 그래프의 일관성은 선언이 아니라 검사다 (U15-b)

신선도는 §6·§3.3·§6.4가 다룬다. **일관성은 어디에서도 다루지 않았다.** [계획의 상시 검사 열하나와 오라클 넷](plan/README.md)을 전수로 보면 전부 *빌드·재구축·회귀*에 대한 것이고 **저장된 그래프가 자기 규칙을 지키는가**를 보는 것이 없다. 재구축 등가성 검사는 "두 번 만들면 같은가"를 말할 뿐 "지금 이 그래프가 정합한가"를 말하지 않는다 — 손상·부분 갱신·스키마 진화·중단된 트랜잭션은 그 검사를 통과한다.

#### 불변식 — `schema/graph.toml`에서 파생되며 손으로 세지 않는다

| # | 불변식 | 깨지면 |
|---|---|---|
| 1 | 모든 엣지의 양 끝 노드가 존재한다(`UnresolvedRef`를 향한 것 포함) | 질의가 조용히 빈 결과를 낸다 |
| 2 | 모든 노드·엣지가 스키마에 등록된 라벨·타입이고 필수 속성을 갖는다 | §3.1의 "필수이거나 없거나"가 저장 층에서 무효 |
| 3 | 한 노드의 속성 `producer`들이 그 노드의 `provenance`와 정합한다(§3.4) | 출처 파티션이 거짓이 된다 |
| 4 | `inferred` 노드의 `evidence_refs`가 비어 있지 않다(§9.1) | P3이 문장으로 되돌아간다 |
| 5 | `candidate` 후보 집합의 크기가 `K` 이하이고, 초과분에 대응하는 `UnresolvedRef`가 있다(§5.1) | 절단이 조용해진다 |
| 6 | 모든 `Residual`·`ScopeReduction`이 실재하는 좌표에 결박되어 있다 | 잔여가 유령이 된다 |
| 7 | 2층의 결박 색인이 가리키는 실체가 의도 저장소에 있다([R-21](plan/00-risks.md#r-21)) | **승인 노동의 유실이 조용히 일어난다** |
| 8 | 낡음 등급이 전파 규칙과 정합한다 — `live` 노드의 입력에 `stale`이 없다(§6.4) | KG의 일부만 신선하다 |

> **`pal doctor`가 이 여덟을 돌리고 결과가 `Envelope`로 나온다.** 위반은 로그가 아니라 **산출**이며, 자기 자신에게도 D9가 걸린다 — 검사하지 못한 것은 `Residual`이지 "이상 없음"이 아니다.

- **언제 도나**: ① 2층 재구축 후 ② 스키마 버전이 오른 뒤 첫 질의 ③ 사용자 호출 ④ CI. 매 질의마다 돌리지 않는다 — 그것은 P12 위반이다.
- **표본 검사를 1급으로 둔다.** 10⁷ 엣지에서 전수는 비싸므로 기본은 표본이고 전수는 명시적 호출이다. **표본이었다는 사실이 산출에 실린다**(§4.2의 첨부와 같은 형태).
  - **좌표를 가질 수 없는 것은 표본에서 빼지 않는다 (2026-08-12 · [F22-4 게이트](gates/F22-4-doctor.md)).** 표본 밖은 `Residual`이고 잔여는 좌표에 결박된다(§8.1). `Change`·`Actor`처럼 코드 좌표를 갖지 않는 노드를 표본에서 빼면 **그 사실을 결박할 자리가 없고**, 결박 없는 잔여는 아래 불변식 6이 유령이라 부르는 것이다. **불변식 하나가 표본 정책을 강제하는 자리이며 이것은 도출이지 결정이 아니다.**

#### 갱신 중의 질의 — 스냅샷 격리 (U15-d)

워킹트리는 계속 변하고 2층은 그 뒤를 따라간다. 그 사이에 질의가 온다.

1. **질의는 하나의 일관된 스냅샷 위에서만 실행된다.** 읽기 트랜잭션이 열린 시점의 2층을 보고, 그 동안 갱신이 진행돼도 답이 섞이지 않는다.
2. **갱신은 원자적으로 커밋된다.** 부분 갱신된 인덱스가 보이는 창이 없다. 중단되면 이전 상태이며 `doctor`의 불변식 1·2가 그것을 검사한다.
3. **재구축 중에는 능력이 값으로 표시된다** — `ProjectionFreshness.rebuild`. 답을 막지 않고 진행 중임을 싣는다(§2.3과 같은 규칙).
   - **자리는 `RebuildState`가 아니라 `Capable<RebuildState>`다 (2026-08-13).** 이 절은 재구축을 값으로 표시하라고만 적었고 *"관측하지 못하는 빌드는 무엇을 적는가"*를 적지 않았다. `Settled`를 기본값으로 두면 그것은 관측이 아니라 **선언되지 않은 추측**이고, 진짜로 재구축 중인 경우와 구별되지 않는다. 그래서 같은 구조체의 `matches_worktree`와 같은 형태를 쓴다 — 모르면 `NotBuilt{F05, "rebuild-progress"}`. **재구축의 시작과 끝을 아는 것은 2층을 소유한 쪽이므로 관측 경로는 F05가 만든다.** 자리가 아예 없던 동안 그 사실은 산출에서 빠져 있었고, 빠진 것은 소비자가 셀 수 없다([F22-4 게이트](gates/F22-4-doctor.md)의 빚 · ADR-0002와 같은 규칙이 검사가 아니라 **산출**에 걸린 형태다).

### 12.8 D31 — git 워크플로와의 결합 (U18)

설계는 git을 **읽는다**(SoT·blob·커밋). 그러나 사람과 팀이 실제로 일하는 단위 — 브랜치·PR·리뷰·머지 — 와는 결합하지 않았고, 그 결과 **의도층이 한 사람의 로컬 파일에만 산다.** 승인 노동이 [R-10](plan/00-risks.md#r-10)이 말한 대로 이 프로젝트에서 가장 비싼 것이라면, 그 산물이 팀에 공유되지 않는 것은 설계 결함이다.

#### 세 결합

| # | 결합 | 형태 | 무엇이 닫히나 |
|---|---|---|---|
| 1 | **의도의 정본을 텍스트로** | `.palimpsest/intent/*.jsonl`이 **원본**이고 `intent.redb`는 그 색인이다([stack §2.2](plan/00-stack.md)의 방향을 뒤집는다) | 백업·리뷰·팀 공유가 git으로 공짜가 된다. [R-21](plan/00-risks.md#r-21)이 한 겹 더 닫힌다 — 파일이 지워져도 git에 있다 |
| 2 | **결박을 커밋에 남긴다** | 커밋 트레일러 `Palimpsest-Binds: <의도 식별자>@<좌표>` | 결박이 **변경과 같은 리뷰를 받는다.** 그리고 `Change` 노드(§1.1)가 git에서 결정론적으로 선다 |
| 3 | **판정의 단위가 브랜치·PR이다** | `--base <ref>` 델타 — 브리핑(§11.5)·구조 평가(§11.6)·이탈률(§11.1)이 전부 이 단위 | §11.6이 *"절대값이 아니라 델타"*라 정했는데 **델타의 기준선이 어디인지가 정해진 적 없었다.** git이 그 답을 이미 갖고 있다 |

#### 텍스트가 정본일 때의 규칙 — 머지가 성립해야 한다

방향을 뒤집으면 두 사람이 같은 파일을 고친다. 충돌이 일상이 되면 1은 이득이 아니라 비용이다.

- **추가 전용(append-only).** 승인·거부·재결박은 새 레코드이고 기존 줄을 고치지 않는다. §3.1의 "승격은 새 노드 생성"과 같은 형태이며 새 규칙이 아니다.
- **결정론적 정렬 + 한 줄 한 레코드.** 충돌이 나면 라인 단위로 해결되고, 대개는 양쪽을 다 취하는 것이 정답이다.
- **레코드에 스키마 버전과 발행 `Actor`가 실린다.** 누가 언제 승인했는지가 git blame이 아니라 데이터로 남는다.
- **`redb` 색인은 파생이므로 커밋되지 않는다.** 지워도 JSONL에서 재구축된다 — 이제 의도 저장소도 "지워도 되는 것"과 "안 되는 것"이 갈린다.

#### P11에 닿는 지점 — 정직하게

결합 2는 **대상 저장소의 커밋 메시지에 줄을 더한다.** P11(*"대상을 변형하지 않는다"*)은 코어가 코드를 고치는 것을 금지하며 사람이 쓰는 커밋 메시지는 그 대상이 아니다. 그러나 경계가 얇다.

- 트레일러는 **사람 또는 호스트가 쓰고 코어는 읽기만 한다.** 코어에 커밋을 만드는 경로가 없다(`pal-git`의 접촉면 다섯에 쓰기가 없다 — [R-15](plan/00-risks.md#r-15)).
- 트레일러가 없어도 모든 것이 성립한다. 결박의 정본은 1의 JSONL이고 트레일러는 **편의이자 리뷰 표면**이다. 없으면 결박이 조용해질 뿐 사라지지 않는다.

#### palimpsest 자신의 개발 방법론

U18은 이 저장소에도 걸린다. [계획 §7](plan/README.md)의 진행 규칙이 이미 절반이고(게이트 기록·ADR은 종료 시점 발행·기준의 사전 등록), 여기서 더하는 것은 셋이다 — **작은 브랜치와 검토 가능한 단위**, **Conventional Commits**(이 저장소가 이미 쓰고 있다), **자기적용**([R-19](plan/00-risks.md#r-19)의 편향을 명시한 채로).

**그리고 이 설계가 이미 갖고 있는 장치들에 알려진 이름을 붙인다.** 빈 스키마보다 아는 형식이 싸기 때문이며(U18-c), 이것은 새 능력이 아니라 저작 비용의 문제다.

| 이 설계의 장치 | 알려진 이름 | 얻는 것 |
|---|---|---|
| 개념·관계 팩(§7.3 · F18) | DDD 유비쿼터스 언어 | 무엇을 적어야 하는지 사람이 이미 안다 |
| `ViewModel`의 `frame`(§12.5) | C4 모델의 레벨 | 뷰의 깊이를 고를 어휘가 생긴다 |
| `Briefing`(§11.5) | 사전부검(pre-mortem) | 변경 전에 무엇을 묻는지가 정해져 있다 |
| `Journey`(§1.1) | 사용자 여정 맵 | 진입점 목록과 여정의 차이가 분명해진다 |
| 결정의 결박(§11.2) | ADR | 이미 쓰고 있는 형식이 좌표를 얻는다 |

**형식을 강제하지 않는다**(U8-b). 이름은 저작을 돕는 안내이고 스키마는 그 이름 없이도 성립한다.

## 13. 결정은 무엇으로 반증되는가

**로드맵은 이 문서가 소유하지 않는다.** 초안은 여기에 슬라이스 S-1~S12를 적었고 [계획 폴더](plan/README.md)가 같은 것을 기능 F01~F23으로 적었다 — **같은 것을 두 곳에 두면 그것이 곧 drift이고**(§0의 분할 규칙), 이 저장소에서 이미 두 번 일어났다. 실행 순서·규모·완료 조건은 계획이 갖고, 이 절은 **각 결정이 어디서 죽는가**만 적는다.

| 결정 | 반증 조건 — 이것이 관측되면 결정이 틀린 것이다 | 판정하는 기능 |
|---|---|---|
| **D1** 좌표·정규화 | 정규화가 포매팅 변경에 digest를 바꾼다 / L1에서 오버로드 재정렬이 흔해 `ordinal` 정체성이 조용한 재결박을 자주 만든다(§2.2) | F02·F03·F09 |
| **D2** 투영은 캐시 | 콘텐츠 주소 캐시로도 과거 커밋 열기가 대화 흐름을 끊는다 | F04 |
| **D3** 출처 4값 | 배정 규칙 넷으로 덮이지 않는 입력이 나타난다 | 전 기능 상시 |
| **D4** 관측 범위 대장 | 범위 안인데 그래프에 없는 심볼이 제시된다 — **계약 위반** | F01·F02 |
| **D5** 엣지 해소 등급 | `candidate` 집합이 실제 프로젝트에서 폭발해 쓸 수 없다 / `scoped` 오해소가 잦아 등급이 거짓 신뢰를 만든다 | F07 |
| **D6** 미해소 참조 | 미해소가 전체의 대부분이라 신호가 없다 | F08 |
| **D7** 결박 상태·반경 | `stale` 거짓 양성률이 높아 사람이 표시를 무시한다 — **[G1](plan/00-goals.md) 반증이고 제품이 없다** / `undeterminable`이 지배한다(§15-42) | **F09** |
| **D8** 능력 재편(E 신설) | 실측 최대 군집의 과거 결함을 `writes` 포함 관계로 재현 검출하지 못한다. 그러면 E를 내리고 C5의 전제층으로 되돌린다 — **되돌리는 비용이 문서 한 행이다**(번호를 옮기지 않았으므로) | F13 |
| **D9** 3분할 판정 | 잔여가 전체의 90% 이상이라 산출이 무의미하다 / **3분할이 기존 도구의 "271개 위험"·"이상 없음" 대비 사람의 다음 행동을 바꾸지 못한다** | F15 |
| **D10·D22** 합성물·서술 제약 | 질의 로그 기반 커버리지가 검증자의 실제 사각을 반영하지 못한다 | F17 |
| **D12** 기준 변경의 결박 | 범위 축소가 적시 제시로 실제 도달하지 못한다 | F20 |
| **D13** 의도층 세 입구 | **적시 제시가 재발을 줄이지 못한다** — 재발 사례에서 `touch`가 규칙을 띄우는지, 띄운 뒤 같은 결함이 다시 나는지. **이 설계에서 가장 큰 단일 베팅**(§15-12) | **F11** |
| **D17·D28** 팩과 provider | 저작되지 않는다 / 저작해도 `UnresolvedRef`·`candidate`가 유의미하게 줄지 않는다 — 그러면 프로젝트별 계층은 비용만 낸 것이다 | P0-preflight · F18·F21 |
| **D18** 브리핑 3분할 | `reach`가 잔여에 압도되어 읽을 수 없다 / **브리핑을 본 뒤의 변경이 계획 이탈률을 낮추지 못한다** — 그러면 이해가 아니라 이해의 착각을 만든 것이다 | F19 |
| **D20** 구조 평가 델타 | §11.6이 든 셋(결박된 기준·3분할·적시 제시) 중 어느 것도 기존 아키텍처 lint 대비 행동을 바꾸지 못한다 | F20 |
| **D21** 거버넌스 경계 | 거버넌스 층 없이 코어 테스트가 통과하지 않는다 / 코어 어휘에 변경 계약·위험 등급이 새어 든다. **반증 조건이자 상시 검사다** | F01부터 CI 상시 |
| **D23** 결과로 채점 | 결과 축을 잴 지표를 사전 등록할 수 없다. 그러면 채점 기준을 행동 축으로 되돌리고 **되돌렸다는 사실을 적는다**(§15-39) | P0-preflight |
| **D24** 조달 | 대상에 조달원이 없다(**2026-08-11 실측: 0/4**) / §7.5의 다섯 몫이 전부 반증된다 — 그러면 그냥 SAST를 돌리는 편이 낫다 | F16b |
| **D25·D33** 스키마와 id | 같은 대상에 대한 두 출처의 판정이 한 노드로 붕괴한다 | F22 |
| **D29** 무결성 | 불변식 검사가 실제 손상을 잡지 못한다 / 전수 비용이 감당되지 않는다 | F22 |
| **D31** git 결합 | 트레일러를 아무도 쓰지 않고 정본을 커밋하지 않는다(§15-41) | F23 |
| **D32** 앵커 비신고·detect-only | — **반증 조건이 아니라 상시 검사다.** 생성자 신고를 앵커로 쓰는 경로, `stale`이 생성기를 부르는 경로가 코드에 없는지 | F09부터 CI 상시 |

**코드 없이 판정되는 것이 먼저다.** 사슬 A(§15.1)는 감사·브리핑·구조 평가 전부가 사람 노동의 뿌리에 매달려 있다고 적는다. **뿌리가 무너지는 설계에서 뿌리를 마지막에 검사하면 무너질 때 이미 가장 비싼 구간의 비용이 지불된 뒤다.** 그리고 그 뿌리들은 전부 코드 없이 검사된다 — 사람이 하는 일의 단가에 대한 질문이지 기계 능력에 대한 질문이 아니기 때문이다. 무엇을 어떻게 재는지는 [P0-preflight](plan/features/P0-preflight.md)가 갖는다.

> **판정 기록을 남기지 않고 다음으로 가는 것이 이 설계의 가장 조용한 실패 경로다.** 통과·반증·**대조 불가** 셋 중 하나를 커밋으로 남긴다([R-18](plan/00-risks.md#r-18)).

### 13.1 D13의 반증이 이 표에서 가장 무겁다

§11.0이 적시 제시를 세 입구 중 하나가 아니라 **목적**으로 승격했다. 그러므로 낡음 감지의 거짓 양성률(D7)만 검사하면 **목적으로 세운 것에 검사가 없다.**

| | 형태 |
|---|---|
| **직접 측정** | 호스트가 조달할 수 있으면(§12.2) 제시된 항목의 열람·반영 비율을 `observed`로 받는다 |
| **대리 측정**(조달 불가 시) | 재발 사례 재현 — `touch`가 그 규칙을 띄우는가, 띄운 뒤 여섯 번째가 나는가 |
| **반증** | 제시는 정확한데 재발이 줄지 않으면 적시 제시는 항해 문제를 풀지 못한 것이고 §11.0의 승격 자체가 틀린 것이다 |

**D23(결과로 채점)이 이 측정을 한 단 더 올린다.** "띄웠는가"가 아니라 "그래서 코드가 달라졌는가"이고, 그 저울이 아직 없다는 것이 §15-39다.

### 13.2 모든 결정에 공통으로 걸리는 기준선 (R8)

사전 등록 3-arm 측정에서 두 달치 오케스트레이션 기계장치가 **잘 쓰인 마크다운 문서 한 장 대비 6/6 vs 5/6**이었고 규율 지표 우위는 임계 정확 경계였다([E §6](research/2026-08-02-ditto-harness-failure-observation.md)). 그러므로 각 결정은 **"이 장치가 없고 대신 같은 내용을 문서로 적어 에이전트에 주면 어떻게 되는가"**를 대조군으로 갖는다. 그 대조에서 이기지 못하는 장치는 기계장치일 이유가 없다.

**그 대조를 어떻게 세우는가.** R8의 근거인 3-arm 자체가 사실상 n=1이므로 형태를 그대로 반복하면 이 기준선은 수사에 그친다.

| 요소 | 규정 |
|---|---|
| **대조군 1 — 문서** | 그 장치가 계산하는 것을 사람이 손으로 적은 마크다운 한 장으로 대체해 에이전트에 준다 |
| **대조군 2 — 기성 그래프 도구 (R11)** | tree-sitter 기반 코드 그래프 MCP 서버. 이미 존재하고 무료이고 설치가 가볍다 — [F §4](research/2026-08-03-precompute-code-graph-precedents.md)가 확인한 동형 시스템은 §12.1의 선택과 거의 같은 물리 형태다. **사실층 산출은 이 대조군을 통과해야 한다** |
| **대조군 3 — 기존 정적 분석 도구** | 감사·구조 평가(D9·D20)의 상대. 백서 §10이 그 영역을 "정밀 분석 엔진이 더 잘한다"고 이미 인정했다. **D24가 그 엔진을 조달원으로 끌어들인 뒤에는 대조군이자 입력이다** |
| **과제** | 그 결정의 반증 조건이 겨냥한 과제. 과제 집합과 평가 코퍼스의 출처는 P0-preflight가 고정한다 |
| **판정** | 사전 등록된 성공 기준. 사후에 고르면 §10의 게이트 오염이고 **그 오염은 이 설계 자신에게 일어난다** |
| **n** | 최소 과제 5건. 6/6 대 5/6 같은 판정을 반복하지 않는다 |
| **기권** | 대조가 성립하지 않으면 "대조 불가"를 명시한다. 생략하고 통과로 처리하지 않는다 |

**기준선이 특히 날카로운 곳과 무딘 곳이 갈린다.**

| | 대조 |
|---|---|
| **흉내 낼 수 없는 것** — D13(적시 제시) · D18(브리핑) · §11.1(계획 결박) | 문서로도(좌표 계산이 필요) 대조군 2로도(기성 도구에 결박도 신선도도 없다) 안 된다 |
| **정면으로 겹치는 것** — D4·D5·D6(사실층) | 대조군 2와 같은 자리다. 이겨야 할 지점은 사실의 양이 아니라 **대장·등급·미해소 참조**이고, 그 셋이 행동을 바꾸지 못하면 **기성 도구를 설치하는 편이 낫다**(§15-29) |
| **대조가 성립하지 않는 것** — D17(팩) | 팩 자체가 문서다. "대조 불가"를 명시하고 통과로 처리하지 않는다 |
| **입력이 대조군인 것** — D24(조달) | semgrep을 이기려는 것이 아니다. **§7.5의 다섯 몫이 그 산출에 무엇을 더하는가**가 대조 대상이다 |

**R11이 대조군 2에 대해 알려주는 수치가 하나 더 있다 — 이 설계에 불리한 쪽이다.** 31개 저장소 평가에서 그래프 경유 83% vs 파일 탐색 92%(토큰 10배·tool 호출 2.1배 절감과 맞바꾼 값)였다. 싸다는 것과 낫다는 것이 같지 않다는 첫 외부 실측이며, 그래프 고유 질의(허브 탐지·호출자 순위)에서만 31개 중 19개로 대조군 이상이었다. 가장 무겁게 걸리는 곳은 §9.4다(§15-28).

**D9가 이 기준선과 충돌한 채 남을 수 있다.** 3분할 감사는 1급 결정이므로 그대로 두면 결정과 기준선이 대치한다. 처분: **이길 지점은 정밀도가 아니라 3분할의 형태다.** 기존 도구가 "271개 위험" 또는 "이상 없음"을 내는 자리에서 `{위반, 잔여, 범위 밖}`이 사람의 다음 행동을 바꾸는가. 안 바뀌면 D9는 틀린 결정이고 그때는 감사를 산출 목록에서 내린다.

## 15. 이 설계가 주장하지 않는 것 / 틀릴 수 있는 지점

§8.1이 `Residual`에 처방한 것을 이 절 자신에게도 적용한다 — 잔여를 사슬로 묶고 각각에 판정 자리를 붙인다.

### 15.1 생사 사슬 — 곱해지는 잔여

**사슬 A — 제품의 감사 가치 전체가 여기 매달려 있다.**

```
승인 노동이 실제로 일어나는가 (§11.4 — 실측 전 가설)
  ∥  해석기 팩이 실제로 저작되는가 (§7.3 — 2026-08-03 지시가 더한 두 번째 뿌리)
      └ 둘 중 하나라도 아니면 → 라벨이 없다 (§7.1)
            └ 없으면 → 3분할 산출이 전부 Residual (§8)
                  └ 그러면 → F15의 반증 조건("잔여 90% 이상")에 즉시 걸린다
                        └ 그리고 → D9 감사가 R8 기준선을 통과하지 못한다 (§13)
                              └ 그리고 → §11.6의 구조 평가·§11.5의 브리핑이 함께 무너진다
```

뿌리가 둘이고 잎이 여섯이다. 사슬로 적으면 우선순위가 따라 나온다 — **§11.4의 승인 비용 장치가 가장 먼저 실측되어야 한다.**

**2026-08-10 지시가 뿌리 후보를 셋 더했다 — 그리고 하나는 사슬을 우회한다.**

| 후보 | 사슬에서의 위치 | 판정 |
|---|---|---|
| ~~`Journey`·`Defect`~~ **`Journey`의 저작**(§1.1) | ~~**새 뿌리 후보.** 둘 다 사람이 써야 생긴다~~ **뿌리로 확정 — `Journey` 하나뿐이다** | **판정됐다 (2026-08-11, [T10](gates/preflight.md#t10--여정결함의-올라탈-곳)).** `Defect`는 수정 커밋에서 소급 결박되어(4/5) 뿌리가 아니고, `Journey`는 되지 않아(0/3) 뿌리다. **곱이 하나 늘었다 — 둘이 아니라 하나.** 나쁜 소식이 예상의 절반이었다는 것이지 없어진 것이 아니다(§15-34) |
| `provider`의 저작(§7.4) | **새 뿌리 후보.** 팩 저작과 같은 실패 양식 | 다만 **절반 이상이 선언으로 되므로**(§7.4의 포트 표) 팩 저작과 같은 뿌리이지 새 뿌리가 아닐 수 있다 |
| **외부 엔진 조달**(§7.5) | **뿌리가 아니라 우회로** | 라벨 저작 없이도 `Finding`을 세우는 유일한 경로다 — 사슬 A가 무너져도 (b)의 일부가 산다. **이것이 D24를 앞당기는 진짜 이유이며 조달 배관 이상의 값이다** |

두 번째 뿌리는 첫 번째와 독립이 아니다. §3.2의 `asserted_via=rule`은 규칙 하나의 승인이 파생 라벨 전부를 세우게 하므로 팩이 서면 승인 노동의 단가가 내려가고, 팩이 안 서면 승인은 좌표 단위로 남아 §11.4의 가설이 더 나쁜 조건에서 시험된다. 두 뿌리는 함께 움직이므로 함께 검사되어야 하며 그 자리가 P0-preflight다(§13).

**사슬 B — 검증 커버리지.**

```
질의 로그 완결성이 성립하는가 (§9.3 — palimpsest가 강제할 수 없다)
      └ 안 하면 → 계산된 값은 "보지 않은 것의 하한"이 아니다
            └ 그러면 → D11이 R2에 답하지 못하고 §14-11이 "부분"에서 "답하지 못함"으로 내려간다
```

**사슬 C — 좌표.**

```
symbol_id가 계산되는가 (§2.2 — L2 미만에서 등급이 내려가고 L0에서 없다)
      └ 없으면 → 결박·잔여 결박·적시 제시가 그 언어에서 성립하지 않는다
            └ 그러면 → 다언어 프로젝트에서 §6·§8·§11이 부분적으로만 선다

**백서에 대한 권고 하나 + 관찰 셋**

1. **권고 — 백서 §11의 사실 오류. 반영 완료(2026-08-03).** "이 저장소는 현재 이 백서 한 파일뿐이다. 코드도 ADR도 없고, git 저장소도 아직 아니다"는 실측과 달랐다(A5). research/README 28장 절차의 (a) 즉시 반영 대상으로 분류해 백서 §11을 고쳤고 백서가 그 자리에서 실제로 낡았다는 사실을 지우지 않고 함께 적었다.

2. **관찰 — 보조 후보 목록에 동적 기법이 없다.** 백서가 보조 후보를 열거한 두 곳(§12-2·§10)이 모두 정적 기법만 든다. 동적 관측(트레이스·컨테이너 덤프·기동 후 라우트 조회)은 목록에 없고 군집 C6이 같은 곳을 겨눴다. (a)도 (b)도 아니라 **(c) 설계 미결**이며 백서 갱신 규칙에 걸리지 않는다. 이 설계가 O로 답을 하나 넣었으므로 백서를 고치는 대신 이 문서가 ADR로 쪼개지는 것이 정상 경로다.

3. **관찰 — 백서가 선례를 하나도 대조하지 않는다 (R12).** 백서 §1·§10·§12는 이 층이 겨냥하는 자리를 논증으로 세우고 기존 도구에 대해서는 §10의 인정 한 줄뿐이다. [F](research/2026-08-03-precompute-code-graph-precedents.md)가 확인한 것은 더 구체적이다 — 사전계산된 코드 그래프를 에이전트에 MCP로 노출하는 것은 2026년의 수렴한 기본값이고 §12.1이 고른 네 선택과 거의 같은 물리 형태가 이미 돌아간다(F §4). 동시에 그중 어느 것도 신선도·출처·확신도 계약을 노출하지 않는다(F §8). 이것도 (c)다 — 백서가 자기 자리를 "비어 있는 칸"으로 서술하는 근거를 논증에서 관측으로 바꿀 수 있다는 뜻이지 백서의 문장이 틀렸다는 뜻이 아니다. **그리고 유리한 쪽으로만 읽으면 안 된다** — 아무도 안 하는 이유가 어려워서일 수 있고 그 판정은 R8 기준선이 한다(§15-30).

4. **관찰 — (c) 항목이 다섯으로 늘었다.** 2026-08-03 지시를 백서에 대조한 결과 조항을 고쳐야만 성립하는 지시는 하나도 없었다([지시 문서 §3](instructions/2026-08-03-owner-direction.md)). 대신 열린 질문 셋이 소진되고 백서가 아직 담지 않은 것 다섯이 (c)로 쌓였다 — ① 산출표에 없는 두 산출(브리핑·구조 평가), ② 백서 §4.3의 형식 제약 다섯째 후보(§9.4), ③ P7과 거버넌스 지원의 긴장, ④ 백서 §4의 세 자리에서 "동료"의 위치, ⑤ 백서 §7 사슬에 기획이 없다는 것. 낱개로는 전부 설계 결정으로 닫히지만, 열린 질문에 답이 쌓이면 어느 시점에 백서가 자기 정체성 절을 다시 써야 한다. 그 판단은 이 문서의 몫이 아니며 판단 시점의 신호는 **(c) 항목이 백서 §12의 남은 열린 질문 수를 넘을 때**로 적어 둔다.
