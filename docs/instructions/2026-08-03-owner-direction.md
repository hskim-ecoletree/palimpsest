# 소유자 방향 지시 — 2026-08-03

> **이 문서의 지위**
>
> - **성격**: **요구사항 원본**이다. 연구([`docs/research/`](../research/README.md))는 증거이고 요구사항이 아니지만, 지시는 제품 방향의 소유자가 낸 요구사항이다. 그러나 [백서](../../WHITEPAPER.md)도 같은 소유자가 쓴 계약이므로, 지시가 백서와 어긋나는 지점은 "지시가 이긴다"가 아니라 **"어느 쪽을 고칠 것인가"가 열리는 지점**이다.
> - **왜 원문을 싣는가**: §2의 정규화는 **해석이다.** 원문이 없으면 정규화가 원문 행세를 하게 되고, 그것은 백서 §1이 고발한 형태다. 그리고 §4의 자기검사는 원문 대조로만 성립한다.
> - **결정을 담지 않는다**: 각 지시의 설계 처분은 [`DESIGN.md`](../DESIGN.md)에 있고 이 문서는 가리킨다. 결정을 두 곳에 두면 한쪽만 고쳐질 때 다른 쪽이 조용히 낡는다.
> - **갱신 조건**: 지시가 추가·철회될 때. 설계 진척으로는 고치지 않는다.

## 1. 지시 원문

세 차례에 걸쳐 들어온 지시를 **받은 순서대로, 손대지 않고** 옮긴다. 명백한 오탈자만 대괄호로 보정했다.

### 지시 1 — 설계 반영 요청

> `docs/DESIGN.md` 설계에 내가 계획한 설계를 반영해줘. 차이나 충돌이 발생하는 모든 부분은 별도 문서로 정리해줘.
>
> - 사람/에이전트가 코드베이스를 정확히 이해하도록 돕는 코드 정적 분석기를 도입한다. (사용자 프로젝트마다 환경이 다르므로 해석기/분석기는 프로젝트마다 별도 구현하도록 설계한다)
> - 에이전트는 코드 정적 분석기를 사용하여 코드 변경 전에는 코드를 어떻게 수정할 지, 어떤 메서드, 추상화, 기존의 설계를 활용할지 어떤 영향 범위가 있는지를 분석하고, 이를 시각화하여 사용자에게 시각화하여 제공한다. (변경에 대해 미리 이해할 수 있도록)
> - 코드 변경 후에는 코드나 데이터의 흐름, 함수 호출 흐름, 의존성 및 소유권 등을 분석하여 구조에 대한 평가를 수행한다.
> - ditto 에 ACG 라고 하는 에이전트에게 적용하는 코드 품질 제어 및 프로젝트의 컨벤션이나 결정 등의 거버넌스 체계가 있는데 이를 위해 palimpsest (GraphRAG 기능) 를 사용한다.
> - 사람이 코드를 더 잘 이해하기 위해 palimpsest 는 GraphRAG 또는 지식 베이스를 활용하여 설명을 시각화하여 보여준다. 특히 코드 베이스에 대한 설명(온보딩/코드 변경 전의 계획/변경 후의 리뷰/등)은 반드시 코드를 직접보고 서술하는 것이 아닌 GraphRAG 및 KG 데이터를 활용하여야 한다. (프로젝트의 서사적/의미적 서술 필수)
>
> **## 코드 베이스 이해에 대한 2개의 발표자료 의견**
>
> `docs/research/2026-08-02-understanding-restoration-mechanisms.md` 를 보면 2개의 발표를 통해 코드 베이스에 대해 인간이 어떤 역할을 하고, 어떻게 하면 코드 공장에서 코드가 붕괴하지 않도록 해야하는가에 대해 담론을 펼치고 있는데.
>
> Geoffrey Litt 은 사람이 여전히 프로젝트에 참여하기 위해 에이전트의 산출물을 이해해야 한다고 주장하고 있고, 몇 가지 방법을 제안했어. 그리고 내가 위에서 palimpsest 는 litt 주장하는 코드 이해를 위한 기법 (explain-diff/micro-world)을 GraphRAG/KG 로 어느 정도 결정론적인 수준으로 제한할 수 있기 때문에 모든 것을 에이전트가 분석하고 서술하는 방법보다는 정확할 것이라고 생각해. (데이터를 생성하는것은 에이전트가 서사를 부여하기 떄문에 비결정론적이지만, 코드 정적분석기를 통한 코드 시각화는 결정론적이다. 그리고 조회도 조회의 목표는 에이전트가 사[용]자의 의도를 해석하기 때문에 비결정론적이지만 쿼리(cypher) 는 결정론적이기 때문에 어느 정도 결정론적이라고 표현함)
>
> 그리고 Dex Horthy 는 여전히 하네스를 잘 설계하는게 중요하다 거기에서 사람이 어디에 설 것이며, 어떻게 해야하는가에 대해 이야기 하고 있지만, 나는 내가 실패했던 ditto 가 이미 어느 정도는 그의 주장에 가까이 가려했다고 생각해. (특히나 ditto 에서 코드를 작성하기 전에 많은 노력과 사람의 확인을 받기위해 의도를 정확하게 파악하기 위한 노력, 사전부검, 완수조건을 생성하고 확인받는 절차가 그 일환이었어) 하지만 나는 실패했어. 더 정교한 프로세스나 규칙이 필요했는지 몰라도, 여전히 사람이 병목인채로 견뎌야 한다라는 주장으로 들리고 그 점에서 나는 아쉬운 느낌이야. 다른 내용은 좋았어

### 지시 2 — 승계 방식

> ACG 를 가지고 올건데. 그대로 가지고 오지는 않을거야. 모델의 성[능]이 좋아진 만큼 더 세세한 규칙으로 행동을 강제하기 보다 자유/창의성을 부여하는 방향으로할거야. 그러니 계약/인터페이스 등은 가져올 필요 없어. 여기에서 새로 지을 거니까. 이것은 기존 palimpsest 레거시에서 가지고 올 때도 마찬가지야. 개념을 가져올 뿐 구현을 그대로 들고 오는게 아니야

### 지시 3 — 정체성

> palimpsest 는 단어의 뜻 그대로 프로젝트의 모든 역사를 서사적으로 담고 있는 기록이야. 여기에서 내가 말하는 '역사'라는 의미는 사용자들의 기획/설계/구현의도/결정사항/코드의 형상 같은 모든 것을 얘기해. 그러므로 palimpsest 는 프로젝트에 대해 속속들이 알고 있는 사관이자 서[사자]이자 큐레이터이자 동료인거지

## 2. 정규화 — U1~U9

대조가 가능하려면 조항 단위로 쪼개야 한다. **정규화가 곧 해석이므로, 원문에서 멀어진 지점을 함께 적는다.**

| # | 정규화된 지시 | 원문에서의 변형 |
|---|---|---|
| **U1** | 사람·에이전트의 코드베이스 이해를 돕는 **코드 정적 분석기**를 도입한다. 프로젝트마다 환경이 다르므로 **해석기·분석기는 프로젝트별로 별도 구현**되도록 설계한다 | 없음 |
| **U2** | 에이전트는 **코드 변경 전에** 정적 분석기로 ① 어떻게 고칠지 ② 어떤 메서드·추상화·기존 설계를 활용할지 ③ 영향 범위를 분석하고, **사용자에게 시각화해 제공**한다 | ①②는 판단이고 ③은 계산이다. 셋을 한 산출로 묶었으나 **출처 축이 다르다** |
| **U3** | **코드 변경 후에** 코드·데이터 흐름, 함수 호출 흐름, 의존, **소유권**을 분석해 **구조를 평가**한다 | "평가"는 규범 판정이므로 기준을 요구한다. 원 지시에 기준의 출처가 없다 |
| **U4** | ditto의 **ACG**(에이전트 코드 품질 제어 + 컨벤션·결정 거버넌스)를 위해 palimpsest의 **GraphRAG 기능**을 사용한다 | "사용한다"의 방향을 원 지시가 정하지 않았고 **U8이 정정했다** — ACG는 외부 소비자가 아니라 **개념 수입원**이다 |
| **U5** | 코드베이스에 대한 설명(온보딩·변경 전 계획·변경 후 리뷰)은 **코드를 직접 보고 서술하지 않고 GraphRAG·KG 데이터를 근거로** 한다. 서사적·의미적 서술을 필수로 한다 | "반드시"를 **소비자 정책**으로 읽었다. 코어는 이것을 강제할 수단이 없다 |
| **U6** | (태도) Litt의 이해 기법(explain-diff·마이크로월드)을 GraphRAG·KG로 **어느 정도 결정론적인 수준으로 제한**할 수 있으므로, 전부 에이전트가 분석·서술하는 것보다 정확하다 | 판정 대상 명제로 다룬다 |
| **U7** | (태도) Horthy의 하네스론은 ditto가 이미 근접했고 실패했다. **사람이 병목인 채 견디라**는 결론이 아쉽다 | 요구가 아니라 방향 판단이므로 설계 처분만 적는다 |
| **U8** | 승계는 **개념만** 한다 — ACG도 palimpsest 레거시도 계약·인터페이스·구현을 들고 오지 않고 여기서 새로 짓는다. 그리고 모델이 좋아진 만큼 **세세한 규칙으로 행동을 강제하기보다 자유·창의성을 부여하는 방향**으로 짓는다 | "자유"의 대상이 무엇인지 원문이 구별하지 않는다. **내용의 자유와 형식의 제약을 가르는 것**이 판정의 전부다 |
| **U9** | palimpsest는 이름 그대로 **프로젝트의 모든 역사를 서사적으로 담는 기록**이다. 여기서 역사는 기획·설계·구현 의도·결정·코드 형상 전부를 뜻한다. 그러므로 palimpsest는 프로젝트를 속속들이 아는 **사관이자 서사자이자 큐레이터이자 동료**다 | 정체성 진술이므로 등급을 매기지 않고, **다른 지시의 해석을 어떻게 바꾸는지**로 다룬다 |

## 3. 백서·설계와의 대조

**판정 등급** — 다섯으로만 분류한다.

| 등급 | 뜻 |
|---|---|
| **정합** | 기존 계약이 이미 요구하거나 허용한다. 설계에 자리만 만들면 된다 |
| **확장** | 계약과 충돌하지 않으나 설계에 새 결정이 필요하다 |
| **긴장** | 계약을 지키면서 만족시키려면 **지시의 형태를 바꿔야 한다** |
| **충돌** | 계약을 고치지 않으면 만족할 수 없다. 백서 개정 대상 |
| **기각** | 채택하지 않는다. 근거를 함께 적는다 |

**전체 결과**: **아홉 지시 중 백서 조항을 고쳐야만 성립하는 것은 없다.** 대신 백서가 열어둔 질문 **셋이 소진되고**(§12-1 승계 범위 · §12-3 서사 규칙 소유자 · §12-4 계열), **긴장이 일곱 곳, 새 잔여가 아홉 개** 생긴다.

| U9-a | 모든 역사를 담는 기록 | **확장** | 백서 §7 | 의도층 어휘에 **기획**이 들어온다. 보존 정책은 "접는 것과 지우는 것은 다르다" |
| U9-b | 사관 | **정합(은유가 정확하다)** | — | **기록하되 통치하지 않는다.** 사관이 게이트를 쥐면 사관이 아니다 |
| U9-c | 큐레이터·서사자 | **정합** | P8 · P9 | 이미 1급. 다만 사관은 전수 보존을, 큐레이터는 선별을 요구한다 — **다른 요구다** |
| U9-d | 동료 | **긴장** | 백서 §4 세 자리 | "동료"는 능동성을 함의하고, **동료와 대리인의 거리는 한 칸이다** |

**처분의 본문은 전부 [`DESIGN.md`](../DESIGN.md)에 있다** — U1→D17, U2→D18·D19, U3→D20, U4·U8→D21, U5→D22, U6→D22의 6단계 대조, U7→승인 비용 설계, U9→정체성 정렬.

### U8-c — 자유는 내용에 걸리고, 제약은 형식에 걸린다

백서 §4.3이 이미 같은 문장을 갖고 있다: *"에이전트는 내용에는 제약을 걸지 않는다 — 제약을 걸면 에이전트를 쓰는 이유가 사라진다. 제약은 전부 형식에 걸리며 네 가지다: 파티션 분리(P2), 좌표 동반(P3), 하한 표시(P4), 자기 판정 금지(P10)."*

그러므로 U8-b는 새 방향이 아니라 **기존 조항의 재확인**이다. 긴장은 "자유"의 범위에서 생긴다 — 아래 다섯은 규칙처럼 보이지만 형식 제약이며, **하나라도 완화하면 설계의 뼈대가 무너진다.**

| 형식 제약 | 완화하면 |
|---|---|
| `evidence_refs`가 비면 합성물을 **저장하지 않는다** | P3이 문장으로 되돌아간다 |
| **선택 필드를 두지 않는다**(필수이거나 없거나) | 빈 필드가 "이 시스템은 이것을 다룬다"는 거짓 신호가 된다 |
| 출처 필드는 **불변**이고 승격은 새 노드 생성 | 세탁 장치가 스키마 수준에서 열린다 |
| 판정 산출은 **`clean`을 내지 않는다** | 거짓 안전이 돌아온다 |
| **조용한 절단 금지** | 그림과 요약이 잘린 것을 감춘다 |

> 자유는 *무엇을 말할 것인가*에 주고, 제약은 *그 말이 어떤 자격인지 감출 수 없게* 하는 데만 쓴다.

## 4. 이 대조가 틀릴 수 있는 지점

1. **정규화(§2)가 곧 해석이고, 이미 한 번 틀렸다.** 초안은 U4를 "ACG가 palimpsest를 호출하는 외부 소비자"로 읽었고 U8이 그것을 정정했다. 같은 종류의 오독이 남아 있을 수 있는 곳은 U9의 "모든 역사"(보존인가 접기 허용인가)와 U2의 "영향 범위"다. **지시 원문에 대한 최종 대조는 소유자만 할 수 있다.**
2. **U2의 "영향 범위"를 전칭으로 읽었다.** 소유자가 처음부터 하한을 의도했다면 D18의 긴장은 존재하지 않는다.
3. **U9의 "모든 역사"를 "무한 보존"이 아니라 "공백이 조용해지지 않을 것"으로 읽었다.** 이 독해가 틀리면 보존 정책 전체가 다시 열린다.
4. **ACG 자료의 대부분은 ditto 저장소의 draft 문서와 ADR이다.** `00-framework`는 `status: draft`이고 구현 상태 서술은 그 문서의 자기 보고다. **실물 코드 확인은 게이트 집행 지점(`src/hooks/stop.ts`) 한 건에 그쳤다.**
5. **"백서 개정이 필요 없다"는 결론이 편의적일 수 있다.** 열린 질문으로 흡수하는 처리는 어떤 지시든 (c)로 분류할 여지를 준다. **반증 형태**: 백서 §12-3을 "프로젝트 정의"로 소진한 뒤에도 **코어가 서사 규칙 어휘를 고정해야만 성립하는 산출**이 나타나면 그 소진은 틀린 것이다.
6. **수입/비수입의 경계는 자명하지 않다.** "fail-closed"를 개념으로 보면 수입 대상이고 게이트 배선의 성질로 보면 아니다. 설계는 후자로 판정하고 형태를 바꿔 수입했다. 그 판정이 틀렸다면 D9와 게이트의 관계가 다시 열린다.

## 5. 판정의 근거 좌표

**결정은 [`DESIGN.md`](../DESIGN.md)에 있다. 이 절은 그 결정이 무엇을 보고 내려졌는지만 적는다.**

### ACG 수입/비수입 — §12.6 처분표의 근거

| §12.6의 행 | 무엇을 보고 판정했나 |
|---|---|
| 변경(Change)의 1급화 — **수입** | 백서 §7의 사슬(결정→코드→여정→가치)에 없던 축이다. DESIGN §11.1의 `Plan`·`Deviation`이 이미 그 자리의 절반을 차지한다 |
| 지속 적합성 — **수입** | ACG의 fitness 추세. DESIGN §10의 "대장 diff"·§8.1의 "잔여의 소멸은 사건이다"가 같은 형태의 씨앗 |
| 스펙/바인딩 2계층 — **수입** | `00-framework`의 자기 규정 — *"스펙 계층은 저장소 중립, 각 산출물이 실어야 할 정보와 게이트가 검사할 성질만 정의한다. 바인딩 계층이 그 저장소의 실제 스키마·분석 도구에 끼워 맞춘다."* **U1이 요구하는 구조와 같은 것이고, palimpsest 쪽에서는 D17 해석기 팩이 그 자리에 들어간다** — 즉 U1과 U4는 별개 지시가 아니라 한 구조의 양쪽 끝이다. **2계층은 개념이므로 수입하고, provider 슬롯 인터페이스는 구현이므로 수입하지 않는다** |
| 기준의 권위를 사람에 — **수입** | `ADR-0004`: `produced_by=user` 권위 기본, 관측에서 자동 박제 금지. DESIGN §7.1·§3의 `asserted` 규칙과 이미 같다 |
| 스키마·ledger 형식 — **비수입** | 스키마 9종(`ChangeContract`·`ImpactGraph`·`FitnessFunction`·`JourneySpec`·`AssuranceSnapshot`·…), ledger 파일 형식·envelope. **U8이 직접 배제한 부류** |
| 게이트 집행 배선 — **명시적 기각** | `src/hooks/stop.ts` — Stop 훅이 ReviewGraph ledger를 읽어 미해소 high-risk가 있으면 continuation을 강제한다. **연구 E가 관측한 실패의 실물** |
| fail-closed 차단 — **형태를 바꿔 수입** | `ADR-0004`의 불변식 — *"ImpactGraph 입력이 부재하거나 `journey_unknown`이면 high-risk로 escalate, 절대 sample down 금지."* **같은 문제를 만난 선행 시스템이 게이트 쪽 해법을 골랐다는 것**이 이 대조가 더하는 정보다 |
| 절대 평가가 아니라 델타 | `ADR-0004`의 `FitnessFunction.baseline.delta_only`. **차용이 아니라 수렴이다** — DESIGN §10의 "대장 diff로 나타난다"가 이미 같은 형태이고 D20이 그것을 구조 기준으로 확장한다 |
| 정적 엔진 통일 — **비수입** | `ADR-0006`(엔진 통일, `ts-analyzer` 삭제, 회귀 1011 pass). 빌드 의존이므로 U와 충돌. 산물은 `observed`로 수용된다 |

### 빌드 의존 정밀 엔진과의 관계 — 대체가 아니다 (U4-c)

ACG는 결정론 엔진을 빌드 의존 엔진으로 통일했고(`ADR-0006`), 그 비용이 ACG 자신의 열린 질문 Q4의 근거로 기록되어 있다(*"`mode: executed`의 비용 — 컴파일 언어 clean build 수 분"*). **palimpsest는 그 자리를 빼앗지 않는다.**

| 빌드 의존 정밀 엔진이 주는 것 | palimpsest가 더하는 것 |
|---|---|
| 현재 커밋의 정밀한 call/dataflow | **임의 과거 커밋에서의 균일한 하한**(U) — 계보가 서는 조건 |
| 위반 목록 | **`{위반, 잔여, 범위 밖}`** — 잔여의 사유별 분해(D9) |
| 단일 빌드 단위 안의 관계 | **저장소 경계를 건너는 `contract` 엣지**(C4) — 그 엔진이 구조적으로 못 넘는 곳(ACG 자신이 `unresolved: cross_repo`로 인정) |
| 코드 사실 | **의도층과의 결박·낡음·계보** |
| 실행 시점의 판정 | **그 판정이 좌표에 결박되어 다시 나타나는 것**(적시 제시) |

**두 산출이 어긋나는 경우가 신호다** — DESIGN §7.2가 O에 대해 세운 규칙이 그대로 적용된다.

### Litt의 두 기법에 대한 처분 (U6)

| 기법 | 연구 D의 판정 | 지시가 바꾸는 것 | 남는 것 |
|---|---|---|---|
| `/explain-diff` | 진단에는 정확히 대응하나 **위험 셋** — (1) 설명은 수용을 늘림 (2) 설명자=생성자 (3) 결박되지 않음 | **(3)은 닫힌다**(DESIGN §9.1의 `evidence_refs` 저장 제약). **(2)도 닫힌다**(§9.2 생산자 분리 + `produced_by`) | **(1)은 열려 있다.** 완화법이 알려져 있지 않다(DESIGN §15-24) |
| 마이크로월드 | 미판정. **백서 §2.2-1(빌드 불가)과 정면 충돌**하며 대상마다 새로 지어야 한다 | 충돌의 전제가 **부분적으로 풀린다** — DESIGN §0.4의 O가 호스트를 통한 실행 조달을 열었다 | **비용은 그대로다.** "대상마다 새로 짓는다"는 P12와 여전히 충돌하고, 생성물의 정확성 판정은 백서 §6.3의 자기참조와 같은 자리다. **주경로 후보가 아니라는 판정은 유지된다** |
